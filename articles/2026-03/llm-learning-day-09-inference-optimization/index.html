大模型推理优化：先找到慢和贵的原因

2026年7月30日 · 阅读需 3 分钟

本地模型能跑起来，不代表能用。常见现象是首个字出来很慢、对话越长越卡，或者并发一高就显存不足。推理优化不是追求一个万能参数，而是先分清时间和内存花在哪里。

先量两个指标​

对用户来说，首个词元延迟决定“多久开始有反应”，生成速度决定“之后吐字多快”。下面脚本可以测一个 HTTP 接口的总耗时；把地址换成自己的服务：

import time
import requests

start = time.perf_counter()
response = requests.post("http://localhost:8000/v1/completions", json={
    "prompt": "用一句话介绍 Python",
    "max_tokens": 30,
})
elapsed = time.perf_counter() - start
print(response.status_code, f"总耗时: {elapsed:.2f} 秒")

连续运行几次，分别记录短提示词、长提示词和多人同时请求的结果。只测一次很容易被模型加载、网络或系统缓存误导。

KV Cache 为什么能加速​

模型逐个生成词元。没有缓存时，每生成一个新词都要重新处理前面已经处理过的内容；KV Cache 会保留这些历史中间结果，新词只计算新增部分。

已有文本 -> 缓存历史信息 -> 只计算新词 -> 更新缓存

代价是缓存会占显存，而且上下文越长、并发越高，占用越明显。遇到“生成一会儿就 OOM”，不要只盯模型权重，也要检查上下文长度、并发数和 KV Cache 预算。MQA/GQA 通过让部分注意力头共享缓存来降低这一成本，效果和兼容性由模型架构决定。

量化是常见的第一步​

量化把模型权重用更少的位存储，例如从半精度降到 8 位或 4 位。通常能减少内存，也可能提高速度；代价是输出质量可能下降，某些硬件上也未必更快。

最实用的验证方式不是看宣传数字，而是用同一批提示词比较：能否装入设备、首词延迟、生成速度，以及回答是否仍可接受。尤其要测试数字、代码、中文专名等你的真实场景。

选工具时的实际取舍​

  • 个人电脑和隐私敏感的离线使用，可以关注 llama.cpp 和 GGUF 模型。
  • NVIDIA 服务器上需要处理许多同时请求时，可以评估 vLLM 的连续批处理和缓存管理。
  • 已有 NVIDIA 部署链路且追求极限性能时，再考虑 TensorRT-LLM。

先按照工具当前版本的官方安装说明运行示例模型，再接入自己的服务。模型格式、显卡驱动和 CUDA 版本不匹配，是比“优化参数不对”更常见的启动失败原因。

限制​

  • 降精度和缩短上下文会影响质量；不能只以显存占用决定方案。
  • 高吞吐优化可能让单个请求排队更久，要同时看延迟和吞吐。
  • 基准结果高度依赖硬件、模型、提示词长度和版本，应记录测试条件。
