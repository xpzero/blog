流式输出是响应头控制的吗？一次对照实验

柯寒2026年9月14日阅读 9 分钟

同样的响应头，为什么有的响应逐块显示，有的却要等全部结束才出现？通过几组对照实验，看看发送节奏、客户端读法和中间层缓冲，分别怎样影响流式输出。

调用 OpenAI 兼容接口时，常能看到文字逐渐出现的打字机效果。配置流式响应的示例里，也经常出现这几个响应头：

Content-Type: text/event-stream
Cache-Control: no-cache
X-Accel-Buffering: no

我的疑问是：流式是不是这些响应头「开启」的？ 从名字看很像——text/event-stream 里就写着 stream。

应用层如何消费这些片段，前文流式输出，以及被切碎的工具调用已经讨论过。这次想弄清楚的是：响应里的数据什么时候能被读到，页面又为什么会等到最后才显示？

直接做实验​

实验环境与范围

实验在浏览器内运行：Service Worker 拦截实验请求，用 ReadableStream 生成响应；页面通过 fetch 读取。源码中的 enqueue() 模拟服务端逐块写入，页面其他请求照常加载。

这能对比响应生成与客户端读取的行为，但没有真实的远端服务器、TCP 传输或 nginx、CDN 链路，不能验证这些环节的缓冲行为。

六个实验分成两组，客户端都固定用 reader.read() 逐块读取：

  • A、B、C 看发送节奏：A 与 B 的响应头相同，只改变写入时机；C 改用普通文本的响应头与内容，检查不用 SSE 是否也能逐块读取。
  • D、E、F 看格式与识别：D 换成 OpenAI Chat Completions 的流式内容示例；E、F 刻意让响应头与内容格式不匹配，区分「读到字节」和「识别 SSE 事件」。

实验改变了什么应观察什么
A 逐块发送每 300ms 写入一块，使用 SSE 头与格式数据陆续读出
B 攒齐发送与 A 相同的头和内容，等 3 秒再一次写入响应头先可读，正文延后集中读出

A 与 B 对比说明，仅有 SSE 响应头，不能保证正文会逐块提供；C 则说明，逐块读取也不一定需要 SSE。D、E、F 进一步提出了另一个问题：响应头和内容格式各自负责什么？

响应头真正的角色​

SSE（Server-Sent Events）规定了事件的文本格式，例如用 data: 表示数据、用空行结束一条消息。它与「响应体能否逐块读取」是两个层面的问题。

开头三个响应头的作用也不相同：

响应头与取值主要使用者作用
Content-Type
text/event-stream		EventSource、DevTools 等声明响应体是 SSE；具体解析还取决于客户端实现
X-Accel-Buffering
no		nginx在配置允许时，关闭当前响应的代理缓冲
Cache-Control
no-cache		浏览器和共享缓存允许存储，但复用前必须验证

自己用 fetch 读取响应体时，text/event-stream 不会自动把字节变成事件，也不会替响应生成方安排写入节奏。实验 C 没有使用这个类型，仍然可以逐块读取；若要处理 SSE 事件，还需要按协议解析内容。

DevTools 的识别则有明确的版本依据：在本文引用的 Chromium DevTools 源码中，EventStream 标签页的判定是 mimeType === 'text/event-stream'。因此，按该版本源码，E 不会显示这个标签页；F 会显示，但无法从其内容解析出有效消息。出现标签页，不等于内容正确，也不等于数据及时到达。

X-Accel-Buffering: no 则确实可能影响到达节奏。nginx 文档说明，它可以关闭当前响应的代理缓冲；proxy_ignore_headers 配置也可以让 nginx 忽略这个指令。本页没有 nginx，所以这一点依据文档，不能由浏览器内实验推出。

另外，no-cache 不等于「不存储」。它要求缓存复用前先验证；禁止存储对应的是 no-store。缓存复用与传输时暂存数据，也不能混为一谈，见 MDN 的 Cache-Control 说明。

所以，更准确的回答是：响应头不是一个通用的「流式开关」；有的声明格式，有的控制缓存或代理缓冲，需要分别看谁会使用它。

前端的读法：另一半开关​

前面的实验一直固定了客户端的读法：用 reader.read() 逐块读取。现在固定响应生成方式，只改变客户端。

下面两种读法都请求实验 A，响应生成方仍然每 300ms 写入一块：reader.read() 每次读到数据就处理；res.text() 则等完整响应体收齐后，才返回字符串。

浏览器实验：启动中…

  • reader.read()（边到边读）
  • res.text()（攒完）
读法：res.body.getReader() 循环，每次读到数据块就处理
预期：服务端逐块发，页面逐块显示——这就是流式
点「运行实验 A」——服务端每 300ms 逐块发送，不变的。
读法：res.text()，内部把整个 body 攒齐才返回
预期：等待完整响应体后，一次显示正文
点「运行实验 A」——同一个服务端，换攒完的读法。
客户端源码（两种读法，任选一种）
// 每次请求只选一种读法；响应体不能重复消费。
// 读法一：边读边处理（省略 UI 日志与重试逻辑）
async function readChunks(url) {
  const res = await fetch(url);
  const reader = res.body.getReader();
  const dec = new TextDecoder();
  while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    console.log(dec.decode(value, { stream: true }));
  }
  console.log(dec.decode());
}

// 读法二：等完整响应体收齐后再处理
async function readAll(url) {
  const res = await fetch(url);
  console.log(await res.text());
}

A + 等完整响应与 B + 逐块读取都会让正文到最后才集中显示：前者在客户端等待完整响应，后者在响应生成方攒齐后才提供内容。它们的总耗时可能不同，但都没有逐步显示正文的效果。

这也区分了两个时刻：数据什么时候可读，以及应用什么时候处理、显示它。即使逐块读取，如果页面等全部处理完才更新，读者仍然看不到渐进输出。

答案​

回到开头：只设置那三个响应头，能开启流式输出吗？不能。 要让页面持续显示新内容，需要整条路径配合：

持续显示新内容，需要服务端及时提供、链路及时转发、客户端及时处理并渲染。

在 LLM 场景中，内容通常随着模型生成逐步提供；本页用定时器模拟这个过程。服务端和链路上的缓冲可能增加延迟，客户端的 res.text()、res.json() 则会等完整响应体收齐才返回。缓冲不一定让流式彻底消失，也可能只是让更新变得更稀疏。

把链路因素暂时排除，可以整理出四种组合。其中前三种有上面的实验入口，最后一种是根据读法推导的结果：

响应生成方式客户端逐块读取并显示客户端等完整响应
逐块写入陆续显示（A）收齐后显示（客户端实验 A + res.text()）
攒齐后写入等待后集中显示（B）收齐后显示（推导，本页未提供该组合入口）

本页验证的是浏览器内生成响应、读取响应的差异。真实部署还要检查服务器框架、压缩、代理等环节；不能把一次 enqueue() 或 write()，直接等同于一次客户端 read()，更不能等同于一个网络数据包或一条 SSE 消息。

易错点​

页面迟迟不显示内容时
  • 检查客户端读法和渲染时机：res.json() / res.text() 要等完整响应；逐块读取后也要及时更新页面。
  • 检查 nginx 代理缓冲：默认是 proxy_buffering on。可用响应头 X-Accel-Buffering: no 或配置 proxy_buffering off 关闭，同时检查响应头是否被忽略。
  • 检查压缩缓冲：Express 的 compression 中间件可能暂存输出。可让 SSE 路由绕开压缩，或按中间件文档在需要时调用 res.flush()。
  • 检查其他中间层：CDN、负载均衡等也可能缓冲，具体行为需要在实际部署中验证。
