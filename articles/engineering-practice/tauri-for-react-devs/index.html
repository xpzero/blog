写给 React 开发者的 Tauri：你的网页怎么长出本地能力

周期2026年11月9日阅读 13 分钟

会 React、没写过 Rust、不懂系统调用，也能做桌面应用。本文用一个小小的「随手记」把 Tauri 走通：你的 React 跑在应用内嵌的 WebView 窗口里，Rust 是随应用自带的后端；前端用 invoke 调后端命令（长得像调 API），后端用事件推送（像 WebSocket）。什么代码放哪一侧、为什么重活不能堵主线程、系统能力（全局快捷键、麦克风这些）在哪一层等你——想看懂全貌，读这一篇就够起步。

你会 React，想做个桌面小工具：全局快捷键、读写本地文件、离线可用。浏览器里，全局快捷键、后台常驻这些做不了，文件读写也只有受限的部分能力，Electron 能做但一个安装包动辄上百 MB。Tauri 的承诺很吸引人：界面用你熟悉的网页技术写，后端用 Rust，安装包只有几 MB——但 Rust 你没写过，"系统调用"更没碰过。

这篇文章把这条路走通。不教你 Rust 语言，只教你站在 React 这一侧需要的全部认知：两边怎么分工、怎么通信、系统能力从哪来。

先把结论放在这里，整个 Tauri 开发就三句话：

  • 你的应用是一个 Rust 程序，里面嵌着 WebView 窗口——系统提供的内嵌浏览器组件（macOS 是 Safari 同款内核，Windows 是 WebView2/Chromium 系，Linux 是 WebKitGTK；浏览器兼容性要按目标平台核对）——你的 React 代码原样跑在那个窗口里；
  • Rust 是自带的后端：没有服务器、没有部署，跟着应用一起装进用户电脑；
  • 两边只有两条通道：invoke，你的 React 调后端函数（长得像调 API）；事件，后端主动推消息给你的 React（像 WebSocket）。学会这两条就能干活。

下面用一个贯穿全文的小应用把两条通道都走一遍。

心智模型：网页住进了 Rust 程序​

先建立一张地图。一个 Tauri 应用在用户电脑上是这样的：

和 Electron 最直观的差别：Electron 给每个应用塞一份完整的浏览器（所以包大）；Tauri 用操作系统自带的 WebView（macOS 上就是 Safari 的内核），你的应用只带上网页产物和一个 Rust 后端。

两个容易想错的地方先钉住：

  • 你的 React 代码不是"编译成"桌面程序。还是那份构建产物（HTML/JS/CSS），只是加载它的人从浏览器换成了应用里的 WebView 窗口。你熟悉的组件、hooks、状态管理全部照旧。
  • Rust 不是另一种"前端框架"。它是编译型语言，干的是后端的活：管数据、调系统、干重活。这篇文章里你只需要会"读懂一个 Rust 函数的形状"，会抄会改，不需要系统学过这门语言。

最小例子：一个按钮调进 Rust​

贯穿全文的例子是一个「随手记」：输入框加一个按钮，点一下把这句话存进后端，界面显示"后端已经存了 N 条"。麻雀虽小，它已经用上了第一条通道。

前端部分，你会觉得眼熟得不像话：

import { useState } from "react";
import { invoke } from "@tauri-apps/api/core";

export default function App() {
  const [text, setText] = useState("");
  const [count, setCount] = useState(0);

  async function save() {
    // 像调 API：给个名字、传个参数、拿个返回值
    const n = await invoke<number>("save_note", { text });
    setCount(n);
  }

  return (
    <>
      <input value={text} onChange={(e) => setText(e.target.value)} />
      <button onClick={save}>存进后端</button>
      <p>后端已存 {count} 条</p>
    </>
  );
}

invoke 的形状就是一次 API 调用：第一个参数是"端点"（后端函数名），第二个是参数对象，返回 Promise。但它不是 HTTP——这个类比到失效边界为止：没有网络请求、没有 URL、没有跨域，消息在应用内部传递，快得多；能调到什么由一份白名单决定（马上讲到）。

后端部分，逐行讲。一个能被网页调用的 Rust 函数长这样：

// 「随手记」后端：一个能被网页调用的函数（Rust 里叫"命令"）
#[tauri::command]
fn save_note(text: String) -> usize {
    //           ↑ 参数     ↑ 返回类型：usize 就是"个数"（无符号整数）
    text.chars().count() // 朴素版：先返回字数，马上升级成真的"存起来"
}

#[tauri::command] 是一个宏——编译时自动展开的注解，它替你生成"让网页调到这个函数"的接线代码。类比 React 世界的组件必须被 export 才能用：Rust 函数必须挂上这个宏、再登记进应用启动时的一份列表，网页才调得到：

fn main() {
    tauri::Builder::default()
        .invoke_handler(tauri::generate_handler![
            save_note, // ← 白名单：登记过的函数网页才能 invoke
        ])
        .run(tauri::generate_context!())
        .expect("error while running tauri application");
}

这份列表就是前面说过的白名单：网页脚本的能力上限就是登记过的这几个函数。Rust 侧的任何其他代码，网页碰不到。

两条纪律顺手立住：

  • 参数名前端写 text（camelCase）、后端写 text；参数多了，前端 userId 会自动对上后端的 user_id（snake_case）——两边各写各的自然风格，框架负责翻译；
  • 后端函数的返回值如果是 Result（Rust 的"成功或错误"包装），成功走 Promise 的 resolve、错误走 reject——和你 try/catch 一个 fetch 的手感一致。

还差一块：笔记存哪？「随手记」的数据放哪？只放 React 状态不行——组件卸载就没了；要放在后端。Tauri 的惯例是交给框架保管：

查看代码：升级成真的存起来（manage 与 State，完整可跑）
use std::sync::Mutex;
use tauri::{Manager, State};

// 数据本体：一个线程安全的动态数组。Mutex 是 Rust 的并发安全容器
// （多个请求同时来也不会打架）——先照抄，细节以后再学
struct Notes(Mutex<Vec<String>>);

#[tauri::command]
fn save_note(text: String, notes: State<Notes>) -> usize {
    //                        ↑ 托管数据自动注入（前端不用传）
    let mut list = notes.0.lock().unwrap(); // 拿到锁（unwrap 先当"必须成功"读）
    list.push(text);
    list.len()
}

fn main() {
    tauri::Builder::default()
        .manage(Notes(Mutex::new(vec![]))) // 交给框架保管：应用活着数据就活着
        .invoke_handler(tauri::generate_handler![save_note])
        .run(tauri::generate_context!())
        .expect("error while running tauri application");
}

.manage 交出去的数据，后端任何命令函数都能通过一个 State 参数取到——这是 Rust 侧的"全局状态"，React 刷新、组件卸载都不会影响它。界面上输错重输没关系，后端那份是唯一的账本。

到这里第一条通道通了：点按钮 → invoke → Rust 函数执行 → 返回值上屏。第一版先用字数占位——按钮上的数字会随输入长度变；折叠区里已升级成真的"存起来"。到这里整条链路你已经能逐环节复述。

反方向：Rust 主动推消息​

第一条通道永远是"你问它答"。但有一类需求反着来：事情发生在后端，界面要跟着变——文件下载完了、后台任务跑到一半了、外设有了动静。轮询能做，但那是界面反复问"好了吗"，语义就反了；正确的关系是后端说"好了"。

这就是第二条通道：后端广播事件，前端订阅。给「随手记」加一个真实的需求：每次存完，侧边的小组件要实时显示最新条数——不管这次保存是从哪个入口触发的。

后端在存完之后广播一条（这版是在折叠区那份完整代码的基础上改的——State<Notes>、.manage 的来龙去脉都在里面）：

use tauri::Emitter;

#[tauri::command]
fn save_note(text: String, notes: State<Notes>, app: tauri::AppHandle) -> usize {
    //                        ↑ 托管数据自动注入   ↑ 对讲机也自动注入（前端都不用传）
    let mut list = notes.0.lock().unwrap();
    list.push(text);
    let n = list.len();
    let _ = app.emit("note-saved", n); // 广播事件（let _ = 表示"结果不要了"）
    n
}

注意 app: tauri::AppHandle 这个参数——前端不用传它，框架自动注入。它是后端手里的"对讲机"：发事件、找窗口、取托管的数据，都从它出发。

前端订阅，和你用过的事件总线是一个形状：

import { listen } from "@tauri-apps/api/event";
import { useEffect, useState } from "react";

function NoteBadge() {
  const [count, setCount] = useState(0);
  useEffect(() => {
    const un = listen<number>("note-saved", (e) => setCount(e.payload));
    return () => un.then((f) => f()); // 组件卸载时取消订阅
  }, []);
  return <span>已存 {count} 条</span>;
}

和 WebSocket 的类比同样有失效边界：没有连接、没有断线重连，事件在应用内部广播，所有窗口都能收到，谁在 listen 谁处理；载荷是序列化后的普通值——JSON 里长什么样，你在 JS 里就拿到什么（对象、数字、数组都行），不是流。

发送方也不限于命令函数——后端的任何代码都能发：定时器、文件监控、系统事件的监听线程。事件也能反着发（JS 里 emit、Rust 里 listen），本文用不到，知道这个对称性即可。界面只需要管订阅，这和你在 React 里管 useEffect 的分工完全一致。

它不是 HTTP：invoke 点下去发生了什么​

会用了，再往下看一层。invoke("save_note", { text }) 点下去，中间发生的事：

  1. 一段框架注入进网页的胶水代码把函数名和参数打包（序列化——因为数据要跨出网页的边界，得变成两边都认的格式）；
  2. 消息经 WebView 与应用之间的内部通道（不是网络）交给 Rust 侧；
  3. 框架按名字查白名单，找到 save_note，解包参数，调用它；
  4. 返回值打包送回网页，你的 await 拿到结果。

两个实际后果。一是过通道要付序列化的成本：传字符串、数字、普通对象毫无压力；传大块二进制、每秒几百次的原始数据流就该重新考虑（正确的姿势：让数据留在 Rust 侧消化成结论再过桥——比如要在界面显示音量，就每秒推一个数字过去，而不是把每秒上万个音频采样搬进网页）。二是白名单在前面讲过的安全含义：网页里任何脚本（包括你引入的第三方依赖里的）能调的后端能力，上限就是登记过的命令。

还有一个对所有前端开发者都直觉的坑：后端慢，界面会卡。不是卡你的 React——是卡消息：后端有个"主线程"负责窗口和消息调度，命令函数如果在它上面干重活（比如同步写一个大文件几秒钟），期间事件推送、窗口响应都会停摆。规矩一句话：命令函数只做编排，重活丢给后台线程（Rust 侧起线程就像你 setTimeout 甩任务一样自然——不过线程是真并行，不是同线程排队），干完了用事件通知前端。更省事的路：把命令函数写成 async fn（Rust 的异步函数），框架会自动把它调度到后台。

什么代码放哪一侧​

两条通道都会用了，日常开发九成的决策其实是"这段逻辑写在前端还是后端"。判断不复杂：

放 React 这侧的：

  • 界面与交互：组件、动效、表单——你本来就最擅长的部分；
  • 纯展示状态：当前 tab、输入框内容、UI 开关。

放 Rust 这侧的：

  • 要活得比界面久的数据：上面「随手记」的笔记列表是缩影——真实项目里是配置、历史记录、缓存，交 .manage 保管；
  • 要碰系统的能力：读写文件、调麦克风、注册全局快捷键、操作剪贴板——这些是浏览器的禁区，是 Rust 侧的主场；
  • 重活：耗时的计算、大文件处理——Rust 的性能加上不堵界面的线程模型；
  • 不想暴露给网页的东西：密钥、只该本机处理的逻辑（白名单是网页能力的上限，没登记的函数网页永远摸不到——注意它防的是网页与第三方脚本，不是本机用户：二进制里的东西挡不住要逆向的人）。

一句话总结分工：界面归网页，能力归 Rust，两边只传"结论"。

系统能力一瞥：真正的深水区在哪​

「随手记」没用上系统能力，但这一天会来：想做全局快捷键、想录麦克风、想往别的应用的输入框里打字。这时候 Rust 侧会直接调用操作系统的接口——macOS 上你会遇到 CGEventTap（监听与合成键盘事件的系统机制）、辅助功能权限（让工具操作其他应用的那道授权）、TCC（macOS 的隐私权限框架）这些词。

这些现在都不需要懂。 需要知道的只有两件事：

  • 这一层的复杂度是操作系统收的，不是 Tauri 收的——换成任何技术栈做原生能力都要趟同一条河；
  • Rust 侧能直达它们，而你的 React 侧只管 invoke 和 listen，两层的分工不变。

一个真实的参照（同款工具的后续两篇实战）：macOS 自定义全局快捷键：从系统注册到 CGEventTap 讲一个语音输入工具怎么用一条系统事件流做出全局热键；macOS 文字注入：从焦点判定到剪贴板还原 讲识别出的文字怎么安全地落进别的应用的输入框。两篇都是"Rust 侧攻坚系统能力、前端零感知"的完整实例——等你想下深水，从它们开始。

从这里出发​

起步只需要三步：

  1. 官方脚手架建项目：npm create tauri-app@latest，模板选 React + TypeScript；
  2. 认识一下工程结构：Rust 侧住在 src-tauri/ 目录，前端照常开发构建，产物由 WebView 加载。把「随手记」敲进去跑通——两条通道各用一次；
  3. 需要什么能力，再去查对应的文档：从前端调用 Rust、从 Rust 调用前端。

Rust 不必先学语言。从抄一个带 #[tauri::command] 的函数开始，报错看不懂就查那一行——两个月后你会发现自己已经会写不少了。
