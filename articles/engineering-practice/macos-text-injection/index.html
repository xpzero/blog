macOS 文字注入：从焦点判定到剪贴板还原

周期2026年11月11日阅读 22 分钟

语音识别的输出是一段字符串，用户要的是它出现在光标闪烁的地方。本文整理 Sayit 的注入方案：一条分层焦点判定链（AX 权威、终端 TTY 判定、Unknown 亮复制按钮），两条注入通道（剪贴板加合成 ⌘V、合成键入事件），一套最小侵入的剪贴板纪律与三重防竞态的延迟还原，以及让文字总有下落的兜底链。

Sayit 是一个本地优先的 macOS 语音输入工具：任何应用里按快捷键开始说话，再按一次停止，识别出的文字多半直接出现在光标所在的位置，浮窗随之消失——不顺利时这段文字去了哪里，正是这篇文章的主题。前文：macOS 自定义全局快捷键：从系统注册到 CGEventTap 讲了按键怎么全局生效，这篇讲最后一步：识别引擎吐出的那串文字，怎么送进"当前光标所在的那个应用"。

这段路比看上去长。识别完成时，系统里正在发生的事情——焦点落在哪个 App 的哪个元素上、剪贴板里装着谁的什么东西、用户是不是已经等不及开了下一轮——每一件都可能让文字送错地方或者凭空消失。这篇文章整理 Sayit 的注入方案。

先给结论。整套方案落在四个部件上：

  • 两条注入通道：paste 模式把文字写进剪贴板再合成一次 ⌘V；type 模式合成携带文字的键入事件。默认 paste，兼容性最好；
  • 一条焦点判定链：AX（macOS 辅助功能 API）权威判定 → 终端 TTY 判定 → Unknown。有输入态就注入；确认没有文本框、或判不出时，都不注入、亮复制按钮（两种情况徽标不同；辅助功能未授权时例外：放行走注入路径以产出权限提示，见后文）；
  • 一套剪贴板纪律：除注入路径外，唯一允许写剪贴板的是用户点击复制按钮；注入写入后 500ms 延迟还原用户原来的纯文本内容，用代数计数器加文本比对防还原竞态；
  • 一条兜底链：判定不该注入，面板亮复制按钮；失败恰好落在模拟按键那一步，文字留在剪贴板；其余一切失败形态，设置页的听写历史兜底。每一层失败都有下落。

要解决什么问题​

用户侧的完整交互只有两步：对着任意应用按热键说话；松手，浮窗显示识别中，几秒到几十秒后文字落在光标处、浮窗消失。这个"任意应用"是注入的全部难度来源。四条硬要求：

  • 全局注入，且送对地方。目标可能是微信的聊天框、浏览器的地址栏、终端的命令行，每个应用接收文字的机制不同，注入不能依赖目标应用的配合；焦点也可能停在根本没有输入框的地方（桌面、Finder 文件列表），这时不能乱粘；
  • 不弄脏用户的剪贴板。剪贴板是全局共享的单槽资源——一次只保留最近写入的一份内容——用户可能刚复制了要用的东西；
  • 浮窗消失不能被注入拖慢。识别完的那一刻，用户已经在等着继续打字了；
  • 任何失败都要有下落。注入落空时系统不会报错，工具必须自己保证文字不丢。

这四条要求，各撞上一个 macOS 的系统现实：

  • 合成 ⌘V 发给的是"当前焦点窗口"——注入工具自己的浮窗如果抢了键盘焦点，⌘V 会粘进自己肚子里；而"光标处是不是文本框"这个信息只有一个权威来源（辅助功能 API），这个来源本身还有多种失败方式；
  • ⌘V 的机制要求文字先在剪贴板里。绕不开这个全局单槽，只能在"写"的纪律和"还原"的时机上做文章；
  • 交付链路里的操作都不便宜：焦点探测是同步的进程间调用，剪贴板有备份与延迟还原，全做完再收浮窗，用户看到的就是"消失很慢"；
  • 键入事件没有"送达回执"；本地识别耗时数秒到数十秒，结果回来时用户可能已经翻篇开了下一轮听写。

后面的机制就是围绕这四个现实长出来的。

两条注入通道​

把文字送进别人的应用，系统层面只有两条路。

paste 模式（默认）：把识别文字写入剪贴板，然后合成一次 Cmd+V 按键。enigo（Rust 的输入模拟库）按下 Meta、点击 V、松开 Meta，三步完成。它的好处是兼容性：几乎所有接受文本的地方都支持粘贴，不管底下是原生控件、网页输入框还是终端。

一个不起眼但致命的细节：合成按键发给的是当前焦点窗口。Sayit 的浮窗全程 focusable: false——它显示波形和状态，但永远不持有键盘焦点。用户说话时焦点一直停在他原来打字的地方，⌘V 自然粘进那个应用。

type 模式：合成携带 Unicode 文本的键盘输入事件，相当于一个极快的打字员——留给完全不想动剪贴板的场景，比如剪贴板里存着要反复粘贴的内容。它不碰剪贴板，代价是没有回执——事件没人消费时文字凭空消失，调用方不知道成功还是落空。所以 type 模式的失败兜底完全依赖下文的历史记录。paste 模式在多数失败下也一样；只有失败恰好落在模拟 ⌘V 那一步时，文字已经写进剪贴板且不再还原，手动 ⌘V 就能取回。

查看代码：合成 ⌘V（press_cmd_v 函数）
// Cmd+V = 按住 Meta(Command) -> 点按 V -> 松开
// （Unicode('v') 会按当前键盘布局映射到 V 键的键码）
fn press_cmd_v() -> Result<(), String> {
    use enigo::{Direction, Enigo, Key, Keyboard, Settings};
    let mut e = Enigo::new(&Settings::default()).map_err(|err| err.to_string())?;
    e.key(Key::Meta, Direction::Press).map_err(|err| err.to_string())?;
    e.key(Key::Unicode('v'), Direction::Click).map_err(|err| err.to_string())?;
    e.key(Key::Meta, Direction::Release).map_err(|err| err.to_string())?;
    Ok(())
}

通道选好，剩下的问题是：这次到底该不该注入？

光标处有没有文本框​

假设用户刚说完一段话，焦点停在 Finder 的文件列表上。这时注入多半落空或粘进意料之外的地方；理想的行为是拦下注入，告诉用户"这里没有输入框，点按钮复制吧"。反过来，焦点明明在输入框里却拦下注入，用户就要多做一步手动粘贴。

误拦和误注入都有代价：

  • 误注入多半是文字落空——⌘V 没落进文本框，什么都没发生，面板却照常收起，用户看到的是"静默消失"，这段话只剩听写历史可取；
  • 误拦截的代价是用户多点一次复制按钮、再手动粘贴。

第一版判据据此选择了宁可放过，不可错拦：只有"确认没有文本框"才拦，判不出（Unknown）就照常注入。后来两件事改变了天平：终端类应用由 TTY 判定稳定救回——Unknown 里最该注入的一大类消失了；Electron 应用靠 AX 唤醒只盲第一轮——永久盲变成一次性。剩下仍会 Unknown 的应用（比如系统设置这类 AX 只报一个窗口的应用），注入本来大概率空打。于是判据改为：Unknown 也不注入，亮一枚“没找到输入位置”的复制按钮。误拦的代价压到一次点击，误注入的代价是凭空消失——方向反了过来。

判定的信息从哪来？分层链，每层失败都有明确定义的归宿：

层判据产出为什么需要它
① AX辅助功能三步查询Input / NoInput / Unknown唯一权威：只有 AX 知道焦点是不是文本框
② 终端判定前台进程树宿主 TTYInput键盘直达终端是注入的正解，与 App 名字无关
③ Unknown以上都给不出答案不注入，亮“没找到输入位置”按钮注入大概率空打，按钮是诚实反馈

② 只在 ① 返回 Unknown 时才参与——AX 给出的 Input/NoInput 是权威，不改写。

AX 三步查询与一条错误码勘误​

AX 的查询链是三步，每步的错误码都有明确语义：

第 1 步  systemwide 入口查 AXFocusedApplication（当前前台应用）
         错误码非 0？→ Unknown，交给终端判定兜底
         （健康通道必有前台 App；查不到说明这条 AX 路走不通——权限、通道故障或目标应用不建 AX 树，行为上不可区分，一律归 Unknown）

第 2 步  前台 App 查 AXFocusedUIElement（当前焦点元素）
         -25212 (NoValue)？→ 连焦点元素都没有 → NoInput，无处落字
         其他错误码？→ Unknown（目标忙、属性不支持等，不下结论）

第 3 步  焦点元素查 AXEditableAncestor（可编辑祖先）
         0 (成功)          → Input，有文本框
         -25212 (NoValue)  → NoInput，焦点不可编辑
         -25205（属性不支持）等 → 查 AXRole 兜底：
                            AXTextField / AXTextArea / AXSecureTextField → Input
                            否则 Unknown

这条查询链里最值得展开的是第 1 步的来历。项目早期调试时，AX 查询在某些应用上全部失败，错误码 -25212 被记成"API 被禁用"。后来翻 SDK 头文件核对，发现张冠李戴了：-25211 才是 kAXErrorAPIDisabled，-25212 是 kAXErrorNoValue——"这个属性没有值"。两个错误码语义完全相反：前者是通道坏，后者在很多上下文里是合法回答。

混淆的后果是判定逻辑的根基不稳：如果 -25212 既可能是"查不到值"也可能是"通道坏了"，第 2、3 步的 NoValue 就不能当作 NoInput 的依据。修复方式是把第 1 步确立为通道体检：健康通道必有前台 App，第一步出现任何错误码都按"通道不可用"处理、归入 Unknown 交给名单兜底；只有第一步成功，后续的 -25212 才恢复它"没有值"的本义。原则一句话：通道故障不冒充判定结果。

AX 盲应用与唤醒​

通道体检还有一个更麻烦的失败源：Electron 和 Chromium 系应用默认不构建自己的 AX 树，对它们跑这条查询链，第 1 步就查不到前台应用（返回 -25212），寸步难行。这不是权限问题，也不是通道问题——同一时刻对原生应用的查询是正常的。

对策是两个官方记载的第三方开关：AXManualAccessibility（Electron 认）和 AXEnhancedUserInterface（Chrome 认）。唤醒时机起初在交付探测里：探测全灭且拿得到前台 pid 时设开关——但建树需要时间，第一轮几乎必然赶不上交付死线，Electron 应用首次听写必撞一次复制按钮。后来把唤醒提前到按下热键开新篇那一刻（对前台应用拨开关，设属性毫秒级、幂等）：录音加识别的整个时长就是建树窗口，首录命中率大幅提升。残余边角仍在：极短的听写叠加冷树，交付时树可能还没建好，那一轮仍按 Unknown 亮一次“没找到输入位置”按钮，下一轮恢复。

查看代码：错误码到判定的映射（classify 函数）
pub fn classify(
    app_err: i32,           // 第 1 步：通道体检
    focus_err: Option<i32>, // 第 2 步：None = 因前置失败未查询
    editable_err: Option<i32>, // 第 3 步
    role: Option<&str>,     // 焦点元素角色（第 3 步的退路）
) -> Verdict {
    use Verdict::*;
    // 通道体检：健康通道必有前台 App。任何错误（含 -25212/-25211）
    // 都不下结论——绝不能把通道故障冒充"非输入态"
    if app_err != AX_SUCCESS {
        return Unknown;
    }
    let Some(fe) = focus_err else { return Unknown };
    // 通道健康。前台 App 连焦点元素都没有 = 无处落字
    if fe != AX_SUCCESS {
        return match fe {
            AX_NO_VALUE => NoInput,
            _ => Unknown, // 目标忙/属性不支持等：不下结论
        };
    }
    match editable_err {
        Some(e) if e == AX_SUCCESS => Input,    // 有可编辑祖先（含自身）
        Some(e) if e == AX_NO_VALUE => NoInput, // 焦点元素不可编辑
        // editable-ancestor 不被支持：退回标准文本角色表
        Some(_) => match role {
            Some("AXTextField") | Some("AXTextArea") | Some("AXSecureTextField") => Input,
            _ => Unknown,
        },
        None => Unknown,
    }
}

终端判定​

AX 判不出时，还有一份不依赖 AX 的信息可用。

终端判定：终端模拟器的定义性特征不是名字，而是"进程树里挂着带控制终端的 shell"。用 ps 读一遍全系统的 pid/ppid/tty 三列，在前台应用的进程子树里找带 TTY 的成员（约 20–30ms）——只要 shell 跑在终端里，Terminal、iTerm2、wezterm、kitty、Warp 都天然满足这一判据，不需要枚举名单。附带效应：带集成终端的 IDE（如 VS Code）同样命中，对它们注入通常正是想要的。这一层尤其重要：实测 wezterm 的 AX 树只报一个 AXWindow，探不出输入框，但焦点在终端窗格里时，键盘输入就落在那里——AX 判不出的地方，TTY 判定补上了。

探测自身的防御​

AX 调用是同步 XPC（进程间调用）：目标应用卡死时，调用方会一起挂住。探测永远不能比交付本身更重要，所以实际查询放独立线程，外层加 300ms 整体死线；超时按 Unknown 收场，走终端判定兜底，仍判不出就亮复制按钮。判定、依据、前台应用一并写进日志（每次听写一行），排查"为什么这次没亮复制按钮"有第一现场。

剪贴板：最小侵入与延迟还原​

判定链决定"注不注"，剪贴板纪律决定"怎么写"。

谁可以写，规则只有两条：

  • paste 模式注入必须写——这是 ⌘V 的机制要求，绕不开；
  • 面板上的复制按钮被点击时写——用户显式要的。

其余路径一律不写。识别完成但判定不该注入时不写（用户剪贴板里可能是他自己要用的内容，不能霸占）；type 模式不写。判定为非输入态时面板亮出“复制后去粘贴”，点击那一刻才写入剪贴板、面板同时收起（收板不等剪贴板写入），写失败则面板回弹亮“复制失败”——静默失败等于让用户以为复制成功、回头找不到字。

写了要还。paste 注入完成后，把用户原来的剪贴板内容放回去。直接还原不行：还原太快，目标应用还没读完剪贴板（Electron 系的事件循环慢），⌘V 会粘到旧内容。所以延迟 500ms。

延迟又引入新竞态：这 500ms 里用户可能点了复制按钮、可能开了下一轮听写又注入了一次，还原线程醒来时剪贴板可能已经换了主人。暴力还原会把用户的新内容回滚掉。三重防护：

t0       注入线程：备份剪贴板（纯文本）→ 代数计数器 +1 → 写入识别文字 → ⌘V
t0+500ms 还原线程醒来，依次检查：
           ① 代数计数器已变？——有人（复制按钮/下一轮注入）写过 → 放弃还原
           ② 剪贴板内容 ≠ 我们写入的文字？——我们之外有人写过（用户手动复制、其他应用）→ 放弃还原
           ③ 两项都通过 → 写回备份 → 计数器再 +1（通知更后来的还原线程）

代数计数器是一个全局原子整数：代码里任何一次剪贴板写入（注入、复制按钮、还原本身）都递增它。还原线程持有自己出发时的代数，醒来发现代数变了就知道有人后来写过。文字比对是第二道锁：就算代数恰好没变，剪贴板内容如果已经不是我们写入的那段文字，也绝不碰。两道检查把竞态窗口压缩到"检查与写回之间"的微秒级。

还原有明示的边界：只备份和还原纯文本。用户剪贴板里如果是图片或富文本，还原不了，识别文字留在剪贴板里作兜底——比清空好。

查看代码：paste 注入与延迟还原（paste_text 函数，节选）
static CLIPBOARD_GEN: std::sync::atomic::AtomicU64 =
    std::sync::atomic::AtomicU64::new(0);

pub fn paste_text(text: &str) -> InjectOutcome {
    if !accessibility_ok() {
        return InjectOutcome::NeedPermission;
    }
    let mut cb = match arboard::Clipboard::new() {
        Ok(c) => c,
        Err(e) => return InjectOutcome::Failed(format!("打不开剪贴板：{e}")),
    };

    let backup = cb.get_text().ok(); // 备份（仅纯文本）
    let my_gen = CLIPBOARD_GEN.fetch_add(1, std::sync::atomic::Ordering::SeqCst) + 1;
    if let Err(e) = cb.set_text(text.to_string()) {
        return InjectOutcome::Failed(format!("写剪贴板失败：{e}"));
    }
    if let Err(e) = press_cmd_v() {
        // 剪贴板已写入但不还原：文字留在剪贴板恰好是注入失败的兜底
        return InjectOutcome::Failed(format!("模拟按键失败：{e}"));
    }

    let text_marker = text.to_string();
    std::thread::spawn(move || {
        std::thread::sleep(std::time::Duration::from_millis(500));
        // 防护①：代数已变 = 有人写过剪贴板，放弃还原
        if CLIPBOARD_GEN.load(std::sync::atomic::Ordering::SeqCst) != my_gen {
            return;
        }
        if let Ok(mut cb) = arboard::Clipboard::new() {
            // 防护②：只在剪贴板仍是我们写入的文本时还原
            if let Ok(cur) = cb.get_text() {
                if cur == text_marker {
                    if let Some(b) = &backup {
                        let _ = cb.set_text(b.clone());
                        // 防护③：还原本身也递增代数，通知后续还原线程
                        CLIPBOARD_GEN.fetch_add(1, std::sync::atomic::Ordering::SeqCst);
                    }
                    // 原剪贴板为空或非文本——留我们的文字作兜底
                }
            }
        }
    });
    InjectOutcome::Injected
}

一次交付的完整时序：

图里有两个刻意安排的顺序。

先发 result 事件、原生收板，再执行注入。判定拿回后先把 result 事件发给面板，随即由 Rust 侧直接把面板窗口收掉，随后才执行注入——三步互不等待。收板走 Rust 原生调用而非前端回环：前端的收板命令要排回主线程队列，会被随后的注入挡在身后（实测被剪贴板读写挡过 1.3 秒——那正是“面板消失很慢”的真相）。剪贴板的备份、写入、⌘V、延迟还原的耗时也一概不体现在浮窗消失上。这个顺序来自真实的体验反馈：注入里的剪贴板读写是新增耗时，把它排在收板之后，浮窗消失的速度就与注入无关。代价是注入万一失败，面板已经收起、看不到失败提示——可接受的取舍，因为文字必定还在听写历史里；个别失败形态下也留在剪贴板，见下文兜底链。

迟到结果只抑制面板，不取消注入。本地识别耗时数秒到数十秒，结果回来时用户可能已经按了热键开了下一轮。每轮听写有一个递增的周期号，识别线程出发时记下它；结果回来先经状态机核对，翻篇的直接丢弃。核对通过进入交付的，守卫基准是状态机接受结果那一刻的周期号（状态机把基准值随交付一起带出），主线程执行时与当前值再比对一次：翻篇了，说明这是上一轮的迟到结果。这时面板事件必须抑制——把用户正在录音的新面板砸掉是灾难——但注入照常：用户说过这段话，文字就该交付。周期号基准在状态机接受结果那一刻采样一次，执行时在主线程闭包里复读。复读是安全的：热键处理与这个闭包都排在主线程队列上、彼此串行，闭包执行期间周期不会再变。若改在交付线程入口跨线程多读一次，两次读取之间就可能隔着新一轮按键——那才是竞态缝隙，也是基准只采样一次、交给主线程串行复读的原因。

还有一个权限细节：辅助功能未授权时，模拟按键会被系统静默丢弃，不报错。这种情况下无论判定结果如何都放行走注入路径拿到 NeedPermission（未授权时判定链本也产不出 NoInput——AX 第一步就会失败，只能得 Unknown），然后面板回弹显示识别文字与一枚“去开辅助功能权限”按钮——点击才跳系统设置。（更早的版本是自动打开系统设置页，后来改为提示式：不打招呼地拉开设置窗比缺提示更突兀。）原因和"复制失败要显示"一样：用户看到"没反应"却不知道缺权限，就没有自救的入口。

兜底链：文字总有下落​

整个注入设计里，没有一层承诺“永远成功”。每种失败形态都有自己的下落：

  • 判定不该注入 → 面板亮复制按钮（确认非输入亮“这里打不了字 · 复制后去粘贴”，判不出亮“没找到输入位置 · 复制后去粘贴”），点击才写剪贴板——有现场提示的失败形态；
  • paste 模式、失败发生在模拟 ⌘V 那一步 → 文字已写入剪贴板且不还原，手动 ⌘V 取回；
  • 其余注入失败与落空（打不开或写剪贴板失败、⌘V 发出但没落进输入框）→ 面板已收、无现场提示，取回归结为下一条；（无权限不在此列——它有自己的现场提示，见前文「时序」一节的权限细节）
  • 任何情况下 → 设置 → 历史，最近 100 条听写结果本地持久化，逐条显式复制。

一个容易想当然的细节：paste 模式“成功注入”之后，剪贴板里通常并没有那段文字——延迟还原在 500ms 后把用户原来的内容放回去了。只有用户原剪贴板为空或非纯文本时才不还原，文字才会留下。

历史记录在识别完成的第一时间写入，与注入成败无关——它是整条链的地基，前面所有环节的任何失败最终都落到这里。对输入工具来说，“偶尔需要手动粘贴”是可以建立信任的缺陷，“字可能凭空消失”不可以。

边界​

  • 剪贴板还原仅覆盖纯文本；图片与富文本格式信息不备份、不还原，识别文字留在剪贴板作兜底。
  • type 模式（合成键入）没有送达回执，落空不可检测；默认使用 paste 模式。
  • 合成 ⌘V 的 V 键按当前键盘布局映射，纯非拉丁布局下可能映射不到——失败落入"模拟按键失败→文字留在剪贴板"的兜底支。
  • Unknown 场景（系统设置等 AX 只报窗口的应用）不注入、亮“没找到输入位置”按钮；Electron 应用冷树上首次听写仍可能撞一次该按钮（AX 唤醒已提前到按下热键开新篇时，录音加识别的整段时长就是建树窗口，但极短听写叠加冷树仍可能赶不上交付），之后恢复精确判定；个别 Electron 版本可能拒绝唤醒设置，维持 Unknown。
  • 焦点探测 300ms 死线，超时按 Unknown 处理（走终端判定兜底，判不出亮按钮），不等待卡死的目标应用。
  • 500ms 还原延迟是经验值：目标应用更慢时 ⌘V 可能粘到还原后的旧内容（错误内容落盘而非落空），该形态同样只能靠听写历史取回。
  • 面板先收后注入的顺序意味着注入失败时面板已消失、无现场提示；文字取回在多数失败形态下只能走听写历史，仅模拟按键失败那一支会把文字留在剪贴板。
  • 以上机制均为 macOS 行为；键码、AX 错误码、NSWorkspace 语义在其他平台不适用。
