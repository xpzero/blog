macOS 自定义全局快捷键：从系统注册到 CGEventTap

周期2026年11月10日阅读 22 分钟

语音输入工具需要全局生效、默认 Fn、可录制自定义的快捷键。本文整理 Sayit 的按键方案：一个绑定即独占（只吞已注册组合）的主动 CGEventTap 统一接收键盘事件，一张 macOS 键码与 W3C Code 名的对照表统一命名，一个 20ms 轮询兜底不派发事件的 Menu 键。

Sayit 是我做的一个本地优先的语音输入工具：按下快捷键开始说话，再按一次停止，识别出的文字注入当前输入框。这篇文章整理它的快捷键系统：怎样让一个键在任何应用里都按得动，怎样把 Fn 这种不产生按键事件的键变成开关，以及怎样让用户在设置页"按一下就录进去"自己的快捷键。

先给结论。这套方案落到三个部件上：

  • 一个主动模式的 CGEventTap——macOS 提供的事件分接器，统一接收系统里流过的键盘事件。绑定即独占：已注册组合的按下与配套抬起被吞掉，其余按键原样放行；
  • 一张 macOS 键码与 W3C 标准键名（KeyboardEvent.code）的对照表，配置解析和快捷键命名共用它，全应用只有这一份真相；
  • 一个 20ms 的状态轮询，兜底一个不派发事件的键（外接键盘的 Menu 键）。

要解决什么问题​

先看用户侧的用法。默认配置是 Option+Space：任何应用里按下开始录音，再按结束。想换键的用户打开 设置 → 使用 → 录音开关，点击快捷键录制框，按下想要的组合，抬起即录入；Esc 退出，退格删掉最后一个已录组合。

对这个交互，快捷键系统要满足三条硬要求：

  • 全局触发。焦点在终端、IDE、浏览器地址栏里都要生效，不能依赖当前应用转发按键。
  • 默认键零冲突。修饰符组合迟早撞上别的软件的快捷键。理想的默认键是 Fn：拇指天然停在那里，几乎没有应用拿它当快捷键，打字时也碰不到。它有一个使用前置条件，见后文 Fn 一节。
  • 可录制自定义快捷键。快捷键录制框要能录下用户按的任何键——包括修饰键本身和系统组合，并给出实时预览。

这三条要求分别撞上 macOS 输入系统的三件怪事：

  • Fn 不派发普通按键事件。它是个"伪修饰键"，按下只更新修饰符标志位（系统为这类事件派发的是 flagsChanged，即修饰键按下/抬起事件），不产生 keyDown。
  • 有些键只更新状态、不派发事件。外接 PC 键盘的 Menu 键在事件通道里完全看不见。
  • 状态读取接口有自己的怪癖。键码 0（ANSI 布局的 A 键）在无人触碰时恒读"按下"。

后三节的方案就是围绕这三件怪事长出来的。

终局架构​

按键从物理键盘到听写动作的路径：

数据流一句话讲完：配置里的方言字符串（如 Option+Space）编译成 (修饰符位, 键码) 对——修饰符位是 Shift/Ctrl/Option/Command 四个修饰键的位掩码——发布进 tap 线程里的匹配集；真实按键流过 tap 回调时，keyDown 时刻拿 (当前标志位, 键码) 与匹配集比对，命中就触发听写开关，同时把这个事件从系统事件流里吞掉（回调返回 NULL），它不再到达前台应用——绑定即独占；未命中、快捷键录入期、Esc 中止一律原样放行。

对照上一节的三条要求：全局触发靠 CGEventTap 的会话级事件流；Fn 靠 flagsChanged 事件；快捷键录制框靠同一个 tap 的捕获状态机。一套事件源，三个用途。

为什么不用现成的两条路​

系统注册​

第一版用 tauri-plugin-global-shortcut 注册组合键，它在 macOS 底层走 Carbon 的 RegisterEventHotKey。这个模型的逻辑是：你先告诉系统要什么组合，系统匹配到了再通知你。

对"全局触发"这一条它够用；另外两条给不了，还附带一个坑：

  • 录制自定义快捷键无从做起。你只能收到已注册组合的命中通知，看不到用户实际按了什么。
  • Fn 注册不了。Fn 不产生按键事件，"修饰符 + 键码"的注册模型表达不了它。
  • 附带的坑：注册可能失败，错误信息只有一句"可能被其他应用占用"，没有协商余地。

还有一个成本反着算：CGEventTap 收键盘事件需要辅助功能权限，而语音输入工具做文字注入本来就要这项权限。权限成本为零，换到的是完整的事件流。

轮询​

第二版为 Fn 加了 20ms 轮询，读 CGEventSourceFlagsState 和 CGEventSourceKeyState 这两个 CoreGraphics 状态函数。快捷键录制框当时也用轮询实现：每 20ms 读一遍所有键的状态，做集合边沿检测，diff 出按下和抬起。

轮询能用，Fn 方案确实靠它工作过，但结构上有三个问题：

  • 延迟最多一个轮询周期（20ms），事件的先后顺序只能靠采样序号推断。
  • 只看得见"按着"这一种状态。按住连发（自动重复）、点击这些事件语义全部丢失，防抖只能靠时间窗猜。
  • 状态怪癖直接毒化边沿检测。键码 0 恒读 true，意味着"没有任何主键按下"这个判断永远不成立，而录入 Fn 恰恰依赖这个判断（确认按住期间没碰过别的键，见后文快捷键录制框一节），随之失效。

事件回调里这些信息原生就有：事件类型、键码、标志位、自动重复字段，每个都精确到单次事件。既然为了 Fn 必须开 tap 收 flagsChanged，其余按键没有理由再走第二条路。轮询最后只保留给一个键，见后文 Menu 一节。

CGEventTap：把系统按键事件接进自己的线程​

CGEventTap 是 macOS 输入系统里的“分接器”：硬件事件从驱动进入当前登录会话，再分发给前台应用；CGEventTapCreate 让你的进程在这条流上挂一个回调，可以选择观察或改写。这里的用法是：

  • kCGSessionEventTap：挂在会话层，看到当前用户的输入。
  • kCGHeadInsertEventTap：插在事件流前端。
  • kCGEventTapOptionDefault：主动 tap，回调返回 NULL 可以把事件从流里移除。

吞键纪律只有一条：只吞已注册组合——命中匹配集的 keyDown、以及它的配套 keyUp（避免孤儿抬起事件漏给应用），返回 NULL；其余一切事件原样返回。快捷键录入期的所有按键（用户正在录入新键）、Esc 中止（属于当前上下文）、未注册键，一个都不碰。

能看见哪些事件由掩码决定：

const MASK: u64 = (1 << 10) | (1 << 11) | (1 << 12); // keyDown | keyUp | flagsChanged

事件类型、键码、标志位在 CGEvent 里都是整数编号。注意事件类型的编号和键的键码是两套互不相干的数字空间，后文两只 bug 分别住在这两套数字里。掩码就是三个事件编号的位标记，这一行值得多看一眼，下一节会讲到写错它的后果。

创建 tap 有一套固定仪式，核心是 CFRunLoop——Apple 事件循环的基础设施，回调挂在它上面才会被投递：

查看代码：tap 的创建与运行（run_tap 函数，节选）
let tap = CGEventTapCreate(
    SESSION_TAP,      // kCGSessionEventTap
    HEAD_INSERT,      // kCGHeadInsertEventTap
    ACTIVE_TAP,       // kCGEventTapOptionDefault：主动 tap，回调返回 NULL 可吞键
    MASK,             // keyDown | keyUp | flagsChanged
    on_event,         // 回调
    info,             // 传给回调的 AppHandle
);
if tap.is_null() {
    eprintln!("[tap] 创建失败：无辅助功能权限？");
    return;
}
let rl = CFRunLoopGetCurrent();
let src = CFMachPortCreateRunLoopSource(std::ptr::null(), tap, 0);
CFRunLoopAddSource(rl, src, kCFRunLoopCommonModes);
CFRunLoopRun(); // 常驻，直到进程退出

三个工程决策藏在仪式背后：

专职线程。 tap 建在一个独立线程里，那个线程除了 CFRunLoopRun 什么都不做。回调的投递依赖它所在的 runloop，如果挂在主线程的 runloop 上，UI 或任何主线程工作卡住时，按键事件跟着挨饿。

指针跨线程。 回调需要 AppHandle（Tauri 的应用句柄）才能触发动作，但创建函数只接受裸指针。裸指针在 Rust 里默认不能跨线程传递（编译器不认为它线程安全），这里包一层显式声明 unsafe impl Send 的载体带过去。有个细节：线程体必须是独立函数而不是闭包——Rust 2021 的闭包按字段精确捕获，在闭包里解构载体会让裸指针字段被直接捕获，绕过那层 Send 声明。

超时自愈。 回调阻塞过久（观察值在秒级），系统会禁用整个 tap，并补发一个 kCGEventTapDisabledByTimeout 事件。回调认出这类事件就对 tap 端口调 CGEventTapEnable 重新打开。这是 CGEventTap 的标准自愈模式，两行代码换"卡一次就永久失灵"变成"卡一次自愈一次"。

权限模型一句话：keyDown / keyUp 需要辅助功能权限，flagsChanged 不需要。上一节说过，这个应用做文字注入本来就要前者。未授权时 tap 创建失败，触发与捕获都不可用，应用会带路去授权。

从 listen-only 到绑定即独占​

这个 tap 的第一版确实是 listen-only（kCGEventTapOptionListenOnly）：只观察、不吞键，当时把它当辅助工具的美德——不该改变系统行为。重审时发现这个美德有代价：

listen-only 下，已注册的组合照样到达前台应用。默认的 ⌥Space 无所谓；但用户自定义 ⌘D、⌘B 这类常用组合时，一个物理动作两处响应——听写开录的同时，IDE 也删掉了它的一行。“全局快捷键”的承诺只兑现了一半：全局触发是有的，全局独占没有。

终稿改成主动 tap，纪律是“绑定即独占”：

  • 只吞两类事件：命中注册集的 keyDown、它的配套 keyUp。
  • 其余一律放行：快捷键录入期一切按键、Esc 中止、未注册键。
  • tap 被系统禁用期间，键会漏给前台应用——这是安全方向的降级：宁可短暂双重响应，不要全局热键失灵；超时自愈（见上文）后恢复独占。

三类事件，各司其职​

掩码里的三个编号对应三种事件，方案给每种安排了明确分工：

事件编号在这套方案里做什么
keyDown10组合匹配触发听写，命中即吞（独占）；捕获态预览组合名；Esc 中止录音（不吞）
keyUp11捕获态提交录入（键码与最近一次 keyDown 一致才算）；非快捷键录入期吞已注册组合的配套抬起
flagsChanged12Fn 的触发与录入；Fn 抬起时顺带检查修饰符标志位

修饰键与主键的配合时序值得单独说。按下 Option+Space，系统先派发 flagsChanged（Option 按下），再派发 keyDown（Space），后者自带当前标志位。所以组合匹配只发生在 keyDown 时刻：拿 (flags & 修饰符位, 键码) 与匹配集比对。flagsChanged 只处理 Fn，普通修饰键的按下抬起不参与触发。

触发选在 keyDown 而不是 keyUp，是为了响应快——语音输入的开关越跟手越好；后面会看到快捷键录制框反着选了 keyUp，要的是手势完整。同一个 tap 上两个时机各取所需。

一只掩码 bug​

事件编号是裸整数，开发期间写错过一版：keyDown / keyUp 被写成了 1 / 2。而 1 / 2 其实是鼠标左键按下 / 抬起。

这版 bug 的症状极具迷惑性：tap 看得见鼠标点击和 Fn，字母、数字、空格的组合全部失灵；鼠标点击还顶着"键码 0"的马甲混进 keyDown 通道，表现为一只来历不明的"幽灵键码 0"。修掉掩码，幽灵同时消失。

教训落在两处：事件编号、键码这类系统常量，注释里钉死出处（SDK 头文件名和实测记录）；对已知会出怪事的输入留防御分支——键码 0 在 keyDown 入口处无条件丢弃。

方言编译：从字符串到键码，只有一张表​

配置是给人写的（Option+Space），tap 匹配的是数字。快捷键配置是一个列表——可以同时绑多个组合，任一命中即触发，Fn 令牌也可以混在其中。中间这层编译把每个方言字符串变成 (修饰符位, 键码)：

"ctrl+shift+s"
  → 按 + 拆分，逐段对照修饰符别名表
      ctrl  -> MOD_CTRL    (1 << 18)
      shift -> MOD_SHIFT   (1 << 17)
      s     -> 短名展开成 Code::from_str("KeyS")
  → 主键查 macOS 键码表：KeyS -> 1
  → 产出 (MOD_CTRL | MOD_SHIFT, 1)，发布进 tap 匹配集

编译规则：

  • 修饰符别名自己认：ctrl/control、alt/opt/option、meta/cmd/command/super/win，大小写不敏感。
  • 主键交给 Code::from_str 解析。Code 是 Tauri 全局快捷键插件里的 Rust 枚举，键名照搬 W3C KeyboardEvent.code 标准——这里只借它的键名表和解析，不用它注册快捷键。它认识整套标准键表，非法名字当场报错。单字符短名先展开再解析（a → KeyA、1 → Digit1），历史上用过的别名（esc、return、反引号）映射到标准名。
  • W3C 名到 macOS 键码的映射必须自己维护。两套标准不同源：W3C 管命名规范，macOS 虚拟键码是 Apple 自己的编号体系。这份对照表是全应用唯一的键码真相表，正向（配置 → 键码）供触发匹配，反向（键码 → 名）供捕获命名，两个方向永不漂移。
  • 拒绝的输入给人话：裸空格（打字会一直触发）、Fn 进组合（它没有 keyDown，表达不成组合的一部分）、多个主键、键码表里不存在的主键，各有各的报错文案。

真相表由单测钉住：键码无重复，每个名字都能被 Code::from_str 解析，键码 0 不得入表。compile("a") 必须报错——A 键在表里缺席是刻意的，原因见下文键码 0 一节。

查看代码：compile 函数的主循环（节选）
for part in s.split('+').map(str::trim).filter(|p| !p.is_empty()) {
    let pl = part.to_lowercase(); // 修饰符大小写不敏感
    let modifier: Option<u64> = match pl.as_str() {
        "ctrl" | "control" => Some(tap::MOD_CTRL),
        "shift" => Some(tap::MOD_SHIFT),
        "alt" | "opt" | "option" => Some(tap::MOD_OPTION),
        "meta" | "cmd" | "command" | "super" | "win" => Some(tap::MOD_COMMAND),
        _ => None,
    };
    if let Some(m) = modifier {
        mods |= m;
        continue;
    }
    if code.is_some() {
        return Err(format!("『{s}』里有多个主键"));
    }
    code = Some(parse_code(part)?); // 主键保留原文：PageUp 这类驼峰名要靠大小写匹配
}

快捷键录制框：捕获是一个后端状态机​

快捷键录制框要录的是全局快捷键，所以捕获必须发生在后端：Fn、Menu 这类键在 WebView 里根本没有 DOM 键盘事件，系统保留组合在更底层就被系统吃掉，DOM 同样看不见。前端输入框设为只读，获得焦点只当作快捷键捕获模式的开关，按键一律由 tap 转发处理。

捕获态的完整事件序列（此时按键流只服务快捷键录入）：

点击快捷键录制框（输入框获得焦点）
  → start_hotkey_capture，tap 进入捕获态
      keyDown 主键            → 预览：组合名实时上屏
      keyUp 同一键码          → 提交：录入这个组合
      Esc                     → 退出录入
      Backspace               → 删除末尾一个已录组合
      Fn 按下再抬起，期间无主键、抬起时无修饰符 → 录入 Fn 令牌
  → 失焦（输入框失焦或窗口失焦）→ stop_hotkey_capture

几个关键决策：

  • keyDown 预览、keyUp 提交。 按下抬起构成一次完整手势。待提交键码记在原子变量里，keyUp 的键码与最近一次 keyDown 一致才提交，自动重复和乱序事件进不来。
  • 自动重复精确丢弃。 按住不放系统会连发 keyDown，事件自带 kCGKeyboardEventAutorepeat 字段，为真的一律过滤，不进任何逻辑。
  • 键码表外的键丢弃。 录进去只会产出编译不了的垃圾条目，在捕获入口就拦下。
  • 窗口失焦必停捕获。 焦点去了别的应用还在打字的话，用户在那里的每次击键都会被录进快捷键配置。
  • Fn 的录入判定在抬起时刻。 按下后再抬起，此刻没有其他修饰符标志位，且手势期间没有主键穿过（一个 disarm 标记记这件事），才算"单独按了一次 Fn"。两个条件各挡一类误录：抬起时修饰符还按着，说明这是个组合手势；期间有主键穿过，说明 Fn 只是顺路。
查看代码：捕获态的 keyDown 分支（节选）
if capturing() {
    match kc {
        K_ESCAPE => {
            stop_capture();
            let _ = app.emit("hotkey-captured", json!({ "cancelled": true }));
        }

    }
    return;
}

系统不按常理出牌的三个键​

Fn：键码 63，只活在 flagsChanged 里​

Fn 没有自己的 keyDown / keyUp。按下时系统派发一个 flagsChanged 事件，键码字段是 63，同时修饰符标志位里 SecondaryFn（第 23 位）置起。方案里 Fn 的触发和录入都建立在这一条事实上：认出键码 63 的 flagsChanged，再读标志位区分按下与抬起，按下即触发听写开关；录入走上文"抬起时无别的键"的判定。

使用 Fn 有一个前置条件：系统设置 → 键盘 →「按下 🌐 键时」要改为"无操作"。默认设置下 🌐 键有系统用途（如切换输入源），设置页检测到用户绑了 Fn 就会给出带跳转按钮的提示。

这个前置条件躲不开，主动 tap 也吞不掉它：吞键只发生在 keyDown / keyUp，而 Fn 两样都没有（只有 flagsChanged，且一律放行）；更根本的是，🌐 的系统用途不依赖这段会话事件流——系统在更早的环节就处理了它，会话级 tap 把事件删掉也撤销不了已发生的动作。想拦在系统前面得挂 HID 层 tap，那需要 root，用户态应用做不了。

Menu：键码 110，只更新状态、不派发事件​

外接 PC 键盘的 Menu 键是探针实测出来的怪键：它更新 HID 键码状态（CGEventSourceKeyState 读得到），但多数情况不派发 keyDown——事件通道里完全看不见。tap 无能为力，只能回到轮询：20ms 读一次键状态，做上升沿检测。全应用只有这一个键走轮询，且只在用户真的绑了它时才启用。

tap 侧仍留了接收 110 的分支，个别环境若真派发事件就直接处理。两条路径并发触发同一个动作时，靠 300ms 防抖去重；捕获态的重复录入靠前端按名字去重。

键码 0：两种幽灵，两个来源​

同一个数字 0，在两个接口里表现成两种幽灵，来源互不相干：

  • 轮询侧，CGEventSourceKeyState(状态, 0) 在无人触碰时恒读 true。两轮探针实测确认。它让"无主键按下"的判断永远为假，毒化整个集合边沿检测。对策：键码 0 从真相表除名，A 键因此不能当主键——没有人拿 A 当全局快捷键，这个代价可以接受，并由单测钉死。
  • tap 侧，掩码写错的那版 bug 里，鼠标点击顶着键码 0 混进 keyDown 通道（见掩码一节）。对策：keyDown 入口对键码 0 无条件丢弃。

两件事合起来的原则：系统接口的怪癖靠实测钉死，钉死之后靠防御分支和单测固化，不指望它下次表现正常。

回调里的生存纪律​

CGEventTap 回调运行在跨 FFI 的系统上下文里，这里的每条纪律都对应一种真实的死法：

  • 不可 panic。 回调是从系统的 C 代码调进 Rust 的，跨过这道 FFI（外部函数接口，即语言之间的调用边界）panic 就是未定义行为。所有分支只做匹配和事件发送，不做可能 panic 的操作。
  • 不可持锁久等。 回调阻塞过久系统就禁用整个 tap，全部热键失灵。Esc 中止录音的判断读无锁的原子标志，而不是共享状态的互斥锁。
  • 动作回主线程。 文字注入链路——enigo（Rust 的输入模拟库）到 HIToolbox（Apple 管输入法的系统框架）——是仅限主线程的 API，非主线程调用会触发 dispatch_assert_queue 断言直接崩溃。所有热键动作经 run_on_main_thread 派发。
  • 吞键最小化。 返回 NULL 的分支只有两个：命中匹配集的 keyDown、它的配套 keyUp。其余一切原样返回。
  • 热发布。 配置每次改动即编译、即整体替换匹配集，tap 不用重建；配置没变化时替换是空操作。设置页因此不需要保存按钮。

动作守卫：300ms 防抖与 CAS​

防抖不住在回调里，住在动作入口 should_handle()——tap 与 Menu 轮询两条路径都会经过它。按住连发、双路径并发，都可能让同一动作触发两次；窗口 300ms，窗口内的重复触发忽略。判定用 CAS（compare-and-swap，比较并交换：仅当值仍是刚才读到的旧值时，写入才成功）：两个路径并发穿过检查窗口时只有一个赢家，toggle 不会双发。

主动 tap 时代的一个细节：即便防抖判输了（动作被忽略），键照样吞——“我们的键”不该因为内部竞态漏给别的应用。

边界​

  • 系统保留组合（如 ⌘Tab）捕获不到：系统在更底层消费了它们，快捷键录制框里按下去没有反应。
  • 已注册组合被独占：绑定之后这个组合不再到达任何前台应用——绑定即独占是设计选择，不是副作用。tap 被系统禁用期间键会漏给应用（安全向降级，自愈后恢复独占）。
  • 孤儿 keyUp 边角：先松修饰符再松主键时，keyUp 的标志位不再匹配注册组合，这个抬起事件会漏给应用——应用一般忽略 keyUp，不做有状态跟踪。
  • A 键不能当主键：键码 0 因幽灵读数被真相表除名。
  • 键码表按 ANSI 布局维护，其他键盘布局（如 JIS）未测。
  • 辅助功能未授权时 tap 创建失败，触发与捕获都不可用（应用本就为文字注入需要这项权限，授权前有带路提示）。
  • Fn 依赖用户改一处系统设置，应用只能提示和带路，无法代改。
  • Menu 键的行为是探针实测结论（两轮），没有官方文档背书；个别环境可能派发事件，双路径靠防抖去重兼容。
