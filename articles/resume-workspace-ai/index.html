把简历编辑器做成可确认的 AI 工作流

2026年7月31日 · 阅读需 5 分钟
Kehan

最初我只想做一个能编辑并打印 A4 简历的页面。做到后面，问题变成了：如果加上 AI 改写，怎样避免用户点一次按钮就让模型覆盖掉整份简历？

这篇记录当前项目的结构和几个实现取舍。项目代码在 resume-pdf-editor。

先把简历当成结构化数据​

页面不是直接编辑 HTML，而是维护一份简历对象：基本信息、教育经历、技能、工作经历、项目经历、个人评价和自定义模块都在这个对象里。

这样做有两个直接收益：

  • 同一份数据可以渲染不同简历模板，也能导出 Markdown 和打印版 PDF。
  • AI 不需要理解页面 DOM，只需要返回同样结构的 JSON。

项目现在是一个 pnpm workspace：

front/     # Vite + React 编辑器和预览
backend/   # Fastify 服务，负责调用 LLM

本地开发时执行：

pnpm install
pnpm dev

前端请求 /api/resume/optimize，由 Vite 转发到本地 Fastify 服务。这样 API Key 不必写进前端源码。

AI 结果不能直接覆盖​

我把 AI 优化拆成三个步骤：

当前简历 + 目标岗位 + JD + 补充描述
  -> 后端调用模型
  -> 返回结构化简历草稿
  -> 前端显示优化前 / 优化后
  -> 用户确认后才应用

“补充描述”既可以写用户希望强调的方向，也可以补充未写进简历但确认真实的背景。后端的固定提示词要求模型不能虚构公司、项目、技术、时间、数据或成果。

这条约束不代表模型输出一定可靠，所以后端还会做两次检查：

  1. 请求进入后端时校验简历和 LLM 配置的字段类型与长度。
  2. 模型返回后再次校验 JSON 是否符合简历结构。

如果模型没有产生变化，前端会明确提示“没有可应用的修改”，并禁用应用按钮。这比无论结果如何都显示“已应用”更诚实。

局部优化需要在服务端限制写入范围​

全量优化之外，当前支持优化整组技能、个人评价和单个项目的描述。

这里容易犯的错误是：前端虽然只给“项目描述”放了一个按钮，后端却把模型返回的整个项目对象写回去。这样项目名称、职责或时间都有可能被意外替换。

现在接口会携带优化范围和目标索引。对于项目描述优化，后端只合并：

result.projects[targetIndex] = {
  ...originalProject,
  intro: optimizedProject.intro
};

界面上的操作点和实际写入范围必须一致。这不是提示词能完全解决的问题，最终仍要由服务端的数据合并规则保证。

本地多简历比先做账号更合适​

应用目前不做登录和云端同步，而是把多份简历保存到浏览器本地存储。用户可以新建、切换、重命名和删除简历，AI 应用结果也会同步保存。

这是一个刻意的边界：对于本地简历工具，先把“编辑、预览、导出、确认 AI 草稿”这些核心路径做顺，比先引入账号、数据库和权限系统更有价值。

两个运行时细节​

LLM 地址不一定只有一种写法​

后端支持填写服务根地址，也支持填写完整的 /chat/completions 地址。服务端会在调用前规范化路径，避免重复拼接。

curl 能通不代表 Node fetch 一定能通​

开发中遇到过一个兼容性问题：同一服务地址用 curl 能拿到认证错误，Node 内置 fetch 却在 TLS 握手前连接被重置。为了避免把这类情况误报为“API Key 错误”，后端改用 Node 的 http/https 请求通道，并按 DNS、拒绝连接、超时和 HTTP 状态码返回更具体的提示。

这不是所有模型服务都会遇到的问题，但排查外部 API 时，最好分别验证：浏览器到本地后端、本地后端到模型服务、模型服务对 Key 的认证。

还没有解决的事​

  • LLM 配置目前只保存在当前浏览器会话，适合本地开发，不适合多人或生产环境。
  • PDF 导入只提取可复制文本，复杂版式仍需人工整理。
  • 目前没有云端同步、版本历史或账号体系。
  • 模型可以改善表达，但不能替用户补出不存在的量化成果。

这些限制会保留在产品说明里，而不是用“AI 自动优化”掩盖掉。对简历这种事实性文档来说，可确认、可撤销通常比自动化程度更重要。
