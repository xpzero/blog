文章写作与审稿

2026年9月25日阅读 8 分钟

本文件适用于 articles/ 下的文章和随文资源，并与根目录 AGENTS.md 一起生效。用户对当前文章的具体要求优先。先确认文章类型、引用版本和实际证据，再决定结构与呈现；不要把推荐结构写成每篇通用模板。

内容、链接与系列​

  • 文章放在最合适的主题目录。目录名、文件名及资源 URL 使用 ASCII，推荐英文 kebab-case；中文用于标题、标签和正文。
  • 已发布文章通常包含 title、description、date、authors、tags；有合适封面才设置 image。未完成或结论不宜发布时设 draft: true；发布时移除。Blog 会自动生成列表、系列、主题、归档和 Feed，无须修改侧边栏或手工索引。
  • 站内文章优先链接相对 .md/.mdx 文件（如 ./02-tool-use.md）；图片和文章放在一起，用相对路径引用，添加有意义的替代文本。移动或重命名时同步检查内部链接、系列顺序和兼容跳转。
  • series、seriesTitle、seriesOrder 定义系列；seriesOrder: 0 为导读。修改 Agent 系列时核对 articles/ai-agent-learning/index.md 与已发布文章顺序连续且唯一；草稿可占后续序号，但不进入生产导航。修改 LLM 系列时核对 articles/llm-learning/overview.md 与系列元数据。

写作主线与初学者视角​

  • 先判断主要类型：总结型整理已验证知识的关系；问题导向型回答具体障碍或任务；探索型调查暂不确定的解释。三者都从真实而具体的疑问开始，交代背景、环境和为什么值得解决。推荐顺序是问题或目标 → 最小可运行或可观察示例 → 求证与解释 → 有边界的回答 → 未解决问题；依类型调整，不拼接三套模板。
  • 作者处于 LLM、Agent 初学阶段。只依赖前文已经建立或本篇已求证的概念；首次使用术语先解释，API、命令、协议名称保留英文并说明作用。可假定读者具备基础 Web 开发知识，不能假定读者读过系列其他文章。
  • 回指确有帮助的旧文时，写“前面”或“前文”，链接文字用“前文：文章标题”；不要用“第 N 篇”。这条只规范发生回指时的写法，不要求每篇回顾上一篇。
  • 个人工作笔记从问题、操作或可见现象切入，不写解释文章安排的元叙述。缺乏作者经历的证据时，不编造猜想、错误尝试、早年阅读、实验或情绪；避免“众所周知”“显然”和事后全知视角。论文或技术史只有直接帮助当前问题时才引入。
  • 讲功能按读者遇到问题的顺序展开：用户要做什么 → 需要哪些数据和接口 → 怎样保存、读取、更新 → 状态与失败。先交代原有流程及其遇到的障碍，再引入解决办法；每个表、字段、指针或机制先交代用途，不按源码模块逐个平铺。正文用流程和具体例子解释，不让读懂文章依赖方法名；必要时再给简短代码和固定版本链接。多个各带用途的字段改用列表。
  • 面向不了解项目的读者写正文：只保留影响主要结论或证据真实性的限制，集中在相关位置简短交代，避免每段反复补充边界。项目内部的调试报错、交付阶段和排障流水账，除非直接帮助解释读者的问题，否则不写进正文；仍须诚实说明模拟数据或未验证范围。
  • 写清关键求证步骤、版本、命令、输入、输出及资料来源；只保留有价值的失败尝试。事实、文档建议、推断、示意和开放问题分别标注；观察到行为不等于证明内部原因或跨网关普遍规律。结论只回答开头的问题，不扩大到证据之外。

代码与跨仓库证据​

  • 修改已发布 build-agent-* 文章的代码、输出或行为前，核对文章指向的 xpzero/demo-agent 固定提交，若本地有 ../demo-agent 也核对；除用户明确要求外只读。保留作为证据的永久链接，位置变化时更新并说明版本边界。
  • 尚未提交的跨仓库实现不能先于证据推送文章；应先提交实现，再补固定提交链接。外部项目机制首次进入主线时说明归属及实际借用的术语、结构或语义；区分本地重写之处。源码链接固定到核对过的提交，当前用法可引官方文档。
  • 代码、命令和配置应可运行，不能运行的标为伪代码；摘录省略上下文时标明。术语、字段、接口、图与输出须与引用版本一致。服务商或网关特有行为注明条件，不把兼容 OpenAI 端点理解为行为相同。操作命令说明失败方式、取舍与必要的回滚步骤。

真实环境与证据边界​

  • 基于真实项目代码的功能、启动方式和运行结果，先在对应版本的真实环境中验证，再写作和下结论。使用项目文档规定的配置、依赖、入口与启动命令，覆盖文中用户操作。独立测试库和无敏感演示数据可经正常配置接入。
  • 若正常启动失败、环境缺失或关键流程未通过，记录错误及其对正文结论的影响，通常保持 draft: true，待修复后再验证。用户明确要求发布时，可以收窄正文到已核实的代码流程与演示页面，并就近说明未验证的功能效果；不得将演示结论写成真实模型运行结果。不能另建临时 Harness、换应用入口、注入服务或模型响应、拦截请求绕过失败，然后把页面写成正常运行证据。不要为了验证调用付费 API 或泄露凭据。
  • 功能截图来自上述真实运行过程。涉及模型或外部服务的功能结论，须使用实际配置的服务取得真实响应；mock、fixture、预览或注入数据只能明确标为测试或演示，不能填补端到端证据缺口。截图附近说明可见状态和环境；保留对应提交、依赖版本、配置、启动命令、输入与输出以便复现，敏感信息可遮盖但不能改结果。
  • 单元测试、集成测试、构建、真实用户流程分别报告通过、失败或跳过以及各自范围。截图只证明特定 UI 状态；模拟模型事件不能证明真实模型会选择工具；真实页面或数据库不能单独证明整个功能可用。页面报错、后端成功但前端没展示等须在相关结论附近写明。
  • 涉及审批、恢复、并发等状态机制时，先定义状态由谁产生、说明什么；区分权限结果、用户决定与执行结果。按真实时序交代持久化边界、副作用、连接结束与恢复事实来源；不同执行顺序不能混为一谈。已知竞争窗口、配置加载时机与恢复限制放在相关边界处。

呈现与检查​

  • Agent 系列新文章按用户要求提供与问题相关的实际代码、截图及图文解释；截图须符合上面的真实环境与证据边界。若无法取得合格的功能截图，写明验证缺口，按上面的发布条件决定是否保持草稿；不能用模拟画面填补证据。图文并茂不等于每节都配图。
  • 根据关系选择表达：知识层级可用 MarkMap，流程或时序可用 Mermaid 或可校对的插图，逐项差异用表格，短内容用正文。先检查示例、表格和截图是否已解释清楚，再决定是否加图；图文对应、箭头和中文标签准确。不强制每节配图或使用固定画图工具；图不是目录的翻版，主结论和证据不能只放在图或折叠区。确有求证前后认识变化才画两种认识，不虚构初始错误。
  • 使用 Docusaurus 内置语法或组件前查 ../guides/docusaurus-writing.md，有疑问再核对当前版本的官方文档和项目配置。已有自定义 MDX 组件见 src/theme/MDXComponents.js；使用 MarkMap 时复用 src/components/MarkMap/ 并本地导入。
  • 标题层级连续；长期引用才加显式 ID，使用 MDX 注释式 ## 标题 {/* #stable-id */}，同页唯一。功能图、代码和截图各有正文解释，保持版本和场景一致。校对图片路径、替代文本、内部链接、图形渲染和构建警告；验证和部署规则见根目录 AGENTS.md。
