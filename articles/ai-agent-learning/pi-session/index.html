pi 的会话：一棵追加式事件树，和它的投影

周期2026年10月27日阅读 28 分钟

恢复、分叉、压缩，pi 会话的三个能力来自同一个设计决策：会话是一棵只追加的 entry 树，模型上下文与内存消息都是它投影出来的视图。

前面两篇走读 pi：一篇跟启动装配，一篇跟一条消息的往返。两篇里有个对象反复露脸——SessionManager。消息定稿的瞬间被它写进会话文件；换模型、压缩、退回历史，也都绕不开它。看得出来，pi 把几乎所有发生过的事——每条消息、每个工具结果、每次换模型——都往这一个文件里存。

这就留下三个问题：这份文件里的数据到底长什么样？什么时候往里存？什么时候从里取？

这篇文章顺着三个问题拆 pi 的会话实现。先给总答案：pi 的会话文件是一棵只追加的 entry 树。存，是在事实发生的瞬间往树上挂一个节点；取，是在需要的时候沿「当前叶子」把树投影成一份线性消息列表。恢复、分叉、压缩这些看着不相干的能力，都是这一个设计的推论。

信息

本文源码核对自 earendil-works/pi 仓库 commit 8efd314f。两个核心文件：packages/coding-agent/src/core/session-manager.ts（约 2000 行，存储）与 agent-session.ts（约 4400 行，编排）。文中 jsonl 证据取自本机 ~/.pi/agent/sessions/ 下的真实会话文件，均为节选、已脱敏。

全景：一个日志，两个视角​

先认三个角色，对应仓库里三个真实的类：

  • Agent（循环层）：跑模型、执行工具的循环，每完成一件事就广播一个事件——消息定稿、回合结束、运行结束；
  • AgentSession（编排层）：订阅这些事件，决定何时往树里写什么；换模型、压缩、树导航这些主动操作也从这里进；
  • SessionManager（存储层）：内存里一棵 entry 树加一个叶子指针，磁盘上一个 .jsonl 文件。所有读写都过它。

三个名字先和上一篇文章的四层图对齐：那篇文章把 pi 分成四层——界面层管输入输出，编排层（AgentSession）管加工与存取，循环层（Agent）跑模型与工具，协议层管各家 HTTP 方言。本文只动中间两层；存储层不是新增的第五层，是编排层里管数据的那部分，单独拉出来看。

数据在三个角色之间走两条方向相反的路——一条管存，一条管取，这就是全文的地图：

  1. 存是事件驱动的：循环层广播「消息定稿」→ 编排层听到 → 往树上追加一个 entry → 磁盘文件追加一行；
  2. 取发生在需要的时刻：循环层准备发请求 → 编排层挂的请求前钩子从树上投影出消息列表 → 用它替换请求里的消息。

这张图里藏着本文最重要的一个反转：内存里的消息数组不是权威数据，树才是。自己动手写 Agent 时最常见的做法是把内存里的 messages 列表当作对话本身，文件只是退出时的备份。pi 把这个关系倒了过来：磁盘上的树是唯一事实源，内存消息只是它投出来的影子——影子随时可以重建，也随时会被重建。

后面的章节按三个问题展开：存了什么、什么时候存、什么时候取，最后看这套机制撑起来的两个应用。

存了什么：一棵只追加的 entry 树​

先看它在磁盘上的真身。

磁盘布局​

pi 的会话落在 ~/.pi/agent/sessions/ 下：每个项目目录一个子目录，目录名是项目路径编码后的字符串；每个会话一个 .jsonl 文件，文件名是「创建时间_会话 id」。本机的真实目录（节选）：

~/.pi/agent/sessions/
├── --Users-...-Documents-workspace-blog-source--/   # 本仓库
│   ├── 2026-10-17T09-30-33-368Z_01a15a86-....jsonl
│   └── 2026-10-21T15-10-48-277Z_01a15f03-....jsonl
├── --Users-...-Documents-workspace-github-pi-mono--/
└── ...

jsonl：一行一个事实​

打开一个真实会话文件看前几行（节选、脱敏）：

{"type":"session","version":3,"id":"01a15f03-...","timestamp":"2026-10-21T15:10:48.277Z","cwd":"/Users/.../blog-source"}
{"type":"model_change","id":"ffb815de","parentId":null,"timestamp":"...","provider":"zai-coding-cn","modelId":"glm-5.3"}
{"type":"thinking_level_change","id":"c782738e","parentId":"ffb815de","timestamp":"...","thinkingLevel":"high"}
{"type":"message","id":"5b83687c","parentId":"c782738e","timestamp":"...","message":{"role":"system","content":"","sections":{...}}}
{"type":"message","id":"...","parentId":"...","timestamp":"...","message":{"role":"user","content":"test"}}

第一行是会话头（header），记录格式版本、会话 id、创建时间、工作目录。之后每行叫一个 entry（条目），是 pi 眼里的一个「事实」。骨架长这样：

查看代码：会话头与 entry 骨架（core/session-manager.ts）
export const CURRENT_SESSION_VERSION = 3;

// 会话头：文件第一行
export interface SessionHeader {
  type: "session";
  version?: number; // v1 会话没有这个字段
  id: string;
  timestamp: string;
  cwd: string; // 会话在哪个目录开的，恢复会话时靠它找回项目
  parentSession?: string; // fork 出来的会话，指向来源会话文件
}

// 除 header 外所有行的公共骨架
export interface SessionEntryBase {
  type: string;
  id: string; // 8 位随机短 id
  parentId: string | null; // 指向上一个 entry，串成树
  timestamp: string;
}

两个设计从这里直接读出来：

  • 只追加：文件只在末尾加行，已有行永不修改、永不删除。进程写一半死掉，之前追加的部分仍然完整可用。
  • entry 是一棵树：每个 entry 带 id 和 parentId。正常聊天时新 entry 挂在当前最新 entry 下面，串成一条链；从历史某节点重聊时，就长出真正的分叉。内存里的 leafId 记住「当前走到哪个节点」，读写都以它为起点。

entry 的类型​

聊天消息只是 entry 的一种。会话里发生过的一切各占一种类型：

type存什么进模型上下文吗
messagesystem / user / assistant / toolResult 消息会
model_change / thinking_level_change中途换模型、换思考档位的记录不会；恢复会话时还原当时配置
usage会话外用量（如缓存预热）不会
compaction压缩摘要会（摘要 + system 快照）
branch_summary从分叉点切走时对被放弃路径的摘要会
context_edit对历史消息的改写/抹除记录不直接进；投影时生效
custom / custom_message扩展私有数据 / 扩展注入的消息custom 不会；custom_message 会
label / session_info书签、会话命名不会，界面导航用

把「换模型」也记进会话文件，换来一个实用的性质：pi -c 恢复会话时，pi 从树上读出「上次聊到这里时用的什么模型、什么思考档位」，原样还原，而不是拿今天的默认配置接着聊。

惰性建文件​

一个细节：会话文件不是启动时就创建的。前两行 model_change、thinking_level_change 这类「开机设置」先留在内存里，直到出现第一条 user 或 assistant 消息，文件才真正落盘——设置行随第一条消息一起写进去。开着 pi 只看了眼就退出，不会留下空会话文件。

查看代码：惰性建文件（core/session-manager.ts）
// 只有会话里出现过 user 或 assistant 消息，才算「有过对话」
private _hasConversation(): boolean {
  return this.fileEntries.some(
    (e) => e.type === "message" && (e.message.role === "user" || e.message.role === "assistant"),
  );
}

_persist(entry: SessionEntry): void {
  if (!this.persist || !this.sessionFile) return;

  if (!this.flushed) {
    if (!this._hasConversation()) return; // 还没有对话：继续留在内存
    const fd = openSync(this.sessionFile, "wx"); // 独占创建：文件已存在则报错，防止误覆盖
    try {
      for (const e of this.fileEntries) writeFileSync(fd, `${JSON.stringify(e)}\n`); // 设置行补写
    } finally {
      closeSync(fd);
    }
    this.flushed = true;
  } else {
    appendFileSync(this.sessionFile, `${JSON.stringify(entry)}\n`); // 之后逐行追加
  }
}

openSync(..., "wx") 的 wx 标志要求「文件必须不存在」——创建那一刻就防止了把别人的会话文件覆盖掉。

什么时候存：持久化是事件的副作用​

树上的 entry 从哪来？看时机就两类：消息定稿的瞬间自动写一批，操作发生的当下显式写一笔。

自动写入：监听事件流​

AgentSession 构造时做的第一批事里就有这一件：订阅 Agent 的全部事件。

查看代码：构造函数里的订阅（core/agent-session.ts）
constructor(config: AgentSessionConfig) {
  // ...
  // 订阅 agent 事件：所有消息/工具事件先流到这里，
  // 用于会话持久化、扩展分发、自动压缩、自动重试
  this._unsubscribeAgent = this.agent.subscribe(this._handleAgentEvent);
  this._installAgentRequestProjection(); // 每次请求前从树投影出消息列表（下一节）
  // ...
}

事件处理器 _handleAgentEvent 收到「消息定稿」事件（message_end）时落盘：

查看代码：message_end → 追加 entry（core/agent-session.ts）
// 处理会话持久化
if (event.type === "message_end") {
  let entryId: string | undefined;
  if (event.message.role === "custom") {
    // 扩展注入的消息：存成 custom_message entry
    entryId = this.sessionManager.appendCustomMessageEntry(
      event.message.customType, event.message.content, event.message.display, event.message.details,
    );
  } else if (
    event.message.role === "system" ||
    event.message.role === "user" ||
    event.message.role === "assistant" ||
    event.message.role === "toolResult"
  ) {
    // 四种标准消息：存成 message entry
    entryId = this.sessionManager.appendMessage(event.message);
  }
  if (entryId) this._entryIdsByMessage.set(event.message, entryId);
  // compactionSummary / branchSummary 等类型在各自的操作里另行追加
}

也就是说，没有任何代码在「对话结束」时显式保存对话。消息定稿的瞬间——流式输出刚走完、工具结果刚拿到——它就已经作为事件被听见、被追加进树、被写进文件。对话进行到哪一步被中断，已发生的都在盘上。

那用户自己发的消息呢？同样走 message_end 通道，四种角色一个入口，用户消息不搞特殊。特殊的是它的「定稿」时机：assistant 消息要流式收完才算定稿；用户消息不会生长，循环一启动就 start、end 背靠背发出——落盘发生在第一个模型请求发出之前。

查看代码：用户消息的事件发射（agent 包 agent-loop.ts，节选）
await emit({ type: "agent_start" });
await emit({ type: "turn_start" });
for (const message of initialMessages) { // 回车提交的用户消息在这里
  await emit({ type: "message_start", message });
  await emit({ type: "message_end", message }); // 背靠背，中间没有等待
}
await runLoop(currentContext, …); // 然后才发出第一个模型请求

这个时序是刻意的。惰性建文件那段源码注释写得很明白（对应 issue #10000）：从用户消息开始记录，而不是等第一条助手回复，保证第一轮就算没跑完，你发的 prompt 也在盘上——按下回车后接口报错、进程崩溃，消息都不丢，pi -c 回来接着发。

显式写入：操作记录在操作里​

另一部分 entry 来自显式调用，散在各操作的第一现场：

  • 换模型：setModel() 内部一句 this.sessionManager.appendModelChange(model.provider, model.id)；
  • 压缩：compact() 完成后 appendCompaction(summary, firstKeptEntryId, ...)；
  • 树导航、打书签、扩展存私有状态，各有对应的 appendXxx()。

原则是一致的：操作改变状态的同一时刻，把这件事记进树，不存在「攒一批再写」。

追加的四步​

所有 appendXxx() 汇到同一个私有方法：

查看代码：_appendEntry 四步（core/session-manager.ts）
private _appendEntry(entry: SessionEntry): void {
  this.fileEntries.push(entry); // ① 追加进内存数组（保留文件原始顺序）
  this.byId.set(entry.id, entry); // ② 进 id → entry 索引
  this.leafId = entry.id; // ③ 叶子指针前移：新节点成为当前位置
  this._persist(entry); // ④ 立即落盘：文件追加一行
}

崩溃安全的账算得很细：

  • 每条消息独立成一行 JSON，写完即可丢，进程死不死都不影响已写的行；
  • 万一最后一行写了一半（没有换行符或 JSON 不完整），下次载入时这一行解析失败会被直接跳过，前面的行不受影响；文件末尾缺换行时还会顺手补上；
  • 配合惰性建文件：没聊过天就退出，磁盘上什么都不会发生。

回头看：持久化不是一次「保存」动作，而是事件流的副作用。谁都不需要记得保存，因为每件事发生的那一刻它已经被记下了。

什么时候取：投影，以及谁才是事实源​

树里存的是事实的完整记录：被放弃的分叉、被压缩的旧消息、被抹掉的失败尝试、换模型的流水——全都在。模型需要的是一条线性的消息数组。什么时候需要？恢复会话之时、发每个请求之前、状态变更之后。从树推导出这份线性列表的过程，pi 的源码里叫投影（projection）。

投影三步​

查看代码：buildSessionProjection（core/session-manager.ts，节选注释）
export function buildSessionProjection(entries, leafId, byId): SessionProjection {
  // ① 路径回溯：从当前叶子 leafId 沿 parentId 走到根，取出这条路径上的全部 entry
  const path = buildSessionPath(entries, leafId, byId);
  const { thinkingLevel, model } = getSessionContextSettings(path); // 顺路还原当时的模型配置

  // ② 压缩感知：路径上有 compaction entry 时，它之前的旧消息不进上下文，
  //    换成 [compaction entry 本身] + [firstKeptEntryId 之后的保留段]
  const contextEntries = buildContextEntries(entries, leafId, byId);

  // ③ 应用改写：context_edit 指向的 entry，内容被替换或整条抹掉
  const edits = new Map();
  for (const entry of contextEntries)
    if (entry.type === "context_edit") edits.set(entry.targetId, entry);
  const projectedEntries = contextEntries.map((e) => ({
    sourceEntry: e, // 每条投影消息都记着自己来自哪个 entry
    messages: projectContextEntry(e, edits.get(e.id)),
  }));

  return {
    entries: projectedEntries,
    messages: projectedEntries.flatMap((e) => e.messages), // 拍平成线性消息数组
    thinkingLevel,
    model,
  };
}

三步换算的效果用一个分叉过的会话看最清楚（图中也画了被放弃的旧路径，它们仍在文件里，只是不在这次的视图里）：

root → u1 → a1 → u2 → a2                     ← 被放弃的旧路径（仍在文件里）
           └→ branch_summary → u2' → a2'      ← 当前 leafId 所在路径

投影结果 = [system, u1, a1, 分叉摘要, u2', a2']

路径上每个 entry 按类型翻译成消息：message 原样；branch_summary 变成一条带说明前缀的摘要消息；model_change 这类状态 entry 不产生消息，只贡献「当时的配置」。投影从不改动树本身——下次换个叶子再投，就是另一条路径的视图。

context_edit：改写和删除都是追加​

投影第③步处理的 context_edit 值得单独看，因为它是「只追加」原则最极端的体现：改历史不改文件。触发改写和抹除的都是程序：自动重试、溢出恢复，以及扩展在回合边界提交的改写草稿（这是唯一能给新内容的入口）。

想改掉某条历史消息时，pi 不去碰那一行 jsonl，而是追加一个新的 context_edit entry，指明目标 entry 和替换内容：

查看代码：appendContextEdit 与投影时的应用（core/session-manager.ts）
// 追加改写记录：targetId 指向要改的 entry，replacement 是新内容
// replacement 为 null 表示「这条从模型上下文里抹掉」
appendContextEdit(targetId: string, replacement: ContextEditEntry["replacement"]): string {
  // 校验：目标必须在当前分支上、必须是可改写的消息类型（此处省略）
  const entry: ContextEditEntry = {
    type: "context_edit", id: generateId(this.byId),
    parentId: this.leafId, timestamp: …,
    targetId, replacement,
  };
  this._appendEntry(entry);
  return entry.id;
}

// 投影时：指向同一目标的多条 edit，最新一条说了算
function projectContextEntry(entry, edit) {
  const messages = sessionEntryToContextMessages(entry);
  if (!edit) return messages;
  if (edit.replacement === null) return []; // 抹掉：这条不产生任何消息
  // 替换：只换 content，消息的角色、时间戳等元数据不动
  return messages.map((message) => ({ ...message, content: edit.replacement.content }));
}

（… 处为省略的实现细节。）

这不是边角功能。本机一个真实会话文件里就有现成证据——那次会话里模型连续失败了三次，每次失败后紧跟一行 context_edit（节选、脱敏）：

{"type":"message","id":"07baa7e8",…,"message":{"role":"assistant","content":[],…,"stopReason":"error",…}}
{"type":"context_edit","id":"ea7514ff","parentId":"07baa7e8",…,"targetId":"07baa7e8","replacement":null}
{"type":"message","id":"787adaeb",…,"message":{"role":"assistant",…,"stopReason":"error",…}}
{"type":"context_edit","id":"17acc4df","parentId":"787adaeb",…,"targetId":"787adaeb","replacement":null}
…（第三次失败同样一对）…
{"type":"message","id":"…",…,"message":{"role":"assistant",…,"stopReason":"stop","content":[{"type":"text","text":"好，先讨论。…"}]}}

这是自动重试机制留下的痕迹。每次重试前，pi 把上一次失败的尝试从模型上下文里抹掉——用 replacement: null 的 context_edit。源码注释写明了意图：

// Keep the failed attempt in raw history while durably omitting it from model projection.
//（把失败尝试留在原始历史里，同时从模型投影中持久地抹掉。）
this._omitRecoveryAttempt(message);

「删除」在这里不是删文件里的行，而是追加一条说「它不算数」的记录。原始历史完好无损，模型看到的上下文干干净净，两个目标同时成立。

谁才是事实源​

到这里可以摊开本文的核心论断了。「取」有三个时机，三处代码，同一个动作——从树重新推导内存消息：

查看代码：三处「从树到内存」的推导（sdk.ts / agent-session.ts）
// ① 出生时：恢复会话，Agent 的初始消息 = 会话投影
const existingSession = sessionManager.buildSessionContext();
// ...
const agent = new Agent({
  initialState: { systemPrompt: "", model, thinkingLevel, tools: [], messages: existingSession.messages },
  // ...
});

// ② 边界时：压缩、改写、扩展注入之后，用投影结果覆盖内存消息
private _refreshFinalizedContext(): void {
  const projection = this.sessionManager.buildSessionProjection();
  for (const entry of projection.entries)
    for (const message of entry.messages) this._entryIdsByMessage.set(message, entry.sourceEntry.id);
  this.agent.state.messages = projection.messages; // 内存 ← 树
}

// ③ 每次请求前：发往模型的请求，消息列表现场重新投影
this.agent.prepareRequest = async (request, signal) => {
  const projection = this.sessionManager.buildSessionProjection();
  const canonicalContext = {
    ...request.context,
    messages: projection.messages, // 请求里的消息 ← 树
    // ...
  };
  // ...
};

三处合起来说明：agent 内存里的 messages 是缓存，不是账本。它出生时从树投影一次，边界处被投影刷新，每次请求前又被投影校准。哪怕把内存消息整个扔掉，随时能从树重建出一模一样的一份。

反过来讲也成立：既然发给模型的永远是投影，那么任何想改变模型所见的行为——删一条失败消息、换一条分支、把一百条旧消息换成一段摘要——唯一的表达方式就是往树上追加 entry。这是下一节压缩机制的全部前提。

压缩：上下文管理为什么住进了会话​

会话越长，投影出来的列表越大——大到逼近模型窗口上限时，就得把远段历史换成摘要，这就是上下文压缩（compaction）。它功能上属于「上下文管理」，听起来该是请求组装环节的事。但在 pi 里，它的算法放在独立模块 core/compaction/，触发在编排层，而结果记录成树上的一个 entry。为什么？

上一节末尾已经回答了一半：发给模型的是投影，改变投影的唯一通道是追加 entry。压缩要做的正是「把一百条旧消息换成一段摘要」——它没有别的实现路径，只能以 compaction entry 的形式写进树，投影时生效。剩下的一半是工程上的清醒分工，模块头注释写得很直白：

// Pure functions for compaction logic. The session manager handles I/O.
//（压缩逻辑的纯函数。I/O 由 session manager 处理。）

三层各司其职：compaction/ 只做无副作用的计算（切点选择、摘要生成、token 估算）；AgentSession 掌握触发时机；SessionManager 负责把结果记进树。

三个触发时机​

触发入口时机
手动/compact 命令用户主动执行，先中止当前运行
阈值_checkCompaction()每次运行结束（agent_end）后检查，也覆盖提交新消息前
溢出_checkCompaction()模型报上下文溢出错误，或响应被长度截断且可恢复

阈值判断一行就能说完：

查看代码：阈值判断与默认值（core/compaction/compaction.ts）
export function shouldCompact(contextTokens: number, contextWindow: number, settings: CompactionSettings): boolean {
  if (!settings.enabled) return false;
  return contextTokens > contextWindow - settings.reserveTokens; // 留出安全余量再触发
}

export const DEFAULT_COMPACTION_SETTINGS: CompactionSettings = {
  enabled: true,
  reserveTokens: 16384,  // 距离窗口上限还剩 16k token 时触发
  keepRecentTokens: 20000, // 压缩时至少保留最近 20k token 不摘要
};

当前 token 数优先取最后一次成功响应里的 usage（真实计数），拿不到时退回「字符数 ÷ 4」的保守估算。

切点：在哪一刀切开历史​

压缩不是「把全部历史换成摘要」，而是切成两段：远段换成摘要，近段原样保留。切点只有一条硬规则：不能切在工具结果上——它必须跟着前面的调用走，切在它身上就是「有结果没调用」的孤儿，provider 校验会直接拒绝请求。用户消息、助手消息、摘要消息都是合法切点。

位置由预算决定：从最新往旧逐条累加 token，累计第一次达到 keepRecentTokens（默认 20k）的位置叫爆点；切点取离爆点最近的合法切点。

先交代清楚「一轮」长什么样（u＝用户消息，a＝助手消息，r＝工具结果）：一轮以用户消息开头，中间是零到多次「助手消息带工具调用 → 工具结果」的往返，最后以一条不再带工具调用的助手回复收尾。例子是两轮：

对话（两轮）：
  第 1 轮：u2 → a2                        （简单问答，没有工具调用）
  第 2 轮：u3 → a3(带工具调用) → r1 → r2 → r3 → a3'（收尾回复，不再调用）
  （r1、r2、r3 各约 8k token，a3' 约 0.5k，预算 20k）

① 找爆点——从最新往旧累加：
   a3' 0.5k → r3 8.5k → r2 16.5k → r1 处 24.5k ≥ 20k ⟵ 爆点在 r1

② 落切点——取离爆点最近的合法切点：
   r1 往后：r2、r3 是工具结果（非法），a3' 是助手消息（合法）→ 切点 = a3'

③ 分段：u2 到 r3 进远段（换成摘要），a3' 留在近段（原样保留）
   u2 → a2 → u3 → a3(调用) → r1 → r2 → r3 │切点│ a3'

④ 摘要分工（拆轮善后）：
   u2 → a2 ────────────────→ 主摘要（第 1 轮及更早，结构化模板）
   u3 → a3(调用) → r1 → r2 → r3 ──→ 轮前缀摘要（turn prefix，三段式）
   a3' ──────────────────→ 近段（原样保留）

切在 a3' 而不是退回本轮开头 u3，是「就近」的结果——能少保留就少保留。代价是这轮被切成两半：u3 到 r3 进远段，收尾回复 a3' 留在近段，这叫拆轮。善后的办法：被切走的部分单独摘要，源码叫 turn prefix（轮前缀）。别被名字里的「前缀」误导——主例子里它是这一轮除收尾回复外的全部内容：用户请求、工具调用、所有结果；只有下面那种兜底场景（切在调用消息上），它才真的只剩一条用户消息。提示词比主摘要短，只要三段：原始请求、目前进展、继续所需上下文；主摘要只管更早的历史，两份摘要拼进同一个 compaction entry 的 summary 字段，以 Turn Context (split turn) 小节隔开，分工就是 ④ 里画的箭头。

还有一种情况：爆点之后全是工具结果（运行中途触发压缩、这轮还没走到收尾回复），之后没有任何合法切点，切点就取之前最近的——助手调用消息 a3 本身，调用和全部结果整对进近段。近段超出预算不受罚：keepRecentTokens 是「至少保留」的软目标，硬约束是上下文窗口。

查看代码：findCutPoint 核心循环（core/compaction/compaction.ts，节选）
// 先收集所有合法切点（非工具结果的消息），再从最新往旧累计 token
let accumulatedTokens = 0;
let cutIndex = cutPoints[0]; // 兜底：从第一条消息开始保留（不切）

for (let i = endIndex - 1; i >= startIndex; i--) {
  const entry = entries[i];
  const messageTokens = …; // 这个 entry 折算的 token 数
  if (messageTokens === 0) continue;
  accumulatedTokens += messageTokens;

  if (accumulatedTokens >= keepRecentTokens) {
    // 预算用满：取这个位置之后最近的合法切点；之后没有，就取全局最后一个
    cutIndex = cutPoints.find((candidate) => candidate >= i) ?? cutPoints[cutPoints.length - 1];
    break;
  }
}

摘要：一次独立的模型调用​

远段消息不是简单截断丢弃，而是发起一次独立的 LLM 调用生成结构化摘要。提示词要求固定格式（Goal / Constraints & Preferences / Progress / Key Decisions / Next Steps / Critical Context），并特别叮嘱保留精确的文件路径、函数名和错误信息——这些是接着干活最贵的信息。

两次细节设计：

  • 文件清单：摘要之外，pi 从 read / write / edit 调用里提取「读过哪些文件、改过哪些文件」，以 <read-files>、<modified-files> 标签拼在摘要尾部（模型可见），并随 entry 的 details 字段累积到下次压缩。它在摘要生成之后才拼接，不是压缩的原料——服务的是压缩后的对话：文件内容原文已被摘掉，模型靠这份确定性索引（不随摘要传承走样）知道自己以前碰过、改过什么。
  • 增量更新：会话第二次压缩时，不从头重摘。上一次的摘要在手，提示词换成「保留既有信息，合并新进展，更新进度和下一步」——摘要本身也是被迭代维护的。

compaction entry 长什么样​

查看代码：CompactionEntry 类型定义（core/session-manager.ts）
export interface CompactionEntry<T = unknown> extends SessionEntryBase {
  type: "compaction";
  summary: string;            // 结构化摘要正文
  firstKeptEntryId: string;   // 近段从哪个 entry 开始保留——就是切点那条消息的 id
  tokensBefore: number;       // 压缩前的上下文 token 数
  details?: T;                // 附件：读改文件清单等
  usage?: Usage;              // 生成摘要那次 LLM 调用的用量
  fromHook?: boolean;         // 是否由扩展生成
  systemMessage?: SystemMessage; // 压缩时刻 system 提示的完整快照
}

对应的文件行示意（按类型定义组装，字段值是编的，标注为示意）：

{"type":"compaction","id":"a1b2c3d4","parentId":"…","timestamp":"…","summary":"## Goal\n梳理项目的会话实现…","firstKeptEntryId":"e5f6a7b8","tokensBefore":96842,"details":{"readFiles":["packages/coding-agent/src/core/session-manager.ts",…],"modifiedFiles":[]},"usage":{"input":42000,…}}

systemMessage 快照值得多看一眼。压缩之后，压缩点之前的 system 消息不再进入投影——连保留段里的也被滤掉，由这份快照代替：它不是某一条原文，而是把此前所有 system 消息（初始提示 + 工具增删等变更声明）重放合并出的「当前生效版」。投影时快照排在摘要消息前面，每个请求都带着它——恢复会话或继续对话，模型的系统提示不会因为压缩而走样；而且它无损（确定性合并），不像摘要正文是有损的。

投影时的效果​

buildContextEntries 处理压缩路径的规则：取路径上最新的 compaction entry，投影成 [system 快照（如有）, 摘要消息]，然后拼上 firstKeptEntryId 到压缩点之间的保留段、压缩点之后的全部 entry。更早的 compaction entry 即使还留在保留区间里，也不再贡献内容——多次压缩时永远只有最新一份摘要生效。

被摘要掉的旧消息没有从文件里消失。它们仍在 jsonl 里躺着，只是不再进投影。想在审计时翻出「当时模型到底看到了什么原文」，随时翻得到。

溢出恢复：一次紧凑的复合流程​

第三种触发（溢出）最能体现整套机制的配合。模型报上下文溢出错误时：

  1. 把失败的这次尝试从投影里抹掉——用的正是上一节的 context_edit(null)；
  2. 触发一次压缩（reason 记为 overflow）；
  3. 重试刚才被打断的回合。

只试一次。再次溢出就明确报错，提示减小上下文或换更大窗口的模型，不会陷入「压缩→重试→再溢出」的循环。

回头看：压缩从头到尾没有「修改」过任何历史——切点、摘要、system 快照、文件清单，全部装进一个新 entry；旧消息、旧摘要原地不动。上下文轻了，账本没动，这是「投影是唯一通道」的完整兑现。

分叉：回溯只是移动指针​

取的视角由叶子指针决定：指针落在哪条路径，投影就取哪条路径。把指针移回历史节点再追加消息，树上就长出分叉。这件事的全部成本，藏在一个短得反常的方法里：

查看代码：branch()（core/session-manager.ts，完整）
/**
 * Start a new branch from an earlier entry.
 * Moves the leaf pointer to the specified entry. The next appendXXX() call
 * will create a child of that entry, forming a new branch. Existing entries
 * are not modified or deleted.
 */
branch(branchFromId: string): void {
  if (!this.byId.has(branchFromId)) {
    throw new Error(`Entry ${branchFromId} not found`);
  }
  this.leafId = branchFromId; // 就这一行
}

移动叶子指针，一个字节都不写盘。之后新追加的 entry 会挂到指针所指的节点下，长出新的分支；被放弃的旧分支原样留在树里。「退回三条消息之前重说」的全部成本，就是给一个字段赋值。

树导航：/tree​

用户侧的入口是 /tree 命令（连按两次 Esc 也能呼出）：把树画出来，方向键选一个节点，回车跳过去。跳转由 navigateTree() 处理，有个贴合直觉的分支逻辑：

查看代码：navigateTree 的落点选择（core/agent-session.ts，节选）
// 根据目标类型决定新叶子的位置
let newLeafId: string | null;
let editorText: string | undefined;

if (targetEntry.type === "message" && targetEntry.message.role === "user") {
  // 选中一条历史 user 消息：叶子移到它的父节点，消息文本放回输入框
  // ——你选的不是「从这里继续」，而是「我想改了这条重新发」
  newLeafId = targetEntry.parentId;
  editorText = contentText(targetEntry.message.content, "");
} else if (targetEntry.type === "custom_message") {
  newLeafId = targetEntry.parentId;
  editorText = contentText(targetEntry.content, "");
} else {
  // 选中其他节点（比如某条助手回复）：叶子直接移过去，从这里继续
  newLeafId = targetId;
}

分支摘要：离开时留张字条​

直接跳走，被放弃路径上的信息就出了投影——模型不知道那条路上发生过什么。/tree 跳转时可以带一份摘要：pi 找出旧叶子到新位置的公共祖先之间这段被放弃的 entry，调一次 LLM 生成摘要，作为 branch_summary entry 挂到新位置上。新分支的投影里于是有这样一条消息：「之前从这条路上尝试过 X、Y，结论是 Z」——旧路径退场，经验留下。

查看代码：collectEntriesForBranchSummary（core/compaction/branch-summarization.ts，节选）
// 旧叶子到公共祖先之间的 entry，就是要摘要的范围
const oldPath = new Set(session.getBranch(oldLeafId).map((e) => e.id));
const targetPath = session.getBranch(targetId);

// 从目标路径往回走，找到两条路径最深的公共祖先
let commonAncestorId: string | null = null;
for (let i = targetPath.length - 1; i >= 0; i--) {
  if (oldPath.has(targetPath[i].id)) { commonAncestorId = targetPath[i].id; break; }
}

// 从旧叶子往回收到公共祖先为止，再反转成时间顺序
const entries: SessionEntry[] = [];
let current: string | null = oldLeafId;
while (current && current !== commonAncestorId) {
  const entry = session.getEntry(current);
  if (!entry) break;
  entries.push(entry);
  current = entry.parentId;
}
entries.reverse();

克隆与分叉：/clone 与 /fork​

树内分叉不换文件；想把某条路径独立成一个新会话文件，走 createBranchedSession()：把根到指定叶子的路径抄进一个新 jsonl，新文件的 header 里 parentSession 指回来源文件——来历可溯。用户侧两个入口都封装在这上面：

  • /clone（克隆）：从当前叶子原样复制，新会话和此刻看到的完全一致——适合「复制一份去试验，原会话不动」；
  • /fork（分叉）：选一条历史 user 消息，新会话只复制到它的父节点为止，消息文本放回输入框等你改了重发；pi --fork 启动参数走同一条路。

从这套设计里学到了什么​

  • 把「事实的完整记录」和「想要的视图」分开。pi 的内存消息数组只是缓存，磁盘上的树才是账本，视图每次从事实推导。判断一个持久化设计，先看这两者有没有分开——分开了，崩溃安全、审计、恢复都是副产品；
  • 改历史不必碰历史。删除、修改、放弃分支，全部表达为追加一条记录、投影时生效。想让「账本不可变」和「视图可变」并存，这是唯一的路；
  • 回溯可以只是移动指针。撤销、重试、分叉共用一个叶子指针，换分支零成本、零破坏——「当前在哪」本来就是树上的一个位置，不是数据的一部分；
  • 权衡要按规模算。文件只增不减、打开全量载入、拆树要整文件重写，这些代价在单用户、几百个 entry 的规模下稳赢——全量投影是毫秒级的事；换成多用户、海量事件的系统，账要重新算。

一个数据结构（追加式 entry 树），一个机制（投影），撑起了恢复、回溯、治理三类需求。
