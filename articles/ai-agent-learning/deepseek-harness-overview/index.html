DeepSeek Harness 源码走读：从一句任务建立全局地图

周期2026年11月3日阅读 14 分钟

从让 Harness 阅读 package.json 和 README 出发，分清 Cordis 的插件装配与 Agent 实例的任务执行，再沿输入、模型、工具和会话记录建立源码阅读地图。

让 DeepSeek Harness 阅读一份 package.json 和 README，再解释项目怎样启动，这句话会经过哪些程序？读过 PI 的循环实现后，还会多一个疑问：Harness 引入的 Cordis 插件系统，和模型、工具的循环是什么关系？

先抓住两条线：Cordis 把能力装配起来，Agent 实例通过循环调用这些能力推进任务。默认循环实现也由插件提供。 沿着这次读文件任务，把装配和执行分开看，就能找到继续读源码的入口。

DeepSeek Harness（命令名 dsh）是 DeepSeek 开源的智能体框架，提供模型适配、工具执行、会话记录和应用入口等能力。本文源码固定到 ce7073d512，仓库版本为 0.2.2-alpha.2。PI 的对照沿用前文：pi 源码走读：开篇与地图中的职责划分。

先把一句话交给 headless​

这次任务只需要命令行输入和最终答案，适合使用内置的 headless profile：接收一个任务，运行完成后输出答案并退出。profile 是一份具名的应用组合，--profile headless 选择的就是这种运行方式。

从源码运行需要 Node.js 24.9.0 及以上版本和 pnpm@11.28.5。先按仓库开发指南准备依赖和构建产物：

git clone https://github.com/deepseek-ai/deepseek-harness.git
cd deepseek-harness
git checkout ce7073d51254c26cd63b22a60835b8f948deb447
pnpm install
pnpm run build

下面的命令都从 Harness 仓库根目录、在同一个 shell 中执行。先创建临时数据目录，再检查入口：

export DSH_HOME="$(mktemp -d)"
pnpm dsh --version
pnpm dsh --profile headless --help

在 Node.js 24.18.0 下，版本输出为 0.2.2-alpha.2，帮助输出说明了这种运行方式：

Usage: dsh --profile headless [options] [task...]

Answer one task and exit; the answer goes to stdout and diagnostics to stderr.

任务接下来需要两份内容已知的文件。准备一个没有第三方依赖的 Node 项目，下面是 package.json 中启动脚本的节选：

"scripts": {
  "start": "node index.mjs",
  "dev": "node --watch index.mjs"
}
查看命令：创建演示项目与独立的 Harness 数据目录

示例使用 macOS / Linux 的 shell 命令，数据分开存放在两个临时目录：

  • DEMO_DIR 保存被读取的项目，下面用 mktemp 创建。
  • 前面创建的 DSH_HOME 保存这次演示的 profile 和会话，替代默认的 ~/.dsh。
DEMO_DIR="$(mktemp -d)"

cat > "$DEMO_DIR/package.json" <<'JSON'
{
  "name": "harness-study-demo",
  "version": "1.0.0",
  "private": true,
  "type": "module",
  "scripts": {
    "start": "node index.mjs",
    "dev": "node --watch index.mjs"
  }
}
JSON

cat > "$DEMO_DIR/index.mjs" <<'JS'
console.log("Harness study demo is running.");
JS

cat > "$DEMO_DIR/README.md" <<'MD'
# Harness study demo

A dependency-free Node.js command-line project.

Run `pnpm start` for one execution. Run `pnpm dev` to restart after file changes.
MD

复现时在同一个 shell 中继续执行后面的命令，让两个目录变量保持有效。保留 DSH_HOME 才能在后续命令中继续访问本次演示的会话。

任务需要可用的模型配置。这个版本的默认组合选择 deepseek-official / deepseek-flash，通过 DEEPSEEK_API_KEY 引用密钥；随附 headless 从启动环境或 .env 解析它，具体顺序见凭据说明。使用其他模型时，需要按适配器支持的方式配置对应路由。

将要求作为位置参数交给 headless。文件使用绝对路径，明确指定读取对象：

pnpm dsh --profile headless "请阅读 $DEMO_DIR/package.json 和 $DEMO_DIR/README.md，说明项目怎样启动，以及 start 与 dev 的区别。只读取文件，不修改项目，不运行项目命令。"

它的输入是一段自然语言。最终答案需要解释 start 执行一次脚本、dev 在文件变化后重新执行，两者的依据都在演示文件中。

在任务开始前，应用先被装配出来​

同样是 dsh，为什么换一个 profile 就能切换运行方式？因为启动器先读取 profile，再把其中声明的插件配置交给 Cordis 加载。

这个版本的 headless 模板组合了两个 bundle。bundle 是可叠加的一层插件配置：

  • dsh-base 提供模型、工具、会话、AgentLoop 等共享能力。
  • dsh-headless 增加任务参数解析和一次性任务运行器，并调整这种运行方式所需的配置。

它们的关系可以先画成这张装配图：

图中的配置叠加有先后顺序，插件激活则取决于依赖是否就绪。不能根据 YAML 中的排列位置推断启动顺序。

Cordis 是负责插件组合与生命周期的框架。 它创建插件运行的上下文 ctx，插件通过 ctx.llm、ctx.tools、ctx.sessions 等名字使用服务。服务是插件向其他插件提供的能力接口；它可以被依赖，也可以通过事件与其他能力协作。

沿着源码看，runProfile()把组合配置交给 boot()。后者创建根 Context、挂载 Loader，并加载配置树。Loader 在这里负责把配置项加载为实际运行的插件。

可以先用一个无需模型的命令检查默认组合：

pnpm dsh --profile headless --dump-default-config

输出中可以找到 AgentLoop 的插件配置：

- id: agent-loop
  name: '@deepseek-ai/dsh-agent-loop'
  config:
    agents: []

同一项也存在于 base 的原始配置。这说明默认循环实现通过 dsh-agent-loop 插件装入应用。agents: [] 表示这里没有声明启动时创建的 Agent；headless 运行器会根据收到的任务创建实例。

AgentLoop 服务，和正在干活的 Agent​

PI 的 Agent 类持有运行状态、管理消息队列，并提供 prompt()、abort() 等控制入口。启动一次运行时，它在内部调用 runAgentLoop()。模型与工具交替执行的逻辑由循环函数实现。

Harness 的默认实现中，AgentLoop 是一个 Cordis 服务，负责创建、恢复和管理 Agent 实例。真正运行任务的实例在源码中叫 ReactLoopAgent，循环由它内部的方法推进。理解这里的装配过程，需要分清四个角色：

角色在这次任务里负责什么
headless runner取得任务、创建 Agent、提交输入、输出最终结果
AgentRegistry（ctx.agents）提供创建和管理 Agent 的公共入口，连接已注册的工厂
AgentLoop 服务提供默认工厂，创建由循环驱动的 Agent 实例
ReactLoopAgent 实例接收输入，在循环中请求模型、调用工具并更新会话记录

headless 为这次任务新建一个 Agent 实例，再把任务交给它。四者的协作关系如下：

AgentLoop 的声明中，有一处值得直接看：

export class AgentLoop extends Service implements AgentFactory {
  static inject = ['agents', 'sessions', 'llm', 'tools', 'systemPrompt', 'sessionProjections']
  // 其余类成员省略。
}

Service 表明它是服务插件，inject 列出启动所需的能力。初始化时，它向 Agent 注册表登记创建工厂，这项登记也由 Cordis 管理生命周期。于是，headless 调用 ctx.agents.create() 时，就能通过该工厂创建 ReactLoopAgent 实例，持有本次会话、接收输入并推进运行。后文将这个具体实例简称为 Agent。

这句话怎样变成一次模型请求​

回到“阅读两个文件并解释启动方式”。headless 解析出任务文本后，把它包装为用户消息并提交：

agent.followup(createUserMessage({
  content: [{ type: 'text', text: task }],
  source: { kind: 'user' },
}))

这一步先把输入送进 inbox，也就是等待运行步骤领取的输入区域。循环被唤醒后，才决定这段输入怎样进入本次模型请求。

先说明这里的执行单位：

  • step 是一次逻辑上的模型请求及其工具处理。 大致对应 PI 的一次 turn，同一步内还可能发生请求重试。
  • turn 是 Agent 从开始处理输入到满足结束条件的一段运行，可以包含多个 step。 在普通单任务场景下，它更接近 PI 的一次 run，但两者接纳后续输入的边界不同。

读文件通常需要先请求工具，再带着结果请求回答，所以一项任务可以经过多个 step。

preStep() 负责请求前的准备，可以沿着四件事理解：

  1. 领取等待处理的输入，并捕获本步的模型选择。
  2. 从工具服务取得本步可用的工具集合。
  3. 通过提示词服务组装指令、运行上下文和工具 schema。schema 描述工具名称及参数，让模型知道可以请求哪些操作。
  4. 经过 agent/pre-step 扩展点，决定接纳、改写或拒绝这一步的输入。

在这次任务里，自然语言要求只是请求的一部分。模型还需要知道当前系统的行为要求，以及读取文件等工具的调用方式。它们由已经装配好的服务共同提供。

进入 step() 后，循环准备模型调用，将接纳的用户输入和相应系统消息写入 Session（会话对象），再构造实际请求。

每次构建模型请求时，循环通过 session.deriveMessages() 从内存中的 Session 取得当前有效的对话消息，作用类似 PI 的会话上下文构建，再由模型适配器转换为接口所需的请求格式。

对照 PI：deriveMessages() 对应哪一步？

按职责和返回值对照，Harness 的 deriveMessages() 接近 PI coding-agent 的 buildSessionProjection().messages：两者都为模型请求取得当前有效的对话历史。

  • Harness 的 deriveMessages() 从 Session 事件记录中取得消息列表，排除 turn 边界等非消息事件，并反映压缩、替换后的有效内容。
  • PI 的 buildSessionProjection() 结合当前分支、压缩记录和上下文编辑生成投影，消息列表位于 .messages，整个对象还包含来源条目和会话设置。buildSessionContext() 则基于这份投影返回会话上下文。

在本文对应版本中，两边都会在构建模型请求前取得当前有效的对话历史。PI 的这一步由 coding-agent 安装的 prepareRequest 接入。日常请求使用内存中的会话记录，工具结果写入会话后就能进入下一次上下文。随后，下游再进行模型消息转换与协议序列化。

如果模型请求读文件，谁真正去读​

任务要求读取文件，具体选择哪些工具仍由模型响应决定。下面按一个条件分支推演：如果模型返回 read 调用，框架接下来怎样处理它？

返回内容会带上工具名称与参数，例如要读取的文件路径。Agent 从模型回复（assistant 消息）中找出工具调用，再把这批调用交给工具服务。关键判断在 step() 的工具分支：

const toolCalls = message.content.filter(block => block.type === 'tool-call')
if (toolCalls.length === 0) return { kind: 'completed' }

有工具调用时，随后执行 ctx.tools.execute(...)。工具管线承担参数检查、策略介入和执行协调。read 的实现再通过文件系统服务读取内容。模型提出调用要求，运行中的程序负责实施操作。

工具结果先记入 Session，再作为对话历史进入下一次请求。工具批次在处理调用和结果时记录 tool/call 与 tool/result。普通读文件工具完成后，控制权返回 Agent 的循环。只要工具批次没有声明任务已经结束，循环就准备下一步，取得包含读取结果的消息历史，再构造请求。此时消息历史中已有用户任务、模型发出的 read 调用和工具返回的文件内容，模型由此获得 start 和 dev 的具体定义，再生成解释。

如果后续回复不包含工具调用，这一步可以报告完成。循环还会检查输入与续跑条件，确认没有待处理工作后关闭 turn，运行器才进入结果收尾。读完一个文件只是中间步骤，不能据此判断整项任务已经回答完毕。

屏幕上的答案，和背后留下的记录​

在默认文本模式下，headless 把输出分成两个通道：

  • stdout（标准输出）输出最终答案，方便保存或交给其他程序。
  • stderr（标准错误流）显示模型提供的实时推理增量。日志和进度信息也常使用这个通道，写入它不代表报错。

运行器的收尾逻辑先等待 Agent 与子任务停稳，再等待会话记录保存完成，然后从本次运行的记录中取出最后一条非空 assistant 文本。退出状态还要看最终 turn 的结束原因，进入空闲本身不等于任务成功。
