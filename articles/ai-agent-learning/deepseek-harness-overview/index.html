先抓住两条线：Cordis 把模型、工具和默认循环等能力装入应用；任务运行器再创建一个带状态的 Agent 实例，由实例内部的循环推进任务。 插件解决能力从哪里来，实例解决这一句话现在执行到哪里。

DeepSeek Harness（命令名 dsh）是 DeepSeek 开源的智能体框架，提供模型适配、工具执行、会话记录和应用入口等能力。本系列源码固定到 ce7073d512，仓库版本为 0.2.2-alpha.2。PI 的对照沿用前文：pi 源码走读：开篇与地图中的职责划分。

先把一句话交给 headless​

DeepSeek Harness 接收自然语言任务，调用模型决定下一步，再由本机程序执行模型请求的工具。这里的输入是一句读文件要求，输出是项目启动方式的解释。这种一次性任务适合使用内置的 headless profile：接收任务，运行完成后输出答案并退出。profile 是一份具名的应用组合，--profile headless 选择的就是这种运行方式。

从源码运行需要 Node.js 24.9.0 及以上版本和 pnpm@11.28.5。下面的准备命令依据仓库开发指南，后续命令都从 Harness 仓库根目录、在同一个 shell 中执行。

cd deepseek-harness

Answer one task and exit; the answer goes to stdout and diagnostics to stderr.

准备一个没有第三方依赖的 Node 项目：package.json 中的 start 是 node index.mjs，dev 是 node --watch index.mjs。README 也说明这两个命令的用途。这样，回答是否有文件依据就有了明确的判断标准。

在任务开始前，应用先被装配出来​

同样是 dsh，为什么换一个 profile 就能切换运行方式？因为启动器先读取 profile，再把其中声明的插件配置交给 Cordis 加载。

这个版本的 headless 模板组合了两个 bundle。bundle 是可叠加的一层插件配置：

  • dsh-base 提供模型、工具、会话、AgentLoop 等共享能力。
  • dsh-headless 增加任务参数解析和一次性任务运行器，并调整这种运行方式所需的配置。

配置叠加有先后顺序，插件激活则取决于依赖是否就绪。不能根据 YAML 中的排列位置推断启动顺序。

Cordis 是负责插件组合与生命周期的框架。 它创建插件运行的上下文 ctx，插件通过 ctx.llm、ctx.tools、ctx.sessions 等名字使用服务。服务是插件向其他插件提供的能力接口；它可以被依赖，也可以通过事件与其他能力协作。

这也划出了阅读源码的两个层次：

  • 装配层决定使用哪些实现，以及依赖齐全时哪些插件可以运行。更换 profile，主要改变这一层的组合。
  • 执行层决定任务如何推进。默认 Agent 循环在固定位置调用模型、工具和扩展点，并依据返回值决定继续或结束。

例如，插件可以补充请求前的运行环境，循环决定在哪一步接纳这些内容。改变配置覆盖顺序和改变执行阶段顺序，是两件不同的事。

沿着源码看，runProfile()把组合配置交给 boot()。后者创建根 Context、挂载 Loader，并加载配置树。Loader 在这里负责把配置项加载为实际运行的插件。

在这套组合中，应用先有两个共享服务：

  • AgentRegistry 暴露为 ctx.agents，保存创建工厂和已经登记的实例。其他插件通过它创建、查找 Agent。
  • AgentLoop 暴露为 ctx.agentLoop，是默认循环实现提供的服务。它在初始化时向注册表登记自己作为创建工厂。

因此，ctx.agents.create() 这个公共入口有了实际执行者。此时可以还没有任何任务实例。默认配置正是如此：

为这项任务创建一个带状态的实例​

headless 从参数取得任务文本，选定模型，再生成一个新的 sessionId，记录当前工作目录 cwd。它随后调用 ctx.agents.create()，传入这次会话的身份、目录、模型选项和初始化回调。调用返回一个 AgentHandle，其中的 agent 才是接下来接收任务的对象，dispose() 则是释放它的入口。

创建不是在注册表里加一个名字就结束。沿着这次调用，实际发生的是：

  1. 注册表转交创建请求。 AgentRegistry.create() 找到已登记的工厂，调用它的 createAgent()。注册表提供公共接口，具体怎样创建由工厂决定。
  2. 工厂先取得会话。 AgentLoop.createAgent() 按 sessionId 创建一个 Session 对象。配置了持久化后端时，也为会话取得写入句柄。
  3. 工厂构造循环实例。 它把会话、模型选项和运行服务所在的 Context 传给 new ReactLoopAgent(...)。这个对象保存任务状态，也实现推进任务的方法。
  4. 初始化完成后再交给调用者。 工厂把 Session 加入会话服务，执行 headless 提供的初始化回调，再把 Agent 加入注册表并等待创建通知完成。headless 随后取得可以提交任务的实例。

对应源码是注册表的委托、会话的创建和实例的登记。创建或初始化失败会使这次调用失败，headless 不会拿到一个可用实例继续提交任务。

这三个名字不是三个相继执行模型请求的层。AgentRegistry 保存工厂和实例的索引，AgentLoop 提供工厂，真正持有这项任务的是新建的 ReactLoopAgent。后面将它简称为 Agent。

它在构造时得到的几个成员，决定了后面的数据去向：

实例成员保存或连接什么读两个文件时怎样使用
session本次会话的事件记录，以及从中得到的有效消息历史记录任务、模型回复、工具调用与结果，供后续请求取用
inbox操作两列待处理输入的入口：next-turn 和 next-step新任务先排入 next-turn，到执行边界才被领取
phase当前处于空闲、维护还是运行中。运行时含 turn、step 和取消信号阻止同一实例重复启动驱动，记住当前执行位置
loopCtx创建工厂所属的运行 Context，可访问 llm、tools、systemPrompt 等服务每一步通过它取得工具、构造提示词、请求模型和执行工具

inbox 的两列内容也由 Session 中的队列变更记录推导出来。实例持有的是操作这两列内容的对象，并非另存一份与会话无关的输入数组。phase 则是驱动当前运行的内存状态。二者回答的问题不同：前者说明“还有什么待处理”，后者说明“现在有没有驱动在处理”。

实例另有一个限定自身作用域的 ctx。初始化回调通过这个 Context 安装本实例需要的能力，相关监听随作用域一起释放。它与连接共享运行服务的 loopCtx 各有用途。

PI 的 Agent 类也保存状态、队列并暴露控制入口，内部调用 runAgentLoop()推进模型与工具循环。Harness 默认实现把对应的实例叫作 ReactLoopAgent，又在它外面提供了可由插件替换的工厂入口。比较两者时，要把“一个任务实例”与“创建实例的共享服务”分开。

提交输入，谁把空闲实例变成运行中​

回到“阅读两个文件并解释启动方式”。实例创建时是空闲的。headless 把任务文本包装为用户消息，调用 agent.followup(...)。用户消息包含文本内容和 source: { kind: 'user' }，还带有自己的消息身份。

followup() 连着做两件事：

  1. 把消息放入 inbox.nextTurn，并将这次队列变更记入 Session。此时它还是待处理输入。
  2. 唤醒实例自己的驱动。空闲实例立即将 phase 改成 running，建立取消信号，把 step 置为 0，再启动内部的 kick() 方法。

这次状态切换发生在异步执行之前。因此，即使运行期间再有人提交输入，也会加入已有实例的队列，由正在运行的驱动在后续边界领取。它不会为每条消息另起一个并行循环。

kick() 的主体是反复运行 turn()。这两个执行单位需要先分清：

  • step 是一次逻辑上的模型请求及其工具处理。 大致对应 PI 的一次 turn，同一步内还可能发生请求重试。
  • turn 是 Agent 从开始处理输入到满足结束条件的一段运行，可以包含多个 step。 在普通单任务场景下，它更接近 PI 的一次 run，但两者接纳后续输入的边界不同。

对于当前这个新实例，第一次唤醒会开启 turn 1，并尝试进入 step 1。读文件以后还要让模型解释内容，因此这个 turn 可以继续进入 step 2、step 3。step 的增加不要求重新创建实例。

headless 提交后调用 whenIdle() 等待。实例内部用 activityDone 保存驱动结束的 Promise，whenIdle() 等的是这个活动停稳。模型请求报错或任务被取消同样会停稳，所以“等到空闲”只说明驱动结束，结果还要检查会话里的结束原因。

send(message: UserMessage, target: InboxTarget, wakeup: boolean): void {
  const wakingAfterAbort = wakeup && this.phase.kind !== 'idle' && this.phase.abort.signal.aborted
  const resolvedTarget = wakingAfterAbort ? 'next-turn' : target
  this.inbox.splice(resolvedTarget, Infinity, 0, [message])
  if (wakeup) this.wakeDriver(wakingAfterAbort)
}

第一个 step 怎样取得这句话​

运行已开始，待处理输入还没有等同于模型请求。进入第一个 step 前，preStep()按顺序取得这一轮所需的内容：

  1. 从 inbox 领取待处理消息。开启 turn 的边界会取出一条 next-turn 消息，也接纳已有的 next-step 输入。当前例子领取到的就是那句读文件要求。
  2. 读取实例的模型选择，并通过 loopCtx.tools 确定这个模型、本实例在本步可用的工具。没有模型选择会直接报错。
  3. 通过 loopCtx.systemPrompt 取得系统提示和运行环境内容，再让 agent/pre-step 扩展点决定本步接纳哪些消息。扩展可以调整输入，也可以拒绝进入本步。

接纳通过以后，step() 才将输入作为 user/message 记入 Session，并记录需要提交的提示词和运行环境。随后 buildRequest()调用 session.deriveMessages()，取得当前有效消息历史，连同模型配置和工具说明构成请求。最后交给已准备的模型调用，或 loopCtx.llm.stream()，由模型适配器转换为服务商协议。

所以，这句话有两个不同的时刻：先作为“待处理输入”进入 inbox，后作为“本步接纳的用户消息”进入模型可见历史。Session 会保存两种事件，但队列变更记录本身不会原样发给模型。

此时，各对象的状态已经能连起来：Agent 的 phase 指向 turn 1 / step 1，inbox 中这条待处理消息已被领取，Session 中有了用户任务，模型请求使用从 Session 得到的消息列表。共享的 AgentLoop 服务负责创建这个对象，后面的逐步推进由对象自己完成。

如果模型请求读文件，谁真正去读​

任务要求读取文件，具体选择哪些工具仍由模型响应决定。下面按一个条件分支推演：如果模型返回 read 调用，框架接下来怎样处理它？

返回内容会带上工具名称与参数，例如要读取的文件路径。Agent 从模型回复（assistant 消息）中找出工具调用，再把这批调用交给工具服务。相应分支位于 step()。

有工具调用时，随后执行 loopCtx.tools.execute(...)。工具管线承担参数检查、策略介入和执行协调。read 的实现再通过文件系统服务读取内容。模型提出调用要求，运行中的程序负责实施操作。

工具结果先记入 Session，再作为对话历史进入下一次请求。工具批次在处理调用和结果时记录 tool/call 与 tool/result。普通读文件工具完成后，控制权返回 Agent 的循环。只要工具批次没有声明任务已经结束，循环就进入下一步，取得包含读取结果的消息历史，再构造请求。

模型可以一次请求读取两份文件，也可以分步读取。两份内容都返回后，消息历史中已有用户任务、模型发出的 read 调用和工具返回的内容，模型才有机会据此解释 start 和 dev 的具体定义。

如果后续回复不包含工具调用，这个 step 可以报告完成。当前 turn 还会检查本轮是否有续跑输入，有就继续下一步，没有就关闭 turn。若 next-turn 仍有排队任务，驱动再开启下一 turn。当前例子只有一项任务，两列队列都没有后续工作时，驱动才退出，把 phase 改回 idle。

因此，读完一个文件只是中间步骤。甚至得到一条纯文本回复，也要经过循环的结束检查，运行器才能进入结果收尾。

屏幕上的答案，和背后留下的记录​

在默认文本模式下，headless 把输出分成两个通道：

  • stdout（标准输出）输出最终答案，方便保存或交给其他程序。
  • stderr（标准错误流）显示模型提供的实时推理增量。日志和进度信息也常使用这个通道，写入它不代表报错。

运行器的收尾逻辑先等待 Agent 与子任务停稳，再等待会话记录保存完成，然后从本次运行的记录中取出最后一条非空 assistant 文本。退出状态还要看最终 turn 的结束原因，进入空闲本身不等于任务成功。

对照 PI：把执行概念对齐​

读过前文：pi 源码走读的读者，到这里会不断认出熟悉的形状，但名字对不齐：两边都有 turn，指的东西却差一层。PI 的一个 turn 在 Harness 里叫 step，Harness 的一个 turn 更接近 PI 的一次 run。名字对齐了，两个系列的机制才能互相印证。

两边的执行结构同构，对应关系一张表说清：

DeepSeek Harnesspi这一层在做什么
Agent 实例（ReactLoopAgent）与它的 Session会话 AgentSession（内含循环层 Agent 与会话树）一段对话的运行时：保存状态与记录，空闲时也在
turn（turn/start → turn/end）一次运行 run（agent_start → agent_settled）处理一批输入，直到满足结束条件
step（一次模型请求及其工具处理）回合 turn（turn_start → turn_end）问一次模型，执行它要求的工具
inbox 的 next-step 列steering 队列半路改方向：手头的活干完，下一个请求带上新输入
inbox 的 next-turn 列follow-up 队列排队等收尾：当前这段忙完，再办这件新事

记法：把 Harness 的三层整体上移一层——实例对会话、turn 对运行、step 对回合。

两边的嵌套形状相同，各画一张：

Harness：Agent 实例（绑定一个 Session，空闲不销毁）
 ├── turn 1：处理第一批输入
 │    ├── step 1：请求模型 → read 调用 → 执行工具
 │    └── step 2：带结果再请求 → 文字回答
 ├──（空闲，等下一条输入；turn 编号接着涨）
 └── turn 2：处理下一批输入
pi：会话 AgentSession（大部分时间空闲）
 ├── 运行 1：从按下回车到彻底安静
 │    ├── 回合 1：请求模型 → read 调用 → 执行工具
 │    └── 回合 2：带结果再请求 → 文字回答
 ├──（空闲，等下一次回车）
 └── 运行 2：……

结构相同，四处细节不同：

  • 排队输入被吸收的层不同。 PI 的 follow-up 在同一个 run 内部兑现：外层循环发现有货，接着转一圈内层，多出一个回合，run 不结束。Harness 先写 turn/end 收掉当前 turn，再开一个新 turn 处理 next-turn 输入。语义都是“忙完再办”，记录上 Harness 多一次 turn 边界。
  • 结束的判定道数不同。 PI 的 run 有两道终点：agent_end 是循环层说完话，编排层做完重试、压缩检查和 before_settle 窗口，才是 agent_settled（前文：数一数 pi 的生命周期）。Harness 用 whenIdle() 等驱动停稳，再查 Session 里的结束原因。重试的归属也不同：Harness 记在同一个 step 内；PI 由编排层在后处理决定，需要再跑时以 continue() 另开一趟 agent_start，对应 Harness 在同一个驱动里再开一个 turn。
  • 实例的出身不同。 Harness 经 AgentRegistry 委托 AgentLoop 工厂创建实例，循环实现是可替换的能力；PI 的循环层 Agent 由编排层直接持有，没有这层工厂。
  • 记录的形状不同，投影的思想相同。 PI 的会话是追加式的 entry 树，每次请求前投影成线性消息列表；Harness 的 Session 是事件日志，每次请求前用 deriveMessages() 取有效历史。两边都是持久记录作权威，内存每次从记录推导。

对照止于执行层的一次运行怎么拆。装配、压缩与扩展权限，两个系列各自展开。

回到开头的问题​

装配层装入能力，执行层的实例推进任务。开头提出的三个问题，答案都落在这条链上：

  • 谁保存这次对话：Session。任务、模型回复、工具调用与读取结果都记在这里，后续请求从它取得有效历史。
  • 谁记着尚未处理的输入：inbox。任务先排入 next-turn，到执行边界才被领取。运行中再提交的输入加入同一实例的队列。
  • 谁决定读完文件以后再问一次模型：实例内部的循环。工具批次没有声明任务结束，循环就带着读取结果准备下一步。回复不再包含工具调用、队列也没有待处理输入时，驱动才退出。

任务结束后，phase 改回空闲，Session 留下完整记录，headless 从中取出最后一条非空 assistant 文本交给 stdout。更换 profile，改变的是装配层装入哪些能力。这句话经过的每一步，始终由同一个 Agent 实例推进。
