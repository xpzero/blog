读 pi 的入口源码时，会看到它默认加载了几个扩展。它们是什么，为什么随程序一起提供的功能也要走扩展加载？

MCP 是接入外部工具服务器的通信协议，pi 对它的支持就是内置扩展提供的。如果另一个扩展也注册了 /mcp 命令，pi 会保留第三方实现，让内置 MCP 扩展退出最终加载结果。理解这件事，就能串起扩展怎么加载、怎么管理、怎么替换。

四个内置扩展提供什么​

扩展是一段在 pi 加载时执行的代码，可以注册工具、命令、模型提供方和事件处理函数。pi 随 CLI 提供四件内置扩展：

内置扩展提供什么用户会接触到的入口
llama.cpp连接 llama.cpp 推理服务器，将本地模型接入 pi/login llama.cpp、/llama
codemode执行模型写的 JavaScript，组合其他工具调用codemode 工具
tool-search搜索已注册但尚未声明给模型的工具，并启用命中项tool_search 工具
mcp连接外部 MCP 工具服务器，管理其工具与资源mcp.json、/mcp

这四件扩展默认加载，但它们提供的能力不一定立即可用。例如 codemode 和 tool-search 虽然注册了工具，却都设置了默认不激活；llama.cpp 则需要配置服务器。扩展加载成功，表示它完成了注册，不代表所有功能都已开启。

写一个注册 /mcp 的测试扩展​

在测试项目的 .pi/extensions/takeover-mcp.ts 中放入下面这段代码。它只注册一个 /mcp 命令，处理函数留空，用来观察名字冲突后的选择：

// takeover-mcp.ts
export default function (pi: any) {
	pi.registerCommand("mcp", {
		description: "Third-party takeover of /mcp for the replacement experiment",
		handler: async () => {},
	});
}

这段演示用 any 省略了类型导入。进入放有该文件的测试项目，再启动 pi；项目配置与扩展需要先通过项目信任。下面的截图从该项目目录调用 pi 源码仓库根目录的 pi-test.sh 启动：

图中的 [Extension issues] 把警告挂在 builtin:mcp 名下，正文指出 takeover-mcp.ts 注册了 /mcp，所以内置 MCP 扩展没有进入最终扩展集合。

这里替换的是整件 MCP 扩展。这个空处理函数不会连接服务器，内置版的连接逻辑也不会继续运行。因此，这个文件只适合观察替换行为；移走它并重新加载后，才能恢复内置实现。

从入口到扩展对象，代码怎样接起来​

刚才只放了一个文件，pi 就发现并执行了它；内置 mcp 的工厂函数则在源码中导入。两种来源怎样进入同一套判定？

pi 源码中的入口文件 packages/coding-agent/src/main.ts 先收集工厂定义：

const extensionFactories = [...builtInExtensions, ...(options?.extensionFactories ?? [])];

factory 是加载时要调用的函数，调用方通过 options 还能传入自己的定义。内置清单如下：

查看代码：四个内置扩展的定义
// packages/coding-agent/src/extensions/index.ts（节选）
export const builtInExtensions: InlineExtension[] = [
	{ name: "llama.cpp", factory: llamaExtension, builtin: true },
	// Replaceable: an extension that registers `codemode`, `tool_search`, or `/mcp` (such as a third-party
	// MCP extension) takes over instead of running alongside the built-in one.
	{ name: "codemode", factory: codemodeExtension, replaceable: true, builtin: true },
	{ name: "tool-search", factory: toolSearchExtension, replaceable: true, builtin: true },
	{ name: "mcp", factory: mcpExtension, replaceable: true, builtin: true },
];

builtin: true 让定义进入内置资源表，replaceable: true 让加载结果可以在同名冲突时让位。这两个属性还没有执行替换，只是给后面的加载与筛选提供输入。

文件、内置和内联怎样加载​

pi 接收扩展的方式主要有三种。文件与内置资源的发现和加载由 ResourceLoader（资源加载器）组织：

方式从哪里取得代码常见使用者
文件扩展全局 ~/.pi/agent/extensions/、项目 .pi/extensions/、安装的包或 -e 指定的文件CLI 用户、扩展作者
内置扩展pi 源码中已经导入的工厂函数pi 自带功能
内联扩展调用方通过 extensionFactories 直接传入函数或定义对象把 pi 嵌入自己程序的开发者

“内联”指直接传入函数。这与 RPC 模式不同：RPC 是外部程序控制 pi 进程的一种运行方式，并不等于给 pi 传入了内联扩展。

内置扩展还有一个特殊标识：builtin:mcp、builtin:codemode 这样的资源路径。磁盘上没有这些文件，资源系统用它们来登记、选择和禁用内置功能，这就是标题里“伪装成文件”的意思。

两条资源加载路径最后会合：

文件路径 → 导入模块，取得工厂函数 ─┐
                                 ├→ 调用工厂，收集注册结果 → 合并扩展列表
builtin: 路径 → 查找已有工厂函数 ─┘

内联工厂 → 调用工厂，收集注册结果 ─→ 合并扩展列表

导入磁盘上的 JavaScript、TypeScript 模块时，pi 使用 jiti。它是一个运行时模块加载库：优先尝试原生加载，需要转换时再处理源码，让扩展作者可以直接提供 .ts 文件。Node 的 TypeScript 原生支持会随版本与语法而变化，jiti 负责这里的加载兼容。

加载器从资源路径中区分 builtin:，普通路径交给文件加载器，内置路径则取出已有工厂。下面是两条路径合并的实际实现：

查看代码：文件与 builtin: 资源怎样汇入一个加载结果
// packages/coding-agent/src/core/resource-loader.ts（完整方法）
private async loadExtensionPaths(paths: string[], runtime?: ExtensionRuntime): Promise<LoadExtensionsResult> {
	const isBuiltinPath = (path: string) => path.startsWith(BUILTIN_PATH_PREFIX);
	const result = await loadExtensionsCached(
		paths.filter((path) => !isBuiltinPath(path)),
		this.cwd,
		this.eventBus,
		runtime,
	);
	for (const path of paths.filter(isBuiltinPath)) {
		const builtin = this.builtinExtensions.get(path.slice(BUILTIN_PATH_PREFIX.length));
		if (!builtin) {
			result.errors.push({ path, error: `Unknown built-in extension: ${path}` });
			continue;
		}
		try {
			const extension = await loadExtensionFromFactory(
				builtin.factory,
				this.cwd,
				this.eventBus,
				result.runtime,
				path,
			);
			extension.hidden = true;
			extension.replaceable = builtin.replaceable === true;
			result.extensions.push(extension);
		} catch (error) {
			result.errors.push({ path, error: error instanceof Error ? error.message : "failed to load extension" });
		}
	}
	return result;
}

工厂执行后，注册结果放在哪里​

调用工厂之前，加载器先为这件扩展创建一个对象，里面有 tools、commands、flags、handlers 等集合。传给工厂的 pi API 绑定到这个对象：调用 registerCommand("mcp", …)，就是往当前扩展的 commands 表写入 mcp。

执行 takeover-mcp.ts 的工厂
  → pi.registerCommand("mcp", …)
  → 当前扩展.commands 中出现 mcp

执行内置 mcp 的工厂
  → 注册它自己的 /mcp 和会话事件处理函数
  → 另一个扩展.commands 中也出现 mcp

工厂都执行成功
  → 合并扩展对象
  → 筛选最终要使用的扩展

这一对应关系可以直接在加载器里核对：

查看代码：调用工厂与保存命令注册的对应位置
// packages/coding-agent/src/core/extensions/loader.ts
// initializeExtension 中的节选：为本件扩展创建 API，再调用它的工厂。
const extension = createExtension(extensionPath, resolvedPath);
const load = createExtensionAPI(extension, runtime, cwd, eventBus);
try {
	await factory(load.api);
	load.commit();
} catch (error) {
	load.discard();
	throw error;
}
// 同文件 createExtensionAPI 的 registerCommand 中节选：写入绑定的扩展对象。
extension.commands.set(name, {
	name,
	sourceInfo: extension.sourceInfo,
	...options,
});

因此，下面的替换逻辑拿到的是已执行工厂、携带注册结果的扩展对象，不只是文件路径或函数名。它能枚举每件扩展注册了什么，也就有了比较依据。

replaceable：比较注册名，过滤整件扩展​

测试文件叫 takeover-mcp.ts，内置扩展叫 mcp，两者的扩展名并不相同。触发让位的是它们都注册了 命令 mcp。

判定比较三类注册名：

  • 工具名：例如 tool:tool_search。
  • 命令名：例如 command:mcp。
  • 启动标志名：例如 flag:custom-option。

前缀把类别分开，工具 mcp 与命令 /mcp 不会因此撞名。扩展自身的文件名、显示名不参与这项判定。

taken 为什么不会被可替换内置覆盖​

omitReplacedExtensions() 先收集不可替换扩展注册的名字，建立 taken 表，再检查可替换扩展是否与表中名字冲突。

以刚才的测试为例：

候选列表：
  takeover-mcp.ts  replaceable 未设置，注册 command:mcp
  builtin:mcp      replaceable 为 true，也注册 command:mcp

建立 taken：
  先筛掉 replaceable 为 true 的扩展
  因此 command:mcp → takeover-mcp.ts

过滤最终列表：
  takeover-mcp.ts 不可替换 → 保留
  builtin:mcp 可替换，查到 command:mcp 已被占用 → 移除

先过滤，再建 Map 是这里的关键。可替换的内置 MCP 扩展根本不进 taken，不会因为排在后面就覆盖用户扩展。

Map 对重复 key 采用后写覆盖先写。如果两个不可替换扩展都注册 /mcp，taken 保存后者，但两者仍都会被本函数保留，冲突交给后续诊断。在让位逻辑里，Map 最终保存谁，只影响警告引用哪一个占用者，不改变“这个名字已经被占用”的判断。

查看代码：omitReplacedExtensions 完整函数，含关键中文注释
// packages/coding-agent/src/core/resource-loader.ts（中文注释为本文所加）
function omitReplacedExtensions(
	extensions: Extension[],
	warnings?: Array<{ path: string; warning: string }>,
): Extension[] {
	// 比较各扩展注册的工具、命令和标志名，扩展自身的名字不参与。
	const names = (extension: Extension) => [
		...[...extension.tools.keys()].map((name) => `tool:${name}`),
		...[...extension.commands.keys()].map((name) => `command:${name}`),
		...[...extension.flags.keys()].map((name) => `flag:${name}`),
	];
	// 先排除可替换者，再建占用表；三个可替换内置不会进入此表。
	const taken = new Map(
		extensions
			.filter((extension) => !extension.replaceable)
			.flatMap((extension) => names(extension).map((name) => [name, extension] as const)),
	);
	return extensions.filter((extension) => {
		if (!extension.replaceable) return true;
		const replacement = names(extension)
			.map((name) => ({ name, extension: taken.get(name) }))
			.find((value): value is { name: string; extension: Extension } => value.extension !== undefined);
		if (!replacement) return true;
		// 只有 builtin: 来源的被替换者会生成这条警告。
		if (extension.path.startsWith(BUILTIN_PATH_PREFIX)) {
			const builtinName = extension.path.slice(BUILTIN_PATH_PREFIX.length);
			const [kind, rawName] = replacement.name.split(":", 2);
			const registeredName = kind === "command" ? `/${rawName}` : kind === "flag" ? `--${rawName}` : rawName;
			warnings?.push({
				// 归属是被替换的内置扩展；正文引用注册同名项的扩展路径。
				path: extension.path,
				warning: `Extension ${replacement.extension.path} registers ${kind} \`${registeredName}\`, so built-in extension \`${builtinName}\` was not loaded. To use \`${builtinName}\`, run \`pi config\` and make sure it is enabled under Built-in extensions, then disable or remove the existing extension. We recommend only having one or the other loaded at a time.`,
			});
		}
		// 移除整件扩展，后续不再使用它的工具、命令和事件注册。
		return false;
	});
}

这里是加载后的筛选。工厂函数此前已经执行过，过滤不会撤销工厂直接产生的外部副作用。因此，准备支持替换的扩展应在工厂中完成注册，把连接服务器等长生命周期操作放到会话事件里执行。

hidden 与 replaceable 分别能在哪里设置​

这两个属性解决不同问题：hidden 只影响启动时的 Extensions 列表，replaceable 决定能否按上述规则让位。

加载方式hiddenreplaceable
文件扩展没有声明入口，默认显示没有声明入口，默认不可替换
内联扩展，直接传函数不隐藏不可替换
内联扩展，传 { name, factory, … } 对象可设置可设置
内置扩展加载器统一设为 true由源码定义决定

四个内置里，mcp、codemode、tool-search 可替换，llama.cpp 未设置这个标记，按不可替换处理。普通用户可以启停它们，不能通过 settings.json 修改这些属性。

可替换的内联扩展也会被筛掉，但不会生成上面那条内置扩展警告：警告分支要求路径以 builtin: 开头。

截图中的 Extensions 列表只显示 lifecycle-log.ts 和 takeover-mcp.ts，也与 hidden 有关。内置扩展默认就不在该列表中，不能靠它有没有出现在启动列表里判断是否加载成功。

这里的 hidden 作用于扩展名的显示。read、bash、edit、write 是工具，本来就不属于这个启动扩展列表，实际调用时仍会展示执行过程。工具上的 exposure: "hidden" 则表示禁止访问，与扩展的显示标记是两个独立设置。

怎样关闭一件内置扩展​

运行 pi config，可以在 Built-in 区勾选或取消这些扩展，也可以在全局或项目的 settings.json 中写：

{
  "extensions": ["-builtin:tool-search"]
}

项目设置可以覆盖用户设置。启动参数 --no-extensions 会关闭自动加载的扩展，-e builtin:mcp 则能显式选择内置扩展资源。

禁用扩展与关闭工具仍是两回事：

操作效果
禁用 builtin:tool-search扩展不加载，tool_search 工具不会被它注册
扩展保持加载，但不激活 tool_search工具已注册，模型当前看不到它的声明

按默认配置只执行 pi 时，tool-search 扩展会加载，但 tool_search 不会自动激活，因此模型看不到它的声明。配置或其他扩展显式开启它时，才会改变这个结果。

下面的两次测试都用 pi --tools tool_search 显式选择这件工具，只改变是否禁用扩展：

扩展设置启动命令声明给模型的工具
未禁用 builtin:tool-searchpi --tools tool_search包含 tool_search
设置 "extensions": ["-builtin:tool-search"]pi --tools tool_search没有工具声明

第一行由 --tools tool_search 激活工具；第二行的扩展根本没有加载，工具未注册，所以相同的参数也选不到它。--tools 可以选择已有工具，不能让被禁用的扩展重新加载。

内置扩展的“内置”，首先体现在默认随 CLI 加载。它们随后进入扩展列表，使用注册、筛选与资源管理机制。是否隐藏、是否允许让位，则由各自的加载属性进一步决定。
