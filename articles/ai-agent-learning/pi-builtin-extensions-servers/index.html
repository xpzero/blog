pi 怎样使用本机运行的模型？又怎样让模型调用外部服务器上的工具？这两件事分别由 llama.cpp 和 mcp 内置扩展接入。

llama.cpp 扩展把推理服务器上的模型接到 pi 的对话流程里；mcp 扩展把工具服务器上的操作接到 pi 的工具执行流程里。前者决定谁生成回答，后者提供生成回答时可以调用的能力。

下面各用一次基本操作贯穿实现：让一个本地模型接收对话，以及让外部 echo 工具回显一条消息。

llama.cpp 扩展：从连接服务器到发出一次对话请求​

基本使用：配置连接、加载模型、选择模型​

llama.cpp 是运行模型的推理软件，llama-server 是它提供 HTTP 接口的服务器程序。pi 不负责执行模型权重，而是请求这个服务器完成推理。

这里的“加载模型”，可以先理解为：**llama-server 将磁盘上的模型文件映射或装入内存，并按配置使用 GPU 显存，准备执行推理。**模型文件需要事先取得，例如从 Hugging Face 下载到 ~/models。下载把文件保存到磁盘，加载让服务器能够运行它，二者是不同步骤。

本例假定模型文件已经在 ~/models 中，再启动支持 router 的 llama-server。router 可以发现模型目录中的多个模型，再按请求加载、卸载。下面是 pi 官方接入文档中的启动示例，具体内存与 GPU 参数需要适合本机：

查看命令：启动一个显式加载模型的 llama-server
llama-server \
  --models-dir ~/models \
  --no-models-autoload \
  --jinja \
  --host 127.0.0.1 \
  --port 8080 \
  -ngl 999 \
  -c 32768

这里关闭了自动加载。服务器启动后，在 pi 中依次做三件事：

  1. /login llama.cpp：填服务器地址，默认是 http://127.0.0.1:8080，API key 可以留空。
  2. /llama：打开服务器模型列表，选择一个磁盘上已有、但尚未加载的模型，让 llama-server 将它准备到内存或显存中。
  3. /model：从 pi 可用的模型中选中它，再输入对话任务。

预期结果是：选中的本地模型接收后续请求，pi 展示它返回的回答。**/llama 管服务器上的模型，/model 管当前会话用哪个模型。**拉取目录只取得名称和状态，加载由 llama-server 准备模型权重与推理环境，选择则改变 pi 的会话状态。模型权重不会进入 pi 进程；pi 保存的是向哪个服务器、哪个模型发送请求的信息。

这三个命令也不全属于 llama.cpp 扩展：/login、/model 是 pi 的通用命令，扩展提供的是它们需要的模型接入能力，以及专门的 /llama 管理命令。

下面按这条成功路径画出主要交互，目录刷新中的重复读取在图中合并展示：

接下来始终追踪同一个模型，示意 ID 记为 local-chat。这个名字只用于解释数据流，不是预设或实测模型名。

启动 pi：注册接入能力，此时还没有加载任何权重​

pi 调用 llama.cpp 扩展工厂（扩展的初始化函数）时，扩展先创建一个 provider 并注册它。provider 是 pi 认识一类模型所需的一组接口，负责连接配置、模型目录和请求执行。

查看代码：扩展把 provider 和 /llama 注册到哪里
// packages/coding-agent/src/extensions/llama/index.ts（节选）
export default function llamaExtension(pi: ExtensionAPI): void {
	const provider = createLlamaProvider();
	pi.registerProvider(provider.provider);

	// 目录同步、加载、卸载和下载函数定义省略。
	pi.registerCommand("llama", {
		description: "Manage llama.cpp router models",
		handler: async (_args, ctx) => {
			if (ctx.mode !== "tui") {
				ctx.ui.notify("/llama is available in interactive mode", "warning");
				return;
			}
			// 读取连接信息和打开模型管理界面的逻辑省略。
		},
	});
}

注册后的 provider ID 为 llama.cpp，通用 /login 由此能找到它的登录处理函数，模型运行时也能找到它的目录刷新和推理接口。/llama 则进入这件扩展自己的命令处理器，只在交互界面开放。

createLlamaProvider() 内部先建立空的聊天模型、分类模型数组。后面的目录刷新会填充它们；有目录缓存时也可以先恢复元数据。这里注册的是运行接口，没有启动 llama-server，也没有读取或装载模型权重。

输入 /login：服务器地址怎样变成后续请求的连接配置​

输入 /login llama.cpp 后，通用登录流程找到该 provider 的 auth.apiKey.login。这个函数先接收服务器地址和可选 key，再调用 LlamaClient.list() 检查服务器。

LlamaClient 是这个扩展的 HTTP 客户端。它把 list() 转换成 GET /models，检查响应是否有 data 数组，以及条目中是否包含模型 ID 和状态。只有取得了可识别的 router 目录，登录函数才返回连接凭证。

查看代码：检查连接后返回什么配置
// packages/coding-agent/src/extensions/llama/provider.ts（login 函数内节选）
const enteredUrl = await interaction.prompt({
	type: "text",
	message: "llama.cpp server URL",
	placeholder: process.env.LLAMA_BASE_URL ?? DEFAULT_LLAMA_SERVER_URL,
});
const serverUrl = normalizeLlamaServerUrl(
	enteredUrl.trim() || process.env.LLAMA_BASE_URL || DEFAULT_LLAMA_SERVER_URL,
);
const apiKey = (
	await interaction.prompt({
		type: "secret",
		message: "API key (optional)",
	})
).trim();
await new LlamaClient(serverUrl, apiKey || undefined).list({ signal: interaction.signal });
return {
	type: "api_key",
	key: apiKey || undefined,
	env: { LLAMA_BASE_URL: serverUrl },
};

返回值交回 pi 的通用认证流程保存。里面的 LLAMA_BASE_URL 是服务器管理地址，之后 /llama 和模型目录刷新都会从认证接口取到它，无需再询问用户。

登录成功后，pi 的交互模式在 completeProviderAuthentication() 中调用模型运行时的 refresh({ providers: [providerId] })，请求刷新这个 provider 的模型目录。因此，目录获取不只发生在 /llama 中。**登录检查取得目录是为了确认服务器可用，后续刷新才负责更新 pi 维护的模型列表。**若服务器上的模型已经可用，就可能直接通过 /model 选择。

本例关闭了自动加载，local-chat 此时仍为 unloaded，还需要下一步。

输入 /llama：从模型目录发出加载请求，再等待状态变化​

/llama 处理器首先通过当前上下文的模型接口读取 llama.cpp 连接配置，创建 LlamaClient。这里的上下文是 pi 传给命令处理器的对象，提供模型目录、认证和 UI 等运行接口。

打开管理界面之前，处理器读取服务器目录。服务器可能返回下面这样的记录（示意，只列相关字段）：

{
  "id": "local-chat",
  "status": { "value": "unloaded" }
}

这份记录会显示在 /llama 中，但不一定成为 /model 的可选项。前者展示服务器发现的模型及其状态，后者展示 pi 可以用来对话的模型。

用户选中这个未加载项后，处理器进入 loadModel()，调用 client.loadAndWait()。它先发出请求：

POST /models/load
请求体：{ "model": "local-chat" }

这个 HTTP 请求返回，并不代表加载已经完成。loadAndWait() 还会监听服务器进度事件，并反复 GET /models 检查同一 ID 的状态。目录报告 loaded 时才完成等待；失败标记或退出码会转成错误。

local-chat: unloaded
  → 用户选择加载，发送 POST /models/load
  → 服务器读取本地模型文件，映射或装入内存，状态变为 loading
  → pi 读取进度与目录状态
  → local-chat: loaded，等待结束

状态的产生方是 llama-server，pi 读取并展示它。这次操作使用服务器磁盘上已有的文件，不需要再从 Hugging Face 下载。loaded 表示权重和推理环境已准备好，使用多少 CPU 内存、多少 GPU 显存取决于服务器配置。

/llama 中另有下载操作，用于尚未取得模型文件的情况：pi 让用户搜索并选择仓库，然后要求 llama-server 下载到它管理的存储中。本例的加载路径从“文件已经存在”开始。

加载之后：服务器记录怎样进入 pi 的模型目录​

服务器已经加载 local-chat，但 pi 还要取得更新后的元数据。loadModel() 在等待完成后调用 syncCatalog()：

查看代码：加载之后怎样刷新 pi 的模型目录
// packages/coding-agent/src/extensions/llama/index.ts（节选）
const syncCatalog = async (
	ctx: ExtensionCommandContext,
	client: LlamaClient,
	catalog?: LlamaModelInfo[],
): Promise<LlamaModelInfo[]> => {
	const signal = AbortSignal.timeout(15_000);
	const current = catalog ?? (await client.list({ signal }));
	provider.setCatalog(current, client.serverUrl);
	const result = await ctx.modelRegistry.refresh({
		providers: [LLAMA_PROVIDER_ID],
		// /llama already contacted the configured llama.cpp server, so keep this refresh live even in PI_OFFLINE.
		allowNetwork: true,
		signal,
	});
	if (result.aborted) throw new Error("Model catalog refresh timed out.");
	const refreshError = result.errors.get(LLAMA_PROVIDER_ID);
	if (refreshError) throw refreshError;
	return current;
};

这里连着两步：

  1. provider.setCatalog() 先根据服务器目录填入 provider 的模型数组。
  2. ctx.modelRegistry.refresh() 请求模型运行时刷新 llama.cpp，进入 provider 的 refreshModels()，补齐能力信息，并发布、缓存新目录。

刷新时，代码先按状态过滤可选模型：

  • loaded：已加载，可以选用。
  • sleeping：休眠中，也可以选用，请求时由服务器唤醒。
  • unloaded：只有来自服务器预设配置、允许自动加载且未标记失败时才可以选用。

只用于分类决策、不生成对话文本的模型也不会进入聊天模型列表。

因此，本例中的 local-chat 从 unloaded 变为 loaded，是它能够进入聊天模型目录的关键变化。

筛选后的服务器记录交给 toPiModel()，得到 pi 的模型对象。下面是字段关系示意：

字段local-chat 对应的值后续用途
idlocal-chat请求体里指定哪个模型
providerllama.cpp找到负责认证与请求的 provider
apiopenai-completions使用兼容 Chat Completions 的协议实现
baseUrlhttp://127.0.0.1:8080/v1请求发送到本地服务器
contextWindow根据运行值、配置或缓存取得pi 判断上下文容量
input文本，或文本与图像pi 判断可发送哪些输入

toPiModel() 对已加载模型还可以使用 /props 返回的聊天模板信息，设置推理能力。为了避免唤醒休眠模型，刷新不会为了这项信息强行请求所有模型的属性。

最后，refreshModels() 使用 context.publish() 更新 provider 的模型数组，并保存目录元数据。/model 从模型运行时读取这个可用目录，因而能看到新的 local-chat。缓存保存的是名称、能力等信息，权重仍由 llama-server 管理。

输入 /model：选中模型之后，请求为什么会发给它​

/model 是通用模型选择器，展示 pi 的可用模型目录，可以同时包括 llama.cpp、OpenAI 等不同 provider。选择 local-chat 后，界面调用 session.setModel(model)，把前面得到的模型对象交给会话。

会话首先检查该 provider 是否有认证配置，再更新负责推进模型请求的 Agent 对象，并把这次选择保存为会话记录：

// packages/coding-agent/src/core/agent-session.ts（setModel 中的连续节选）
const previousModel = this.model;
const thinkingLevel = this._getThinkingLevelForModelSwitch(model);
this.agent.state.model = model;
this.sessionManager.appendModelChange(model.provider, model.id);

这一步没有让服务器再加载权重。它修改的是 agent.state.model 指向哪个模型对象。如果用户选择同时保存为默认模型，还会额外更新全局默认设置。

接下来用户输入一条消息，Agent 循环使用当前模型对象准备请求。模型运行时根据 provider: "llama.cpp" 解析认证信息，再调用该 provider 的流式接口。llama.cpp provider 委托给已有协议实现：

// packages/coding-agent/src/extensions/llama/provider.ts（provider 对象中节选）
stream: (model, context, options) => stream(model, context, options as ProviderStreamOptions | undefined),
streamSimple: (model, context, options) => streamSimple(model, context, options),

api: "openai-completions" 选择 Chat Completions 编码，baseUrl 指向本地 /v1，请求参数中的 model 使用 ID local-chat。所以正常路径发往的是 llama-server 的 /v1/chat/completions，不是 OpenAI 服务器。

llama-server 根据 ID 使用已加载模型生成输出，协议层把流式响应转为 pi 的消息事件，UI 再显示回答。如果模型返回工具调用，后续仍进入 pi 正常的工具循环。

到这里，三个命令通过数据接上了：登录保存连接配置，加载改变服务器状态并更新模型目录，选择把目录中的模型对象写进会话，发送消息时使用这个对象发出请求。

同一条主线上的其他操作：卸载、下载、分类与恢复
  • 卸载：/llama 请求 /models/unload，等待服务器报告未加载状态，然后重新同步目录。它改变服务器状态，不等同于选择另一个会话模型。
  • 下载：pi 搜索 Hugging Face 仓库并让用户选择量化版本，实际下载请求交给 llama-server。量化版本是权重采用的不同精度或压缩形式。下载完成后仍需更新目录，受限仓库还要求服务器具备相应凭证。
  • 分类：provider 还可以把模型登记为分类器，供脚本回答类别、布尔或分数问题。决策模型使用 /v1/systemone，普通聊天模型可以通过候选标签的下一 token 概率适配，分类入口与聊天选择分开。
  • 取消与错误：如果用户选择先卸载其他模型再加载新模型，扩展会记录原来的加载项；新模型失败或取消时，尝试恢复它们。Retry 重新连接并读取状态，不自动重复被中断的业务动作。

mcp 扩展：从配置服务器到完成一次工具调用​

基本使用：接入 echo，观察一次回显​

MCP（Model Context Protocol）是客户端与外部工具服务器通信的协议。本例的服务器只提供 echo：接收 message 字符串，返回 demo-echo says: 加上传入文本。推理仍由 pi 当前选择的大模型完成，echo 只执行回显。

新建一个能运行 Node.js 的测试项目，把下面折叠区的代码保存为根目录的 mcp-echo-server.js。示例使用 require()，可直接放在没有设置 "type": "module" 的空项目中。然后创建 .pi/mcp.json：

{
  "mcpServers": {
    "demo": {
      "type": "stdio",
      "command": "node",
      "args": ["mcp-echo-server.js"],
      "exposure": "direct"
    }
  }
}

stdio 表示通过进程的标准输入、标准输出交换协议消息；command 与 args 指定 pi 要启动的程序。direct 表示连接后把工具直接声明给模型。

从这个目录启动 pi，通过项目信任后输入：“调用 demo 的 echo 工具，回显 hello-builtin-extensions。”下面是测试会话中记录的调用和返回值：

CALL:   mcp__demo__echo {"message": "hello-builtin-extensions"}
RESULT: demo-echo says: hello-builtin-extensions
查看代码：用于本例的 stdio echo 服务器
// Minimal stdio MCP server for the builtin-extensions article experiments.
// Speaks JSON-RPC over newline-delimited stdin/stdout, protocol 2025-06-18.
const readline = require("node:readline");

const rl = readline.createInterface({ input: process.stdin });

function send(msg) {
	process.stdout.write(JSON.stringify(msg) + "\n");
}

rl.on("line", (line) => {
	if (!line.trim()) return;
	let msg;
	try {
		msg = JSON.parse(line);
	} catch {
		return;
	}
	const { id, method, params } = msg;
	switch (method) {
		case "initialize":
			send({
				jsonrpc: "2.0",
				id,
				result: {
					protocolVersion: "2025-06-18",
					capabilities: { tools: {} },
					serverInfo: { name: "demo-echo", version: "1.0.0" },
				},
			});
			break;
		case "notifications/initialized":
			break;
		case "tools/list":
			send({
				jsonrpc: "2.0",
				id,
				result: {
					tools: [
						{
							name: "echo",
							description: "Echo a message back, prefixed with the server name.",
							inputSchema: {
								type: "object",
								properties: {
									message: { type: "string", description: "Text to echo back" },
								},
								required: ["message"],
							},
						},
					],
				},
			});
			break;
		case "tools/call": {
			const text = `demo-echo says: ${params?.arguments?.message ?? ""}`;
			send({
				jsonrpc: "2.0",
				id,
				result: { content: [{ type: "text", text }] },
			});
			break;
		}
		default:
			if (id !== undefined) {
				send({ jsonrpc: "2.0", id, error: { code: -32601, message: `Unknown method: ${method}` } });
			}
	}
});

服务器里的工具名只有 echo，模型调用的名字却是 mcp__demo__echo。要解释这个差别，也要把进程启动、协议握手、工具注册与实际执行分开。下面是本例的正常时序：

会话开始：从配置找到要启动的进程​

mcp 扩展加载时注册了命令和事件处理函数。会话开始触发 session_start，此时处理函数才读取服务器配置并创建连接，不是在模型决定调用 echo 时才第一次读取 JSON。

配置读取顺序是用户级 ~/.pi/agent/mcp.json，然后是已信任项目的 .pi/mcp.json。项目可以重新定义同名服务器，也可以只覆盖 enabled、exposure、toolExposure。本例只在项目中定义 demo，因此得到 node、脚本参数和 direct 这份配置。

处理函数把文件配置与其他扩展注册的服务器合并，再为每个启用项创建 McpServerConnection。这个对象保留连接状态、客户端和服务器工具清单。

创建客户端传输时，本例选择 StdioTransport，启动 node mcp-echo-server.js，工作目录默认是当前会话目录，所以 args 中的相对脚本路径能找到文件。进程启动后，标准输入输出成为协议通道；日志应输出到 stderr，避免混入协议消息。

服务器和工具是两个不同阶段：**JSON 配置描述怎么找到服务器，服务器连接后返回的清单才描述有哪些工具。**配置没有写 echo 的参数，因为这部分由服务器告诉 pi。

建立连接：initialize 之后才请求 tools/list​

Node 进程起来了，客户端还不能假定它支持哪些操作。McpClient.connect() 先发送 initialize，包含协议版本、客户端信息和客户端能力。测试服务器返回支持的版本和 capabilities: { tools: {} }，表示它提供工具能力。

客户端检查版本后，发送 notifications/initialized 表明初始化完成，再调用 listTools()，发送 tools/list。服务器返回 echo 的名称、描述和参数结构。

这份清单的数据形状如下，摘自演示服务器：

{
  "name": "echo",
  "description": "Echo a message back, prefixed with the server name.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "message": { "type": "string", "description": "Text to echo back" }
    },
    "required": ["message"]
  }
}

inputSchema 是 JSON Schema，描述工具输入。它不是一次调用的实际参数：此时只知道将来需要传一个字符串 message，还没有收到 hello-builtin-extensions。

连接类取得清单后，把它存进 this.tools，将状态设为 connected，再通过 onTools(this) 通知扩展进行注册。onTools 是扩展创建连接对象时传入的回调，实际绑定到 registerTools(connection)，所以连接层取得清单后能够交回扩展层。

下面这段代码连接了“握手完成”与“得到工具列表”：

查看代码：连接完成时如何保存和交出工具清单
// packages/coding-agent/src/extensions/mcp/runtime.ts（connectOnce 中的连续节选）
transport = this.createTransport(this.entry, this.cwd, this.authProvider);
await client.connect(transport);
client.onNotification("notifications/tools/list_changed", () => {
	void this.refreshTools(client);
});

client.onClose(() => this.handleClientClose(client, stdio));

if (client.connectionState !== "connected") throw new Error("connection closed during setup");

this.hasResources = client.serverCapabilities?.resources !== undefined;
this.instructions = client.instructions?.trim() || undefined;

this.error = undefined;
this.onTools(this);
this.changed();

注册工具：echo 怎样变成 mcp__demo__echo​

扩展的 registerTools() 读取连接对象的工具数组，遍历每条定义。对 echo，它先计算 pi 内部的名称 mcp__demo__echo，再用 createMcpToolDefinition() 包装成 pi 能执行的工具，最后调用 pi.registerTool()。

名称加前缀是为了让不同服务器的同名工具能够并存。例如另一个服务器也提供 echo，pi 可以根据不同的前缀找到正确连接。这里服务器名来自配置键 demo，原始工具名则来自刚取得的清单。

转换时，原始数据被放到几个有明确用途的位置：

包装后的字段来源下一步由谁使用
name服务器前缀加原始工具名pi 按模型返回的名字定位工具
description服务器工具说明模型判断用途和使用时机
parameters服务器的 inputSchema模型生成参数，pi 校验参数
exposure服务器或单工具配置pi 决定是否直接激活
execute扩展生成的包装函数pi 执行时通过客户端转发调用

**工具的业务实现仍在服务器。**pi 保存的是描述、参数约束，以及能把调用送到服务器的包装函数。服务器无需把 JavaScript 函数传给 pi。

本例的 direct 工具默认随注册激活。首次发送用户任务前，扩展会等待直接工具服务器的连接准备，默认最多 10 秒；成功路径下 echo 已注册，能进入首次请求。超时则先提示仍在连接，工具后续连接完成才可用。

第一次请求模型：声明怎样变成一次调用​

用户任务交给 Agent 循环时，请求里包含 echo 的名称、说明和 message 参数结构。模型据此返回 toolCall 数据：工具名为 mcp__demo__echo，参数为 { "message": "hello-builtin-extensions" }。

模型返回这个对象时，服务器还没有执行 echo。pi 的 Agent 循环取出调用，按名称找到上一步注册的工具，校验输入并执行调用前钩子，然后进入包装函数的 execute()。

下面这份完整定义，正好连接了“模型能看到的说明”与“pi 真正执行的代码”：

查看代码：MCP 工具定义与实际转发入口
// packages/coding-agent/src/extensions/mcp/tools.ts（完整函数）
export function createMcpToolDefinition(options: {
	server: string;
	tool: McpTool;
	name: string;
	exposure: McpExposure;
	namespace: ToolNamespace;
	timeoutMs: number;
	getClient: () => Promise<McpToolCaller>;
	/** Whether `read_mcp_resource` can read the server's resources. */
	readableResources?: () => boolean;
}): ToolDefinition<TSchema, McpToolDetails> {
	const { server, tool } = options;
	const title = tool.title ?? tool.annotations?.title;
	const annotations = toToolAnnotations(tool);
	const label = `${server}/${tool.name}`;
	return {
		name: options.name,
		label,
		description: tool.description?.trim() || title || `MCP tool ${tool.name} from server ${server}`,
		parameters: toParameters(tool.inputSchema),
		outputSchema: createMcpResultSchema(tool.outputSchema),
		exposure: toToolExposure(options.exposure),
		namespace: options.namespace,
		...(annotations ? { annotations } : {}),
		...createMcpToolRenderers(label),
		async execute(_toolCallId, params, signal, onUpdate) {
			const client = await options.getClient();
			const result = await client.callTool(tool.name, (params ?? {}) as Record<string, unknown>, {
				signal,
				timeoutMs: options.timeoutMs,
				onProgress: (progress) => {
					const total = progress.total === undefined ? "" : `/${progress.total}`;
					const text = progress.message ?? `Progress ${progress.progress}${total}`;
					onUpdate?.({ content: [{ type: "text", text }], details: { server, tool: tool.name } });
				},
			});
			return convertMcpResult(server, tool.name, result, { readableResources: options.readableResources?.() });
		},
	};
}

options.getClient() 在实际执行时取得 demo 当前有效的连接，而不是永久使用注册时的旧连接。它会检查服务器是否仍启用、工具是否仍可用，避免用户停用服务器之后，已经准备好的调用还继续使用旧定义。

接着 client.callTool(tool.name, params, …) 使用原始名 echo，因为服务器没有见过 mcp__demo__echo。客户端把它编码成 tools/call 请求，形状如下（省略关联响应所用的协议请求编号）：

{
  "jsonrpc": "2.0",
  "method": "tools/call",
  "params": {
    "name": "echo",
    "arguments": { "message": "hello-builtin-extensions" }
  }
}

服务器脚本的 tools/call 分支从 params.arguments.message 取出字符串，拼上前缀后返回。到这里，配置中的进程、清单里的工具和模型发来的业务参数才真正连成了一次执行。

返回结果：服务器响应怎样进入第二次模型请求​

echo 返回的 MCP 结果是：

{
  "content": [
    { "type": "text", "text": "demo-echo says: hello-builtin-extensions" }
  ]
}

客户端按请求编号匹配响应，client.callTool() 等待的 Promise 完成，包装函数拿到这份对象，然后调用 convertMcpResult()。它把结果分成三部分：

  • content：给模型阅读的文本或图片，本例就是回显文本。
  • structuredContent：给 codemode 等程序调用方的 MCP 结果，去掉协议中的 _meta 后保留。
  • details：给 UI 等调用方的来源信息，包括服务器名、工具名和可选的全文文件路径。
查看代码：MCP 结果怎样转换成 pi 工具结果
// packages/coding-agent/src/extensions/mcp/tools.ts（完整函数）
export async function convertMcpResult(
	server: string,
	tool: string,
	result: CallToolResult,
	options: ConvertMcpResultOptions = {},
): Promise<AgentToolResult<McpToolDetails>> {
	// Without content blocks, toLlmContent falls back to the structured content as JSON.
	const converted: (TextContent | ImageContent)[] =
		result.content.length > 0 ? await toModelContent(server, result.content, options) : toLlmContent(result);
	if (result.isError && textOf(converted) === "") {
		converted.push({ type: "text", text: `MCP tool ${server}/${tool} returned an error` });
	}
	const { content, fullOutputPath } = await limitMcpContent(converted, options.saveOutput);
	const { _meta: _ignored, ...scriptResult } = result;
	return {
		content,
		details: { server, tool, ...(fullOutputPath ? { fullOutputPath } : {}) },
		structuredContent: scriptResult as unknown as JsonValue,
		...(result.isError ? { isError: true } : {}),
	};
}

对于本次直接调用，结果经过执行后钩子，成为一条 pi 工具结果消息，加入当前对话。Agent 循环再请求模型，模型读取回显文本，才生成最终回答。

模型返回调用：mcp__demo__echo + message 参数
  → pi 找到包装函数，执行校验和钩子
  → MCP 请求：tools/call，name=echo，arguments=参数
  → 服务器结果：content 中的回显文本
  → pi 工具结果消息
  → 第二次模型请求
  → 回答用户

MCP 工具因此和本地 read 工具一样由 pi 的工具循环推进，差别在执行函数内部：read 读取文件，这件工具通过客户端请求外部服务器。

改成 deferred 或 codemode，前面的流程在哪一步变化​

exposure 控制工具怎样到达模型。本例设置 direct，把工具声明直接提供给模型；其他配置改变的是注册之后、执行之前的入口路径。

服务器配置注册之后的默认路线
direct激活工具，将声明直接发给模型
deferred尝试开启 tool_search，模型先搜索并激活工具，再直接调用
codemode，默认尝试开启 codemode，模型提交脚本，由脚本查询和调用工具
hidden保留定义，但禁止模型和脚本访问

这张图画的是各配置的通常入口，不是互相禁止的通道：deferred、codemode 工具都可以被脚本调用，也能被 tool_search 搜索并激活。脚本与检索入口的内部流程见前文：tool_search 与 codemode。

表中“尝试开启 codemode / tool_search”的说法，来自 mcp 扩展的 ensureDiscoveryActive()。会话开始时它从配置收集所有启用服务器的暴露方式：

查看代码：配置怎样决定自动开启哪个入口工具
// packages/coding-agent/src/extensions/mcp/index.ts（节选，结尾警告段省略）
const ensureDiscoveryActive = (ctx: ExtensionContext) => {
	// From the config, so the tool is active before the servers connect. Resource tools share
	// their server's exposure.
	const exposures = new Set<McpExposure>();
	for (const server of servers) {
		if (isEnabled(server)) for (const exposure of configuredExposures(server.entry)) exposures.add(exposure);
	}
	const needsCodemode = exposures.has("codemode");
	const needsToolSearch = exposures.has("deferred");
	if (!needsCodemode && !needsToolSearch) return;
	// Only a tool of these names that declares `reachesTools` can reach MCP tools; another
	// extension's tool of the same name without it is never activated.
	const tools = pi.getAllTools();
	const hasReachingTool = (name: string) => tools.some((tool) => tool.name === name && tool.reachesTools);
	const hasCodemode = hasReachingTool(CODEMODE_TOOL_NAME);
	const hasToolSearch = hasReachingTool(TOOL_SEARCH_TOOL_NAME);
	const active = pi.getActiveTools();
	const activate: string[] = [];
	if (needsCodemode && hasCodemode && autoEnableCodemode && !active.includes(CODEMODE_TOOL_NAME)) {
		activate.push(CODEMODE_TOOL_NAME);
	}
	if (needsToolSearch && hasToolSearch && !active.includes(TOOL_SEARCH_TOOL_NAME)) {
		activate.push(TOOL_SEARCH_TOOL_NAME);
	}
	if (activate.length > 0) pi.setActiveTools([...active, ...activate]);
	const reachable = [...active, ...activate];
	if (hasCodemode && reachable.includes(CODEMODE_TOOL_NAME)) return;
	if (hasToolSearch && reachable.includes(TOOL_SEARCH_TOOL_NAME)) return;
	if (warnedUnreachable) return;
	warnedUnreachable = true;
	const reason = needsCodemode && hasCodemode && !autoEnableCodemode ? " (autoEnableCodemode is false)" : "";
	ctx.ui.notify(
		`MCP tools are only reachable from the codemode or tool_search tool, but neither is active${reason}; they cannot be called.`,
		"warning",
	);
};

读取它时注意三点：

  • 判断依据是配置，不是连接状态。configuredExposures() 把服务器级 exposure 和每件工具的 toolExposure 覆盖值都收进来，所以只要某件工具被覆盖成 codemode 或 deferred，对应的入口工具就会被开启，即使服务器级配置是 direct。
  • 同时需要入口工具存在。hasReachingTool() 检查注册表里是否有同名工具、且声明了 reachesTools——被禁用或被第三方同名替换的入口工具不会被开启。
  • **autoEnableCodemode 只拦 codemode 这一支。**mcp.json 顶层设为 false 时，codemode 不再自动激活；deferred 对应的 tool_search 不受这个开关影响。两个入口都不可用时，扩展警告一次并说明原因。

这段代码在 session_start 时执行，早于服务器连接：模型第一条请求就能携带入口工具的声明。

改成 deferred 的测试中，模型先得到服务器指引，再搜索 echo：

MCP servers whose tools are not declared to you. Load the tools of `tool_search` servers with `tool_search`.
- mcp__demo (tool_search)
CALL:   tool_search {"limit": 5, "query": "echo"}
RESULT: Loaded 1 tool. They are available from your next call:
        - mcp__demo__echo: Echo a message back, prefixed with the server name.

CALL:   mcp__demo__echo {"message": "deferred-demo"}

工具被激活后，下一次请求才发送 echo 的完整声明。从 echo 包装函数开始，仍走前面的 tools/call 路径。

改成 codemode 的测试中，没有传 --tools，扩展根据服务器配置开启 codemode，并给模型另一条指引：

MCP servers whose tools are not declared to you. Call the tools of `codemode` servers from codemode scripts.
- mcp__demo (codemode)

模型先读 codemode 文档，再提交脚本：

const result = await tools.mcp__demo__echo({ message: "codemode-mcp-demo" });
text(JSON.stringify(result, null, 2));

脚本仍进入同一个 echo 包装函数，MCP 请求不变。不同的是返回时，codemode 取出工具的 structuredContent，所以 result 是整个 { content: […] } 对象。脚本选择输出后，模型才收到外层 codemode 结果：

Script completed
Wall time 0.1 seconds
Output:
{
  "content": [
    { "type": "text", "text": "demo-echo says: codemode-mcp-demo" }
  ]
}

服务器配置中的 codemode 实际会映射成工具内部的 deferred：

// packages/coding-agent/src/extensions/mcp/tools.ts
export function toToolExposure(exposure: McpExposure): ToolExposure {
	return exposure === "codemode" ? "deferred" : exposure;
}

这个映射让默认 MCP 工具也不进入 codemode 的长工具目录。模型先得到服务器级指引，脚本需要具体签名时，再查询工具说明。它节省的是预先声明所有工具的篇幅，脚本、检索和实际输出仍然占用输入输出。

工具先不声明时，连接和调用怎样衔接​

MCP 扩展从配置中就能判断需要哪个入口工具，因此会在服务器连接完成前尝试激活 codemode 或 tool_search。每个服务器还有一个表示本轮连接准备完成的 ready Promise。

模型准备发出第一次请求时，pi 最多等 10 秒直接工具服务器。间接工具不一定要在第一次请求前连好：扩展可以先列出服务器名和访问方式。

真正执行检索或脚本之前，MCP 扩展监听 tool_call 事件，再决定等哪些连接。tool_search 的 reachesTools() 返回 "all"，会等待可能参与搜索的启用服务器；codemode 读脚本中可能出现的服务器名，使用检索或枚举接口时也等待所有相关服务器。

等待发生在工具执行前，所以检索能看见刚注册的 echo，脚本执行器也能把它放进自己的可调用工具集合。连接失败则报告错误，等待本身不能把失败服务器变成可用服务器。

主流程上的异常与其他能力
  • 断开与重连：连接对象保存 connecting、connected、disconnected 等状态。多个等待共享正在建立连接的 Promise；连接断开后的下一次调用会尝试重连，再获取工具清单。
  • 清单变更：服务器发送 notifications/tools/list_changed 后，pi 重新获取定义。被撤回的工具重新注册为 hidden，阻止后续访问。
  • 重试边界：连接时部分临时 HTTP 错误可以重试，但普通工具调用不能因为临时错误就重发，因为服务端可能已经执行。资源读取可重试；明确的会话失效允许重建会话后重试一次。
  • 大结果与错误：直接调用的模型正文超过 20 KiB 时截去中间部分，全文另存文件；脚本取得完整 MCP 结果。isError: true 对模型是错误结果，脚本拿到结构化对象时则需要自己检查字段。
  • 资源读取：服务器声明 resources 能力时，pi 提供 list_mcp_resources、list_mcp_resource_templates、read_mcp_resource，通过同一连接列举和读取文档或数据。
  • 授权：远程 HTTP 服务器需要 OAuth 时，连接标记 needs-auth。用户通过 /mcp 完成浏览器授权，令牌保存后用新凭证重连；认证层负责后续刷新。
  • 管理与扩展接入：/mcp 可以重连、启停和改暴露配置。其他扩展也能用 pi.registerMcpServer() 登记服务器，随后交给这套连接与工具适配逻辑；文件中的同名配置优先。

沿这两条主线看，扩展接入的东西不同：llama.cpp 把服务器模型转换为会话可选择、可请求的模型对象；mcp 把服务器工具定义转换为可声明、可执行的 pi 工具对象。真正串起它们的，是转换后的对象怎样进入 pi 已有的模型请求与工具执行流程。
