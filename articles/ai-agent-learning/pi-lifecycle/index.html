数一数 pi 的生命周期：到底有多少事件，多少层

周期2026年10月27日阅读 23 分钟

pi 的生命周期事件不是一串，是四层套娃：会话包着运行，运行包着回合，回合包着消息和工具调用。这篇从数事件入手，一层层剥开每个生命周期的开始、推进与结束，回答「回答完了为什么还在忙」。

前面的文章走读 pi，能看到同一个事实：模型的流式返回被翻译成事件向上广播，消息定稿由事件触发落盘，界面上每一点变化背后都有事件。可以推断，这个系统背后有一套庞大而有序的事件体系。

那到底有多少个事件？它们各自承载着什么？在我看来，这些事件加起来就是 pi 的生命周期——每一个都在标记某样东西的开始、进展或结束。

这篇文章就来回答这两个问题，并把这条生命周期完整地画出来。路线：先数一数，再看清嵌套，然后顺着调用链一层层剥开，从会话剥到一次工具调用，最后合回来。

信息

本文源码核对自 earendil-works/pi 仓库 commit 8efd314f。三个主要文件：packages/agent/src/types.ts（事件定义）、packages/agent/src/agent-loop.ts（循环层）、packages/coding-agent/src/core/agent-session.ts（编排层，约 4400 行，节选）。

事件不是一串，是四层套娃​

先数。事件定义在三个地方，口径一层比一层大：

定义处个数内容
循环层 AgentEvent（packages/agent/src/types.ts）10模型循环的最小事件集
编排层 AgentSessionEvent（agent-session.ts）再加 13 种压缩、重试、排队、落盘等编排事件
扩展协议 ExtensionEvent（extensions/types.ts）32 个成员、展开 41 种以上全部，加上会话、请求、输入级事件

数循环层这 10 个的时候，有个东西肉眼可见：它们天然分成四组。

分组事件
运行agent_start、agent_end
回合turn_start、turn_end
消息message_start、message_update、message_end
工具tool_execution_start、tool_execution_update、tool_execution_end

每组都是同样的形状：一个开始，一个结束，中间夹零到多个更新。而且四组不是并列的——外面那组的开始永远先于里面那组，里面那组的结束永远先于外面那组。一次真实会话的事件流，画出来就是这样：

事件是四层套娃，生命周期也是。给每层起个中文定名，全文复用：

中文定名代码名边界
会话AgentSessionsession_start 到 session_shutdown
一次运行runagent_start 到 agent_settled
一个回合turnturn_start 到 turn_end
一条消息messagemessage_start 到 message_end
一次工具调用tool calltool_execution_start 到 tool_execution_end

“运行”是这里的术语，指从你按下回车到 pi 彻底安静下来的一次完整处理：请求模型、执行工具、带着结果再请求，直到给出最终答复。四层的数量关系是层层多对一：

  • 一个会话里有零到多次运行，每次回车启动一次；
  • 一次运行里有一到多个回合；
  • 一个回合里恰好一条 assistant 消息——一次模型请求产出一条回复，多一条就跨入下一个回合；此外还可能有零到多条注入消息（起始或转向的 user 消息、声明工具变更的 system 消息）；
  • 一次工具调用对应恰好一条 toolResult 消息。

注意一个细节：运行那层的边界是 agent_settled，不是 agent_end。agent_end 之后还有事发生。这个悬念先按下，"合拢"一节揭晓。

接下来逐层剥：从会话开始，一路剥到一次工具调用，再合回来。

会话：一切的容器​

最外层是会话。pi 启动，装配好编排层和扩展，发出 session_start。退出或换会话前，发出 session_shutdown。所有其他事件都发生在这两个事件之间。

session_start 带一个 reason 字段，常见三种取值：

  • startup：进程启动，新会话就绪；
  • reload：执行 /reload，扩展运行时被整体替换，会话事件对扩展重放一次；
  • 切换或恢复会话：从磁盘加载历史会话，扩展借此重建分支敏感状态。

这层的价值在边界，不在过程。每个扩展文件都导出一个默认函数，pi 加载扩展时调用它、传入 API 对象，扩展的事件订阅和命令注册全在这个函数体里——pi 文档称它为 factory，直译工厂函数（后文完整源码里的 export default function lifecycleLogExtension(pi) 就是）。pi 的扩展文档对开发者有句直白的要求：工厂函数里不许开长活资源（进程、socket、watcher、timer），要从 session_start 里开，从 session_shutdown 里关。原因是有些调用只加载扩展不启动会话，工厂函数里开的资源没人收尾。这条规则等于把资源的生命兜进会话的生命：开头之后才能开，结尾之前必须关，资源不会泄漏到会话之外——pi 退出后不会有孤儿进程还在后台跑。

一次运行：从按下回车到真正安静下来​

会话大部分时间是空闲的：输入框等着，没有事件。你在输入框里敲下一句话，按下回车——这行字不会直接去请求模型，它先进入编排层的提交处理：展开斜杠命令和提示词模板，检查模型认证。处理完，它作为起始消息，启动第二层生命周期：一次运行。

先抛一个现象：模型把最后一个字都说完了，屏幕上指示器还在转。回答结束了，为什么 pi 还在忙？答案藏在运行的启动和收尾里。

启动：回车之后、请求之前​

编排层接到 prompt() 调用，并不直接请求模型。发请求之前有五步：

  1. 压缩预检：上一轮对话若已越过压缩阈值，先压缩再发（压缩的存储侧见前文：pi 的会话）；
  2. before_agent_start：扩展的干预窗口，可以改系统提示词、往本轮注入消息，甚至换模型；
  3. 组装起始消息：用户消息（或扩展的 custom 消息）加上待注入的 nextTurn 消息、扩展消息，若提示词或工具清单有变，先补一条 system 消息声明差异；
  4. agent.prompt()：控制权交给循环层，agent_start 事件发出，运行开始；
  5. 后处理循环：等循环层跑完，编排层接管判断要不要继续。

一个容易被忽略的设计：从第 1 步开始，pi 就算"忙"了。这期间用户再按回车，消息不会另起一次运行，而是进入正在启动的这次运行。所以"运行"的边界比"模型在生成"宽得多。

查看代码：运行的主体骨架（agent-session.ts，节选并简化）
private async _startRun(trigger, onStarted?) {
    this._isAgentRunActive = true;
    const messages = await this._prepareRun(trigger);   // 步骤 1-3
    onStarted?.();
    await this.agent.prompt(messages);                  // 步骤 4
    while (!this._agentRunAbortRequested) {
        if (await this._handlePostAgentRun()) {         // 重试 / 压缩 / 排队消息
            await this.agent.continue();
            continue;
        }
        if (!(await this._runBeforeSettleBoundary())) break;  // 扩展最后的续跑窗口
        await this.agent.continue();
    }
    await this._emitAgentSettled();                     // 步骤 5 收尾：settled
}

原代码里每步都有错误处理和排队细节，这里只保留骨架。

循环层的双层循环​

agent.prompt() 把控制权带进循环层。循环层的核心是两层 while：

  • 内层：只要本轮回复里还有工具调用、或队列里有转向消息，就继续——请求模型、执行工具、带着结果再请求，一个回合接一个回合；
  • 外层：内层停下来后，检查 follow-up 队列。运行中用户排的"等它忙完再发"的消息在这里兑现，有就再转一圈内层。
查看代码：双层循环（agent-loop.ts，节选并简化）
while (true) {                                          // 外层：follow-up 驱动
    let hasMoreToolCalls = true;
    while (hasMoreToolCalls || pendingMessages.length > 0) {   // 内层
        // prepareNextTurn → 注入 steering 消息 → prepareRequest
        const message = await streamAssistantResponse(/* ... */);
        if (message.stopReason === "error" || message.stopReason === "aborted") {
            /* 硬退出：直接 turn_end → agent_end */
        }
        const toolCalls = message.content.filter((c) => c.type === "toolCall");
        if (toolCalls.length > 0) {
            const batch = message.stopReason === "length"
                ? await failToolCallsFromTruncatedMessage(toolCalls, emit)  // 批量判失败
                : await executeToolCalls(/* ... */);
            hasMoreToolCalls = !batch.terminate;
        } else {
            hasMoreToolCalls = false;
        }
        const decision = await config.finishTurn?.(/* 本回合 */);
        if (decision?.action === "end") { /* 扩展判定结束 */ }
        pendingMessages = await config.getSteeringMessages?.() ?? [];
    }
    const followUps = await config.getFollowUpMessages?.() ?? [];
    if (followUps.length > 0) { pendingMessages = followUps; continue; }
    break;                                              // 没人再喂消息，运行结束
}
await emit({ type: "agent_end", messages: newMessages });

退出的判定全在这段里，三个条件满足其一，内层就停：

  • 模型出错或被中止（硬退出）；
  • 扩展的 finishTurn 判定结束；
  • 既没有待执行的工具，也没有排队的消息。

内层停后，外层再确认一次 follow-up，没人接就 agent_end。

agent_end 之后，故事还没完​

回到开头的现象。循环层发出 agent_end，运行并没结束——控制权回到编排层的后处理循环：

  • 自动重试：刚才是可重试的错误？按设置退避重试，agent_end 事件在编排层还会带上 willRetry: true；
  • 压缩检查：上下文越界了？插入一次压缩；
  • agent_before_settle：扩展最后一次可以续跑的窗口，可以补消息、请求再继续一轮；
  • 都没有，才发出 agent_settled，isStreaming 归 false，指示器停。

所以**"模型说完了"是 agent_end，"pi 真正安静下来"是 agent_settled**，中间隔着编排层的全部收尾。这两个事件之间的窗口，就是那个指示器多转的部分。

一个回合：一次思考，一次行动​

往里剥一层。回合是运行的基本单元：一次模型请求，加上这次请求派生的工具执行和结果回填。turn_start 到 turn_end 之间，固定发生这几件事，顺序从不变：

  1. prepareNextTurn 钩子：回合开始前，宿主可以替换上下文、追加消息、换模型（压缩这类长操作可以塞在这里）；
  2. 注入转向消息：用户在上一回合执行工具时插的话，从 steering 队列取出，走一遍消息的固定事件流程后进入上下文；
  3. prepareRequest 钩子：请求发出前最后一站，前文：pi 的会话讲的投影就挂在这里——从会话树上把当前分支读出成发给模型的线性消息列表；
  4. 流式响应：一条 assistant 消息从 message_start 长到 message_end（下一节展开）；
  5. 工具执行：回复里的每个工具调用各走一遍自己的事件（再下一节展开）；
  6. finishTurn 钩子：回合收口，返回 continue 可以强制再来一轮，返回 end 直接终止运行。

两个队列的注入时机也在这层见分晓。同样是运行中插话：

  • steering（转向）：回合边界注入。当前回合的工具照常执行完，下一个请求带上你的话——"手头的活干完，但方向听我的"；
  • follow-up（跟进）：运行边界注入。整个运行都要结束了才轮到它——"等你忙完所有事，再做这件新事"。

界面层让你选哪种（提交时带 steer 还是 followUp 标记），生命周期决定它何时生效。这也解释了另一个常见困惑：同样是运行中回车，有时下一秒就被模型引用，有时要等整个任务收尾——不是排队bug，是两条队列、两个注入点。

一条消息：从第一个字到定稿​

回合里再剥一层，是消息。前文：一条消息的往返跟过 assistant 消息的流式过程，这篇补上它没展开的四个面。

这套事件适用于所有消息，不只 assistant​

称它仪式，是因为形式和顺序完全固定：不管消息是什么角色、从哪来，都得从 message_start 进、message_end 出，一步不能少，失败了也要补齐。每种角色的消息都要把这套仪式走一遍。一次运行里，至少五类消息各走各的仪式：

消息从哪来有没有 update
用户消息回车提交、steering/follow-up 队列注入无
system 消息工具清单或提示词变更时的差异声明无
assistant 消息模型流式响应有，每个增量一次
toolResult 消息每个工具调用的结果无
custom 消息扩展注入；纯展示的不进模型上下文，其余转换为 user 消息进入无

只有 assistant 消息是"长出来的"，其余都是整条出现、整条定稿。订阅者拿到的是统一接口：不管消息从哪来，message_start 一定有一个 message_end 与之配对。

assistant 消息的两条收尾路径​

流式的主线前文讲过：每个增量带来累积到当下的完整快照，循环层用它原地替换对话记录（transcript）末尾那条正在生长的消息。这里补两个前文没讲的细节。

一是那条消息的出生：流的第一个事件先送来一个空骨架，占住对话记录末尾的位置（运行期间装在 context.messages 里），message_start 随之发出——所谓“正在生长的消息”，起点是一条空消息。

查看代码：空骨架的构造与占位（pi-ai 适配器与 agent-loop.ts，节选）

骨架里角色、模型已定，内容为空、用量全零、停止原因待定；后续每个增量带来的都是这份骨架长满后的完整快照。

二是收尾：有两条路径。

模型流以 done 或 error 帧结束时，取最终定稿替换对话记录末尾的 partial，发 message_end。但流可能哪个都不送来——连接断了，迭代器走完却没收到结束帧。循环层在 for await 之后还有一道兜底：再取一次 result()，有 partial 就替换，没有就直接把定稿压进对话记录。

查看代码：done/error 分支与流中断兜底（agent-loop.ts，节选）
for await (const event of response) {
    switch (event.type) {
        case "done":
        case "error": {
            const finalMessage = await result();
            if (addedPartial) {
                context.messages[context.messages.length - 1] = finalMessage;  // 替换 partial
            } else {
                context.messages.push(finalMessage);  // 流一个字没吐，整条压入
            }
            await emit({ type: "message_end", message: finalMessage });
            return finalMessage;
        }
    }
}
// 流结束却没走 done/error：同样的收尾再来一次
const finalMessage = await result();
if (addedPartial) context.messages[context.messages.length - 1] = finalMessage;
else context.messages.push(finalMessage);
await emit({ type: "message_end", message: finalMessage });

addedPartial 标记对话记录末尾是否已有 partial 占位，两条路径靠它决定替换还是压入。

一个 message_end，四层消费​

事件发出去之后谁在听？以 message_end 为例，同一次广播依次穿过四层：

  1. 循环层的状态机（Agent.processEvents）：维护两个状态字段——streamingMessage 是"进行中"的槽位，装着正在流式生长那条消息的最新快照（开始时置位，每个增量更新）；state.messages 是"已完成"的账本，内存里的权威副本。message_end 到达时，状态机做两个动作：把 streamingMessage 清空，把定稿消息压进 state.messages——这条消息从进行时搬进完成时；
  2. 编排层的落盘（AgentSession._handleAgentEvent）：按角色分派，system/user/assistant/toolResult 调 sessionManager.appendMessage() 挂到 entry 树；custom 消息走另一个方法（appendCustomMessageEntry()），落成另一类节点，但仍在同一条消费链上——这就是"每条消息定稿即落盘"的精确含义；
  3. 扩展：message_end 处理器可以整条替换这条定稿消息（保持角色不变）——订阅者不止能看；
  4. 界面：渲染进对话流。

落盘发生在扩展事件分发之后，所以扩展替换过的消息，落盘的是替换后的版本。

三本账​

同一条消息，在循环层里同时记在三本账上：

  • newMessages：循环层本次运行的返回值，agent_end 事件带出去的就是它——只装本次新增；
  • context.messages：循环层的工作账本，就是运行期间装着对话记录的那个列表——起点是运行开始时从 state.messages 复制的快照，之后边跑边追加；
  • state.messages：循环层对外暴露的状态，只通过 message_end 事件进账——消费链第一层里那本“已完成”的账。

前两本在循环层内部，随运行生死；第三本跨运行存活，是下一次运行的起点。分开记账的原因：运行结束时要回答"这次新增了什么"（给重试和落盘对账），也要回答"现在全部是什么"（给下一次投影）。

补一句 transcript 的名分：对话记录运行期间装在 context.messages 里（占位、替换都发生在它身上），定稿后沉淀进 state.messages——源码给后者的注释就叫 Conversation transcript，而发给模型的请求带的，是投影转换后的又一份。

失败也闭合​

最后一块：运行中途抛异常（不是模型报错，是代码异常），事件流会不会断在半空？不会。Agent 的运行包装器捕获异常后，合成一条失败的 assistant 消息，把剩余仪式补完：

查看代码：失败时补全事件序列（agent.ts，节选）
private async handleRunFailure(error: unknown, aborted: boolean): Promise<void> {
    const failureMessage = {
        role: "assistant",
        content: [{ type: "text", text: "" }],
        stopReason: aborted ? "aborted" : "error",
        errorMessage: error instanceof Error ? error.message : String(error),
        /* ... */
    };
    await this.processEvents({ type: "message_start", message: failureMessage });
    await this.processEvents({ type: "message_end", message: failureMessage });
    await this.processEvents({ type: "turn_end", message: failureMessage, toolResults: [] });
    await this.processEvents({ type: "agent_end", messages: [failureMessage] });
}

订阅者视角的保证由此成立：只要见到 agent_start，就一定会等到 agent_end，无论中间发生了什么。落盘、UI、扩展都不需要为"事件流断在半路"写防御代码。

一次工具调用：真正干活的地方​

剥到最里层。assistant 回复里每个工具调用，都是一段独立的小生命周期，四个阶段：

  1. 拦截：beforeToolCall 钩子。参数已验证，扩展可以返回 block: true 拦下这次调用，模型会收到一条错误结果说明被拦的原因；
  2. 执行：调用工具的 execute()。执行中的部分结果通过 onUpdate 回调流出，变成 tool_execution_update 事件——长任务（比如持续输出的 bash）执行到哪一步，订阅者实时可见；
  3. 修正：afterToolCall 钩子。执行完了，扩展可以按字段覆盖结果：换内容、换错误标记、换用量，不提供的字段保留原值；
  4. 定稿：tool_execution_end 事件带上执行耗时；随后结果组装成一条 toolResult 消息，走上一节的消息仪式进入对话记录。
查看代码：顺序执行路径（agent-loop.ts，节选并简化）
await emit({ type: "tool_execution_start", toolCallId, toolName, args });
const preparation = await prepareToolCall(/* 含 beforeToolCall 拦截 */);
const executed = await executePreparedToolCall(
    preparation, signal,
    (partial) => emit({ type: "tool_execution_update", /* ... */ }),   // onUpdate
);
const finalized = await finalizeExecutedToolCall(/* 含 afterToolCall 修正 */);
await emitToolExecutionEnd(finalized, emit);
const toolResultMessage = createToolResultMessage(finalized);
await emitToolResultMessage(toolResultMessage, emit);   // message_start → message_end

并行路径同样四阶段，区别在调度：所有调用先逐个 prepare，允许并行的再同时执行。

三个值得记的细节：

顺序还是并行，每个回合单独定。 一条回复里多个工具调用，默认并行执行；任一调用声明自己必须独占（executionMode: "sequential"），整批退回顺序模式。并行时事件顺序有个讲究：tool_execution_end 按完成序发，toolResult 消息按源序发——先完成的工具先报告，但消息序列保持模型看到的样子，不因执行快慢而乱序。

截断的调用批量判死。 模型回复被输出上限截断（stopReason === "length"）时，里面的工具调用参数可能是残缺的 JSON 硬凑出来的，看起来合法，实际是断的。pi 不赌：这一批全部判失败，每个都按完整仪式发事件，错误信息告诉模型"参数可能被截断，请重新发起调用"。

终止要全票。 工具结果可以带 terminate: true，投一张"这批干完就停"的终止票。一张票没有决定权：一批调用全部投了，票才生效——全票制避免单个工具的单方面判断掐断整批工作。投票入口有三个：

  • 工具 execute() 返回的结果自己带；
  • beforeToolCall 拦截时可以投；
  • afterToolCall 可以改票。

这张票是循环层自定义的调度提示，只有 loop 的全票判定消费它：不随 toolResult 发给模型，pi 自己的订阅者也不读（事件载荷里带着，只是完整结果对象的原样透传）。全票生效时，终止的也不是工具执行（批次总会执行完），而是"带着结果再请求模型"的下一回合。

合拢：结果如何一层层浮回终端​

剥到最里层了。现在原路合回去，看一次完整运行的全貌——这次用时序图，把四层生命周期和调用关系放在一张图里：

合拢路径上还有两件事值得单独说。

错误与中止。 模型出错（stopReason === "error"）或用户按 Esc 中止（"aborted"），在内层循环里是硬退出：不再执行任何工具，直接 turn_end → agent_end。但事件序列照样闭合——中止不是把事件流掐断，而是让每一层用正常仪式宣布结束。中止的实现是协作式的：一个 AbortSignal 从运行顶部传到工具执行和每个钩子，工具和扩展自己负责检查信号。中途异常的路线上一节讲过：合成失败消息，补完仪式。

settled 期间的插队。 agent_settled 广播期间来了新回车怎么办？编排层把它压进延迟队列，等 settled 的全部监听器跑完再执行——settled 必须是最后一个事件，这是给"pi 彻底安静了"这个语义的兜底。

回头再数：扩展看到的事件​

层层剥开又合拢，回到入口的问题：到底多少个事件？

循环层 10 个，编排层再加 13 种，扩展协议的 union 有 32 个成员——其中 SessionEvent 一项就打包了 10 种会话事件（启动、关闭、切换前后、分叉前后、压缩前后、树导航前后），全部展开是 41 种。扩展多出来的那些不是新生命周期，是同一批生命周期的更多切面：会话事件（切换、分叉、压缩前后）、请求事件（发前、响应后、原始流）、输入事件（用户回车、bash 命令）、UI 事件，等等。

更重要的是，扩展事件和核心事件的区别不在数量，在权限。核心订阅者（UI、落盘）只能看，扩展订阅者按事件不同有不同干预权限，而且干预窗口逐级收紧：

窗口事件能做什么
运行前before_agent_start改系统提示词、注入消息、换模型
消息定稿message_end整条替换这条消息
工具执行前tool_call改参数、拦截
工具执行后tool_result覆盖结果字段
回合结束turn_end追加消息、请求再跑一轮
运行收尾agent_before_settle最后一次续跑机会
彻底结束agent_settled只能看

越靠后的窗口权限越小：运行前什么都能改，彻底结束后什么都改不了。这个漏斗就是 pi 的回答——扩展能深入到什么程度，取决于它站在生命周期的哪个位置。

现在数数的账算完了：10 个核心事件，四层生命周期，一套权限逐级收紧的扩展协议。

结语：事件即协议​

回到开头的两个问题，答案齐了：

  • 有多少事件、各自承载什么：循环层 10 个，编排层共 23 种，扩展协议展开后 41 种；每一个都在标记某样东西的开始、进展或结束；
  • 生命周期是怎样的：一条，四层嵌套——会话、运行、回合、消息与工具调用；每层同样的形状（开始、更新、结束），由调用链上不同层的代码启动和关闭，agent_settled 是全系统对“安静”的最终裁决。

数完之后再回头看，最有意思的不是数字，是形状。生命周期的四层，每层只需要三个事件（开始、更新、结束），不需要更多——因为每个订阅者都只关心“它开始了”“它有进展”“它结束了”。界面靠这套事件渲染，落盘靠它触发，扩展靠它介入，pi 的可扩展性整个架在这十几个事件上。
