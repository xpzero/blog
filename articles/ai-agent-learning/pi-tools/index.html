打开 pi，不做任何额外配置，模型能调用哪些工具？

答案是一张四行的清单：read、bash、edit、write。pi 内置的工具有七个，但默认激活的只有这四个。grep、find、ls 同样注册在案，要靠启动参数或设置手动开启。

注册和激活是两回事，这条缝隙正是理解工具系统的入口：工具怎么定义、模型怎么知道一个工具、一次调用经过哪些站、多个工具并发时怎么不打架。这篇文章解剖这七个内置工具，把这些问题一次讲清。

信息

本文源码核对自 earendil-works/pi 仓库 commit 8efd314f，主要文件是 packages/coding-agent/src/core/tools/ 下的工具定义与 packages/agent/src/agent-loop.ts 的执行管线。文末实测在同版本源码上运行。

注册不等于激活：模型看到的清单从哪来​

先看事实。pi 启动时把七个工具全部注册进工具注册表，但默认激活名单写死为四个：

// packages/coding-agent/src/core/settings-manager.ts
export const DEFAULT_TOOL_NAMES: readonly string[] = ["read", "bash", "edit", "write"];

只有激活的工具会被声明给模型——它的名字、说明和参数结构进入模型的视野，模型才能发起调用。开启另外三个工具，有两个用户入口和一个代码接口：

  • 启动参数：pi --tools read,bash,edit,write,grep（-t 是简写），只影响这一次启动；
  • 配置文件：settings.json 里的 defaultTools 字段，重启或 /reload 后生效。写法分两种：
    • 直接写工具名，如 ["read", "grep"]——这份名单就是全部激活的工具，默认四件套不再保留；
    • 名字带符号，如 ["+grep"] 在现有清单上追加一项，["-bash"] 移除一项；
  • 代码接口：setActiveTools()，扩展和 SDK 程序在运行中调整激活集用的方法——比如工具检索扩展把搜到的工具装进激活集，靠的就是它。终端用户不需要直接碰这个方法。

为什么默认关掉三个搜索工具？pi 的系统提示词里有一条给模型的规则，原文是 "Use bash for file operations like ls, rg, find"——列目录、找文件、搜内容，bash 一个工具都能做。默认工具面保持最小，需要更省 token 或更结构化的搜索输出时再开。最小化默认值是取向，不是能力边界。

七个工具的全貌：

工具用途输出上限默认激活

解剖 read：一个工具由什么构成​

read 是七个工具里最简单的一个，正好当标本。一个工具由四部分构成。

**第一部分：参数 schema。**用 TypeBox（一个用 TypeScript 写 JSON Schema 的库）声明参数，每个字段的 description 是写给模型看的：

// packages/coding-agent/src/core/tools/read.ts
const readSchema = Type.Object({
	path: Type.String({ description: "Path to the file to read (relative or absolute)" }),
	offset: Type.Optional(Type.Number({ description: "Line number to start reading from (1-indexed)" })),
	limit: Type.Optional(Type.Number({ description: "Maximum number of lines to read" })),
});

offset 是从 1 开始数——这种细节不靠模型猜，写在字段说明里。参数 schema 同时承担三件事：给模型看用法、请求前做校验、生成工具声明。

**第二部分：description，工具的说明书。**它是定义对象上 description 字段的值，源码原文如下（模板字符串，原文一行，此处折行展示）：

// packages/coding-agent/src/core/tools/read.ts
description: `Read the contents of a file. Supports text files and images
(jpg, png, gif, webp, bmp). Images are sent as attachments. For text files,
output is truncated to ${DEFAULT_MAX_LINES} lines or ${DEFAULT_MAX_BYTES / 1024}KB
(whichever is hit first). Use offset/limit for large files. When you need
the full file, continue with offset until complete.`,

// 这两个常量定义在 packages/coding-agent/src/core/tools/truncate.ts
export const DEFAULT_MAX_LINES = 2000;
export const DEFAULT_MAX_BYTES = 50 * 1024; // 50KB

渲染之后，模型读到的就是"2000 lines or 50KB"。插值常量同时被截断逻辑使用——说明书里的数字和实际行为永远一致，不会各说各话。

注意它把两件事都写了：限制（截断到 2000 行或 50KB），以及绕过限制的方法（用 offset/limit 续读，读全文件就一段段接下去）。说明书不只描述能力，还教模型在边界处怎么办。

第三部分：execute，统一的执行签名。

// packages/agent/src/types.ts（节选，中文注释为本文所加）
execute: (
	toolCallId: string,        // 这次调用的编号
	params: Static<TParameters>, // 通过 schema 校验的参数
	signal?: AbortSignal,      // 中止信号：用户按 Esc 时它会触发
	onUpdate?: AgentToolUpdateCallback, // 部分结果回调：边执行边上报
): Promise<AgentToolResult>;

四个参数固定不变，所有工具一样。长任务需要的两个通道——响应中止、流式回报——都开在签名里，工具想用就拿，不用也兼容。

**第四部分：返回结构。**一次工具执行返回一个结果对象，但读它的不止模型一个——终端界面要把它渲染出来，用代码直接调用工具的程序（比如脚本批量调度工具、通过 SDK 把 pi 嵌进自己应用的程序）也要从它取数据。结果结构用三个字段分别服务这三方：

// packages/agent/src/types.ts（节选，中文注释为本文所加）
export interface AgentToolResult<T> {
	content: (TextContent | ImageContent)[]; // 发给模型的正文
	details: T;                              // 给界面渲染的细节（如截断信息）
	structuredContent?: JsonValue;           // 给程序调用方的结构化数据，不发给模型
	isError?: boolean;                       // 不抛异常的失败报告
	terminate?: boolean;                     // 建议本批工具跑完就停（全票才生效）
}

拿 read 举例：模型拿到文件正文（content），终端界面拿到截断标记等渲染细节（details），程序调用方拿到符合 outputSchema 的结构化数据（structuredContent）。一份结果，三个去向，各取所需，互不干扰。

扩展阅读：read 的两处设计与一段小声明（core/tools/read.ts）
// ① 系统提示词贡献：工具自带的“介绍与守则”文案
export const readToolSystemPromptContribution = {
	snippet: "Read file contents",
	guidelines: ["Use read to examine files instead of cat or sed."],
} as const;

// ② 可插拔的 operations：文件 I/O 的替换接口，默认实现读本地文件
export interface ReadOperations {
	readFile: (absolutePath: string) => Promise<Buffer>;
	access: (absolutePath: string) => Promise<void>;
	detectImageMimeType?: (absolutePath: string) => Promise<string | null | undefined>;
}

// 另有一处小设计：read 声明了 constrainedSampling: { type: "json_schema", strict: "prefer" }。
// 受约束采样（constrained sampling）是部分服务商提供的能力：让模型生成工具参数时
// 直接贴着 JSON Schema 走，从源头减少参数不合法。"prefer" 表示支持就用，不支持不强求。

① 系统提示词贡献：守则跟着工具走。

  • 为什么需要：description 随 API 请求的工具声明走，回答“这个工具是什么、参数怎么填”；但“用 read 而不是 cat/sed”“用 bash 而不是 ls/rg/find”是工具之间的分工规则，发生在模型决定用哪个工具之前——放不进任何单个工具的 description，需要一个全局位置。
  • 起什么作用：snippet 成为系统提示词里 Available tools 清单的一行（- read: Read file contents）；guidelines 逐条进入 Guidelines 段，参与塑造模型的工具取舍。
  • 什么时候生效：会话启动和每次激活集变化时，pi 收集激活工具的这两类文案重组系统提示词；工具停用，文案自动消失。守则跟着工具走，不靠人维护提示词模板。

② 可插拔 operations：工具做什么与 I/O 在哪做解耦。

  • 换的是什么：read 的实现分两半——逻辑半（截断、图片处理）不依赖环境，I/O 半（真正读字节）强依赖环境。工厂函数的 options.operations 就是那道缝，pi 构建内置工具时用默认本地文件系统。
  • 谁在换：替换发生在扩展侧。官方示例 gondolin 用 registerTool 注册同名工具顶掉内置的：展开内置定义保留全部声明与守则，只重写 execute，执行时用指向本地微虚拟机的 operations 现场构建 read 实例。
  • 效果：模型看到的工具一字未变，变的只是每个字节实际从哪来——同一份工具逻辑适配本地、沙箱等不同环境。

看完 read，工具的形状就清楚了：schema 声明参数，description 写说明书，execute 按统一签名干活，一份结果三个去向。后面六个工具只是换了实现，形状不变。

其余六个：各自解决什么问题​

bash：唯一会跑起来的工具​

默认四件套里，只有 bash 会在机器上真正执行东西，它的设计也最厚：

  • 没有默认超时。timeout 是可选参数（单位秒），不传就一直等——适配构建、安装这类长命令；
  • 输出流式回传。stdout 和 stderr 每有数据就通过 onUpdate 上报，长命令执行到哪，界面实时可见，不用等结束；
  • 截断方向与 read 相反。read 保头（从头读，offset 续读），bash 保尾（保留最后 2000 行或 50KB——命令的错误和最终状态通常在结尾），全量输出另存临时文件，结果里告知路径；
  • 中止杀整棵树。命令以独立进程组启动，中止信号触发时杀掉整个进程树，不留后台孤儿。

edit：精确替换，不做模糊匹配​

edit 只做一件事：按原文精确替换。参数是一个编辑数组，每条指定 oldText 和 newText：

  • oldText 必须在原文件中唯一，且与其他编辑不重叠；
  • 多条编辑都对照原文件匹配，不是前一条改完再匹配后一条；
  • 匹配不到就报错返回，不做"最接近的"猜测。

确定性优先：工具行为可预测，模型才敢规划调用顺序。相邻的两处改动怎么办？说明书直接建议合并成一条编辑，省得两条 oldText 挤在同一片区域。

write：只干两件事​

新建文件，或整体重写。说明书里的指南只有一句："Use write only for new files or complete rewrites"（write 只用于新文件或完整重写）。父目录不存在会自动创建。局部修改是 edit 的领地，write 不掺和。

grep / find / ls：可选的搜索三件套​

默认关闭的三个工具，各自的上限见表格。grep 支持正则与字面量两种模式、glob 过滤、大小写开关、上下文行，尊重 .gitignore；find 按 glob 模式找文件；ls 列目录。

什么时候值得开？三个工具的输出比 bash + 命令行更规整、更省 token，批量检索密集的任务里更划算。日常场景，bash 兜底就够了。

并发不打架：两道闸门​

一条模型回复可以带多个工具调用。默认并行执行，两道闸门防止并行出乱子。

第一道：批内调度。一批调用默认同时跑；只要有一个工具声明自己必须独占（executionMode 为 sequential），整批退回顺序执行。并行的批次里，事件顺序有个讲究：执行结束事件按完成序发，结果消息按源序发——先完成的工具先报告进展，但写进对话的结果序列保持模型发起调用的原序，不因执行快慢而乱。

**第二道：文件级互斥。**edit 和 write 的每次写操作都经过一个按文件排队的队列：同一个文件（按真实路径解析）的写操作串行执行，不同文件仍然并行。模型并行发起两个 edit 改同一个文件，不会互相覆盖。

一次调用的管线​

从模型发出调用，到结果回到对话，经过五站：

前三站里，两处"没执行就结束"都返回说明性错误：工具不存在，模型收到 "Tool xxx not found"；参数过不了 schema，收到具体的校验错误。拦截发生在参数校验之后，扩展可以通过 beforeToolCall 把调用拦下，原因作为错误结果返回，模型读完知道该换什么方法。

执行这一站的骨架，正文直接看：

// packages/agent/src/agent-loop.ts（节选）
const startedAt = performance.now();
const result = await prepared.tool.execute(
	prepared.toolCall.id,
	prepared.args,
	signal,          // 中止信号原样传给工具
	(partialResult) => { /* onUpdate：部分结果 */ },
);
const durationMs = Math.round(performance.now() - startedAt);

工具抛异常不会打断流程，catch 之后异常消息变成错误结果。于是失败有两条路：

  • throw：结果里只有错误消息，适合简单的失败；
  • isError: true：不抛异常，content 给模型讲清失败原因，details 和 structuredContent 照常保留给界面与程序调用方。

最后一站的细节：结果消息上可以带 terminate 投票，建议"这批工具跑完就停"。一张票没有决定权，一批调用全部投了才生效——避免单个工具的单方面判断掐断整批工作。还有一种特殊失败：模型输出被长度上限截断时，里面的工具调用参数可能是残缺 JSON 硬凑出来的，看起来合法，实际是断的。pi 不赌，这一批调用全部按错误返回，错误信息请模型重新发起。

实测：一个综合任务串起工具​

讲完机制，跑一次真的。演示项目是四个文件的小应用：main.js 读 config.json、调用 utils.js 的格式化函数、输出标签与主版本号。埋了一个类型错误——config.json 里 version 是数字，main.js 却对它调 split。

从标本到方法：一个好工具长什么样​

七个工具讲完了。回头看，它们共享同一套形状：schema 声明参数，description 写说明书，execute 按统一签名干活，一份结果三个去向；哪些工具进入模型视野，由激活集这道闸门控制。

这套形状的每一处设计，本身就在示范怎么写好一个工具。提炼成八条：

  1. **参数 schema 即文档。**字段说明写给模型看，"offset 从 1 开始数"这种细节不靠猜。schema 同时服务声明、校验、文档三件事。
  2. **说明书写边界，也写出路。**read 写清截断上限和续读方法，bash 写清保留尾部和临时文件路径。限制不说，模型撞上才知道；出路不说，撞上了也不知道怎么办。
  3. **错误是给模型的下一句话。**工具不存在、参数不合法、执行失败，都返回说明性错误和补救方向。模型读完错误就知道下一步，这是工具与模型协作的关键接口。
  4. **一份结果，三个去向。**content 给模型，details 给界面，structuredContent 给程序调用方。分开服务不同消费者，不互相污染。
  5. **长任务开两个通道。**接住 signal 响应中止，用 onUpdate 流式回报进展。签名里都留好了，不用是工具的事，不能用是设计的事。
  6. **确定性优先。**edit 的 oldText 唯一匹配、对照原文、不模糊猜测。工具行为可预测，模型才敢规划调用顺序。
  7. **并发需求自己声明。**需要独占就标 sequential，写同一份资源就进互斥队列。工具最清楚自己的约束，别让调用方猜。
  8. **输出有上限。**每个工具都截断并告知续读方式。上下文窗口是所有工具共享的公共资源，谁都不该一个人吃光。
