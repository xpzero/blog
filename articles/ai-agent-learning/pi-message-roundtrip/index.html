一条消息的往返：pi 如何把你的话送给模型，再把模型的话还给你

前文：pi 的上下文装配流程拆解停在界面启动、等待输入的时刻。这一篇从下一秒开始：你输入一句话，按下回车——在第一个字出现在屏幕上之前，pi 内部发生了什么？

为了讲清楚这件事，我在 pi 的源码仓库里真实跑了一次：

输入「读取并分析 pi 的 agent-loop 文件内容」，模型先找到文件、读了它和它的类型定义文件，然后流式输出了分析。

这一次运行产生了 4 个发往模型的 HTTP 请求，我用 whistle 代理抓了下来。本文的去程和回程，都会用这次运行的真实数据做证据。

先看全景。pi 在这条链路上是四层结构，去程和回程走的是两条不同的通道：

去程是一条函数调用链：界面层把消息交给编排层，编排层加工后交给循环层，循环层组装出请求发给模型 API——每一层都是上层"喊"下层干活。回程是一条事件流：模型 API 的流式响应进入循环层后，被翻译成一连串事件，逐层向上广播，界面层只是听众之一。下行靠调用，上行靠事件，这是理解整个往返的钥匙。这四层是本文的叙述分层，对应 pi 仓库的包边界：界面（tui 与交互模式）、编排（coding-agent 核心）、循环（agent 包）、协议（ai 包）。

去程·提交：字符如何变成一次提交​

按下回车之前，你已经能看到 pi 的状态：空闲时底部是安静的输入框，处理任务时有工作指示器在转。所以回车有两种可能的时机——pi 闲着，或者 pi 正忙。同一次按键，消息在这两种时机里的去向一样吗？

到源码里找答案。界面层有个主循环，短得出奇，它的全部工作就是：等一条输入，交给编排层，再等下一条：

while (true) {
    const userInput = await this.getUserInput();
    await this.session.prompt(userInput);
}

这四行循环在任何时刻只可能停在两个位置：getUserInput（等输入），或 session.prompt（等本次对话处理完）。回车落在哪个位置，消息就走哪条路：

  • 空闲：消息直接进入处理流程（下一节的加工）；
  • 运行中：消息进入队列，等模型忙完手头的活再投递。
查看代码：运行中的提交分流（interactive-mode.ts）
// 流式进行中，消息带 steer 行为进入 prompt()
// 这里处理扩展命令（立即执行）、提示模板展开和排队
if (this.session.isStreaming) {
    this.editor.addToHistory?.(text);
    this.editor.setText("");
    await this.session.prompt(text, { streamingBehavior: "steer" });
    this.updatePendingMessagesDisplay();
    this.ui.requestRender();
    return;
}

// 正常提交
// 先把待处理的 bash 组件移入聊天区
this.flushPendingBashComponents();

if (this.onInputCallback) {
    this.onInputCallback(text);
} else {
    this.pendingUserInputs.push(text);
}

流式进行中，回车提交的消息带 steer 标记（转向当前任务）进入排队；正常提交则兑现主循环等待的回调（onInputCallback）。

回头看：你按下回车的瞬间，界面层只做了一件事——把字符串变成一次函数调用的参数。接下来的一切都发生在编排层。

去程·出发前的加工：消息在出发前被组装成什么​

字符串进入编排层后，并不能直接发给模型。它要先过几道关卡，顺序是固定的：

  1. 扩展拦截：如果输入以 / 开头且命中某个扩展注册的命令，这条输入根本不会发给模型——扩展自己处理（比如 /login 打开登录流程）；
  2. 指令模板展开：/skill:xxx 这类指令会展开成完整指令文本，模板也会替换占位符；
  3. 鉴权：确认模型已配置、凭证有效，否则当场报错，消息退回。

我们的「读取并分析 pi 的 agent-loop 文件内容」不含斜杠，三道关卡都直接通过。接下来编排层把这条输入组装成一组出发的消息：用户消息（文本，可带图片）在最前面，如果系统提示（system prompt，发给模型的背景说明）有变化会附带一条系统消息，加上本次运行允许的工具清单。这组消息才是交给循环层的行李。

查看代码：编排层入口的加工链（agent-session.ts，节选）
async prompt(text: string, options?: PromptOptions): Promise<void> {
    // 先处理扩展命令（即使流式进行中也立即执行）
    if (expandPromptTemplates && text.startsWith("/")) {
        const handled = await this._tryExecuteExtensionCommand(text);
        if (handled) return; // 扩展命令已执行，不再发送给模型
    }

    // 发出输入事件供扩展拦截（在指令/模板展开之前）
    const processedInput = await this._runInputHandlers(text, options?.images, /* ... */);
    if (!processedInput) return;
    const { text: currentText, images: currentImages } = processedInput;

    // 展开 skill 指令（/skill:name 参数）和提示模板（/template 参数）
    let expandedText = currentText;
    if (expandPromptTemplates) {
        expandedText = this._expandSkillCommand(expandedText);
        expandedText = expandPromptTemplate(expandedText, [...this.promptTemplates]);
    }

    // 流式进行中，按选项经 steer() 或 followUp() 排队
    if (this.isStreaming) { /* ...排队，直接返回... */ }

    // 校验模型与鉴权 ...
    await this._startRun({ messageType: "user", prompt: expandedText, images: currentImages }, /* ... */);
}

_startRun 内部（_prepareRun）构造出发消息：用户消息、扩展注入的消息、以及系统提示变化时的补丁，一起交给循环层。

回头看：进入编排层的不是"一句话"，出发的也不是"一句话"——是一个包含用户消息、工具清单、系统提示的组合包。

去程·请求的最终形态：四件事​

循环层拿到组合包后，每次发请求前还要做四件事。这四件事决定了你的消息最终以什么形态出现在 HTTP 请求里。

每次请求从活动分支重建消息列表（投影）​

先交代一个贯穿后文的概念：会话中已提交消息的完整序列，pi 源码里叫 transcript（对话记录）。它有两种存在形态：

  • 运行时：内存里的一份消息数组；
  • 落盘后：会话文件里的条目（落盘细节见「回程·归档」）。两种形态中，文件里的记录是权威，内存数组是它的工作副本。

pi 的会话文件是一棵树：你可以回到历史某条消息重新继续，旧分支不删、新分支并存。但模型 API 只接受一条线性的消息序列。所以每次请求前，pi 都从当前位置沿活动分支回溯到根，把这条路径投影成一份“模型可见的消息列表”。关键性质：投影只影响本次请求，会话文件本身不动。

查看代码：从会话文件投影出模型可见消息（session-manager.ts，节选）
export function buildSessionProjection(
    entries: SessionEntry[],
    leafId?: string | null,
    byId?: Map<string, SessionEntry>,
): SessionProjection {
    const path = buildSessionPath(entries, leafId, byId);       // 活动分支：从根到当前叶
    const { thinkingLevel, model } = getSessionContextSettings(path);
    const contextEntries = buildContextEntries(entries, leafId, byId);
    const edits = new Map<string, ContextEditEntry>();
    for (const entry of contextEntries) edits.set(entry.targetId, entry);

    const projectedEntries = contextEntries.map(
        (sourceEntry, index): ProjectedSessionEntry => ({
            sourceEntry,
            messages: projectContextEntry(sourceEntry, edits.get(sourceEntry.id)),
        }),
    );
    return {
        entries: projectedEntries,
        messages: projectedEntries.flatMap((entry) => entry.messages),  // 拍平成线性列表
        thinkingLevel,
        model,
    };
}

源码注释对投影结果的描述："Model-visible messages after context edits"。

自定义消息类型转换为 user 消息​

pi 内部的消息类型比模型 API 的四种角色（system / user / assistant / toolResult）多：bash 执行记录、上下文压缩摘要、分支摘要、扩展自定义消息都是独立的内部类型。发送前有一个统一转换：这些非标准类型一律转成 user 消息（摘要类会包上说明文字），四种标准角色原样保留。我们的主场景里没有这些特殊类型，但这次转换每次请求都会执行。

查看：pi 内部的八种消息类型（convertToLlm 之前）

查看代码：内部消息类型到 API 角色的转换（core/messages.ts，节选）
/**
 * 把 AgentMessages（含自定义类型）转换为 LLM 兼容的 Message。
 */
export function convertToLlm(messages: AgentMessage[]): Message[] {
    return messages
        .map((m): Message | undefined => {
            switch (m.role) {
                case "bashExecution":
                    if (m.excludeFromContext) return undefined;
                    return { role: "user", content: [{ type: "text", text: bashExecutionToText(m) }], timestamp: m.timestamp };
                case "custom":
                    return { role: "user", content: /* ... */, timestamp: m.timestamp };
                case "branchSummary":
                    return { role: "user", content: [{ type: "text", text: BRANCH_SUMMARY_PREFIX + m.summary + BRANCH_SUMMARY_SUFFIX }], timestamp: m.timestamp };
                case "compactionSummary":
                    return { role: "user", content: [{ type: "text", text: COMPACTION_SUMMARY_PREFIX + m.summary + COMPACTION_SUMMARY_SUFFIX }], timestamp: m.timestamp };
                case "system":
                case "user":
                /* ...四种标准角色透传... */
            }
        })
        .filter((m): m is Message => m !== undefined);
}

内部账本比对外口径丰富，出口处统一"翻译"成 API 认识的四种角色。

system 消息折叠到开头​

对话记录里的 system 消息不止开头一条：初始系统提示在头部，运行中插入的工具增删声明也是 system 消息，散布在各自触发的位置。发送前 pi 检查模型目录里的兼容性标志 supportsMidConvoSystemMessages（声明“该模型支持对话中间的 system 消息”），没有这个标志就当 false，按检查结果分三种情况处理：

  • 声明支持对话中间 system 的模型（OpenAI 及多数兼容厂商的模型、Anthropic 新模型）：原样保留散布形态；
  • 未声明支持的模型（pi 默认按不支持处理）：把全部 system 消息重放折叠成开头一条；
  • 系统提示走独立参数的 API（Google、Bedrock 等）：折叠结果从 messages 数组中拿出来，放进请求顶层独立的 system 字段。

折叠不是只保留第一条——那样中途的声明就丢了。具体动作：按时间顺序重放全部 system 消息，内容依次合并、工具增删声明累计出净变化，得到一条“当前生效”的 system 消息放在开头，原位置的那些从请求中移除。折叠是能力协商的缺省值，不是对厂商的判定——未声明不等于服务端不支持。

我们的抓包用的是 GLM（智谱，OpenAI 兼容接口）：pi 的模型目录没给它声明这个能力，所以走了折叠——尽管实测 GLM 接口本身接受中途 system 且模型会遵循。下面会直接看到 system 是 messages 的第一条。

工具清单靠重放声明​

请求顶层的 tools 列表不是直接取"当前可用工具"，而是逐条重放对话记录里所有工具增删声明算出来的结果。为什么绕这一道：会话可以重启恢复、可以从旧分支继续，"当前状态"无法说明模型当时被告知过哪些工具，只有重放对话记录里的声明才能精确复现。这也是本文反复出现的一个原则的具体化：发给模型的，永远是对话记录的投影。

回程·流式：模型的话如何变成"一条消息"​

请求发出后，模型 API 以 SSE（Server-Sent Events）流式返回。响应不是一整块，而是一串帧，每一帧只携带一小段增量。这次运行的最终回复包含这样的帧：

data: {"choices":[{"delta":{"role":"assistant","content":"Agent"}}]}
data: {"choices":[{"delta":{"role":"assistant","content":"Message"}}]}
data: {"choices":[{"delta":{"role":"assistant","content":"→"}}]}

协议层的适配器收到帧后，把增量追加进正在生长的消息，每来一个增量就发出一个事件，携带累积到当下的完整 partial（部分消息）。循环层拿到 partial 后替换对话记录末尾那条正在生长的消息——不是往尾部追加，而是整体替换为“到目前为止的完整版本”。这条“正在长大的消息”始终保存在对话记录的末尾位置，它的每个版本对上层都是一个完整快照。

查看代码：流式接收与 partial 替换（agent-loop.ts，节选）
for await (const event of response) {
    switch (event.type) {
        case "start":
            partialMessage = event.partial;            // 第一个 partial：空消息
            context.messages.push(partialMessage);      // 占住对话记录末尾
            await emit({ type: "message_start", message: { ...partialMessage } });
            break;

        case "text_delta": /* text/thinking/toolcall 的增量都走同一路径 */
            partialMessage = event.partial;
            context.messages[context.messages.length - 1] = partialMessage;  // 原地替换
            await emit({ type: "message_update", assistantMessageEvent: event, message: { ...partialMessage } });
            break;

        case "done":
            const finalMessage = await result();        // 完整定稿
            context.messages[context.messages.length - 1] = finalMessage;
            await emit({ type: "message_end", message: finalMessage });
            return finalMessage;
    }
}

三种生命周期事件在这里定型：message_start（消息开始）、message_update（每个增量一次，携带完整快照）、message_end（定稿）。

流式结束不等于回程结束。如果这条回复里带工具调用——我们这次运行的第一轮回复就是"我要执行 find 命令找文件"——循环层会执行工具、把结果追加进对话记录，然后带着工具调用和结果重新投影、发出下一个请求。下面是第二次请求里 messages 数组的真实增长：

查看抓包：请求② 工具调用与结果进入消息序列（whistle 实录，节选）

assistant 的工具调用（tool_calls）和工具执行结果（role: "tool"）作为一对消息进入序列，随第二次请求一起发回给模型。这次运行共发生 3 次工具调用（bash 跑 find 定位 → 读 agent-loop.ts → 读 types.ts）。第一个调用有点绕：模型要找文件，而 find 工具默认未激活，只能借 bash 执行 find 命令——若手动开启 find 工具，这里会是一次独立的工具调用。最后一个请求的回复是纯文本，没有工具调用，循环就此收尾。

回头看：从模型视角，"一条消息"是一串增量帧；从 pi 视角，它始终是对话记录末尾那条不断被替换的完整消息。工具调用则驱动"模型请求 → 执行工具 → 模型请求"的循环，直到模型不再要求执行任何工具。

回程·归档：每条消息定稿即落盘​

事件流向上广播的路上，编排层做两件事。

第一件：事件到达界面层之前，会先路过扩展系统——扩展可以监听这些事件做自己的事。

第二件：每条消息收到定稿事件（message_end）的瞬间，就被写入会话文件。会话文件是 JSONL 格式，每行一个条目，每个条目记着自己的父条目——所有条目连成一棵树，就是前面“投影”的原料。落盘发生在定稿的当下而不是对话结束时，所以无论对话进行到哪一步被中断，已发生的消息都已在盘上，重启后可以完整恢复。

查看代码：定稿即落盘（agent-session.ts，节选）
// 处理会话持久化
if (event.type === "message_end") {
    let entryId: string | undefined;
    if (event.message.role === "custom") {
        entryId = this.sessionManager.appendCustomMessageEntry(/* ... */);
    } else if (
        event.message.role === "system" ||
        event.message.role === "user" ||
        event.message.role === "assistant" ||
        event.message.role === "toolResult"
    ) {
        entryId = this.sessionManager.appendMessage(event.message);  // 写入 JSONL 树
    }
    if (entryId) this._entryIdsByMessage.set(event.message, entryId);
}

四种标准角色消息在定稿事件里追加进会话文件；会话文件每个条目带 id 和 parentId，构成树。

回头看："对话记录"不只是一个内存概念——它的持久形态就是会话文件，每条消息定稿的瞬间就从内存走向磁盘。

回程·上屏：从事件到屏幕像素​

最后一段路。界面层订阅编排层的事件流，按三种事件处理：

  • 消息开始事件（assistant）：为这条消息创建一个渲染组件；
  • 更新事件：把携带的完整快照交给组件重画；
  • 定稿事件：做最后一轮处理——组件带最终内容重画并退出流式状态，工具卡片随之定稿。

这也是同一个定稿事件出现在两处的原因：编排层听到它落盘（上一节），界面层听到它收尾，一次广播、各取所需。

工具卡片的一生：

  1. 模型流式输出工具调用的参数时（参数可能要分好几帧才传完），界面层发现消息里出现了新的工具调用，就立刻创建对应的工具卡片——此时卡片上只有工具名和不完整的参数，整体呈待定底色；
  2. 参数流完，参数定形，工具开始执行；
  3. 工具执行的事件陆续到达（开始、中间输出、结束），卡片随之更新；
  4. 结果回来，底色切换为成功色或错误色，卡片定稿。

你在屏幕上看到一张工具卡片从灰暗到点亮的全过程，背后就是这三个工具执行事件。

你自己那条消息的显示，走的也是事件回流。界面层从不直接渲染“刚提交的字符串”——用户消息同样以消息开始事件的形式回到界面层才上屏。正因为如此，print 模式、JSON 模式、RPC 模式可以和终端界面共用完全一样的核心：核心只发事件，不认识任何界面。

最后一个问题：流式期间每秒可能到达几十个更新事件，每个都触发一次全量重画，界面为什么不闪？因为渲染请求是节流合并的——界面层有最小渲染间隔，间隔内到达的所有更新请求合并到下一帧；而每帧的绘制走差分渲染，只重绘发生变化的终端单元格。

查看代码：渲染节流（tui.ts，节选）
requestRender(force = false): void {
    if (force) { /* ...立即渲染... */ return; }
    if (this.renderRequested) return;      // 已有排程，合并
    this.renderRequested = true;
    process.nextTick(() => this.scheduleRender());
}

private scheduleRender(): void {
    const elapsed = performance.now() - this.lastRenderAt;
    const delay = Math.max(0, TuiBase.MIN_RENDER_INTERVAL_MS - elapsed);  // 最小渲染间隔
    this.renderTimer = setTimeout(() => {
        /* ...doRender：差分渲染，只输出变化的单元格... */
    }, delay);
}

回头看：屏幕上的每一次变化，都是事件流的终点；而"看起来流畅"，是节流合并与差分渲染的功劳。

收尾：一次完整往返​

把全部环节按时间排开，就是这次运行（3 次工具调用、4 个请求）的完整时序：

四层的职责一句话总结：

层职责认识谁
界面层收集输入、渲染事件只认识编排层
编排层会话的编排与会话数据的存取（加工、排队、落盘、投影）认识循环层
循环层循环推进一次运行（发请求、执行工具、发事件），附带循环所需的状态与队列只认识模型 API 抽象
协议层把请求翻译成具体厂商的 HTTP 协议不认识 pi

这张表能解释三个日常体验：

  1. 模型还在输出时，你为什么还能打字、还能回车——输入通道和渲染通道是分离的，排队机制让运行中的提交进队列而不是阻塞界面；
  2. 中止后，排队的消息为什么退回输入框——退回的是队列里尚未投递的消息（已投递的留在对话里），它们与你正在打的草稿拼在一起放回输入框，什么都没丢；
  3. print / JSON / RPC 模式为什么“免费”拥有同样的能力——核心只发事件，多一个界面只是多一个听众。
