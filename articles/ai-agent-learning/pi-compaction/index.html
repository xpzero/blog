pi 如何压缩上下文：从触发判断到继续对话

周期2026年10月28日阅读 18 分钟

pi 执行一次命令，工具返回了大段日志。模型还要继续分析，下一次请求也会带上这些新增内容：如果上下文快装不下了，这轮任务怎么继续？

pi 会在请求边界等位置检查上下文。达到阈值时，它把较早历史整理成摘要，保留近期消息，再用更新后的上下文继续请求。原始记录仍保存在会话文件中。

先用一个示意流程把这件事连起来：

这里的“上下文”，指模型处理下一次请求时携带的信息。压缩改变的是后续请求使用的消息内容，会话文件中的历史仍可回溯。pi 从会话记录生成当前消息视图的过程叫投影。

本文基于 earendil-works/pi 仓库 8efd314f 提交的源码走读，按实现推断执行流程。排障对话与 token 数字用于示意。

什么时候检查：沿着一次运行看​

工具返回日志，只是上下文增长的一个位置。用户开始新任务前，会话可能已经切换过分支。模型完成回答后，新增回复也可能让上下文接近上限。因此，自动检查分布在三个阶段。

把一次用户操作放到时间线上：

运行准备时，检查的是已有历史。 这一步发生在 agent_start 之前，新提交的用户消息随后才被组装进去。它能处理上次中止后留下的上下文等情况。

准备下一次模型响应时，检查的是当前投影。 回到开头的例子：模型决定运行命令时，尚不知道命令会返回多少日志。工具结果回来后，pi 在下一次请求前重新检查，把这部分新增内容算进去。这里接在下一回合的准备流程上，压缩完成后更新请求上下文，执行继续向前。

底层运行结束后，会话还有收尾工作。 agent_end 表示底层循环结束，会话层随后还会判断错误恢复、压缩和排队消息。需要继续时，它会重新进入运行，最后才发出 agent_settled。

因此，用户看到“模型停止输出”，和“会话已经空闲”之间，可能还有一次压缩。自动压缩由这些执行边界触发，空闲时停在输入框里等待本身不会定时触发检查。

手动 /compact 是另一个入口，由用户主动发起。它与自动压缩的后续行为，放到执行过程之后比较。

根据什么判断：已有计量，加上新增内容​

知道检查位置后，还需要一个读数：当前上下文大约有多少 token？token 是模型处理文本等内容时使用的计量单位。读数偏高会过早触发压缩，偏低则可能让下一次请求超出窗口。

模型响应中的 usage 记录一次调用的用量，包含输入与输出计量。新 usage 已经计入当次请求携带的历史，历次 usage 不能累加，否则相同历史会被重复计算。

pi 优先采用仍适用于当前历史的有效 usage，需要时再估算它之后新增的内容。编辑或压缩可能让旧计量失效，中止、报错或全零计量则可能需要回扫。得到可用读数后，再与阈值比较：

当前上下文 token 数 > 模型上下文窗口 - reserveTokens

默认 reserveTokens = 16,384

reserveTokens 是提前触发压缩的预留量。取数逻辑决定了这条触发线是否有意义：既要算上新增内容，也要避免继续采用已经过时的计量。

展开取数逻辑：有效 usage、编辑与压缩的顺序，以及中止后的回扫

先区分两个对象：最后一条助手消息可能刚刚报错或被中止，最近一份有效 usage则可能在更早的消息上。估算器回扫时，会跳过中止、报错和计量全零的助手响应。

下面分四种场景解释。数字均为示意，各条时间线都以检查前没有发生额外的历史变更为前提。它们也可能组合出现，例如中止之前刚发生过压缩，此时回扫找到的计量仍需核对压缩边界。

历史未被编辑或压缩：采用有效计量，必要时补增量。 助手刚完成响应，之后没有新增内容时，可以直接采用它的 usage。工具调用则不同：模型发出调用时的 usage 还没有计入随后返回的工具结果。

助手回复（usage = 70,000）→ 检查
读数：70,000

助手发出工具调用（usage = 70,000）→ 工具返回日志（估算 18,000）
                                       ↓
下一次响应前检查：70,000 + 18,000 = 88,000

下一次响应前的估算器把有效 usage 作为基准，再估算后面的新增消息。运行准备与收尾的直接取数分支，则直接采用传入助手消息的 usage。是否补增量要结合检查位置判断。

发生过编辑或压缩，助手响应在其后：新计量可以作基准。 上下文编辑通过 context_edit 记录省略或替换消息，压缩通过 compaction 记录摘要与保留边界。二者都可能改变下一次请求携带的历史。

先编辑，再得到新响应：
  省略旧日志 → 用编辑后的历史请求模型 → a2 回复（usage = 52,000）
  读数：52,000 + a2 之后新增内容的估算量

先压缩，再得到新响应：
  追加压缩记录 → 用“摘要 + 近期消息”请求模型 → a2 回复（usage = 18,000）
  读数：18,000 + a2 之后新增内容的估算量

a2 已经反映历史变更的结果。如果它之后没有新增内容，增量就是零。这里的 a2 来自后续对话请求，生成摘要的调用另行记录 usage。

助手响应在最近一次编辑或压缩之前：旧计量失效。 会话保留了助手消息，也保留了它当时的 usage。修改投影不会重新计算消息里已有的计量字段。

先回复，再编辑：
  a1 回复（usage = 70,000）→ 省略旧日志 → 检查
  旧计量包含已省略的日志，按当前投影重估。

先回复，再压缩：
  a1 回复（usage = 90,000）→ 追加压缩记录 → 检查
  当前上下文：摘要 + 保留的 a1
  a1 原文仍在，旧计量却包含已被摘要替代的历史。

这里要区分检查位置：

  • 下一次响应前，投影估算核对有效 usage 与当前分支中最近一次编辑或压缩的顺序。旧计量在变更之前，就按当前投影重估。
  • 运行准备与收尾会检查当前助手消息，以及回扫取数时找到的 usage 来源。任一检查发现对应消息早于最近一次压缩，就跳过本次阈值判定，避免刚压完又被旧读数触发。
  • 运行准备与收尾通过前置检查后，若当前投影包含上下文编辑，则进入同一个投影估算器，验证计量是否仍然适用。

重估使用当前投影中的内容，省略的消息不再参与，被替换的消息按新内容计算。文本主要按字符数除以 4 估算，图片等内容另有估算规则。

用户中止、模型报错或计量为零：回扫有效 usage，并估算后续内容。 用户按 Esc 中止时，本次运行的收尾不会据此立即触发压缩。用户再次提交消息后，运行准备允许检查被中止的助手响应。

已有 a1（有效 usage = 70,000）→ 用户补充问题 → a2 生成到一半
                                                 ↓ 用户按 Esc
本次运行结束：跳过压缩检查，保留 a2 已生成的部分正文
                                                 ↓ 用户再次提交
运行准备：检查 a2，估算器向前寻找有效 usage

估算器跳过 a2 的计量，越过没有 usage 的用户消息，找到 a1。a1 之后保留下来的消息正文仍然需要估算：

计量基准：a1 的 usage = 70,000
后续增量：用户补充问题 + a2 的部分正文，假设估算为 2,000
当前读数：70,000 + 2,000 = 72,000

这一步发生在新提交的消息组装之前，增量只覆盖检查时已有的内容。普通错误响应或全零 usage 也会触发回扫估算。整段上下文找不到有效 usage 时，估算全部消息；找到的 usage 若已跨过编辑或压缩边界，则按前面的边界规则处理。

下面是相关代码节选，省略上下文并补充中文注释。compaction.ts 负责用量换算、阈值判断与增量估算：

export function calculateContextTokens(usage: Usage): number {
    return usage.totalTokens || usage.input + usage.output + usage.cacheRead + usage.cacheWrite;
}

export function shouldCompact(contextTokens: number, contextWindow: number, settings: CompactionSettings): boolean {
    if (!settings.enabled) return false;
    return contextTokens > contextWindow - settings.reserveTokens;
}

// estimateContextTokens() 内，省略无有效 usage 时的整份估算分支
// 已有计量覆盖的消息不再估算，只累计之后的增量
const usageTokens = calculateContextTokens(usageInfo.usage);
let trailingTokens = 0;
for (let i = usageInfo.index + 1; i < messages.length; i++) {
    trailingTokens += estimateTokens(messages[i]);
}

return {
    tokens: usageTokens + trailingTokens,
    usageTokens,
    trailingTokens,
    lastUsageIndex: usageInfo.index,
};

触发以后：生成摘要，再更新上下文​

继续用排障对话作示意。工具结果返回后，pi 判断需要压缩。接下来先准备摘要材料，再决定哪些消息继续保留原文。

压缩前：
  早期需求与排查记录 + 已完成的工具调用 + 近期分析与提问

处理：
  较早历史 → 整理目标、进展、约束与后续事项
  近期消息 → 保留原文

压缩后：
  压缩摘要 + 保留的近期消息

近期消息的保留量由 keepRecentTokens 控制，默认是 20,000 token。它与触发线上的 reserveTokens 用途不同：前者用于选择保留范围，后者用于提前触发压缩。

切点还要满足消息结构要求。例如，工具调用与工具结果存在对应关系。如果切在一轮任务中间，摘要需要补上被截去的那一轮前半段，帮助模型理解保留下来的后半段。具体切点算法见前文：pi 的会话：一棵追加式事件树，和它的投影。

准备好材料之后，执行流程如下：

entry 是会话文件中的一条记录。compaction entry 保存摘要和保留边界，投影时据此组合“摘要 + 近期消息”。此前的原始消息仍保存在文件中，读取会话时也能还原这次压缩的作用。

默认摘要生成会单独调用模型，有自己的中止信号与重试策略。切点拆开一轮对话时，可能分别生成历史摘要与轮前缀摘要，再合并结果。压缩本身因此也会消耗 token，并且可能等待、失败或被中止。

摘要请求的 usage 描述的是生成摘要的调用。它可以随压缩记录保存，后续对话请求的大小则仍按当前投影及相应计量判断。

压完以后：接下来继续什么​

相同的摘要生成机制，接在不同入口后面，后续动作也不同。

场景压缩后的主要去向
运行准备时达到阈值继续组装新消息，启动用户这次请求
下一次模型响应前达到阈值用更新后的上下文继续请求
运行收尾时达到阈值处理排队消息或完成会话收尾
可恢复的溢出或截断尝试使用更新后的上下文继续运行
手动压缩完成压缩，被中止的回合由用户决定如何继续

模型已经报错时，怎样恢复​

提前检查依赖估算，模型服务仍可能返回上下文溢出错误。收尾检查识别这类错误后，会尝试压缩并恢复。部分满足恢复条件的长度截断，也使用这条路径，原因标记同为 overflow。

恢复时，先处理那次选定的失败响应：

收到可恢复的失败响应 → 追加 context_edit，持久化省略编辑
                              ↓
重新投影，排除失败响应及关联工具结果 → 尝试压缩
                                      ├─ 成功 → 继续请求模型
                                      │           ↓ 再次溢出或同类截断
                                      │       报告恢复失败
                                      └─ 失败或取消 → 结束此次恢复

context_edit 是改变投影的一种会话记录。这里将 replacement 设为 null，表示省略目标消息。失败响应依然保存在文件里，后续投影会应用这条编辑。

省略编辑先持久化，压缩随后才开始。 如果摘要生成失败，前面的编辑仍然有效。因此，这条恢复路径不能理解为“压缩失败就回到所有操作之前”。

这种压缩后恢复的机会限制为一次，避免反复压缩、反复发送同一轮请求。再次失败时，pi 发出带错误信息的 compaction_end，扩展侧收到 session_compact_failed，把后续决定交还用户。

还有一种情况：助手响应已经成功完成，但用量判断显示上下文超限。这时保留已完成的回复，只执行压缩，供后续请求使用。

错误恢复会核对产出响应的模型与当前选择是否匹配，也会检查该响应及其 usage 是否仍适用于当前投影。这样，换模型或编辑历史后，旧响应的错误与读数不会直接触发不适用的恢复。

// _checkCompaction()：已确认需要恢复，省略判定与再次失败的通知分支
this._overflowRecoveryAttempted = true;
this._omitRecoveryAttempt(assistantMessage, toolResults); // 先持久化省略编辑
const retry = await this._runAutoCompaction("overflow", willRetry);
if (retry) this._failedResponse = assistantMessage;
return retry; // 交给外层决定是否继续运行

// _omitRecoveryAttempt()：省略记录 ID 查找与一致性校验
for (const targetId of targetIds) {
    if (!targetId) continue;
    const editId = this.sessionManager.appendContextEdit(targetId, null);
    const entry = this.sessionManager.getEntry(editId);
    if (entry) this._emit({ type: "entry_appended", entry });
}
this._refreshFinalizedContext(); // 省略编辑写入后，立即更新投影

上面合并了调用处与被调用方法的节选。省略编辑及投影刷新完成之后，才进入等待摘要的压缩流程。

手动压缩与摘要失败​

用户通过 /compact 主动发起压缩，最终进入会话的 compact() 接口。这个接口先中止当前 Agent 操作，再开始压缩，也不自动恢复被它中止的回合。

历史太少、没有可摘要部分时，会返回 Nothing to compact (session too small)。当前分支末尾已经是压缩记录时，会返回 Already compacted。

摘要生成阶段失败或被中止时，只要还没有执行追加步骤，就没有新的 compaction entry。已有历史继续保留，调用方通过结束事件和失败通知得知结果。若前面已经执行了溢出恢复的省略编辑，那些记录也继续保留。

写入成功的压缩记录与失败通知用途不同：前者影响会话恢复后的投影，后者告诉当前界面和扩展这次操作的结果。

查看代码：手动压缩先中止当前操作（core/agent-session.ts，节选）
async compact(customInstructions?: string): Promise<CompactionResult> {
    await this.abort(); // 等待当前操作中止，再启动压缩
    this._compactionAbortController = new AbortController();
    this._emit({ type: "compaction_start", reason: "manual" });
    // ...压缩准备、摘要生成与错误处理省略
}

回到开头的大段日志：pi 在下一次请求前重新检查容量，必要时生成摘要、追加压缩记录，再从这些记录生成新的上下文继续分析。历史是否保留、模型下一次看到什么、失败后接着做什么，分别由会话记录、投影和运行编排负责。

树导航时还可以生成分支摘要，用来把离开分支上的工作带到新位置。它与当前对话达到容量阈值的触发场景不同，相关流程见前文：pi 的会话：一棵追加式事件树，和它的投影。
