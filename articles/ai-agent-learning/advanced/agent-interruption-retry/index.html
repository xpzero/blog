Agent 运行中断与有限重试：停止、部分回复与模型降级

柯寒2026年9月29日阅读 11 分钟

停止请求如何持久化，部分回复如何保留，模型失败何时可以重试或降级，以及为什么连接结束不等于运行结束。

一个能调用工具的流式 Agent 运行起来之后，很快会遇到三个绕不开的问题：

  1. 回答已经跑偏，用户点击停止——此时模型还在生成，工具可能马上要执行，后端应该做什么？
  2. 模型服务返回限流或临时错误——直接把错误抛给用户，还是悄悄重试？重试到什么时候？
  3. 生成到一半连接断了——已经生成的那半段回答，是丢了重来，还是想办法保住？

这三个问题的共同点是：浏览器的连接只是观看执行的窗口，不是执行本身。断开连接、点击停止、服务报错，都不会让已经发生的事实消失。本文介绍一套处理这些情况的后端机制：给一次消息处理划定边界，把停止意图和部分回复持久化，对模型失败做有限重试和降级。

例子来自一个用 Python FastAPI 后端、OpenAI SDK 流式接口、SSE 向网页推送事件的 Agent 项目。

一次消息的处理是一个运行​

用户发一条消息，后端往往要请求模型好几次：模型先选择工具，工具执行完，再请求模型生成下一段回答。把这整段处理叫作一次运行（Run）：从后端接受用户消息开始，到这条消息完成、被停止或失败结束。

运行和连接是两个生命周期。用户刷新页面或切换会话时，SSE 连接断了，但后端线程还在继续执行。反过来，模型流结束了，运行也未必结束——可能还有业务结果需要核实。把两者分开，是后面所有机制的基础：

接受消息时，路由在一个数据库事务里保存用户消息、创建 Run 并占用会话；然后才启动工作线程。如果同一会话已有活跃运行，第二个聊天请求会收到 HTTP 409。这个检查放在后端而不是只禁用页面的发送按钮，因为用户可能开两个页面同时提交。

Run 有两个活跃状态：

  • running：模型和工具还在处理这条消息。
  • finishing：停止意图已登记，或模型处理已结束但还有业务结果待核实。

终态有五种：completed、stopped、failed、timed_out、limit_reached。注意 completed 只表示"这条消息处理完毕"，不保证业务操作全部成功——业务结果要看操作记录（下一篇文章展开）。终态与释放会话在同一个收尾事务里落定；释放之后，会话才能接受下一条消息。

停止是登记意图，不是掐断线程​

收到停止请求时，后端不能直接杀掉工作线程——正在写数据库的事务、执行到一半的工具都可能留下不一致的状态。可行的做法是协作式停止：

  1. 停止接口先在数据库里持久化 stop_requested 标志；
  2. 工作线程在安全边界上检查这个标志——读流 chunk 的间隙、每个工具执行前后、重试退避的等待中；
  3. 检查到标志就抛出停止信号，由上层保存已有事实并收尾。
server/agent/loop.py（节选）
def _check_stop(should_stop):
    if should_stop is not None and should_stop():
        raise RunStopped()

这样能保证停止之后不再发起新的模型请求、不再启动新的工具，但不能瞬间打断一个已经阻塞的网络读取或正在执行的工具。只有当前流片段返回、工具执行完，线程才有机会看到标志。

有一个竞争窗口值得注意：工具启动前要先检查"没有停止"，然后才登记执行——停止请求可能恰好插在这两步之间。解决办法是把停止标志、运行状态、截止时间和工具登记放到数据库的同一个原子判定点里检查，让"谁先取得启动资格"有确定的答案。

但这只解决资格问题，不能撤销已经开始的副作用。文件已经覆盖，停止不会恢复旧文件；订单请求已经发出，停止也不能证明订单未创建。停止承诺的是"不再开始新动作"，不是"回到停止之前"。业务适配器支持取消时可以尝试取消，但结果仍要作为事实保存下来。

因此，点击停止之后页面不会立刻解锁输入框。停止接口最多短暂等待收尾，然后返回 ended 或 processing；有待核实的业务操作时，会话继续保持占用，直到结果确认或截止时间耗尽。

半截回答也要持久化​

如果生成的文字只存在网页内存里，停止或刷新之后就会消失。所以后端在收到每个 text_delta 事件时，先把它累积写入数据库的同一条助手消息，再把事件发给浏览器：

server/api/chat_stream.py（节选）
if event["type"] == "text_delta":
    text_parts.append(event["text"])
    assistant_message_id = database.upsert_partial_assistant(
        run_id, session_id, user_message_id, "".join(text_parts)
    )

生成期间这条消息的状态是 incomplete；正常完成后转为 finished。被停止或中断时，它保持 incomplete，页面显示"回复未完成，已按中断时内容保存"。

注意区分两个层次：incomplete 是消息状态，回答这段文字是否完整；stopped 是运行状态，这次处理为什么结束。半段回答能告诉用户"当时说到哪里了"，但不能证明任何业务操作成功——操作成功与否要看操作事实，这是下一篇文章的主题。

下面是实际运行中的效果：生成一篇长文的中途点击停止，页面保留了已生成的部分正文，并明确标注保存方式，而不是丢弃或假装完整：

模型失败：哪些能重试，重试几次​

模型请求会失败：网络超时、HTTP 429 限流、5xx 服务错误，也可能是不必重试的 401、参数错误。重试策略要先回答两个问题：这是什么类型的失败，以及这次尝试已经产生了什么。

第二个问题更关键。流式请求收到第一个 chunk 之后再断开，页面上可能已经显示了文字，模型可能已经开始生成工具调用参数。此时原样重发一次，用户会看到两份答案交错，半截的工具参数也可能与重试后的新参数冲突。所以重试要满足一个前提——本次尝试还没有产生任何可见输出：

server/agent/loop.py（节选）
except Exception as error:
    if (emitted or text_parts or partial_tool_calls or
            not (_retryable(error) or isinstance(error, ModelRequestTimeout)) or
            failures + 1 >= max_attempts):
        raise
    failures += 1
    # 在剩余预算内退避，再次尝试

emitted 记录已发出的事件，text_parts 和 partial_tool_calls 记录已收到的正文或工具参数碎片——哪怕碎片还没聚齐、工具还没执行，也不能当作"什么都没发生"。按这个规则分类：

失败类型处理
网络连接错误、请求超时无可见输出且预算充足时重试
HTTP 429、5xx同上，有限重试
401、403、请求参数错误不可重试，结束本次处理并交代错误
已有可见文字或工具参数碎片后的流错误不原样重试，保留部分事实

这是本地的防重复规则，不保证供应商那边没有处理或计费——它是为了页面不出现两份答案，不是为了省 token。

实际运行中，这条规则的效果是：流在正文已经输出大半时超时，页面保留已生成的部分正文并如实展示错误，而不是从头重试让用户看到两份答案：

重试要有预算​

无限重试等于把故障变成雪崩。这套实现给了一次运行内明确的预算：

预算限制
一次 Run 的总时限300 秒
逻辑模型请求最多 10 次
每个逻辑请求的实际尝试最多 3 次
单次模型请求60 秒，且不超过剩余 Run 时间
重试退避0.25 秒起指数增长，封顶 1 秒

"逻辑请求"是一次生成需求，比如工具执行完之后向模型请求总结；"实际尝试"是它的失败重试。SDK 自带的重试被关掉，由 Agent 循环统一计数和控制，发送前把计数写入数据库。

退避用的是固定的短指数序列，不解析服务方返回的 Retry-After。如果服务场景要求遵守对方的等待时间，需要额外实现，而且仍要受总时限约束。

主备模型共用预算​

配置备用模型后，前两次尝试用主模型，最后一次切换到备用模型。切换不重置尝试上限，也不延长时限——降级是预算内的补救，不是新的一轮。

示例项目配置主模型 glm-5.3、备用模型 glm-4.6，都是启动时从配置读取的；验证时在主模型连续失败的场景下，第三次请求由备用模型完成，页面正常收到完整回答。有一个容易忽略的细节：备用模型自己也可能连接失败，这时候和主模型失败走同一条路径处理，而不是再换回主模型无限循环。

连接结束不等于运行结束​

POST 聊天流里的 done 事件表示"回答已产生"，error 表示"发生错误"。但它们只描述了模型流的结局，不能证明业务核实也完成了——有待确认的操作存在时，模型流结束，Run 仍处于 finishing。

所以前端刷新或重进会话时，不是看聊天流有没有结束，而是：先读历史；如果会话仍被占用（不能发送），就连接一个只读的恢复流，跟随运行直到它发出 stream_end——一个专门的终态信号，表示运行已落定、事件已排空。恢复流的机制（快照、事件回放、缓存边界）在下一篇文章展开。

到这里可以回答开头的问题了。点击停止：后端持久化停止意图，在安全边界停止发起新动作，半截回答按中断时内容保存。模型限流：在无可见输出的前提下有限重试，预算耗尽前降级到备用模型。连接断开：执行仍在后端继续，事实都已落库，重连后按数据恢复展示。贯穿所有机制的是同一条原则——连接可以断，意图要落库，已发生的事实不能抹掉。

版本与验证说明：本文机制依据 demo-agent 项目的实现（分支 feat/interruption-retry-recovery，基线提交 250b20f 及其后的中断恢复改动）。行为经后端与前端自动化测试覆盖；限流、断流等故障场景通过本地故障网关注入验证，未在真实供应商故障下逐一复现；业务操作使用本地演示适配器，未连接真实订单系统。
