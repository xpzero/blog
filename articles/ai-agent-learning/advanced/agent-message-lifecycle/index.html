生成到一半：Agent 消息的停止、中断与恢复

柯寒2026年10月2日阅读 11 分钟

流式 Agent 生成到一半时，刷新、点停止、后端崩溃各会发生什么：消息状态机、过程落库、双层停止意图、resume 三步裁决与执行线程的分离。

一个能调用工具的流式 Agent 上线后，用户很快会做出三件事：生成中刷新页面、生成中点击停止、以及后端进程不知什么时候崩溃重启。这三件事分别对应三个问题：

  1. 刷新后，那半截回答还在吗？正在生成的部分能接上吗？
  2. 点了停止，模型立刻停了吗？已经执行过的工具算不算数？
  3. 后端崩了重启，那条没回完的消息算什么？

这三个问题的共同背景是：浏览器的 SSE 连接只是观看执行的窗口，不是执行本身。想清楚"什么事实落在数据库、什么状态只在内存里"，三个问题就都有了确定的答案。本文用 Python FastAPI 后端、SQLite、SSE 推送的前端 Agent 项目做例子，逐个展开。

消息的状态从哪来​

用户发一条消息，后端往往要请求模型好几次：模型先选择工具，工具执行完再请求模型生成下一段，直到给出最终答复。这整段处理需要身份——"这条助手消息正在生成中"。最常见的做法是新建一张执行记录表，把执行状态和消息分开。但另一种更轻的做法是把执行状态直接内联在助手消息行上，四个字段各管一件事：

  • status：这条消息完没完。只有 unfinished（生成中）和 finished（已落定）两个值；
  • finish_kind：以什么方式结束。done（自然完成）、stopped（用户停止）、error（编排错误）、max_turns（轮次上限）、interrupted（进程崩溃后判死）五种终态；
  • deadline_at：这一轮最多允许执行到什么时候。超过就不再等它——这是崩溃后兜底的判死依据；
  • stop_requested：用户是否说过"停"。它是停止意图的字据，后面会看到判死逻辑靠它区分"谁的责任"。

发送消息的同一时刻，后端就预建这条助手消息行（status='unfinished'、写入 deadline_at），无一例外。用户消息和助手消息同时出现，之后的所有生成过程都挂在助手消息上。状态机如下：

两条规则贯穿始终：

  • 终态单向：unfinished → finished 一次性落定，之后任何写入都是 no-op，迟到的事件一律丢弃；
  • 锁与终态同体：会话内存在 unfinished 行就拒绝新消息（HTTP 409），终态落定即解锁。没有第二把锁对象，前后端读同一个事实。

生成中的内容存在哪​

只有最终答案的 content 字段不够用。停止、崩溃、刷新三个场景都需要回答"已经生成到哪里了"，而 content 要等终态才写。过程需要一个真相源：一张 message_fragments 表，挂在助手消息上，每个片段产生即落库——一段文字、一次工具调用、一次工具结果、最后的终态，各是一条记录：

message_fragments
    message_id   -- 挂在哪条助手消息上
    seq          -- 消息内单调递增：回放顺序，也是去重键
    type         -- text | tool_call | tool_result | terminal
    status       -- fragment 级状态：tool_call=running，tool_result=finished
    payload      -- 片段全文 JSON

seq 由 SQLite 在 INSERT 语句内部发号（子查询取当前最大值加一，RETURNING 带回），不依赖进程内计数器。一条消息的片段只有一个写者（会话锁保证），数据库写本身串行，所以不需要应用层协调。

后端推给浏览器的不是模型的原始流，而是项目自己的 SSE 事件协议。在浏览器 DevTools 的 Network 面板里选中 chat 请求，EventStream 视图能看到后端实际返回的每一帧：

从上到下依次是 user_message（携带已落库的用户消息 ID）、若干条 text_delta（每条是一个 fragment 级的正文段）、最后的 done（携带助手消息 ID）。前端拿到的就是这些事件——恢复回放时重放的也是同一序列，所以刷新前后页面行为一致。

执行线程每产生一个事件做两个动作，顺序固定：

server/api/chat_stream.py（节选）
seq = self.database.append_fragment(self.message_id, type_, payload)
active_runs.publish(self.message_id, payload, seq)   # 带着库发的 seq 进内存广播

先落库、后广播——内存里的每个事件必然已在数据库，两层永不分叉。content 与 fragments 的分工：一个管结果（终态时从 text 片段按 seq 拼出全文，一次写入），一个管过程。生成期间 content 为空，页面读到"content 为空 + status=unfinished"时，知道该去接实时流而不是展示半截静态文本。

点停止：意图的两层状态​

后端不能直接杀掉执行线程——正在写数据库的事务、执行到一半的工具都可能留下不一致的状态。可行的做法是协作式停止：执行线程在安全边界上检查信号——读模型流的间隙、每个工具执行前后。检查到就停止发起新动作，保存已有事实并收尾。

但"停止意图"存在哪，决定了几个边角场景的语义。只用内存信号：点停止的同一瞬间进程崩溃，信号随进程消失，重启后没人知道用户说过停。只用数据库标志：活着的执行线程每次读流都要查一次库，代价不合理。所以意图分两层：

server/api/routes.py（stop 路由，节选）
result = database.request_stop(session_id)   # 第一层：stop_requested=1 落库（字据）
stop_signals.set(session_id)                 # 第二层：内存 Event 置位（喊话）
  • 库里的字据（stop_requested）：不怕崩溃。判死逻辑读它来决定终态语义——有字据收口为 stopped（用户确实说了停），没有收口为 interrupted（它自己断的）；
  • 内存的喊话（threading.Event）：活着的执行线程在安全边界检查它，毫秒级响应。

两层各服务一个时刻：正常运行靠喊话快停，崩溃之后靠字据把语义说清。

停止有两个诚实的边界。其一，它不能瞬间打断一个阻塞中的网络读取或执行中的工具——只能等当前调用返回、在下一个边界停下。其二，停止不撤销已发生的副作用：文件已经写入就是写入了，搜索已经执行就是执行了。停止承诺的是"不再开始新动作"，不是"回到停止之前"。

如果停止发生在第一个字吐出之前，消息行会以 stopped 终态落库但没有任何内容，页面显示"已为你停止输出"。

刷新页面：resume 的三步裁决​

刷新后页面重新加载，前端先拉历史，看到"最后一条助手消息是 unfinished"就连接恢复接口 GET /api/sessions/{id}/resume。这个接口做三步判断，每一步依据一个明确的事实：

第一步查库：会话里没有 unfinished 行，直接 204，前端只拉历史，零额外开销。

第二步判断"这个 unfinished 还活着吗"，依据两个事实：超过 deadline_at（兜底），或者进程内没有这条消息的 Run（精确）。这里需要定义 Run：正在执行的消息在进程内的运行态——一个事件缓冲加订阅者队列，随进程生灭。它不是执行状态的真相源（真相源是库），只是活消息的加速层：刷新重连时从这里回放，比读库重组快而且保真。

关键推理是"行在、Run 不在"为什么能等价于"进程重启过"。因为发送路径的顺序是先建 Run、再预建数据库行：只要库里有 unfinished 行，Run 必然建过；进程内现在找不到，只可能是进程重启把内存清了。反过来，执行正常结束时终态落库与 Run 销毁同时发生，不会出现"行还没落终态但 Run 已经没了"的正常路径。所以这个判定是安全的——直接判死收口，不用等 180 秒的 deadline。

判死收口（reaper 模块）做四件事：读 stop_requested 定终态语义；从 text 片段按 seq 拼出全文回填 content；落终态（单向）；补一条 terminal 片段。之后会话解锁，页面看到的是"生成中断，内容未完成"加半截正文——事实如此，就展示如此。

第三步是活着的情况：attach 在一把锁内同时拿到 Run 的事件快照和挂上实时队列——快照与订阅原子交接，不存在"回放完了但新事件已经过去"的夹缝。前端先按序重放快照，再消费实时事件，直到收到终态事件解锁。回放是全量的（seq 从 0 重建），不做增量续传——刷新是低频动作，全量重放简单可靠，省掉了断点协商的复杂度。

崩溃重启：判死，不补跑​

后端进程崩溃，内存里的 Run 全部消失，正在执行的线程不存在了。重启后，数据库里那些残留的 unfinished 行就是崩溃的痕迹。谁来收口？判死逻辑挂在两个入口上：

  • 恢复接口：用户点开这个会话时，resume 的三步裁决走到第二步，判死、回填、快照返回；
  • 发送接口：用户不看旧会话直接发新消息时，发送路径先跑一遍判死再校验会话锁——否则一个永不点开的会话会因为残留的 unfinished 行永远 409。

判死之后不补跑。恢复展示 ≠ 恢复执行：重启后的页面展示"当时说到哪里"，但不会自动让模型接着写下去。用户想继续，发一条"继续"，那是一条新消息、新的一轮执行，模型基于上下文自己识别接续意图。自动续跑看似贴心，实则危险——崩溃前模型正要执行一个写文件操作，重启后自动补跑可能把半截状态写坏。恢复只负责呈现事实，推进永远由用户决定。

小结​

回到开头的三个问题：

  1. 刷新：半截回答一直在数据库里（fragments 实时落库）。resume 三步裁决发现执行还活着，接上实时流继续看；执行在后台线程里，刷新根本不打断它；
  2. 停止：意图分两层落库+喊话，执行线程在安全边界协作停止，已生成的部分定格为 stopped 终态；工具副作用不撤销；
  3. 崩溃：内存的 Run 随进程消失，残留的 unfinished 行由判死逻辑收口——回填文字、落 interrupted（或读到停止字据落 stopped）、解锁。不自动补跑。

贯穿一切的是状态与判断的归属分明：身份在消息行上，过程在 fragments 表里，运行态在进程内的 Run 中，停止意图一半在库里一半在内存。每个判断（resume 走哪条路、终态是哪种、锁什么时候放）都只依赖明确的事实来源，连接断不断、进程死不死都改变不了已落库的事实——这就是"连接只是观看执行的窗口"的全部含义。
