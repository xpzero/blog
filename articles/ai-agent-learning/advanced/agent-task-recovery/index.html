Agent 任务恢复：刷新续看、重启核实与安全继续

柯寒2026年9月29日阅读 12 分钟

区分刷新续看、进程重启核实与用户继续任务：用持久化事实、只读恢复流和经过后端校验的模型建议避免重复执行。

"恢复"这个词在 Agent 应用里至少覆盖三个完全不同的场景：

  1. Agent 正在生成回答，用户刷新了网页——想接着看；
  2. 订单请求刚提交，后端进程崩溃重启——需要核实那个操作到底成没成功；
  3. 任务停止之后，用户说"继续"——希望推进下一步。

如果把这三种都实现成"重新发一次聊天请求"，后果很直观：页面收到重复的回答，业务系统收到第二笔订单，或者模型在不知道前面执行过什么的情况下重新规划。正确的做法是先把它们分开，再为每一种找到对应的事实来源。本文介绍一套这样的恢复机制，承接前文：Agent 运行中断与有限重试：停止、部分回复与模型降级建立的运行（Run）概念。

先分清要恢复的对象​

恢复机制依赖几个持久化对象，各自回答不同的问题：

  • Session / Message：哪个会话、说过什么话。
  • Run：一条用户消息的完整处理过程（前文已建立）。它有始有终。
  • Task：用户要达成的目标，例如"确认 A、B、C 三笔订单"。它有目标版本，可以跨越多次 Run。
  • Operation：一次具体操作的执行事实，有稳定 ID、状态和已确认结果，指向所属的 Task 和发起它的 Run。

它们不是严格的树状嵌套——Task 属于会话，通过关联表连接多个 Run；Operation 同时关联 Task 和 Run：

之所以要拆这么细，是因为不同对象的"完成"互不蕴含：Run 结束不代表 Task 完成；操作确认成功，也不代表崩溃前的模型答复完整。页面因此同时展示消息、运行结论和任务操作进度，而不是把它们揉成一个"成功"标记。

回到开头的三个场景，后端各自要做的事：

用户动作或故障后端应做什么会不会自动请求模型
刷新、切换后切回读取历史，订阅原 Run 的事件和事实不会
后端进程重启接管遗留 Run，查询原业务操作并收尾不会
Run 已结束后用户说"继续"新消息创建新 Run，基于任务事实判断下一步会，但不能直接重放旧操作

前两种都不请求模型——这是整套机制的底线：恢复只读取和核实事实，绝不自动重发任何有副作用的动作。

刷新之后：把正在执行的流接回来​

前文讲过，工作线程在后端独立执行，网页刷新杀不死的只是观看连接。刷新之后要做的，是把这条连接重新接上正在发生的执行：

流程是：网页先加载历史；如果会话仍被运行占用（不能发送），就连接恢复接口 GET /api/sessions/{id}/resume。这是一个只读传输——不创建 Run，不重发工具，更不会重发用户消息。

恢复接口先发一个快照事件 resume_snapshot，包含四项内容：

  • history：消息、会话指针、能否发送、任务进度；
  • user_message_id：这次恢复对应哪个用户轮次；
  • replay：能否按事件缓存重新展示这一轮的输出。

replay 是关键分岔。逐字生成的体验要恢复，靠的是进程内的事件缓存：运行执行时，后端把发给浏览器的每个事件同时存进一个内存缓存（默认上限 4096 个事件、8 MiB）。刷新后的新连接从这个缓存按序回放，再实时跟随后续事件——用户看到的就像从未离开。

实际运行中，生成一篇长文的中途刷新页面，恢复流在半秒内接管：已生成的正文从缓存回放，新内容继续实时跟随，页面同时标明会话仍在处理、输入框保持锁定：

回放之前为什么要清掉这一轮的展示​

历史接口返回的数据里，可能已经包含"工具执行前的文字"和部分助手正文。如果前端在旧内容上直接追加缓存事件，同一批 text_delta 会出现两遍。所以 replay=true 时，前端先保留用户消息、重建这一轮的助手展示区，再按事件原顺序回放：文字 → 工具调用 → 工具结果 → 后续文字，结束后把数据库 ID 和时间戳校准回去。

replay=false 时（缓存不可用，比如缓存超限被清空、或者进程重启过），只能承诺展示持久化下来的事实：保存的半段正文、已确认的操作状态。这时不能因为某个工具卡片缺失就断定"工具没执行过"——未知就是未知。

缓存的边界​

内存缓存是体验优化，不是可靠性承诺，它的边界都做了显式处理：

  • 容量：超过事件数或字节数上限，精确回放被取消，缓存清空，恢复退化为事实快照；
  • 订阅数：一次执行最多 8 个恢复订阅（防止反复刷新占住内存），超出的连接收到 429；每个订阅有独立游标，互不干扰；
  • 断点续传：缓存事件的 SSE id 用 用户消息ID:序号 编码（如 17:23），支持标准 Last-Event-ID 从断点继续；游标失效（序号超范围、轮次不匹配）就重新给快照，不猜；
  • 进程：缓存只在单进程内成立。重启后内存消失，恢复自动退化为事实快照——功能降级，不出错。

流结束与会话解锁是两件事​

恢复流里可能收到 done 或 error——它们只是发生过的事件，不代表恢复可以结束：Run 可能还在 finishing，后端还在核实业务结果。恢复接口会跟随到运行进入终态、事件排空，才发出 stream_end。前端收到后再读一次历史，校准消息和发送权限。恢复连接失败时显示"连接中断，请刷新重试"，不自动无限重连——更不会偷偷重发聊天请求。

请求发出去了没有：pending 标记​

还有一个更早的裂缝：用户点发送的一瞬间刷新了，这条消息到底发出去没有？前端在发送时把会话 ID 和 pending 标记写进 sessionStorage，刷新后按两种情况处理：

  1. 请求还没到后端：pending 会话的历史返回 404，前端清掉临时标记，回到可发送状态，不重发原消息；
  2. 后端已保存消息、响应还没回来：相同 ID 的历史存在，前端接回原 Run，拿到可靠消息 ID 后清除 pending。

已建立的会话返回 404 时显示加载失败，而不是当成空白新会话——那会让用户以为历史丢了。

进程重启后：先核实，不补跑​

最难的一种恢复：业务请求已经提交给外部系统，回执还没写进数据库，进程崩溃了。此时本地没有任何成功记录，但**"本地没有记录"推不出"业务没有执行"**。

这套机制的做法是在发起任何业务请求之前，先在数据库登记一个 Operation，状态标为 maybe_submitted——"已启动，结果未知"。状态机表达的事实是：

状态含义
maybe_submitted启动登记已落库，是否实际送达不确定
processing业务已受理，尚无最终结果
unconfirmed查询未能给出可靠定论
succeeded / failed / cancelled业务证据确认的最终结果

注意只有拿到业务证据（查询回执、对账结果）才能进入终态。运行超时不能把未知改成失败，消息里的半段回答也不能充当成功证据。

后端启动时（FastAPI 的 lifespan 钩子），把上次遗留的 running 状态 Run 转为 finishing 并记录原因，然后启动一个后台线程逐个查询这些遗留操作——只查，不重新提交，不请求模型。查询有结果就落库并释放会话；持续无法确认的，等到原 Run 的截止时间按 timed_out 收尾，未知保持未知。

这里有个反直觉但重要的决定：崩溃前模型答复没写完整时，哪怕操作已核实成功，Run 仍以 failed（进程丢失）结束。业务成功和回答完整是两件事，不能互相顶替——用户需要知道"订单成功了，但当时的说明文字丢了"，而不是一个含混的绿色对勾。

用户说"继续"：新的一轮判断​

前两类恢复都不碰模型。只有用户明确发来新消息（"继续"、"现在到哪了"、"改成确认两笔"），才创建新的 Run。但此时模型对"接下来该做什么"的判断，不能建立在聊天记录的印象上，而要建立在任务事实上。

会话已有任务事实时，后端把任务、目标版本、全部操作状态、待确认问题和已批准步骤组成快照，连同恢复提示词交给模型。模型不再自由发挥，而是通过一个专用工具 recovery_suggestion 提交结构化建议：意图、动作、引用哪些操作、需要执行时还带步骤和参数。

两个设计值得展开。

后端为什么要在执行前重新读库校验：模型思考的几秒里状态可能已经变了——原操作刚被核实成功，或目标版本被修改。模型建议里声称的状态永远不能覆盖数据库事实；引用的操作不存在、版本对不上，建议直接作废。

模型建议不产生授权。一个步骤能不能执行，取决于它是否经过用户的显式批准（planned_steps.approved，来自编排层的批准流程），工具和参数是否与批准一致，依赖是否成功。模型的"建议执行"只是提议。此外，同一任务步骤只允许登记一个 Operation：已有可靠结果的直接复用，已尝试未知的去查询——不能用一个新的调用 ID 绕开这个限制重跑一遍。

恢复模式下，最终答复由后端根据校验结果和业务证据拼装，不直接展示模型自由生成的文字——用户看到的结论必须能追溯到事实。

修改目标要有显式确认​

模型建议修改任务目标时，后端先存为待确认信息。用户必须发送一条以"确认修改目标为："开头、包含完整新目标的消息，且内容与建议一致，后端才更新目标并递增版本。旧操作和旧批准属于旧版本，新目标下需要重新评估。多这一步是因为目标变更会让已有工作作废或错位，值得一次显式的用户决定。

小结​

把三种"恢复"分开后，每一种都有明确的事实来源和动作边界：

  • 刷新续看靠持久化消息 + 进程内事件缓存 + 只读恢复流，绝不重发请求；
  • 重启核实靠操作登记（maybe_submitted）+ 启动时的查询线程，只查不补跑；
  • 继续任务靠任务事实快照 + 后端校验的模型建议，复用已有结果，不重放旧操作。

贯穿的原则和前文一致：恢复的对象是事实，不是动作。连接、进程、模型都可能中断，但已落库的事实不会——把"发生过什么"和"接下来做什么"分开回答，"恢复"才不会变成"重来一遍"。

版本与验证说明：本文机制依据 demo-agent 项目的实现（分支 feat/interruption-retry-recovery，基线提交 250b20f 及其后的中断恢复改动）。文字输出与生成中刷新恢复经实际配置模型（glm-5.3 / glm-4.6）验证；缓存超限、订阅容量、进程崩溃重启等场景通过受控脚本与本地演示业务适配器验证（真实写入 SQLite 后强制终止进程再重启核实），未连接真实订单或支付平台。
