扒Pi loop源码：了解神奇”魔法“

周期2026年10月22日阅读 5 分钟

外面夸夸那么多，难道是有什么神奇魔法吗？

最近在读 pi 的源码，还没看Pi源码的时候，把它当成一个神奇包裹看待了，一点也没从实际考虑，agent底层是什么，只觉得，它一定有"魔法"。但是扒代码的时候，也发现了，关于loop层就是必备的概念、不同的设计。loop循环、拼接消息、请求LLM、拼接LLM的流式返回、执行工具、返回消息给用户，流程就是这么个流程了，但是里面的设计很巧妙，这大概就是被外面夸夸的原因吧。记一些对我来说比较新颖的点，省的忘了。

steer 和 follow-up：不打断，也能把消息塞给模型​

当AI正在分析你发的消息的时候，你又想补充内容，怎么办？

我之前基本是直接打断，发一条新消息。或者是直接发一个不需要调整之前任务的消息进队列排队。

pi里有两个队列，可以不中断agent的运行，也能把新消息带给模型。一个是**steer（转向）队列，一个是follow-up（追加）**队列。

  • steer（转向）：你发的消息是想纠正方向的——「不对，别用那个库」。这条消息不会打断当前运行，而是排进队列，在下一个回合边界（一次工具调用执行完、下次请求模型之前）塞进上下文。模型下一轮就看到了，自己调整方向。
  • follow-up（追加）：你发的消息是个新任务——「做完这个顺便把测试也跑了」。它同样先排队，但等 agent 本轮任务干完、正要停下来的时候，pi 检查这个队列发现有货，就把循环拉起来继续跑，开新一轮。

两条队列、两个注入时机，都写在循环骨架里：

// 内层循环：还有工具要执行，或者有排队的 steer 消息
while (hasMoreToolCalls || pendingMessages.length > 0) {
  // ...请求模型、执行工具...
  pendingMessages = (await config.getSteeringMessages?.()) || [];
}

// agent 本来要停了——看看有没有 follow-up
const followUpMessages = (await config.getFollowUpMessages?.()) || [];
if (followUpMessages.length > 0) {
  pendingMessages = followUpMessages;
  continue; // 循环被拉起来，再跑
}

第一次看懂的时候真的惊艳到我了（感觉我是原始人了！）：插话不打断，追加不丢失，而且这套东西不是外面包一层实现的，是长在 loop 本体里的。任何用这个内核的外壳，都天然得到这套行为。

（后来查了下，类似机制正在变成主流：Claude Code 会把排队消息在工具调用边界注入当前回合，Codex 有 steer/interrupt 双键位，OpenCode 的 API 干脆就叫 delivery: "steer" | "queue"。）

各种生命周期和钩子函数，loop 只是架子​

看代码之前先看的markdown文件，一进来就看到事件流的整理，想想react的挂载、卸载，这不就是生命周期吗！？

prompt("Hello")
├─ agent_start
├─ turn_start
├─ message_start   { message: userMessage }      // Your prompt
├─ message_end     { message: userMessage }
├─ message_start   { message: assistantMessage } // LLM starts responding
├─ message_update  { message: partial... }       // Streaming chunks
├─ message_update  { message: partial... }
├─ message_end     { message: assistantMessage } // Complete response
├─ turn_end        { message, toolResults: [] }
└─ agent_end       { messages: [...] }

再细扒一下，还有beforeToolCall、afterToolCall、finishTurn，乖乖，不得了哦，这不就是把各种决策点都做成钩子函数了吗？原来，没有神奇魔法，也是一步一步逻辑缝合吗？这样的话，loop就只是loop啦，本该是这样的。虽然我之前在demo-agent里把loop和agent也拆开了，但是还是前辈们经验十足啊，orz。

我很喜欢这种拔插式的功能设计逻辑，很方便，核心是稳的，想要功能，做一个扩展加上去就好咯~。但是优点也是缺点，pi太极简了，需要安装扩展才能更好的使用；langgraph+langchain，封装的太完整了，不好扩展（暂时没有尝试过，但是按照惯例，应该是这样的）。全看使用者如何取舍了。

个人感觉:

快速：框架
小而美：自己写，自己设计
又想快速、又想小而美：套壳(比如用pi的核心功能，组装自己的agent)。但是对于开发而言基本也是框架了，要先了解和学习。

几乎没有 try/catch：错误也是一条消息​

扒代码的时候发现，似乎loop里很少有try-catch，难道不怕报错吗？让AI给我总结了一下，原来是loop里的钩子函数(我这么叫)，你可以做事情，但是你要为你做的事情兜底，我loop只是一个架子。也是，loop主要是为了和LLM API交互，拿到LLM的返回，想要有业务逻辑，那是调用方的事情，处理业务方可能造成的错误？No！业务方的报错无法预测，放在loop太累了。自己做的孽自己受...。

收尾​

三个点其实说的是一件事：这个循环里几乎没有什么是它自己说了算的。什么时候注入消息、什么时候继续、出错怎么办——全留给了外面。所以它才能只有九百多行，才能被套上各种外壳当内核用。

虽然只是一个loop，读完最大的感受倒不是学会了什么技巧，而是，没有神奇魔法，有的只是如何设计、使用。去看、去发现，而不是只感叹。
