pi 的上下文装配流程拆解

周期2026年10月25日阅读 18 分钟

从一次干净的 pi 命令入手跟读启动链路：解析参数、引导配置与会话定位、工厂一次调用装配服务与会话、运行时最后诞生，直到界面启动等待输入。

信息

代码入口文件是: coding-agent/src/main.ts

从执行一次干净的pi命令入手，看看pi的上下文装配流程是什么样子的。

解析参数：最先拿到的输入​

虽然我们按执行pi但没有参数的方案走，但是pi是有很多参数的，程序第一步也是解析参数。执行pi --help可以看到有很多的参数信息:

# 继续上一次会话
pi --continue '你觉得这对吗？'
# 使用指定模型开新会话
pi --model openai/gpt-4o "Help me refactor this code"
# 限定工具开新会话
pi --tools read,grep,find,ls -p "Review the code in src/"
# 开会话的时候，禁用哪些工具
pi --exclude-tools 工具名
...

可以看到，是否有参数、参数是什么，还是很重要的，我觉得可以媲美是否投了个好胎了。 拿到参数之后，就要根据参数信息进行分支处理了(if线)。但是这就有点太细了，我们先把整个流程串下来。

参数解析的代码在 packages/coding-agent/src/cli/args.ts。解析结果是一个 Args 对象，上面那些命令行示例里的参数都是它的字段（这里只列一部分）：

查看代码：Args 参数对象定义（cli/args.ts）
export interface Args {
  provider?: string; // --provider，指定厂商
  model?: string; // --model openai/gpt-4o
  apiKey?: string; // --api-key
  continue?: boolean; // --continue / -c，继续上一次会话
  resume?: boolean; // --resume / -r，从会话列表里挑一个恢复
  session?: string; // --session，按 id/路径打开指定会话
  fork?: string; // --fork，从某个会话分叉出新会话
  tools?: string[]; // --tools read,grep,find,ls
  excludeTools?: string[]; // --exclude-tools，禁用指定工具
  noTools?: boolean; // 不加载任何工具
  print?: boolean; // -p，非交互的一次性执行
  mode?: Mode; // text / json / rpc，输出模式
  help?: boolean; // --help
  version?: boolean; // --version
  messages: string[]; // 位置参数，作为首条消息
  fileArgs: string[]; // @file 形式的参数，读文件内容拼进首条消息
  // 未识别的 flag：可能是扩展注册的，先存着，等扩展加载后再匹配
  unknownFlags: Map<string, boolean | string>;
  // 解析过程中的警告/错误，不会立刻退出，攒到最后统一处理
  diagnostics: Array<{ type: "warning" | "error"; message: string }>;
}

parseArgs() 本体就是一个逐个扫描的 if/else 长链，把 argv 里的字符串翻译成上面的字段：

查看代码：parseArgs() 解析循环（cli/args.ts）
export function parseArgs(args: string[]): Args {
  const result: Args = {
    messages: [],
    fileArgs: [],
    unknownFlags: new Map(),
    diagnostics: [],
  };

  for (let i = 0; i < args.length; i++) {
    const arg = args[i];

    if (arg === "--") {
      // "--" 之后的内容全部当作消息文本（@开头的例外，算文件参数）
      for (const positionalArg of args.slice(i + 1)) {
        if (positionalArg.startsWith("@")) {
          result.fileArgs.push(positionalArg.slice(1));
        } else {
          result.messages.push(positionalArg);
        }
      }
      break;
    } else if (arg === "--help" || arg === "-h") {
      result.help = true;
    } else if (arg === "--version" || arg === "-v") {
      result.version = true;
      // ...同一个 flag 的长/短写法归一
    } else if (arg === "--continue" || arg === "-c") {
      result.continue = true;
    } else if (arg === "--resume" || arg === "-r") {
      result.resume = true;
    } else if (arg === "--provider" && i + 1 < args.length) {
      result.provider = args[++i]; // 带值的参数：吃掉下一个 argv
    } else if (arg === "--model" && i + 1 < args.length) {
      result.model = args[++i];
    }
    // ...后面还有几十个分支，没匹配上的进 unknownFlags，
    // 留给扩展注册的 flag 去认领
  }

  return result;
}

回到入口 main()（packages/coding-agent/src/main.ts），拿到解析结果后就是文章开头说的那条"if线"分支处理，几个典型分支长这样：

查看代码：main() 中的参数分支处理（main.ts）

  }
}

  console.log(VERSION);
  process.exit(0);
}
if (parsed.export) {
  // --export：把已有会话导出成 HTML 等格式
  result = await exportFromFile(parsed.export, outputPath);
  process.exit(0);
}

// 根据 TTY 判断运行模式：
// 显式指定了 rpc/json 就用指定值；
// 否则只要 stdin/stdout 有一个是管道（比如 echo xxx | pi）就走 print 模式；
// 都是终端才走交互式 TUI
let appMode = resolveAppMode(parsed, process.stdin.isTTY, process.stdout.isTTY);

// 会话相关的互斥校验：--fork 不能和 --session/--continue/--resume 混用

validateSessionIdFlags(parsed);

到这里，参数把"这次启动想要什么"说清楚了：开新会话还是恢复旧的、用什么模型、开哪些工具。意图有了，材料还没找——模型列表、上次聊到哪、装了哪些扩展。接下来的章节跟着 main() 一件件把它们找出来。

引导配置与会话定位：先回答"在哪开、开哪个"​

main() 要先回答两个更基础的问题：这次在哪个目录干活、面对哪个会话。要回答它们，pi 先读自己的设置：会话记录放在哪、用户的默认配置是什么，都记在 settings.json 里。

设置也是文件，落在磁盘上。pi 的配置文件统一住在一个根目录下，默认 ~/.pi/agent/，目录约定对应 packages/coding-agent/src/config.ts：

查看代码：配置目录约定（config.ts）
// 用户配置根目录，默认 ~/.pi/agent/
// 也可以通过环境变量（如 PI_CODING_AGENT_DIR）重定向到别处
export function getAgentDir(): string {
  const envDir = process.env[ENV_AGENT_DIR];
  if (envDir) {
    return expandTildePath(envDir);
  }
  return join(homedir(), CONFIG_DIR_NAME, "agent");
}

// 自定义模型列表（自定义厂商/中转站的模型就登记在这里）
export function getModelsPath(): string {
  return join(getAgentDir(), "models.json");
}

// 各厂商的 API Key / 凭证
export function getAuthPath(): string {
  return join(getAgentDir(), "auth.json");
}

// 用户设置（默认模型、主题等，配一次以后每次启动都生效）
export function getSettingsPath(): string {
  return join(getAgentDir(), "settings.json");
}

// 用户自定义主题目录
export function getCustomThemesDir(): string {
  return join(getAgentDir(), "themes");
}

然后看 main() 在这一步做了什么——只做定位：迁移旧配置、读 settings.json、定出会话记录目录、按参数打开或新建会话记录：

查看代码：main() 中读取配置与定位会话（main.ts）
const cwd = process.cwd();
const agentDir = getAgentDir(); // ~/.pi/agent/

// 旧版本配置格式迁移（只在升级后首次执行，避免老用户的配置失效）
const { migratedAuthProviders: migratedProviders, deprecationWarnings } =
  runMigrations(cwd);

// 创建配置管理器：把 settings.json 等配置从磁盘读进内存

  parsed,
  cwd,
  sessionDir,
  startupSettingsManager,

定位的产物是 SessionManager，看下它做了什么：

查看代码：SessionManager 主要结构（core/session-manager.ts）
export class SessionManager {
  // ---------- 内存态：会话树 + 索引 ----------
  private sessionId: string;
  private sessionFile: string | undefined; // .jsonl 文件路径，inMemory 模式下没有
  private sessionDir: string;
  private cwd: string;
  private persist: boolean; // --no-session 时为 false，后文所有写盘都先看它
  private flushed: boolean = false; // 文件是否已创建（惰性：第一条 user/assistant 消息才建）
  private fileEntries: FileEntry[] = []; // 按追加顺序排列的全部 entry
  private byId: Map<string, SessionEntry>; // id → entry 索引
  private leafId: string | null = null; // 树的当前叶子：新 entry 默认挂在这下面

  // ---------- 静态工厂：main() 里那几个会话分叉的入口 ----------
  static create(cwd, sessionDir?, options?); // 新建会话
  static open(path, sessionDir?, cwdOverride?); // --session / --resume：按文件打开
  static continueRecent(cwd, sessionDir?); // --continue：接最近一次会话
  static inMemory(cwd, options?, entries?); // --no-session、--help 等：不落盘的会话
  static findById(cwd, id, sessionDir?); // --session-id：按 id 找会话文件
  static async list(cwd, sessionDir?); // 当前项目的会话列表
  static async listAll(); // 跨项目全局会话列表

  // ---------- 追加 entry：AgentSession 运行中调用的那一批 ----------
  appendMessage(message); // 追加一条消息（用户/助手/工具结果）
  appendModelChange(provider, modelId); // 换模型记一笔
  appendThinkingLevelChange(thinkingLevel); // 换思考档位记一笔
  appendUsage(kind, provider, model, usage); // 分模型用量统计
  appendCompaction(summary, firstKeptEntryId, tokensBefore); // 压缩摘要
  branchWithSummary(branchFromId, summary); // 分叉时对被放弃路径记摘要
  appendCustomEntry(customType, data?); // 扩展私有数据
  appendCustomMessageEntry(...); // 扩展注入的消息（会进上下文）
  appendLabelChange(targetId, label?); // 书签
  appendSessionInfo(name); // 会话命名
  appendContextEdit(targetId, replacement); // 改写历史消息的记录

  // ---------- 内线：所有 append* 的公共出口 ----------
  private _appendEntry(entry) {
    this.fileEntries.push(entry); // 内存树
    this.byId.set(entry.id, entry);
    this.leafId = entry.id; // 叶子指针前移
    this._persist(entry); // 立即落盘
  }
  _persist(entry); // 惰性建文件（openSync "wx"）之后 appendFileSync 逐行追加
  private _rewriteFile(); // 改历史场景（如 context_edit）时整文件重写

  // ---------- 树的查询与投影 ----------
  getEntry(id) / getChildren(parentId) / getBranch(fromId?) / getTree();
  getLeafId() / getLeafEntry() / resetLeaf(); // branch() 把叶子移回历史节点，实现“回溯”
  buildContextEntries(); // 从树投影出发给 LLM 的那部分 entry
  buildSessionProjection(); // 投影成完整会话视图（含 system / 摘要 / 消息）
  buildSessionContext();

  // ---------- 分叉 ----------
  branch(branchFromId); // 内存内回溯：只移叶子，不写盘
  createBranchedSession(leafId); // 落盘：复制出新的 .jsonl 分叉文件
}

可以看到，它一个类包揽了会话的内存树、磁盘文件和查询投影三块职责。也就是负责处理session文件创建/打开和session数据的存取。感觉更像是后端用来存储数据库的逻辑。

到这里，"在哪开、开哪个"有了答案。项目级的设置、扩展、AGENTS.md 都跟着会话的工作目录走，目录定了，真正的装配才开始——那是一次运行时调用里的事。

创建运行时：一次调用，三批对象嵌套诞生​

main() 没有直接 new 服务、new 会话，而是先定义一个工厂闭包 createRuntime，把 CLI 参数、扩展列表这些进程级的固定输入捕获进去，然后交给 createAgentSessionRuntime() 执行。这一次调用里，按顺序诞生三批对象：

createAgentSessionRuntime(工厂)
  ├─ ① 服务：ModelRuntime / SettingsManager / ResourceLoader
  ├─ ② 确定模型和工具范围（buildSessionOptions）
  ├─ ③ 会话：new Agent + new AgentSession
  └─ ④ new AgentSessionRuntime：运行时对象最后诞生

服务装配​

这一步装配的产物叫"服务"——支撑会话运转的长驻内存对象，类型名就叫 AgentSessionServices，一共三样：

  • ModelRuntime：模型接入。内置厂商目录、models.json 里自定义的厂商和模型、auth.json 里的登录凭证，都由它装进内存；
  • SettingsManager：设置。全局 ~/.pi/agent/settings.json 与项目 .pi/settings.json 合并成一份内存配置；
  • ResourceLoader：资源收集器。扩展（内置 + 用户安装）、skill、prompt 模板、主题、AGENTS.md，这些统称"资源"，由它统一发现和加载。

装配入口是 packages/coding-agent/src/core/agent-session-services.ts 里的 createAgentSessionServices()：

查看代码：createAgentSessionServices() 服务装配（agent-session-services.ts）
export async function createAgentSessionServices(
  options: CreateAgentSessionServicesOptions,
): Promise<AgentSessionServices> {
  const cwd = resolvePath(options.cwd);
  const agentDir = options.agentDir
    ? resolvePath(options.agentDir)
    : getAgentDir();

  // 模型运行时：内置厂商目录 + models.json 里的自定义厂商/模型 + auth.json 里的凭证
  const modelRuntime =
    options.modelRuntime ??
    (await ModelRuntime.create({
      authPath: join(agentDir, "auth.json"),
      modelsPath: join(agentDir, "models.json"),
      signal: options.modelRuntimeSignal,
    }));

  // 配置管理器（磁盘上的 settings.json → 内存对象）
  const settingsManager =
    options.settingsManager ?? SettingsManager.create(cwd, agentDir);

  // 资源加载器：负责扩展（含内置工具、用户安装的插件工具）、skill、
  // prompt 模板、主题、AGENTS.md 等上下文文件的发现与加载
  const resourceLoader = new DefaultResourceLoader({
    ...(options.resourceLoaderOptions ?? {}),
    cwd,
    agentDir,
    settingsManager,
  });
  await resourceLoader.reload(options.resourceLoaderReloadOptions);

  // 扩展在加载时可能声明了自定义 Provider / 虚拟模型，这里注册进模型运行时
  const extensionsResult = resourceLoader.getExtensions();
  for (const { name, config, extensionPath } of extensionsResult.runtime
    .pendingProviderRegistrations) {
    modelRuntime.registerProvider(name, config);
    // （注册失败会收集为 diagnostic，最后统一报告，不会静默吞掉）
  }

  // 刷新模型目录：合并内置列表与自定义列表，此阶段禁止联网
  await modelRuntime.refresh({ allowNetwork: false });

  return {
    cwd,
    agentDir,
    modelRuntime,
    settingsManager,
    resourceLoader,
    diagnostics,
  };
}

可以看到，这一步把 ~/.pi/agent/ 目录约定下的模型、凭证、设置、扩展分门别类装进三个服务对象，后面的请求循环都从它们取料。

确定模型和工具范围​

服务和会话之间，工厂还定两件事：这次用什么模型、开哪些工具。规则很直接：命令行参数优先——--model/--provider 指定模型，--tools/--exclude-tools 圈定工具范围；参数没提的，用 settings.json 里保存的默认模型、默认工具兜底。解析发生在 buildSessionOptions()，结果作为选项传给下一步创建会话。

创建会话​

工厂的第二步是创建会话本体，两个对象在这里诞生：new Agent()——pi-agent-core 的请求循环执行器，真正调模型、跑工具回环的；new AgentSession()——会话对象，单个会话的"大脑"，手里攥着请求循环、存储（sessionManager）、工具表和系统提示词。全仓库唯一的 new AgentSession 就藏在 createAgentSession() 里，也只在工厂跑起来时才执行到。

它的构造函数做了三件事：订阅 agent 事件（所有消息/工具事件先流到这里）、挂载投影和扩展钩子、注册工具并构建系统提示词。主要结构长这样（方法签名节选）：

查看代码：AgentSession 主要结构（core/agent-session.ts）
export class AgentSession {
  // ---------- 聚合的核心对象 ----------
  readonly agent: Agent; // pi-agent-core 的请求循环执行器：真正调模型、跑工具回环的
  readonly sessionManager: SessionManager; // 上面说的：会话数据的唯一持有者
  readonly settingsManager: SettingsManager;

  // ---------- 运行态 ----------
  private _steeringMessages: string[] = []; // 流式响应中途插话的排队消息
  private _followUpMessages: string[] = []; // 等本轮结束再发的排队消息
  private _pendingNextTurnMessages / _pendingCustomMessages; // 排队进下一轮/本轮的上下文消息
  private _compactionAbortController ...; // 压缩 / 分支摘要 / 自动重试的可取消状态
  private _toolRegistry: Map<string, AgentTool>; // 工具注册表（内置 + 扩展）
  private _allowedTools?: (name) => boolean; // --tools 白名单
  private _excludedTools?: (name) => boolean; // --exclude-tools 黑名单
  private _baseSystemPromptOptions; // 组装好的系统提示词（分段）
  private _runSystemPromptOptions?; // before_agent_start 钩子改写后的本次运行版本

  constructor(config) {
    // 订阅 agent 事件：所有消息/工具事件先流到这里
    this._unsubscribeAgent = this.agent.subscribe(this._handleAgentEvent);
    this._installAgentRequestProjection(); // 每次请求前从会话树投影出消息列表
    this._installAgentBoundaryHooks(); // 挂载 transformContext 等扩展钩子
    this._buildRuntime({...}); // 注册工具、构建系统提示词
  }

  // ---------- 发消息一族 ----------
  async prompt(text, options?); // 主入口：斜杠命令 / 扩展拦截 / skill 展开 / 排队分流都在这
  async steer(text, ...); // 流式中途插话，影响当前行为
  async followUp(text, ...); // 排队，等本轮结束再发
  async sendCustomMessage(...); // 扩展以用户身份注入消息
  async executeBash(...) / recordBashResult(...); // 会话内的 bash 执行与记录

  // ---------- 模型与工具 ----------
  async setModel(model) / cycleModel(...); // 换模型（同时 appendModelChange 落盘）
  setThinkingLevel(...) / cycleThinkingLevel(); // 思考档位
  setActiveToolsByName(names); // /tools 的落点：改工具集并重建系统提示词
  getActiveToolNames() / getAllTools() / getToolDefinition(name);

  // ---------- 压缩与树导航 ----------
  async compact(instructions?); // /compact：压缩历史
  setAutoCompactionEnabled(...); // 超阈值自动压缩
  async navigateTree(targetId, { summarize }); // 跳到树上任意节点，可对放弃路径生成摘要
  getUserMessagesForForking(); // 列出可分叉的用户消息

  // ---------- 会话信息与导出 ----------
  setSessionName(name) / getSessionStats() / getContextUsage();
  exportToJsonl() / exportToHtml();

  // ---------- 扩展与生命周期 ----------
  subscribe(listener); // UI 订阅会话事件
  async bindExtensions(...); // 绑定扩展运行时（含 UI 上下文）
  async reload(...); // /reload：重载资源后原地更新
  dispose();

  // ---------- 内线：Agent 事件 → 落盘 ----------
  private _handleAgentEvent = async (event) => {
    await this._emitExtensionEvent(event); // 先给扩展
    this._emit(event); // 再通知 UI 监听器
    if (event.type === "message_end") {
      // “何时存什么”在这里决定：普通消息 appendMessage，
      // 扩展消息 appendCustomMessageEntry → 交给 SessionManager 落盘
      entryId = this.sessionManager.appendMessage(event.message);
    }
  };
  private _rebuildSystemPrompt(toolNames); // 工具集变化时重建系统提示词
}

运行时对象最后诞生​

服务和会话都就位，最后一层才是运行时对象自己：new AgentSessionRuntime(...) 把工厂的全部产物抱走，同时把工厂闭包存进身上，留给以后换会话时重放。这个类的注释写得很直白：

Owns the current AgentSession plus its cwd-bound services.

Session replacement methods tear down the current runtime first, then create and apply the next runtime.

翻译过来就是：持有当前的 AgentSession 和与它绑定在当前工作目录上的那批服务。换会话的方法会先拆掉当前这套运行时，再创建并应用下一套运行时。

查看代码：AgentSessionRuntime 主要结构（core/agent-session-runtime.ts）
// main() 调的入口：先跑一遍工厂，再建运行时包裹住结果
export async function createAgentSessionRuntime(createRuntime, options) {
  const result = await createRuntime(options); // 跑工厂：服务装配 + AgentSession
  return new AgentSessionRuntime(
    result.session,
    result.services,
    createRuntime, // 工厂存在身上，之后 /new /resume /fork 都复用它重建
    result.diagnostics,
  );
}

export class AgentSessionRuntime {
  // ---------- 持有：当前会话 + 服务 + 重建工厂 ----------
  private _session: AgentSession; // 当前会话（换会话时被整体替换，不是原地修改）
  private _services: AgentSessionServices; // 当前 cwd 绑定的服务（ModelRuntime 等）
  private readonly createRuntime: CreateAgentSessionRuntimeFactory; // 装配工厂

  // ---------- UI 绑定的回调 ----------
  private rebindSession?: (session) => Promise<void>; // 换会话后界面重新绑定新 session
  private beforeSessionInvalidate?: () => void; // 旧会话失效前的同步清理（如拆扩展的 TUI 组件）

  // ---------- 读取当前状态 ----------
  get session() / get services() / get cwd() / get diagnostics();
  setRebindSession(cb) / setBeforeSessionInvalidate(cb);

  // ---------- 换会话四件套：核心职责 ----------
  async switchSession(sessionPath, options?); // /resume：打开另一个会话文件
  async newSession(options?); // /new：新开（可带 parentSession 指向来源）
  async fork(entryId, options?); // fork：从某个 entry 分叉出新会话
  async importFromJsonl(inputPath, cwdOverride?); // /import：导入 jsonl 文件

  // ---------- 生命周期 ----------
  async dispose(); // 退出：session_shutdown(quit) → dispose 当前会话
}

四个换会话方法内部是同一套固定五步，拿 switchSession() 的真实代码看（节选）：

async switchSession(sessionPath, options?) {
  // ① session_before_switch 事件：扩展可以取消这次切换
  const beforeResult = await this.emitBeforeSwitch("resume", sessionPath);
  if (beforeResult.cancelled) return beforeResult;

  const previousSessionFile = this.session.sessionFile;
  const sessionManager = SessionManager.open(sessionPath, undefined, options?.cwdOverride);
  assertSessionCwdExists(sessionManager, this.cwd);

  // ② 拆旧的：等当前回合收尾 → session_shutdown 事件 → dispose 旧会话
  await this.teardownCurrent("resume", sessionManager.getSessionFile());

  // ③ 重跑装配工厂：重新执行服务装配 + 创建新 AgentSession
  this.apply(
    await this.createRuntime({
      cwd: sessionManager.getCwd(),
      agentDir: this.services.agentDir,
      sessionManager,
      sessionStartEvent: { type: "session_start", reason: "resume", previousSessionFile },
    }),
  );
  // ④ apply() 把手里的 _session / _services 换成新的

  // ⑤ 界面重新绑定新会话
  await this.finishSessionReplacement(options?.withSession);
  return { cancelled: false };
}

界面启动：第一屏出现的时候​

运行时装配完，回到 main()，离第一屏出现还有三步，外加半步。

第一步，initTheme() 把主题设置应用到界面——主题设置早在引导阶段就读进了内存，这里才真正生效。第二步，组装首条消息：stdin 管道里的内容（比如 echo "xxx" | pi）、位置参数、@文件引用，拼成初始消息。第三步，new InteractiveMode(runtime) 然后 run()，TUI 起来，光标开始闪。

最后半步是给扩展的：界面起来后，InteractiveMode 调 session.bindExtensions()，把 UI 上下文交给扩展调度器 ExtensionRunner，扩展此刻才收到 session_start 事件——装配期它们一直安静等着这一刻。

查看代码：main() 尾部的三步与模式分道（main.ts）

}

尾声：启动只是工厂的第一次运行​

回看整条链：参数解析定了意图，引导配置定了"在哪开、开哪个"（SessionManager 诞生），然后一次运行时调用里工厂跑完三批对象——服务、会话、运行时，最后主题应用、界面起来、扩展收到 session_start。四个角色各守一层：SessionManager 管数据（内存树 + 磁盘文件），AgentSession 管行为（何时往树里写什么、何时发请求），AgentSessionRuntime 管编排（多个会话之间怎么换），工厂是它们共同的生产线。

启动只是这条生产线的第一次运行。之后的 /new、/resume、fork、/import，都是同一座工厂的重放——上面换会话五步的代码就是重放的完整过程：通知扩展、拆掉旧会话、重跑服务装配和会话创建、换引用、界面重新绑定。
