Agent 会话管理：刷新页面后，刚才的对话去哪了？

柯寒2026年9月23日阅读 12 分钟

从网页刷新后的空白聊天区出发，沿着会话列表、SQLite 消息存储、历史回显与续聊，理解 demo-agent 的会话管理。

网页上的 Agent 已经能聊天了。但刷新页面后，聊天区又是空的：刚才的对话去了哪里？如果还想接着聊，靠浏览器里的一份消息数组显然不够。

我之前写过 demo-agent 的多会话实现，但那一版完全交给 AI 写，写完之后我对代码失去了掌控感，于是决定重写一份。实际上这一版的代码仍然是 AI 写的，只是换了一种协作方式。这篇读的是重写后的 feat/little-agent 分支：SQLite 会话由 PR #2 引入，网页历史列表在 PR #6 完善；代码以提交 75efdbb为准，和以前的系列文章不是同一版。切换模型时，所用中转站不支持 Responses API，因此这版又使用 Chat Completions。

刷新后，先找回会话​

这版页面刷新后默认生成一个新的空会话 ID，不会自动选回刚才的会话。不过左侧仍列着数据库中已有的会话；点击旧会话，就能加载它的消息。这样“刷新后聊天区空了”和“对话记录丢了”是两回事。

下面两张图来自同一台机器上运行的项目页面。刷新后，左侧仍有 6 条会话，主区是空的；点击其中一条后，主区回显了 5 条消息。**图中灰色遮盖由截图后处理加入，只遮盖原有会话标题和消息正文，不是页面的加载占位；未改动会话数量、选中状态和页面布局。**这些现有会话不是本次新发给模型的测试输入。

为了让左侧在刷新后还有内容，前端调用 GET /api/sessions。后端从 SQLite 的 chat_sessions 读取以下字段，按更新时间倒序返回：

  • id：会话 ID，用来选中记录
  • title：标题，给列表显示
  • current_message_id：会话的当前消息指针
  • created_at / updated_at：创建与更新时间，列表按更新时间倒序

标题取首条用户消息去掉首尾空白后的前 30 个字符；用户还没真正发送消息时，页面可以暂时显示本地标题，但数据库里没有空会话。代码见 list_sessions() 与 create_user_turn()。

这张会话表的设计参考了 DeepSeek 网页版接口返回的会话数据形状，这是本项目的设计来源说明，不能据此推断 DeepSeek 后端的表结构。目前我没有可公开核对的那份原始响应，因此不逐字段声称两者一一对应；以下字段及行为均以 demo-agent 自己的代码为准。

点开一条会话，消息从哪里来​

列表只有会话摘要，还不足以回显聊天内容。每条消息另存在 chat_messages：session_id 指明所属会话，role 区分用户与助手，content 是文本，parent_id 指向前一条消息。表结构在 connection.py。附件如果存在，则通过 message_files 关联到消息——这张表本文只点到为止，它是为后面讲文件上传与解析的文章做的铺垫，此处先专注消息本身。

图中 chat_messages 指向自身，是为了表示消息链；current_message_id 是会话指向链尾的指针。它是根据固定提交中的建表 SQL 整理出的关系图，不是数据库客户端导出的原始截图。

源码中对应的核心建表片段如下，status 也在这里被限制为 finished 或 failed：

server/database/connection.py
CREATE TABLE IF NOT EXISTS chat_sessions (
    id TEXT PRIMARY KEY,
    title TEXT NOT NULL,
    current_message_id INTEGER,
    FOREIGN KEY (current_message_id)
        REFERENCES chat_messages(id) ON DELETE SET NULL
);

CREATE TABLE IF NOT EXISTS chat_messages (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id TEXT NOT NULL,
    parent_id INTEGER,
    role TEXT NOT NULL CHECK (role IN ('user', 'assistant')),
    status TEXT NOT NULL CHECK (status IN ('finished', 'failed')),
    content TEXT NOT NULL
);

这是从固定提交 connection.py 第 10–32 行摘出的片段；省略了时间字段、外键完整定义和附件表。

点击旧会话时，前端请求 GET /api/sessions/{id}；后端返回会话信息与该会话按消息 ID 排列的全部消息及附件。前端的 useSessionMessages 将历史消息映射成聊天气泡，并把会话的 current_message_id 留给下一次发送使用。历史中的助手回复是已保存的最终文本，不是当时逐字输出的完整事件过程；工具调用与结果没有持久化，刷新后也不会重新显示。

切换会话时，前端先清空当前消息视图并递增 sessionGeneration（页面视图的代次），取消旧的历史请求；即使旧请求随后返回，也会检查代次，避免把上一条会话的消息放到当前页面。历史没加载好时不能发送。这些是页面状态保护，不是数据库里的会话版本号。

新对话什么时候真正成为一条历史​

空聊天页已经有前端生成的 UUID，但并没有立刻写入 chat_sessions。第一次发送 POST /api/chat 时，前端带上 session_id、parent_message_id: null 和消息正文。后端在一个事务里创建会话、保存用户消息，并把 current_message_id 更新为这条用户消息的 ID。这样刷新后才能在历史列表中找到它。

接下来后端才开始模型请求，并通过 SSE（服务端逐帧推给网页的 HTTP 响应）先发 user_message，告诉前端已保存的用户消息 ID。模型生成时的 text_delta 让页面实时显示文字；只有本轮产出 done 且最终文本非空，后端才把助手回复写库，并在 done.message_id 中返回助手消息 ID。流程见 api.py 的 chat()。

这个时序图把关键持久化边界标出来：用户消息先入库，助手消息等最终文本确认后才入库。模型事件经过后端转成项目自己的 SSE 事件；浏览器没有直接消费模型原始 chunk。

chat() 中对应的实际顺序是先调用 create_user_turn()，收到 done 后才调用 add_assistant_message()：

server/api.py
user_message_id = database.create_user_turn(
    session_id=session_id,
    parent_message_id=body.parent_message_id,
    content=body.message,
    file_ids=body.ref_file_ids,
)
chain = database.get_message_chain(session_id, user_message_id)

for event in stream_events(items, context=context):
    if event["type"] == "done" and event["content"]:
        message_id = database.add_assistant_message(
            session_id=session_id,
            parent_message_id=user_message_id,
            content=event["content"],
        )

这是固定提交 api.py 第 124–168 行的省略片段；完整实现还处理错误事件、会话锁和 SSE 封装。

首次发送：新 UUID + parent_message_id = null
  → 写入 Session 和用户消息 #12，当前指针指向 #12
  → 模型回复完成后写入助手消息 #13，当前指针指向 #13
  → 再发一条消息时，以 #13 为 parent_message_id

上面的 #12、#13 是说明关系的示例 ID，不是截图中会话的真实数据。若助手没有产出非空最终文本，代码不写助手消息，done.message_id 仍指向用户消息。

为什么续聊还需要一个“当前消息 ID”​

从左侧找回一条会话并看到历史后，还要回答“下一句接在哪里”。chat_sessions.current_message_id 记录当前最新消息；发送下一句时，浏览器把它作为 parent_message_id 传回。后端要求它等于数据库中的当前指针，否则返回 HTTP 409 stale_parent_message，避免旧页面在会话已更新后继续写入。

后端保存新用户消息后，沿 parent_id 一路查回去，再倒序排列，加上 system message，拼成本轮发给 Chat Completions 的上下文。Agent loop 只处理这份临时上下文，不直接读写会话数据库。这样回显使用已保存消息，续聊又能根据同一条消息链重建模型输入；但目前尚无长会话的截断或摘要，历史很长时仍可能触及上下文窗口。

图中只画续聊时的检查：浏览器带来上次看到的消息 ID，数据库用当前指针判断这条会话有没有被更新。检查通过后，后端保存新用户消息，再沿 parent_id 重建模型上下文；助手回复保存成功时，指针继续推进。代码见 create_user_turn() 第 54–66 行。

生成到一半刷新，会看到什么​

这里的写入时机尤其关键：用户消息在模型开始前就已保存；流式文字只是当前页面上的临时展示。若请求在助手最终回复写库前出错，历史里可能只有用户提问，刷新后不会找回之前屏幕上出现的半截回答。此时不需要重发提问：这条用户消息就是会话的当前指针，点击左侧会话，前端通过 GET /api/sessions/{id} 拿到 current_message_id 就能恢复父指针，下一句从这条用户消息接起。后端的失败流测试用模拟事件验证了“错误后保留用户消息和当前指针”；它不能证明浏览器关闭时服务端一定停在同一时刻。如果后端已把完整助手回复写库，之后刷新就会回显那条回复。

当前网页没有主动停止生成按钮，也没有单独持久化“已取消”或“失败回合”的运行记录。仅凭“有用户消息、没有助手消息”不能断定是用户中断；停止生成涉及真正的后端取消、工具副作用和回合状态，留给后续单独处理。

从头到尾串一遍​

把散在各节的步骤按时间连起来，一个会话的完整流程是：

  1. 打开新聊天，前端用 crypto.randomUUID() 生成 session_id；此时数据库里还没有这个会话。
  2. 第一次 POST /api/chat 携带 session_id、parent_message_id: null 和消息正文；后端在一个事务里创建会话、保存用户消息，并把 current_message_id 指向它。
  3. 后端先发 user_message SSE 事件，返回已持久化的用户消息 ID；随后沿这条父消息链组装本轮的模型上下文。
  4. 模型回复完成且最终文本非空时，后端保存助手消息、推进 current_message_id，并在 done.message_id 返回助手消息 ID。
  5. 下一轮发送以上一条消息 ID 作为 parent_message_id；后端校验它等于会话当前指针，否则返回 409 stale_parent_message。
  6. 模型或网络失败时，用户消息已入库、仍是当前指针；重新加载会话即可拿到 current_message_id 恢复父指针，从这条用户消息继续。
  7. 刷新页面后，前端默认生成新的空会话；通过 GET /api/sessions 找回历史列表，点击后 GET /api/sessions/{id} 回显已保存的消息。

一句话概括：Session 是随第一句对话惰性创建的；每轮对话由“保存用户消息 → 重建上下文 → 模型生成 → 保存助手消息”组成；消息链和 current_message_id 共同决定了回显什么、从哪里续聊。

验证范围​

代码依据是提交 75efdbb。我通过本地运行的项目页面（从该仓库 server/、web/ 启动的 uvicorn 与 Vite）观察了刷新、左侧列表和点击旧会话回显，并核对了接口返回的字段名、列表数量及页面消息条目数量。这次检查没有发起新的模型请求，“发送新消息 → 模型完成 → 再刷新”的端到端路径未验证，因此文中关于生成中刷新的结论以代码与测试为依据，而不是真实模型的复现。

后端从 server/ 执行 uv run python -m unittest discover -s tests -v，此前记录为 49 项通过（模拟 Agent 事件与临时 SQLite，覆盖“错误后保留用户消息和当前指针”等失败路径，但不证明真实服务端到端行为）；前端从 web/ 执行 pnpm lint、pnpm build、pnpm test：lint 报告 6 条现存组件导出警告，构建通过，16 项测试通过。涉及真实模型的发送及生成中刷新仍待验证，这篇因此保留 draft: true。
