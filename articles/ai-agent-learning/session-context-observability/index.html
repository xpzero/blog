会话越来越长，Agent 还记得什么？

柯寒2026年9月25日阅读 9 分钟

从一次旧会话的续聊出发，理解历史为何放不进模型请求、近期截断与摘要怎样配合，以及页面和统计能证明什么。

打开旧会话，页面已经能显示之前的消息，也能接着聊。但如果这个会话越聊越长，模型回答下一句时，还能看到最早聊过的内容吗？

页面显示旧消息，只说明应用保存了这些对话。模型不会自己去数据库翻历史；每次提问，后端都要重新准备这一轮发给模型的内容。所谓“记得”，在这里先指这次请求里有没有带上那段历史，而不是模型长期保存了这条会话。

原来的续聊方式：把对话历史再发一遍​

先看没有长度管理的流程。用户在旧会话中发出新消息，后端保存这条消息，沿着当前会话的消息链找回此前的用户提问和助手回复，按先后顺序与系统提示一起发给模型。系统提示是应用放在请求开头、交代模型任务的消息；模型这一轮收到的是重新拼好的请求，不是数据库本身。

假设先后聊了 A、B、C，现在又发出 D。这里的字母只是示意，不是实际请求记录：

数据库中的会话：A → B → C → D
没有长度管理时，本轮尝试发送：系统提示 + A + B + C + D

下一轮还会取回更长的历史。模型单次请求能容纳的内容有上限，还要为回答留空间；如果把过长的历史照单全发，请求可能因提示词超长被拒绝，用户拿不到这一轮回答。例如智谱接口文档列有 prompt 超长的 400 错误。这种错误不是模型读了前半段再忽略后半段。

因此，长度管理必须发生在发送前。下面讨论的是 demo-agent 的这一版实现：它怎样缩短本轮输入，以及缩短之后还能保留什么。

先缩短输入：留下近期原文​

最直接的办法是从新到旧挑消息，优先保留最近的原话。如果预算只装得下 C、D，本轮就不发送 A、B。数据库仍保存 A、B，页面也可以回显它们；只是模型这次回答时看不到它们。

图中两行请求对照的是尚未使用摘要的情况。变化的是本轮发给模型的内容，数据库里那四条原文没有被删掉。

这版程序把本轮输入的默认预算设为 24,000 个字符：先给系统提示和已有摘要留位置，再从最新消息向前保留原文。它按字符长度估算，并非模型能接收的 token 数；因此这个预算仍不能保证请求一定不会超长。

截断解决了“输入不断增长”的问题，却留下一个更难回答的问题：如果 A 中约定了用户目标，B 中定了限制条件，只发 C、D 时，模型还能依据那些早期约定回答吗？它们仍在数据库里，但这轮请求已经没有它们。摘要就是为这个缺口准备的。

摘要要解决什么问题​

摘要把较早的对话压缩为一段短文本，让它与近期原文一起进入下一轮输入。这样模型有机会得到早期目标和约束，不必每次重发全部原话。但压缩会丢失细节：摘要只能代表它实际收录的那些消息，也不能保证模型能从中恢复某句原话。

继续用 A、B、C、D 举例：假设 A、B 已被收录进摘要，而这轮留给原文的预算只够放 D。发送的内容会是“系统提示 + A、B 的摘要 + D 的原话”。**C 仍在数据库，却既没进摘要，也没在这轮请求里。**这是示意情形，用来区分两种容易混淆的缺失：早期消息被摘要代替，较近的消息也可能因本轮预算而暂时没发送。

在哪里看A、B、C、D 各是什么状态
数据库和页面历史四条原文都还在，页面可以回显
本轮发给模型的内容A、B 用摘要代表，D 保留原话，C 暂时没发送
摘要的边界停在 B，表示 A、B 已收录；不记录 C 在本轮是否被截掉

    living = [row for row in chain_rows

    reserved = estimate_tokens(system_prompt) + (

摘要从哪一轮开始起作用​

这轮模型请求发出时，用的是当时已有的摘要和近期原文。助手回复保存后，后端在聊天流收尾时检查是否需要更新摘要；达到条件才启动后台任务，另发一次模型请求生成新摘要。它不会改变刚刚结束的回答。

图中两种下一轮的结果，取决于它开始时新摘要是否已经保存。无需等后台更新完成才能继续聊天；如果下一轮先到，仍会使用旧摘要。

历史达到设定长度时，后台会尽量留下最近的原文，把更早的一批内容和旧摘要合成新摘要。如果更新失败，已保存的摘要保持不变；本轮输入仍按长度挑选近期原文。具体触发条件和处理步骤可见回复后的触发流程与摘要构造方式。

页面上的分隔线能告诉我什么​

重新打开旧会话，页面仍会加载保存的原文。它会在已收录消息的末尾画“更早的对话已压缩为摘要”的线，但不显示摘要正文，也不列出某一轮被长度预算临时截掉的消息。回到示例：线可以画在 B 后面；C 即使在线后，也不保证进了本轮请求。要确切知道某轮发了什么，必须观察那轮实际组装的输入。

下图展示一条演示会话重新打开后的历史页面：旧消息仍在，摘要分隔线也出现了。会话数据由本机模拟模型和较低的触发阈值生成；这张截图用于说明页面呈现，真实模型的摘要效果仍待验证。

统计面板能补上这份答案吗​

一次用户提问可能触发多次模型请求，还可能调用工具。后端为聊天过程记录每次模型请求的耗时与用量，以及工具执行的成败和耗时；页面可以查看按会话聚合的统计。但这些记录没有保存每轮发给模型的完整输入，因此不能从统计反推 C 有没有被截掉。

后台生成摘要的请求没有记入这份聊天统计；面板上的次数和用量因此不包含它。接口未返回实测用量时，页面会按字符数估算 token，并标上“估”。统计查询与账本可用于核对统计口径。

同一条模拟模型演示会话的面板显示“3 次模型请求”和“约 520 token（估）”。这组数字是演示账本的页面显示，不是实际服务商用量或费用。

回到开头的问题​

旧会话能回显所有原文，不等于模型每次都看到了所有原文。没有长度管理时，后端会尝试把消息链随新问题一起发送，过长请求可能被接口拒绝；这版实现先按字符预算选近期原文，再用摘要代表已收录的早期消息。摘要只能保留部分要点，未收录的中间消息也可能因本轮预算被略过。

页面分隔线只说明摘要收录到了哪里，统计面板也不保存本轮输入。要回答“模型这一轮具体收到哪几条原话”，还需要记录当时组装并发送的内容。

本文的流程以文中链接的代码版本为依据；截图展示的是模拟模型演示会话。真实模型生成摘要的效果尚未完成验证。
