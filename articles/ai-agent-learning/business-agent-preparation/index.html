做一个业务 Agent 需要准备什么：一次项目复盘

周期2026年10月12日阅读 15 分钟

做完一个带业务目标的 Agent 项目，盘点个人认为需要的准备、做完才理解的事，附术语、RAG 优化方案与 Agent 范式速查。

前段时间做了一个带明确业务目标的 Agent 项目：健身私教国际认证的备考助手，能对教材溯源问答、自动出题刷题、做学习规划，技术上用 LangGraph（把 Agent 流程画成图来编排的框架）组织多个子图，检索增强问答（RAG，先从语料检索相关片段、再让模型基于片段回答）做知识层。这篇不复盘项目本身，只整理一件事：动手之前，我以为主要工作是调通 LLM API；做完才发现，一半以上的精力花在教程不细讲、但个人认为很需要的"准备"上。

文章分三部分：上半是我认为需要的准备（七项，其中参数后台一项可选），中段是做完才理解的事，下半是可以收藏的速查区（术语、RAG 优化方案、三种范式）。项目细节不展开，只作为结论的出处。

全文结构一张图：

一、个人认为需要的准备​

1. 提示词资产：system prompt 只是零头​

写 demo 时一个 system prompt 就够；真做业务，prompt 的主体很快变成"功能性 prompt"——每个节点干一件小事的指令：把用户的口语问句改写成检索 query、让小模型给检索结果打分判断"够不够回答"、给出题按评分标准打质量分、扮演较真考生给题目挑刺。这类 prompt 的数量会反超 system prompt。

要准备的不只是"写"，还有"组织"：按业务域分文件集中管理；静态指令与带变量的模板（str.format 占位符那种）分开；占位符命名有约定。prompt 会成为数量最大的代码资产，第一天就要有组织约定，否则两个月后没人说得清"改这条会影响什么"。

2. 意图识别与路由：业务超过一个"科室"就要分诊​

问答、出题、刷题、规划——业务超过一件事，第一道工序就是判断用户这句话该交给谁。这就是 supervisor（分诊）节点要做的事。实践下来，两级路由的性价比最高：

  1. 规则快路径：关键词词表命中就直接路由，零成本零延迟，能吃掉大部分明确的请求；
  2. LLM 结构化路由：没命中的再走轻量模型，用结构化输出（约束模型输出符合 JSON Schema）返回"意图 + 置信度 + 一句理由"，抗住各种说法变体。

三个容易漏的细节：复合请求要拦截（"帮我看看学得怎么样，顺便出几道题练练"一句话两个意图，关键词快路径会误判，得靠信号词强制它走 LLM）；低置信别硬选，送到一个柔性兜底的科室（我的项目里是导师 agent，它能接着把其他科室当工具连着调）；路由本身挂了也要有默认去向。

另外，路由词表别写死在代码里——它是调试期改得最频繁的东西（见第 4 节）。

3. 密钥与模型分层：不止两行 env​

开发环境的 key 清单：LLM API key（按厂商）、观测平台的 key（我用 LangSmith 做链路追踪；LangChain 系项目靠几个环境变量就能开启，不用写接入代码）、数据库连接串。全部走 .env，不进仓库，留一份 .env.example 说明每个变量的用途。

但比 key 更重要的准备是模型分档：重活（生成答案、出题）用强模型；高频小活（路由判定、打分、查重这类"裁判"任务）用轻量 fast 模型——裁判调用占大头，两档之间的成本和延迟能差一个量级。还有一档容易忽略：embedding（把文本变成向量的模型，检索的地基）和 reranker（重排序模型）可以本地跑 ONNX，完全免 key、免配额——但要提前想清楚部署形态，这直接决定 RAG 一节的选型。

4. 可调参数的后台（可选）：方便改参数​

这一项不是必需，它解决的只是"方便"：会频繁改的东西——prompt、路由词表、阈值、开关——不用每次改代码、重启、发版。我的做法是两层读取：数据库覆盖层优先，没有覆盖就用代码默认值，删除覆盖即回到默认。

"prompt 配置能不能放后台？"能，但必须带防护：保存时校验占位符集合与默认值一致——编辑时删掉一个 {变量}，调用点 format 直接崩；再做一次试渲染让语法错误当场暴露；词表类配置做 JSON 格式校验。本质上就是把"改参数"从发版流程里摘出来，调试时的体验差别很大。

只是开了这扇门，就得回答"改完怎么知道变好没变"——这就轮到评测出场了。

5. RAG 与 embedding 选型：结构可以迭代，选型要趁早​

有知识问答就要准备 RAG。一条实操经验：检索结构可以后补迭代——加重排、调融合权重、改分块策略都是增量改动；但 embedding 选型要趁早，换 embedding 模型等于全库重新嵌入，越晚改成本越大。

选型时三个比榜单更真实的约束：语言匹配（中文语料用中文模型）；本地吞吐（只在本地部署时才是约束，embedding 走托管 API 的话这条可以忽略；CPU 上跑大模型不现实，我试过一个多语言大模型，吞吐直接不可用，只能回退）；区分度（太小的模型语义区分不足，检索指标天花板低）。验证方式只有一个：拿自己的语料建金标准，跑 Recall@K 对比——又是评测的事。

6. 会话状态与中断可恢复：教程的盲区​

业务流程几乎一定有"不能一口气跑完"的环节：生成学习计划要等用户确认，确认前可能还要求改两版。这意味着两件事要提前准备：

  • interrupt（中断）：流程走到"等确认"就停下来，把控制权交给人；
  • checkpointer（状态持久化）：图的执行状态落到数据库。用户明天再来、进程中间重启过，草稿还在，能从断点继续。

demo 教程几乎不覆盖这块，但它是"业务流程 Agent"和"问答玩具"的分水岭之一。

7. 评测：金标准是最大的准备工作​

为什么必须有：改任何东西——换 embedding、调分块、改一条 prompt——都需要基准，否则不知道是变好了还是变坏了。我项目里检索指标从 0.425 提到 0.545——用的是本地免费的 embedding 模型，没指望这个数字冲多高，重要的是每一步优化都有同一套基准可比；哪天换更强的模型，还是用它来量差距。

两类评测对应两层风险：节点流转（这句话该进哪个科室——意图路由准确率，路由错了后面全错）；数据校验（检索的 Recall@K / MRR，该召回的有没有排到前面；引用正确率，答案里的引用是不是真的支持结论）。

而最大的准备工作是金标准集（golden set，带标准答案的评测集）：检索的"问题 → 标准 chunk"、路由的"问题 → 应去意图"、引用的"答案 → 支持句"，每类先要有这样一套对应关系，指标才有得算——怎么构建、由谁构建，取决于各自的场景。最后让评测脚本输出退出码卡进 CI，门槛变成制度而不是自觉。

二、做完才理解的几件事​

1. 运行时质量闸门不等于离线评测。 离线评测测系统水平，但生成类内容每条都是新的，离线集测不完。给出题上闸门链：证据句与原文的逐字相似度（grounding）卡幻觉、与库内已有题查重、小模型按评分标准打质量分、再来一轮对抗评审。离线管水平，闸门管单条，缺一不可。

2. 确定性优先：每个环节先问"必须用 LLM 吗"。 客观题判分是纯规则、错题复习排程是 SM-2 算法（背单词软件同款的间隔重复算法）、多路检索融合是 RRF 公式——全是零 LLM 的纯代码，快、稳、免费。"哪里不用 LLM"和"哪里用"是同等重要的设计决定。

3. 失败路径占一半工作量。 每个 LLM 调用点都要预备"它挂了怎么办"：路由失败有默认去向、设置层损坏回退代码默认、工具环有步数上限防失控、收尾合成失败给固定话术。demo 只写 happy path，业务 Agent 的一半工作量在 unhappy path。

4. 可观测不是装个 key。 观测平台的真正价值在 trace 粒度：一次请求能拆到节点级——哪次路由、哪次检索、分数构成多少。排障时"能不能定位到是哪个节点哪次调用出的问题"才是验收标准。

5. 耗时任务要出请求线程。 文档解析、扫描版 PDF 的 OCR、批量出题是分钟级任务，放请求里必然超时。准备后台队列：任务表记状态、前端轮询进度、完成后再触发下游（比如索引完成自动出题）。

三、速查区​

术语速查​

术语是什么怎么理解
HyDEHypothetical Document Embeddings：先让 LLM 生成一段假想答案，用它做向量检索桥接"文体差"：用户问句是短口语，语料是长书面语，同一件事的两种文体在向量空间离得远；把查询侧也变成"文档"，两边就同文体了
RRFReciprocal Rank Fusion：多路检索结果按排名融合，分数是各路 1/(k+排名) 之和不比分数比排名：向量分和词面分量纲不同，排名才是通用货币
Recall@K前 K 条结果中包含正确答案的比例RAG 检索最常用的门槛指标（我项目卡 Recall@5 ≥ 0.75）
MRRMean Reciprocal Rank：第一个正确结果排名倒数的平均比 Recall 更严：关心正确答案"平均排第几"
reranker / cross-encoderquery 与文档拼在一起过编码器打相关分精排用：比向量检索（bi-encoder）准，但每对都要跑一次模型，只能给粗召回的前几十条
chunk文档分块，检索的最小单元大小、重叠、是否带【书名·章节】上下文前缀，都直接影响召回
grounding生成内容与原文的可追溯性最硬的测法是证据句与原文的逐字相似度
NLINatural Language Inference：蕴含 / 中立 / 矛盾三分类引用校验的语义判官：词面对不上时，判"这句结论是否真被原文蕴含"
tool calling模型按 schema 请求调用外部工具，结果回填后继续生成Agent 的"手"：模型只出"调什么 + 参数"，执行在代码侧
结构化输出约束模型输出符合 JSON Schema路由判定（意图 + 置信度 + 理由）就靠它，比手写"请返回 JSON"协议稳
supervisor分诊节点：先判意图再分发子图多业务 Agent 的前台
HITLHuman-in-the-Loop：关键动作前中断等人确认计划确认、审批类业务必需
checkpointer图执行状态的持久化会话中断可恢复的地基：状态落库，重启续跑
SSEServer-Sent Events流式输出的传输协议，打字机效果的载体
金标准golden set：带标准答案的评测集评测的前置工程，也是工作量最大的一块
SM-2间隔重复排程算法错题"几天后该再出现"不用 LLM，用它

工具调用更基础的介绍见前文：让模型用上它接触不到的数据。

常用 RAG 优化方案​

分块（chunking）本身就有好几种流派，先单列；其余手段按"解决什么问题"排列。

手段解决什么问题代价 / 前置条件
固定长度分块（大小 + 重叠）最简单可控的分块基线太长稀释语义、太短丢上下文，参数要靠评测试出来
按结构分块（标题 / 章节 / 段落边界）尊重文档天然的语义边界，块更完整只适用于结构化语料（Markdown、带目录的教材）
语义分块在相邻文本 embedding 相似度骤降的地方切开，块内语义更聚集全语料先算一遍 embedding，构建成本高
父子分块（small-to-big）小块检索更准，大块（父块）喂给 LLM 保住上下文要维护父子两层索引和映射关系
混合检索（向量 + 词面）向量对关键词精确匹配弱，词面对同义改写弱，两路互补两套索引都要维护，融合权重要调
查询扩展（multi-query）一个问法召回不全；生成多个变体查询分别检索再合并每个变体都要检索一次，还要写合并逻辑
HyDE 改写口语短问与书面长文的文体差每次检索多一次 LLM 调用，延迟与成本
加权 RRF多路结果怎么合成一个排序权重没有理论值，只能评测驱动地调
reranker 精排粗召回排序不准CPU 上单条延迟秒级，只精排前几十条的小窗口
chunk 上下文前缀（【书名·章节】）分块脱离出处后语义不完整嵌入时就要带上，事后补等于全库重嵌入
权威级加权语料来源质量不齐保守用：只做平局打破；权重大会压坏正确排序（实测教训）
元数据过滤先按来源 / 类型 / 时间收窄范围再检索入库时要打好元数据
金标准驱动迭代一切优化都需要尺子先得有一套金标准

三种 Agent 范式（基础理解）​

ReAct：想一步、做一步。 模型每轮决定"下一步调什么工具"，看到结果再决定下一步，步骤完全依赖前序结果。适合探索型任务——比如先查学情，看到薄弱点在哪，再决定出什么题。我的项目里导师 agent 就是这个形态：把查学情、出题、调计划当工具连续调用。

Plan-and-Execute：先出完整计划，再逐步执行。 适合能预先分解的多步任务；还有个省钱套路——规划用强模型做一次，执行用便宜模型做多次，偏了再重规划。我的项目里没有严格对应：规划子图是给"用户"做学习计划，不是 agent 自己拆解任务，这点不硬套。

反思：生成之后自己当评委，按批评修改再交卷。 适合质量敏感的生成任务；评委换个角色效果往往更好——让模型扮"较真考生"给题目挑刺，比"请你检查一下"抓出的问题多得多。我项目里出题的对抗评审、问答的"检索自评 - 改写重试"都是这个思路。

一句话选择建议：流程能写死就写死（静态编排），下一步看结果再定的用 ReAct，单次生成质量要求高的加反思环节。

收尾：准备清单总表​

#准备项一句话理由
1提示词资产功能性 prompt 数量反超 system prompt，第一天就要有组织约定
2意图识别与路由业务多于一个科室就要分诊；两级路由 + 复合拦截 + 兜底
3密钥与模型分层key 只是入场券；重活强模型、裁判活 fast 模型、本地模型免 key
4可调参数的后台（可选）方便改参数、改配置不改代码；prompt 可放，但要带占位符校验和回退
5RAG 与 embedding 选型检索结构可迭代；embedding 选型趁早，换一次重嵌入一次
6会话状态与中断可恢复interrupt + checkpointer，有"等确认"环节的业务必需
7评测节点流转 + 数据校验；金标准是前置工程，退出码卡 CI

每一样都从最小版本开始：prompt 先按域分文件，路由先上词表，评测先攒二十条金标准。跑通再升级，别一开始就搭全套。
