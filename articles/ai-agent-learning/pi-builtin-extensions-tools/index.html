tool_search 让模型搜索并启用工具，codemode 让模型写脚本调用其他工具。它们分别接收查询词和代码，都是 pi 的工具。

要理解它们，需要把一次任务从头走完：启动时工具怎样进入 pi，用户输入后模型收到什么，模型返回工具调用后谁来执行，执行结果怎样回到下一次模型请求。这条外层流程相同，两件工具在执行阶段做的事情不同。

先把 pi 的正常工具循环摆出来。以用户要求读取一个文件为例：

① 用户在 pi 输入任务
   → pi 整理对话消息和当前工具声明
   → 第一次请求模型

② 模型返回 read 的 toolCall，包含工具名和参数
   → pi 根据名字找到 read 的执行函数
   → pi 校验参数、执行工具、取得结果

③ pi 把工具结果加入对话
   → 再次请求模型
   → 模型根据结果回答，或继续发起工具调用

模型返回的 toolCall 是“请调用哪件工具、传什么参数”的数据，真正执行由 pi 完成。pi 的 runLoop() 负责推进这个循环：请求模型、检查回复中的工具调用、执行、加入结果、开始下一轮。以下按正常成功路径展开。

tool_search 和 codemode 都嵌在这条循环里。它们不会另起一个聊天模型，只是执行函数各有分工。

tool_search 工具​

先完成一次基本使用​

工具很多时，可以先让模型知道有检索入口，等需要时再提供具体工具的声明。声明包括工具名称、说明和参数结构，模型靠它决定怎样调用。

这里用一个本地测试服务器做例子。它通过 MCP（接入外部工具服务器的通信协议）向 pi 提供一件回显工具：

  • 服务器名是 demo，工具名是 echo，注册进 pi 后叫 mcp__demo__echo。
  • 工具接收 message 参数，返回 demo-echo says: 加上传入文本，便于观察调用是否发生。
  • 服务器配置为 "exposure": "deferred"，表示先注册工具、暂不向模型声明。

服务器代码和接入配置见本地 echo 服务器的搭建示例。接入后运行：

pi --tools +tool_search

再输入：“先搜索 echo 工具，再用它回显 deferred-demo。”测试会话记录了下面两次调用：

CALL:   tool_search {"limit": 5, "query": "echo"}
RESULT: Loaded 1 tool. They are available from your next call:
        - mcp__demo__echo: Echo a message back, prefixed with the server name.

CALL:   mcp__demo__echo {"message": "deferred-demo"}
RESULT: demo-echo says: deferred-demo

结果是一次回显，过程却有两件工具参与：先由 tool_search 找到 echo，再由 echo 执行操作。下面的时序图把正常成功路径连起来，省略了 read、bash 等与本例无关的工具声明。

注意图中两次不同的执行：搜索阶段只激活 echo，没有执行它；第二次模型请求取得 echo 声明之后，模型才发起真正的回显调用。下面沿这条顺序解释每一步。

启动：扩展注册工具，pi 选出激活列表​

pi 加载内置 tool-search 扩展，调用它的工厂函数。工厂把 createToolSearchToolDefinition() 返回的对象交给 pi.registerTool()，其中包含名字、说明书、参数结构和 execute() 执行函数。

这里要区分三个状态：

  • 扩展已加载：扩展的初始化代码执行了，可以注册工具、命令和事件。
  • 工具已注册：pi 保存了工具定义，能够按名字找到它。
  • 工具已激活：它被选入当前工具列表，可以在模型请求里提供声明。

tool_search 显式写了 defaultActive: false，所以默认执行 pi 时，它已经注册，但不会随注册自动激活。前面的 --tools +tool_search 才把它追加到默认工具选择中。MCP 扩展看到 deferred 服务器配置时，也会尝试激活它。

普通外置扩展工具则默认 exposure: "direct"、defaultActive: true，随注册自动激活。exposure 表示工具供模型或脚本访问的方式；开启 tool_search 不会把其他普通工具改成延迟声明。

// packages/coding-agent/src/extensions/tool-search/tool.ts（常量与完整函数，其余定义省略）
export const TOOL_SEARCH_TOOL_NAME = "tool_search";

export function createToolSearchToolDefinition(
	options: ToolSearchToolOptions = {},
): ToolDefinition<typeof toolSearchSchema, ToolSearchToolDetails> {
	return {
		name: TOOL_SEARCH_TOOL_NAME,
		label: TOOL_SEARCH_TOOL_NAME,
		description: TOOL_SEARCH_DESCRIPTION,
		promptSnippet: "Search for tools that are not loaded yet and load the matches",
		parameters: toolSearchSchema,
		// Searching is not something scripts need; it changes what the model sees.
		exposure: "model-only",
		// A query can match any tool that is not declared yet.
		reachesTools: () => "all",
		async execute(_toolCallId, { query, limit }) {
			if (query.trim() === "") throw new Error("query must not be empty");
			const max = limit ?? DEFAULT_TOOL_SEARCH_LIMIT;
			if (!Number.isInteger(max) || max <= 0) throw new Error("limit must be a positive integer");
			const tools = options.tools ? searchAndLoad(options.tools, query, max) : [];
			const text =
				tools.length === 0
					? "No matching tools found."
					: `Loaded ${tools.length} tool${tools.length === 1 ? "" : "s"}. They are available from your next call:\n${tools
							.map((tool) => `- ${tool.name}: ${tool.description.trim().split(/\r?\n/)[0]}`)
							.join("\n")}`;
			return { content: [{ type: "text", text }], details: { loaded: tools.map((tool) => tool.name) } };
		},
	};
}

入口传入的 tools: pi 提供了读取全部工具、读取激活列表和修改激活列表三个接口。它让检索工具能改变当前会话的工具选择。

这件工具的 exposure: "model-only" 表示只供模型直接调用，不能被其他工具或脚本嵌套调用。它控制的是调用入口，与前面 defaultActive 控制是否自动激活是两回事。

第一次模型请求：知道检索入口，还不知道 echo 的参数​

用户提交任务后，AgentSession（pi 的会话对象）准备消息和工具列表，再交给 Agent 循环请求模型。此时模型得到 tool_search 的声明，却没有 echo 的完整声明。

工具定义中的 description: TOOL_SEARCH_DESCRIPTION 是给模型的使用说明，内容如下：

查看说明书：tool_search 发给模型的描述
# Tool discovery

Searches over deferred tool metadata with BM25 and exposes matching tools for the next model call.

Some of the tools, such as tools of MCP servers, may not have been provided to you upfront, and you should use this tool (`tool_search`) to search for the required tools. For MCP tool discovery, always use `tool_search`.

说明书告诉模型：有些工具还没提供，需要时先搜索，命中项在下一次请求中可用。MCP 扩展还会提供服务器简介，指明该服务器的工具通过 tool_search 取得。

于是，第一次模型响应可以返回 tool_search 调用，查询词是 echo。这是模型根据任务作出的选择，pi 的外层循环随后执行它。

说明书没有复制全部候选工具名单，后台新增工具时它无需变化。连续请求中相同的输入文本，可能由支持提示缓存的服务商复用计算；其他输入变化及服务商规则仍会影响缓存命中。

执行检索：筛选候选、排序、修改激活列表​

pi 从工具表中找到 tool_search，校验参数并执行调用前钩子，再进入前面代码里的 execute()。它检查 query 不能为空、limit 必须为正整数，未指定数量时默认取 8，然后调用 searchAndLoad()。

MCP 工具可能还在后台连接。tool_search 的 reachesTools: () => "all" 表示搜索可能涉及全部工具，MCP 扩展据此在执行前等待相关连接完成，让新工具有机会先注册进来。

searchAndLoad() 处理的是下面这几份数据（只列本例相关工具）：

已注册工具：read、tool_search、mcp__demo__echo
已激活工具：read、tool_search

筛选候选：
  只取 exposure 为 codemode 或 deferred 的工具
  再排除已激活项
  → 留下 mcp__demo__echo

为候选构造检索文本，查询 "echo" 并排序
  → 命中 mcp__demo__echo

调用 setActiveTools：
  原激活列表 + mcp__demo__echo
查看代码：searchAndLoad 的完整实现
// packages/coding-agent/src/extensions/tool-search/tool.ts
function searchAndLoad(
	tools: NonNullable<ToolSearchToolOptions["tools"]>,
	query: string,
	limit: number,
): ToolSearchResultTool[] {
	const active = tools.getActiveTools();
	const candidates = tools.getAllTools().filter((tool) => isSearchable(tool.exposure) && !active.includes(tool.name));
	const documents = candidates.map((tool) => createToolSearchDocument(tool, tool.namespace));
	const matches = new Bm25Ranker().rank(query, documents, limit);
	if (matches.length > 0) tools.setActiveTools([...active, ...matches.map((match) => match.name)]);
	return matches.map((match) => ({
		name: match.name,
		description: candidates.find((tool) => tool.name === match.name)?.description ?? "",
	}));
}

**修改激活列表和执行 echo 是两个动作。**此处只加入工具名，echo 的业务函数还没有运行。execute 返回的 Loaded 1 tool… 是检索工具自己的结果，外层循环把它加入对话。

普通 direct 工具即便默认未激活，也不在这里的搜索池中；hidden（禁止访问）工具同样不会成为候选。只有已注册、尚未激活的 codemode、deferred 工具参与检索，实际激活还受启动时工具限制约束。

下一次模型请求：刷新工具，才真正调用 echo​

当前这次请求已经结束，不能在途中把新声明塞回模型。下一轮开始前，pi 的会话对象会重新读取激活列表，更新工具说明和系统提示，并把最新工具对象交给 Agent 循环。

关键就在 _installAgentNextTurnRefresh()：它注册“下一轮准备”回调，回调中的 selectedTools 取当前激活列表，返回的 context.tools 取当前工具对象。

此时第二次模型请求同时包含检索结果和 echo 的工具声明。模型才能根据 message 参数结构返回 mcp__demo__echo 调用，pi 再走一遍执行流程，得到回显结果。结果进入第三次模型请求后，模型给出最终回答。

所以，tool_search 的原理可以落在两个具体位置上：执行时修改会话的激活列表，下一轮准备时把新列表变成模型请求中的工具声明。工具集变化也会随对话记录保存，恢复会话或切换分支时按对应路径恢复。

排序怎样发生，哪些场景适合用​

候选匹配使用 BM25，一种按关键词相关性打分的算法。每件工具的待检索文本来自：

  • 工具名及下划线拆开的形式。
  • 工具描述。
  • 参数结构中的字段名与说明。
  • 所属命名空间的名称、描述和指引，例如 MCP 服务器信息。

查询和文档都先拆分 camelCase、转小写、去停用词（删除 a、the、with 等常见、区分度低的英文词），再归并部分英文单复数。排名综合词频、查询词在工具集合中的稀有度、文档长度，只返回正分命中。

当前分词只保留英文字母与数字。纯中文查询会得到空查询词，返回 No matching tools found.；中英混合查询依赖留下来的英文部分。工具说明书没有要求英文，也没有自动翻译或针对性错误提示，因此中文对话中不能保证模型会发出有效查询。使用英文工具名或关键词可以改善当前查询，但中文描述的检索仍受分词限制。

它主要适合接入大量 MCP 工具，或者扩展、SDK 开发者批量提供延迟声明工具的场景。对后者，exposure 是每件工具的字段，可以在注册循环中统一设为 deferred。少量默认工具通常不需要检索，开启 tool_search 也不会自动隐藏它们的说明。

codemode 工具​

先完成一次基本使用​

codemode 接收模型写的 JavaScript，在准备好的执行环境中运行。脚本可以批量调用工具，也可以串联有依赖的调用、筛选结果，再把需要的内容返回模型。

当前目录准备两个小文件：a.txt 内容是 alpha file content，b.txt 内容是 beta file content，然后运行：

pi --tools +codemode

输入：“用 codemode 并行读取 a.txt 和 b.txt，把内容拼起来返回。”测试会话中，模型提交的脚本如下：

const [a, b] = await Promise.all([
  tools.read({ path: "a.txt", offset: null, limit: null }),
  tools.read({ path: "b.txt", offset: null, limit: null }),
]);
return a + b;

返回结果为：

Script completed
Wall time 0.1 seconds
Output:
alpha file content
beta file content

这里外层是一件 codemode 工具，里面调用了两次 read。下图把 pi 的外层循环与脚本内的并行调用放到同一条时间线上；“codemode 执行器”是 pi 内部的执行逻辑，QuickJS 脚本在 worker 线程中运行。

两次 read 的结果先回到脚本，模型收到的是 codemode 最后生成的一条结果。下面依次看脚本怎样进入执行器、工具调用怎样跨过执行环境边界，以及返回值怎样回到外层循环。

启动与第一次请求：把执行脚本的能力告诉模型​

codemode 的扩展工厂注册一件名为 codemode 的工具，并设置 defaultActive: false。前面的启动参数将它激活；默认的 read、bash、edit、write 仍按普通工具保留。使用 MCP 的默认脚本访问方式时，MCP 扩展也会尝试自动开启 codemode。

用户提交任务后，pi 给模型发送对话和工具声明。codemode 的声明包含参数结构和说明书，参数只有一个字符串字段：

// packages/coding-agent/src/extensions/codemode/tool.ts（节选）
export const codemodeSchema = Type.Object({
	code: Type.String({
		description: "Raw JavaScript source.",
	}),
});

模型的第一条响应可以是 codemode 工具调用，统一参数结构为 { code: "脚本内容" }。支持语法约束工具输入的模型接口也可以直接生成原始脚本，协议层再把它还原进 code 字段。执行器最终处理的都是这个字符串。

说明书先规定脚本的写法，再介绍可用接口和工具目录。下面是固定开头的原文：

查看说明书：模型怎样得知脚本格式和执行规则
Run JavaScript that calls other tools. The input is raw JavaScript (not JSON, no code fence), run as an async function body in a QuickJS sandbox: top-level `await` and `return` work. No Node, file system, network, or timers.
- `await tools.<name>({ ...args })` resolves to a string, or an object if the tool's declaration says so, and rejects with an Error on failure. A tool whose declaration returns an object resolves on failure too when it returned that object; check its fields. Calls still running when the script ends are cancelled.
- Optional first line: `// @options: {"max_output_tokens": 10000, "timeout_ms": 60000}`

其中“not JSON”描述的是脚本内容的写法：不要把代码本身写成一份 JSON 文档，也不需要 Markdown 代码围栏。工具调用在 pi 内部仍然有 code 参数。

模型从这里得知顶层 await、return 可用，工具可以通过 tools.<name>() 调用。因此，它能写出上面的 Promise.all() 脚本。

export function createCodemodeExtension(options: CodemodeExtensionOptions = {}): ExtensionFactory {
	return (pi) => {
		pi.registerTool({
			...createCodemodeToolDefinition({
				appendEntry: (customType, data) => pi.appendEntry(customType, data),

			}),
			defaultActive: false,
		});
	};
}

pi 收到调用：取出脚本，准备本次执行环境​

外层 Agent 循环从模型回复中取出 codemode 的 toolCall，找到这个定义，执行参数校验与调用前钩子，再调用 execute()。定义里真正接入执行器的是这一段：

execute: async (toolCallId, params, signal, onUpdate, ctx) =>
	(await loadCodemodeExecutor()).executeCodemode(toolCallId, params, signal, onUpdate, ctx, options),

这里的 ctx 是 pi 传给工具执行函数的上下文（ExtensionToolContext），提供当前会话的运行接口：ctx.tools 列出可嵌套调用的工具，ctx.executeTool() 负责实际执行它们。它只在 pi 宿主侧使用，模型写的脚本访问不到 ctx。

executeCodemode() 先解析 params.code，拆出可选的首行选项和脚本正文，然后取得当前会话允许脚本调用的工具：

  • 已激活的 direct 工具，例如当前默认的 read、bash。
  • 已注册的 codemode、deferred 工具，例如间接提供的 MCP 工具。
  • model-only、hidden 工具不进入集合，脚本不能再启动 codemode，也不能调用 tool_search。

四件基础工具没有设置工具级隐藏，默认使用 direct。扩展在启动 UI 里隐藏名称的 hidden 字段，不影响这里的工具选择。

准备好工具后，pi 创建 CodemodeSandbox。它使用 QuickJS 的 WebAssembly 版本，在 worker 线程中运行 JavaScript。worker 让脚本计算与 pi 主线程分开；QuickJS 的隔离环境让脚本没有 Node 文件系统、网络或模块访问，只能使用开放给它的接口。

脚本本身送进 worker，实际的 read 函数保留在运行 pi 的宿主线程。接下来需要靠消息在两边转交调用和结果。

脚本执行 tools.read：把调用送回宿主，而不是再问模型​

**pi 准备 QuickJS 执行环境时，会根据可调用工具清单创建代理函数，放进脚本的 tools 对象。**脚本调用 tools.read()，代理向 pi 宿主请求执行真实的 read 工具；宿主执行后把结果送回来，代理完成对应的 Promise，await 取得结果，脚本继续运行。

代理负责转交请求和接收结果，实际工具函数保留在宿主侧。这个往返是异步的，所以脚本可以同时发出多次调用，再等待各自的结果。

具体实现跨过两层边界：QuickJS 内的代理通过预先注入的 bridge 回调，把工具名、调用编号和 JSON 参数交给 worker 侧代码；worker 再通过 Node 的线程消息通道将调用发给宿主。宿主收到消息，按工具名找到事先准备的包装函数，调用 ctx.executeTool("read", args)，依次完成参数校验、执行前钩子、实际读取和执行后钩子。

下面只展开一次成功的 read 调用。QuickJS 位于 worker 线程内，worker 通过消息与 pi 宿主线程交互；图里的 read 工具是宿主侧的实际工具实现。

调用编号 id 把一条请求和它的结果对应起来，因此多次工具调用同时等待时，也能完成各自的 Promise。result 表示一次工具调用返回，done 表示整段脚本结束：收到 read 的结果之后，QuickJS 仍可以继续计算或调用其他工具。

这里没有新的模型请求。模型已经交出整段脚本，后面的读取和拼接由程序推进。Promise.all() 会先发出两次读取，再等待两个结果；哪个先完成可以不同，返回数组仍按原来位置排列。工具自身要求串行执行时，pi 的调度器仍会遵守它。

查看代码：宿主工具包装、运行沙箱与结果转换
// packages/coding-agent/src/extensions/codemode/execute.ts（连续节选）
const sandboxTools: CodemodeTool[] = callable.map((tool) => ({
	name: tool.name,
	description: samples.get(tool.name),
	execute: async (args, { signal: callSignal }) => {
		const record: CodemodeNestedCall = {
			id: `${toolCallId}/?`,
			name: tool.name,
			args: previewArgs(args),
			status: "running",
		};
		calls.push(record);
		publish();
		const callStartedAt = performance.now();
		// Only tools from ctx.tools are callable, so ctx is set here.
		if (!ctx) throw new Error("Tool calls need a session");
		const outcome = await ctx.executeTool(tool.name, args, { signal: callSignal });
		record.id = outcome.toolCall.id;
		record.durationMs = performance.now() - callStartedAt;
		if (outcome.isError) {
			record.status = callSignal.aborted ? "cancelled" : "error";
			record.error = truncateText(textOf(outcome.result) || `Tool "${tool.name}" failed`, ERROR_PREVIEW_CHARS);
		} else {
			record.status = "ok";
		}
		publish();
		return toScriptValue(tool, outcome);
	},
}));
// 同文件后续代码节选，沙箱构造的其他选项省略，中文注释为本文所加。
const sandbox = new CodemodeSandbox({
	tools: sandboxTools,
	// 另有全局接口、超时、内存限制、WASM 与 worker 等选项。
});

let result: CodemodeResult;
try {
	const store = ctx ? readCodemodeStore(ctx.sessionManager.getBranch()) : {};
	result = await sandbox.execute(code, { signal, store });
} finally {
	await sandbox.close();
}
// 同文件完整函数：决定工具结果中哪部分交给脚本。
function toScriptValue(tool: AgentTool<any>, outcome: AgentToolCallOutcome): unknown {
	const { result } = outcome;
	if (tool.outputSchema && result.structuredContent !== undefined) return result.structuredContent;
	const text = textOf(result);
	if (outcome.isError) throw new Error(text || `Tool "${tool.name}" failed`);
	return text;
}

最后这个函数解释了 a 为什么是文件文本：read 声明了输出结构，并提供文本形式的 structuredContent，包装函数直接把它交给脚本。没有结构化结果时，执行器合并文本内容；失败且没有可返回的结构化结果时，则抛出错误。

工具原有的限制仍然有效。read 返回的文件文本受自身截断规则约束，bash 则专门提供上限为 1 MiB 的结构化输出，codemode 不会统一取消这些限制。MCP 的结构化结果还可能包含 isError: true，脚本要检查这个字段。

脚本 return：生成一条外层结果，再请求模型​

当两次 read 都完成，QuickJS 继续执行 return a + b。沙箱结束执行，将返回值放在 result.value 中。pi 的执行器把返回值追加到脚本输出，添加完成标记、耗时和 Output:，返回一份普通工具结果。

这时才回到文章开头的外层循环：Agent 等待的 codemode 调用完成了。pi 把这条结果加入对话，带着它再次请求模型，由模型整理成用户看到的回答。

两次 read 属于嵌套调用：执行事件仍可展示在 UI，调用摘要也会附在外层结果的元数据中，但不会各自生成一条提供给模型的工具结果消息。模型看到的正文由脚本选择的输出决定。

这个例子把两个文件完整拼回来了，主要展示执行流程。若脚本先过滤、统计，只返回少量字段，才会减少中间结果占用的上下文。模型生成脚本、工具说明和最终输出仍有 token 开销。

在这条流程上，其他设置分别影响哪一步​

前面的基本流程还受一些设置影响。它们分别对应准备模型请求、执行脚本和提交结果三个阶段。

准备模型请求：on、only 模式和工具目录预算

模型需要知道脚本可以调用什么。codemode 激活时，prepareLoadout() 按当前工具集合更新说明书。

模式模型如何获得调用信息
on，默认普通工具保留独立声明，并在说明里附上脚本调用方式；codemode 目录从非 direct 的可调用工具中选择
only隐藏可由脚本调用的已激活 direct 工具的独立声明，将它们也纳入 codemode 目录候选

目录默认预算约 3000 token，由 codemode.inlineBudget 控制，按每 4 字符估算 1 token。候选按命名空间分组，每轮从每组挑一件较短的工具说明，放不下的组退出。

deferred 工具不列进目录，但可以被脚本查询和调用。MCP 配置中的 codemode 会适配成工具内部的 deferred，所以连接很多 MCP 工具也不会把它们的说明全塞进 codemode 目录。

执行脚本：输出、工具检索、存储与模型接口
接口影响流程中的什么动作
text(value)、return value选择最终交给模型的输出
image(value)输出图片，由宿主保存临时文件
console.log() 等收集日志，放入结果的日志块
searchTools()、describeTool()、describeNamespace()、ALL_TOOLS在脚本中查询可调用工具与说明
store()、load()跨调用保留少量 JSON 数据
models查询模型目录，调用分类器、图像模型，不能运行聊天模型

脚本中的 searchTools() 与独立工具 tool_search 共用 BM25 代码，但只返回工具信息，不改变模型的激活列表。脚本取得工具名和说明后可以继续调用，不必等下一次模型请求。

store() 的成功写入作为 codemode-store 自定义条目进入会话文件，load() 只读取当前分支路径上的值。这是 pi 集成提供的持久化，底层沙箱库本身不写会话文件。

结束与失败：取消、输出限制和已经发生的操作

脚本可以在第一行写：

// @options: {"max_output_tokens": 2000, "timeout_ms": 60000}

输出默认预算约 10000 token，超长时保留开头和结尾，全文另存文件；未指定超时则不设置这项截止时间。pi 为 QuickJS 配置 256 MiB 堆限制，同进程最多同时存活两个 codemode worker，退出中的 worker 也占名额。

失败时，已产生的输出保留并附上错误；此前工具操作不会回滚，未完成调用会收到取消信号，store() 写入不提交。使用 Promise.allSettled() 可以在部分工具失败时继续处理其他成功结果。

沿外层循环看，两件工具的区别就落在了执行后的变化上：tool_search 改变下一次请求可用的工具，codemode 在一次工具执行里完成多个操作，再把选择的输出交回下一次请求。它们都由 pi 的同一条 Agent 循环调度。
