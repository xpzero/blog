Agent 学习小结：不想写确定性代码之后

柯寒2026年9月13日阅读 5 分钟

一个基础 Agent 跑起来了，我却发现自己不想再写确定性的代码。重新想了一遍这个问题：AI 辅助的工作模式下，人应该把控什么。

从零认识一个基础 Agent​

「从零认识 Agent」系列走到第十一篇。demo 已经有个基础 Agent 的样子：会调用工具、流式输出、读写文件、联网搜索，写文件前会请求用户批准，多轮会话存在本地。回看这套代码，AI 写了大部分实现，我负责拆解每一步做什么、检查它写得对不对。

写到这里，我发现自己出了点问题。或者说，发现了一点变化。

我开始不想写确定性代码了​

最近实现新功能时，我越来越不想自己敲那些确定性的代码：循环的边界、参数的解析、异常的兜底。这些东西我完全会写，但 AI 一轮就能给出可用的实现，我再逐行敲一遍，感觉像在用手扶犁耕地。

第一次把一个完整功能整体交给 AI 写的时候，我甚至有点愧疚，像在考试里作弊。后来次数多了，愧疚变成了别的东西：不安。

不安来自哪里​

一个来源很模糊：这样做是不是"正道"？毕业这些年攒下来的手艺，交给模型代劳，我是在升级工作方式，还是在自废武功？

另一个来源很具体：LLM API 是无状态的。每次对话，它都不记得上一次的实现。一个长期项目，全靠 AI 写，意味着每个功能都是"失忆的工程师"接手别人的代码再往下写。我对这个项目的掌控感在流失。代码在仓库里，但"我知道每一行为什么是这样"的那种踏实感没有了。

更现实的问题是 review。AI 一次实现一个很大的需求，几百上千行变更，逐行审既痛苦又不切实际。审不完的代码，等于没审。可要是干脆不审，这个项目还算是我在维护的吗？

重新想这个问题​

后来我想，难受的可能不是"AI 在写代码"，而是我还在用旧标准要求新模式：逐行掌控。这套标准在亲手敲代码的阶段是美德的来源，在 AI 辅助时代变成了痛苦的来源。

有意思的是，答案我其实已经在自己的项目里实践过了。

demo-agent 的模型调用就是无状态的：store=False，服务端不保存任何上下文。我给它的补偿方案是自己在本地管理完整的 Items、做 Session、做 checkpoint。模型没有记忆，我就把记忆做在它外面。

AI 辅助开发里我做的事是一样的。AGENTS.md 是给 AI 的项目规范，README 里 V1 到 V11 的演进记录是项目的历史记忆，每篇文章的验收表和测试清单定义了"什么算做对了"。项目记忆不在我脑子里，也不在模型脑子里，在仓库里。掌控感的挂点，从"我记得每一行代码"换成了"我维护这个项目的记忆和边界"。

第十一篇的权限设计，其实就是这件事的缩影：模型提出工具调用，人裁决 allow、ask、deny，批准后才执行。写的时候我把它当成 Agent 的安全设计，现在看，这就是 AI 辅助工作模式的雏形。

那人应该把控什么​

初步的答案，带着"或许"。

问题的定义权和拆解权在人，这条没什么好犹豫的。拆错了，AI 执行得越好，错得越远。

其次是逻辑和边界。状态放哪里、谁信任谁、失败了怎么办、路径怎么校验，这些是系列文章里真正花篇幅写的东西。至于那个循环用 for 还是 while，我不再在乎了。

然后是验收。测试、验证标准、真实环境里跑出来的证据。AI 写得对不对，由我定义的"对"来裁决。

这样看，我的角色确实在变：从一个写代码的人，变成一个带着开发思维和技术知识的测试。我一开始觉得这话有点自贬，后来想明白了，在这个分工里，测试是最终的质量裁决者。开发思维让我问得出对的问题，技术知识让我在 AI 错的时候能看出来它错在哪。这两样恰恰是毕业这几年攒下来的，没有作废。

结语​

这篇没有结论，只有一个阶段性的答案。手写代码作为默认工作方式的时代大概率结束了，但排期管的是交付，管不了判断。判断由谁来做、怎么做，最近想得比之前清楚了。

系列还会继续往上搭：上下文控制、记忆系统、多 Agent 协作。"人把控什么"这份清单到时候会变长还是变短，不知道。至少现在，我对"不想写确定性代码"这件事没那么不安了。
