让 Agent 读取 README，聊天界面很快就给出了启动说明。回答之前经历了哪几步，工具在哪一步执行，运行又为什么结束？

打开开发者工具中的「会话数据诊断」，可以把聊天内容与运行记录放在一起看。Agent 循环和工具把发生的事写入 Session，检查器读取这些记录，再按 turn、step 展示执行过程。

打开开发者工具，运行一个读文件任务​

「开发者工具」是一个可选的组合包，对应 @deepseek-ai/dsh-experimental-inspector-profile。启用后，Web 应用会增加三个观察入口：

入口用来观察什么
会话数据诊断当前会话的原始记录，以及聊天界面使用的分组与节点
统计页签每轮、每步的上下文、耗时、缓存和工具成本
NodeJS 诊断后端（Host）调试，以及后端、浏览器端（Client）的 Cordis 运行结构

这里从「会话数据诊断」看一次任务怎样执行。它展示执行留下的会话记录。Agent 实例的创建、running/idle 变化和销毁，还涉及另外的运行时通知。

从源码运行时，先按开发文档完成环境与依赖准备，再在仓库根目录构建运行产物、启动 Web 应用：

pnpm run build:artifacts
pnpm run start:web

应用打开后，完成一次最小操作：

  1. 在模型设置中配置可用模型，并在新会话中选中它。
  2. 打开「插件」，在「实验性插件」中找到「开发者工具」并确认开关已开启。列表中没有时，先点旁边的「更多」。
  3. 新建会话，打开右侧边栏，从引导页或新建标签页菜单选择「会话数据诊断」，保留默认的「原始数据」展示。

这个组合包还会记录 Host 发出的 fetch 请求，请求头与正文均未经脱敏。

在终端准备一份内容已知的 README，并打印要发给 Agent 的任务：

CASE_DIR="$(mktemp -d)"
cat > "$CASE_DIR/README.md" <<'FILE'
# Greeting demo

Run `pnpm start` to print a greeting once.
FILE
printf '请用 read 工具读取 %s/README.md，然后用一句话说明项目怎样启动。只读取这个文件，不修改文件，不运行任何项目命令。\n' "$CASE_DIR"

把打印出的任务粘贴到会话中发送。下面是本机 Web 应用的一次实际运行：选用 gpt-6.1-sol，模型通过配置的兼容路由返回了工具调用与回答。右侧面板收起了模型分片子行，可以直接看到任务的主要起止记录。

左边的回答是「在项目目录运行 pnpm start 即可启动，程序会打印一次问候语」。右边能看到工具调用与结果出现在 1/1，后续回答出现在 1/2。打开图片可以放大阅读记录。

图中三条 user/message 只有一条来自用户输入，另外两条是框架补入的运行环境与时间上下文，可通过 source.kind 区分。

从两步记录还原一次执行​

先认出三个概念：

  • Session 是会话对象，保存消息与运行事件，可以跨多次任务继续使用。
  • turn 是 Agent 开始处理一批输入，到满足结束条件的一段运行。
  • step 是其中一次逻辑上的模型请求及其工具处理。一次 turn 可以包含多个 step，同一步内也可能重试模型请求。

面板中的 T/S 表示 turn/step 编号。比如 1/2 表示第一个 turn 的第二个 step。只显示 1 的 turn 起止记录，描述的是整轮边界。

沿着这次记录的序号读取，可以还原下面的过程。这里省略了提示词、请求信息和流式分片，保留实际事件顺序：

 4  turn/start                   开始 turn 1
 6    step/start                 开始 step 1
14      assistant/message        模型回复中提出 read 调用
15      tool/call                处理这项读取调用
16      tool/result              得到 README 内容
17    step/end                   step 1 结束
18    step/start                 开始 step 2
19      assistant/message        模型根据文件内容给出启动说明
20    step/end                   step 2 结束
21  turn/end                     reason.kind = completed

工具调用和工具结果属于第一步。利用工具结果继续生成回答，进入第二步。 工具结果提供了新的上下文，因此循环需要再请求模型。这次任务实际执行了两步，步骤数由模型回复与后续输入共同决定。

每条原始事件都有 type、seq、time 和 data。序号确定事件先后，数据中的 turn、step 等字段说明事件归属。面板沿用这些记录的顺序，再增加缩进与折叠层级。

这些边界由谁写入​

收到用户任务后，Agent 把输入放进等待处理的 inbox。空闲 Agent 被唤醒，循环开始一个 turn，并先追加 turn/start。

随后循环准备下一步：领取输入，确定模型和工具，组装提示词，并通过 agent/pre-step 扩展点决定是否接纳本步。准备通过后，才追加 step/start 并进入模型请求。因此，准备阶段被拒绝或失败时，可以有 turn 起点而没有 step 起点。

模型回复带有工具调用时，循环先记录 assistant/message，再交给工具服务处理。工具服务记录调用及其结果。普通读文件工具完成后，循环结束当前 step，继续准备下一步，让模型读到工具结果。

下一步回复给出完成原因后，循环还会检查是否有待处理输入，并执行 agent/turn-stopping 扩展点，让插件有机会补入续跑输入。满足结束条件后，才追加 turn/end。这条因果链在 Agent 的 turn() 中可以核对。

Session 的记录怎样到达浏览器​

检查器运行在浏览器里，Agent 循环运行在 Host 进程里。连接两边的是 Web 应用已有的会话数据服务：

一条工具结果到达面板，经过下面几个连接点：

  1. Session 先把事件追加到内存日志，再通过 Cordis 的 session/event 通知观察者。
  2. Host 的 Session Controller 订阅当前会话的事件。浏览器通过 session.follow 先取得一段历史快照，再持续接收新增记录。
  3. 浏览器维护当前会话的 eventSource，即供界面订阅的会话事件数据源。历史和新增记录进入同一个已加载窗口。
  4. 检查器从当前会话取得这个数据源，交给 SessionLogModel 组织成表格行，并在数据变化时更新页面。

所以，运行之后再打开面板也能看到已有记录。更早历史超出已加载窗口时，需要使用「加载更早」。看见一行记录，说明它已进入会话数据流，磁盘保存则由持久化层处理，不能仅凭页面出现就断定写盘完成。

平铺记录怎样变成 turn、step 层级​

Session 中的原始记录按序追加。面板里的 turn、step 折叠结构，来自检查器对开始、结束事件的顺序扫描：

  • 遇到 turn/start，将这条原始记录作为当前 turn 的组头。
  • 遇到 step/start，在当前 turn 下打开 step，将后续记录放进这一步。
  • 遇到 step/end，保留它作为 step 的末尾记录，再关闭当前 step 范围。
  • 遇到 turn/end，保留它作为 turn 的末尾记录，再关闭当前 turn 范围。

因此，面板折叠一个 step，只是在界面上收起对应行。它不会影响正在运行的循环。分页只加载到某段历史中间时，检查器也不会凭空补一个开始事件。加载到更早的 start 后，才补上对应层级。

查看源码：用开始、结束事件建立分组

下面是 SessionLogGroups.append() 的节选，省略方法外层及后面的 child() 辅助方法：

    switch (event.type) {
      case 'turn/start':
        this.step = undefined
        this.turn = { ...row, disclosure: 'open' }
        return this.turn
      case 'step/start':
        this.step = { ...this.child(row, this.turn), disclosure: 'open' }
        return this.step
      case 'step/end': {
        const result = this.child(row, this.step ?? this.turn)
        this.step = undefined
        return result
      }
      case 'turn/end': {
        const result = this.child(row, this.turn)
        this.step = undefined
        this.turn = undefined
        return result
      }
      default:
        // Other merge-extensible events inherit the open range.
        return this.child(row, this.step ?? this.turn)
    }

child() 只给表格行增加父级引用和缩进深度。原始事件的数据与顺序仍然保留。

模型回复下面还可以展开 block-start、文本或工具参数 delta 等分片。这里的 delta 表示流式响应中逐次到达的增量。这些子行与顶层的 Session 事件不是一行对一条的关系。

运行时，客户端会把 Assistant 的实时通知暂时组织成 assistant/live 行。一次模型尝试结算后，这些临时内容会由 assistant/message 或失败尝试的 assistant/attempt 记录替换。最终记录的 stream 也保存带时间的分片，检查器可以从它重新展开子行。因此，历史中看到几十条 delta，不等于 Session 为每个 delta 各追加了一条顶层事件。对应实现见客户端事件定义与检查器的分片展开。

同一个面板，为什么还有对话分组​

切换左上角的展示形式到「对话分组」，同一次任务会出现 user、assistant-step、tool-call、group 等行：

两种展示回答的问题不同：

展示形式读取的数据适合回答的问题
原始数据会话事件数据源，包含已记录事件与实时分片先发生了什么，步骤何时开始、结束
对话分组聊天视图已经组装好的 Node、Group 对象哪些内容组成工具卡片、回答和可折叠的工作步骤

Node 是聊天视图使用的内容节点，Group 用来组织节点。检查器从现有 Conversation 读取它们，能够将选中的对象定位回左边的聊天内容。前面的 tool/result 详情与读取操作对应，就是通过记录坐标寻找现有聊天展示位置。

原始事件与聊天节点之间会经过界面组装，因此两种模式的行数和类型可以不同。顺着一次读文件任务，先用「原始数据」确认执行顺序，再用「对话分组」查看展示对象，就能把运行事实与界面组织连接起来。

结束记录怎样说明失败与成功​

成功案例的序号 21 是 turn/end，原始详情中 data.reason.kind 为 completed。判断结果时，这个原因比单纯看到结束行更有用。

一次模型连接失败的实际记录，同样出现了 step/end 和 turn/end。选中最后一条记录，详情显示：

这次运行在第一步请求模型时以 TRANSPORT 错误结束，读文件工具尚未执行。循环在 finally 中记录 step 与 turn 的收尾，所以失败时仍有完整的结束边界。

step/end 说明步骤已经结束，turn/end 说明这一轮已经关闭。要判断任务是否完成，还需要结合 turn/end 的原因与工具结果。检查器把这些事实放在同一个画面中，继续、停止和失败的决定，则由产生记录的 Agent 循环及相关插件作出。
