让 Agent 读取 README，模型先请求读文件，再给出启动说明。为什么读完文件还会继续请求模型，而给出回答以后又能结束？

一次 turn 可以包含多个 step。每个 step 发起模型请求，把回复和工具结果写回 Session，再将“继续”或结束原因交给外层 turn。 外层检查待处理输入和停止扩展点，才决定下一步或结束。开发者工具展示的是这条执行链留下的记录，决定仍由运行端做出。

先把一轮执行接起来​

先约定本文使用的 DSH 术语：

  • Session 是会话对象，保存消息与执行事件，并从这些记录中推导发给模型的有效历史。
  • turn 是 Agent 开始处理一批输入，到满足结束条件的一段运行。
  • step 是 turn 中的一次逻辑模型请求及其工具处理。同一步内遇到可重试错误，还可以再次请求模型。
  • request attempt 是其中一次实际请求尝试。它的流式响应先在内存中累积，再结算成一条会话记录。

执行代码调用 Session.append() 写入记录，Session 再发出 session/event 通知观察者。Session Controller 将记录和临时流式帧传给浏览器，检查器负责展示。因此，模型流结束、一步结束、一轮结束，是三个不同的边界。下面先观察一次完整任务，再沿这条链解释每个边界怎样产生。

外层循环怎样把这些边界连起来​

输入唤醒空闲 Agent 后，驱动器 kick() 启动。它反复调用 turn()，每次等待一整轮处理完。turn() 内部还有一个循环，负责一遍遍准备和执行 step。外层管理轮次，内层推进当前任务。

一轮开始时先记录 turn/start，然后按以下顺序推进：

  1. preStep() 从 inbox 领取候选输入，准备模型与工具，取得允许或拒绝的决定。
  2. 外层检查决定和当前结束原因，通过后记录 step/start，调用 step()。
  3. step() 完成模型请求与工具处理，返回继续或结束原因。外层保存这个结果，并在 finally 中记录 step/end。
  4. 如果已有结束原因且本轮输入为空，执行停止扩展点，再检查一次输入。仍为空就跳出内层循环，否则准备下一步。

跳出内层循环后，turn/end 关闭本轮。正常收尾还有待处理输入时，turn() 返回 true，让 kick() 再开一轮。没有后续工作时返回 false，驱动器结束并把 Agent 状态改为空闲。

查看源码骨架：kick 驱动 turn，turn 驱动 step 并检查停止

下面按 kick() 与 turn() 的原控制流简化。保留决定继续与结束的分支，省略取消检查、工具恢复、资源释放与错误转换细节。它是用于阅读控制流的伪代码：

private async kick(): Promise<void> {
  try {
    while (await this.turn()) {}
  } catch (_error) {
    // 错误已由运行边界报告
  } finally {
    if (this.phase.kind === 'running') {
      const { turn, wakeRequested } = this.phase
      this.setPhase({ kind: 'idle', lastTurn: turn })
      if (wakeRequested && this.inbox.hasPending) this.wakeDriver()
    }
  }
}

private async turn(): Promise<boolean> {
  const phase = this.phase  // 省略 running 检查
  const { signal } = phase.abort
  const turn = phase.turn + 1
  this.session.append('turn/start', { turn })
  phase.turn = turn
  let turnEnds: TurnEndReason | null = null
  let target: InboxTarget = 'next-turn'
  try {
    while (true) {
      const step = phase.step + 1
      const decision = await this.preStep(target, { turn, step })
      if (decision.kind === 'reject') {
        turnEnds = { kind: 'blocked' }
        return false
      }
      if (turnEnds && decision.messages.length === 0) break
      if (phase.step === 0 && decision.messages.length === 0) {
        turnEnds = { kind: 'completed' }
        return false
      }
      this.session.append('step/start', { turn, step })
      phase.step = step
      try {
        const stepEnd = await this.step(decision)
        if (turnEnds === null || turnEnds.kind !== 'max-tokens') turnEnds = stepEnd
      } finally {
        this.session.append('step/end', { turn, step })
      }
      if (turnEnds && this.inbox.nextStep.length === 0) {
        await this.dispatch.serial('agent/turn-stopping', { turn, signal })
      }
      if (turnEnds && this.inbox.nextStep.length === 0) break
      target = 'next-step'
    }
  } catch (error) {
    // 原实现将异常转换为 error 或 aborted，保存到 turnEnds，再上抛
    throw error
  } finally {
    this.session.append('turn/end', { turn, reason: turnEnds! })
  }
  if (!this.inbox.hasPending) return false
  phase.abort = new AbortController()
  phase.wakeRequested = false
  phase.step = 0
  return true
}

驱动器退出时的 wakeRequested 检查接住取消期间延后的唤醒。正常运行中的后续输入由 turn() 收尾后的 inbox 检查接住。

这份骨架将两种“结束”分开：step() 返回了结束原因，仍要经过内层停止检查。一条 turn/end 已经写入，驱动器也仍可能打开下一轮。下面回到第一步，先看模型请求和结果记录怎样产生。

一步怎样发请求，再把结果交给下一步​

第一步开始前，preStep()从 inbox 领取待处理输入，确定本步模型，解析可用工具，组装系统提示，再经过 agent/pre-step 扩展点。这里得到的是“允许进入或拒绝”的准备决定。领取输入与把输入写入模型历史，发生在两个阶段。

允许进入后，外层先追加 step/start，再调用 step()。第一步里的用户任务在这时作为 user/message 写入 Session，系统提示与运行环境上下文也按需留下各自记录。随后 buildRequest() 调用 session.deriveMessages()，取得当前有效历史，连同模型配置和工具声明组成请求。对应实现见本步输入的写入和请求快照的生成。

这样，第一步请求带上“读取 README”的任务。第二步从同一个 Session 取得历史时，已经能带上前一步的 assistant 工具调用和读取结果。turn/start、step/end 这类执行边界仍保留在日志中，供诊断使用。日志记录与发给模型的消息有各自的用途。

请求交给 LLM 接口后，适配器把返回内容转换为统一的 StreamChunk。循环中的 AssistantStreamAttempt负责本次尝试的流式状态，每收到一块内容，会同时做三件事：

  1. 给分片加上时间，累积到可写入会话的 stream 记录中。
  2. 交给内容组装器，形成文本、推理或工具调用内容块。
  3. 发出临时的 agent/assistant-stream 帧，让客户端在结算前也能显示进度。

正常响应结束后，step() 用组装好的内容创建 assistant 消息，追加一条 assistant/message。这条记录包含最终消息和对应 stream。settle() 在记录成功追加之后，才发出指向其 seq 的流结束帧，客户端据此将临时展示接到正式记录上。

在适配器报告的请求失败分支，循环先追加 assistant/attempt，保留本次分片，再询问 agent/request-error 扩展点。如果决定是 retry，step() 内部会再次请求模型，仍属于原 step，否则将错误交给外层收尾。于是，一个 step 可以有多个请求尝试。一个文本增量也不必单独成为一条顶层 Session 事件。 这两点来自流处理与重试实现，前面真实案例的主路径是两步各取得一条正常回复。

这些记录怎样到达检查器​

同一条执行链向外提供两种数据：Session 记录说明已经发生了什么，临时流式帧说明当前请求正在输出什么。它们经过三个连接点到达浏览器：

  1. Agent 循环追加 turn/start、step/start、assistant/message 等记录，工具服务追加 tool/call、tool/result。Session.append() 分配 seq 和时间，把记录加入内存日志，再通过 session/event 通知观察者。
  2. Session Controller 的 session.follow 先提供历史快照，再持续发送新增记录。启用 assistant stream 后，它还监听 agent/assistant-stream，将当前尝试的临时帧一并送出。
  3. 浏览器维护当前会话的 eventSource。聊天视图和检查器消费这个数据源，分别组装聊天内容与原始记录表。

实现分别见 Session 的追加与通知、Host 的 follow与检查器的数据源绑定。append() 返回表示记录已进入内存日志，持久化插件另行异步缓冲写入。因此，页面出现一条记录，证明它已进入会话数据流，落盘要看持久化层的完成情况。

原始数据表沿记录顺序扫描，用 turn/start、step/start 打开分组，用对应的 end 关闭分组。切换到「对话分组」，可以看到同一批记录组装出的聊天节点：

模型流式输出期间，原始数据表可以显示临时的 assistant/live 行。结算后，它由 assistant/message 或 assistant/attempt 记录接替，记录内保存的分片也可以再次展开。所以，几十条文本 delta 子行与几十条顶层 Session 事件含义不同。对应实现见客户端临时事件、分组与分片展开。

这些消费者只展示执行端产生的事实。决定是否请求下一步的，是下面的循环分支。

读完文件，为什么还要再走一步​

第一步的模型回复包含一个 tool-call 内容块，说明模型要求调用 read。循环先将回复记为 assistant/message，随后取出这些内容块，交给工具服务执行。

普通读取完成后，工具服务返回读取结果，但没有声明整个任务已经结束。于是 step() 返回 null，表示当前还没有结束原因。文件内容已进入 Session，循环下一步可以带着它再次请求模型。

这个返回值决定了“读完还要继续”。对应的核心分支如下：

查看源码：模型回复和工具批次怎样决定本步结果

下面节选 step() 中模型回复已记录之后的判断，省略工具执行异常的处理：

if (finish.kind === 'max-tokens') return { kind: 'max-tokens' }

const toolCalls = message.content.filter(block => block.type === 'tool-call')
if (toolCalls.length === 0) return { kind: 'completed' }
const maxParallelToolCalls = this.loopCtx.agentLoop.config.maxParallelToolCalls.get()
const result = await this.loopCtx.tools.execute({
  calls: toolCalls, signal, agent: this, log: { turn, step },
  maxParallelToolCalls, toolSet: decision.toolSet,
})
for (const context of result.additionalContexts) {
  this.inbox.splice('next-step', this.inbox.nextStep.length, 0, [context])
}
return result.concluded ? { kind: 'completed' } : null

concluded 是工具批次给出的结束标记。普通读取提供材料，需要后续模型解释，通常返回 false。工具还可以提供 additionalContexts，循环会将这些补充信息送进下一步的输入区域。

这里的几种结果，各自改变后续行为：

本步发生的事step() 的结果交给外层循环的含义
普通 read 完成，工具批次没有声明结束null继续准备下一步，让模型处理结果
模型正常回复，没有工具调用{ kind: 'completed' }本步认为可以结束，交给外层检查
工具批次明确声明 concluded{ kind: 'completed' }工具已给出结束意图，交给外层检查
模型响应达到输出上限{ kind: 'max-tokens' }保留截断原因，交给外层检查

工具执行成功与任务完成是两件事。 read 成功只能说明文件已读到。这项任务还要求解释启动方式，答案需要第二步生成。

completed 也是循环的控制结果，不等于答案正确。 没有工具调用，只能让默认循环认为本步可以收尾。回答是否符合文件内容、是否满足用户要求，需要另外核对。在这个例子中，README 原文与第二步的启动说明可以直接对照。

  • data.message.toolCallId 与前一条调用的 callId 对应。

tool/call 在工具函数及 tools/pre-execute 策略检查之前写入。因此，看到调用行只能确认开始处理，读取成功要结合后面的结果判断。

没有新用户消息，第二步从哪里开始​

外层 turn() 用 turnEnds 保存本步给出的结束原因。开始时它是 null，普通读取完成后仍然是 null。这意味着当前任务还需要继续，循环可以在没有新用户输入的情况下准备下一步。

输入区域叫 inbox，其中 next-step 保存准备在本轮后续步骤处理的消息。第一步已经接纳的用户任务不需要再次排队，它和工具结果都保留在 Session 的有效历史中。

循环会再次运行 preStep()，准备下一步的输入、模型与工具，经过 agent/pre-step 扩展点。扩展点可以允许或拒绝这一步。允许通过后，外层还会检查本轮是否已有结束原因，以及准备决定中有没有消息需要处理，才记下 step/start 并调用 step()。

前面骨架中的 phase.step === 0 处理本轮尚未执行任何一步的情况。任务输入已被移除或改为空时，这个分支会直接收尾，避免花费一次模型调用。

对这次读取，第二步能进入的条件可以逐项推导：

  1. 第一步返回 null，所以没有结束原因阻止继续。
  2. 第一轮已经执行过一步，第二步不受“首批输入为空就结束”的条件限制。
  3. 第二次准备得到允许进入的决定，因此追加 step/start 1/2，带着已有历史请求模型。

同一段代码也解释了另一个边界：如果插件在准备时拒绝，外层把结束原因设为 blocked。这个候选步骤没有 step/start，也没有调用 step()。blocked 来自准备阶段的拒绝，与模型无工具调用而产生的 completed 含义不同。turn 的起点代表开始处理输入，step 的起点代表一步已通过准备与外层检查，二者不是同时写入。

模型已经回答，为什么还可能继续​

第二步返回的回复没有工具调用，step() 给出 completed。这时 turnEnds 有了结束原因，但循环还要检查 next-step 有没有待处理消息。

如果运行过程中有人通过 steer() 补入本轮后续输入，已有答案仍然写入历史，循环接着处理新输入。只有暂时没有这些消息时，才进入 agent/turn-stopping 扩展点。这个事件让插件在准备停止的时刻，决定是否还需要补入工作。

前面骨架中的停止判断连续检查了两次 this.inbox.nextStep.length === 0，两次检查之间才执行扩展点。

第二次检查不可省略：插件执行期间，inbox 可能从空变成有消息。 如果只在调用插件之前检查一次，插件刚补入的工作便无法让当前 turn 继续。

沿源码推演一个变化：假设第二步已给出启动说明，而停止监听器通过 steer() 补入“再说明它是否持续运行”。第一次检查时 inbox 为空，监听器得以运行。返回时 inbox 非空，循环便继续准备第三步。下一步领取这句话，通过准备后，在同一个 turn 中请求模型。项目的对应测试使用模拟模型断言了这条调度行为。前面的真实截图对应的是没有这项补充输入的两步运行。

inbox 还可以保存 next-turn 输入，它们由 followup() 排队。正常收尾后，驱动器检查仍有待处理工作时会继续打开下一轮。因此，本轮结束与 Agent 进入空闲也有不同的判断边界。

回到真实案例，两个步骤的控制结果可以压缩成这张状态对照：

为什么失败时也有结束记录​

一次模型连接失败的实际记录，同样出现了 step/end 和 turn/end。选中最后一条记录，详情显示：

这次运行在第一步请求模型时以 TRANSPORT 错误结束，读文件工具尚未执行。结束事件之所以仍然存在，是因为循环把“收尾记录”放在 finally 中，把“为什么结束”另外保存在 reason 中。

  • 内层 finally 追加 step/end，关闭已经开始的步骤。
  • 外层异常处理将失败转换为 error，取消则记录为 aborted。
  • 外层 finally 追加 turn/end，同时带上结束原因。

因此，正常路径和异常路径都能留下边界。检查器可以关闭对应分组，调用方也能从原因中区分正常结束、取消或失败。结束行说明执行已收尾，reason.kind 才说明收尾的性质。图中证明的是这次连接失败的错误记录，取消收尾的说明依据上述源码路径。

还有一种值得保留的区别是 max-tokens。它表示模型响应达到输出上限。step() 先写入 assistant 记录，再检查这个原因，命中后直接返回，因此这条截断回复中的工具调用不会在本步被派发。

循环会将这个原因保留在当前 turn 中，即使插件补入输入、后续一步正常完成，结果也不会直接改成 completed。前面更新 turnEnds 时特意检查已有值是否为 max-tokens，就是为了保存这条截断事实。项目的上限原因测试用模拟响应验证了“截断后续跑，最终仍记录截断”的调度行为。

这次读取的两个 step 来自两个不同判断：普通工具完成后仍需要模型处理结果，所以继续。模型回复没有工具调用、本轮输入耗尽、停止扩展点也没有补入工作，所以收尾。请求、消息记录、工具结果沿 Session 到达检查器，而 step() 的结果与 turn() 的停止条件解释了这些记录为什么按这个顺序出现。
