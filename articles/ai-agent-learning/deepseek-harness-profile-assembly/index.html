执行 dsh --profile headless 时，程序怎样知道要加载哪些模型、工具和会话能力？配置文件中写着插件的名字，这些名字又怎样变成 Agent 能调用的服务？

profile 选择配置组合，Loader 把配置条目加载为插件，插件框架 Cordis 在依赖就绪后激活插件。插件公开的服务，再由其他插件或 Agent 使用。 这里有两个需要分开的顺序：配置按层覆盖，插件按依赖激活。

前文：DeepSeek Harness 源码走读：从一句任务建立全局地图沿读文件任务介绍了装配与执行的分工。这里从一次无需模型的插件协作开始，追踪装配过程。

Harness 应用由模型、工具、会话等插件组合而成。各层配置用 patch 描述增加或修改插件条目的规则。要让配置中的一个名字成为可以调用的能力，启动时需要完成三段工作：

配置回答“加载什么、传什么参数”，运行单元回答“现在能不能执行”。沿着同一句问候语，可以看清两者怎样接起来。

先让两个插件协作一次​

假设要给应用加一项问候能力。一个插件负责提供 studyGreeting 服务，另一个插件调用它并打印问候语。服务就是按名字公开给其他组件调用的能力。

提供方在入口 apply(ctx, config) 中注册服务：

ctx.provide('studyGreeting', {
  greet: () => config.message,
})

这里的 ctx 是插件使用的上下文，config 是配置条目传给它的参数。消费方通过 inject 声明需要 studyGreeting，然后调用 ctx.studyGreeting.greet()。

下面把两个插件放进同一个 bundle（组合包）。bundle 是带有插件配置层的 npm 包，一个包可以贡献多个插件条目。配置故意把消费方写在提供方前面：

- insert:
    - id: study-consumer
      name: dsh-study-greeting
    - id: study-provider
      name: dsh-study-greeting/provider
      config:
        message: Hello from bundle

这份 YAML 中，insert 表示增加条目。提供方的三个字段分别承担不同工作：

  • id: study-provider 是配置条目的标识，后续覆盖用它找到这一行。
  • name: dsh-study-greeting/provider 是模块入口，加载器用它寻找代码。
  • config.message 是传给插件的参数，最终会成为问候语。

运行环境需要 Node.js 24.9.0 及以上版本和 pnpm@11.28.5。先按源码开发指南安装依赖，再执行 pnpm run build:artifacts 生成运行产物。下文所有命令在 Harness 仓库根目录、同一个 shell 中执行。

查看完整命令：创建本地 bundle 和独立数据目录

以下使用 macOS / Linux 的 shell。临时 DSH_HOME 保存本例的 profile，DEMO_DIR 保存本地插件源码：

export DSH_HOME="$(mktemp -d)"
DEMO_DIR="$(mktemp -d)"
BUNDLE_DIR="$DEMO_DIR/greeting-bundle"
mkdir -p "$BUNDLE_DIR"

cat > "$BUNDLE_DIR/package.json" <<'JSON'
{
  "name": "dsh-study-greeting",
  "version": "1.0.0",
  "type": "module",
  "exports": {
    ".": "./consumer.mjs",
    "./provider": "./provider.mjs"
  },
  "dsh": {
    "bundle": {
      "patch": "./cordis.patch.yml"
    }
  }
}
JSON

cat > "$BUNDLE_DIR/provider.mjs" <<'JS'
export const name = 'study-greeting-provider'

export function apply(ctx, config) {
  ctx.provide('studyGreeting', {
    greet: () => config.message,
  })
  console.log('[provider] registered')
}
JS

cat > "$BUNDLE_DIR/consumer.mjs" <<'JS'
export const name = 'study-greeting-consumer'
export const inject = ['studyGreeting', 'appReady', 'appExit']

export function apply(ctx) {
  console.log('[consumer] ' + ctx.studyGreeting.greet())
  ctx.effect(() => ctx.appReady.onReady(() => ctx.appExit(0)))
}
JS

cat > "$BUNDLE_DIR/cordis.patch.yml" <<'YAML'
- insert:
    - id: study-consumer
      name: dsh-study-greeting
    - id: study-provider
      name: dsh-study-greeting/provider
      config:
        message: Hello from bundle
YAML

消费方还使用启动器提供的 appReady 和 appExit：整棵应用成功启动后，请求清理并退出进程。它们的接口见命令行服务。

profile 是一份具名的应用组合。通过插件安装命令，把本地 bundle 加入一个新的自定义 profile：

pnpm dsh plugin --profile assembly-demo add "$BUNDLE_DIR"
pnpm dsh --profile assembly-demo

在 Node.js 24.18.0 下，启动输出包含：

[provider] registered
[consumer] Hello from bundle

消费方虽然在配置中排在前面，仍然成功调用了提供方服务。应用随后正常退出。这个例子使用本地问候函数，不需要模型密钥。

profile 怎样找到要加载的插件​

刚才的安装命令同时准备了两件事：

  • 在 $DSH_HOME/profiles/assembly-demo 中创建 profile，并安装本地包的链接。
  • 在 profile 的 package.json 中记录要叠加的 bundle。

这个新 profile 的 bundle 列表是：

[
  "@deepseek-ai/dsh-base",
  "dsh-study-greeting"
]

dsh-base 是新建自定义 profile 时加入的共享能力组合。后面的 dsh-study-greeting 是刚才安装的本地包。包的依赖记录解决“模块从哪里找到”，dsh.profile.bundles 列表解决“哪些包的配置层要参与装配”。

以本地包为例，启动器读取它的 package.json，找到 bundle 的配置入口。相关字段节选如下：

"dsh": {
  "bundle": {
    "patch": "./cordis.patch.yml"
  }
}

于是，这个 YAML 文件中的两个插件条目进入配置组合。条目的 name 再通过包的 exports 分别指向消费方和提供方文件。

对应实现位于 loadProfileDirectory()：按 dsh.profile.bundles 的顺序读取各包声明的 patch，保存成有序的配置层。

查看源码：loadProfileDirectory() 按顺序收集 bundle 配置层

以下节选函数中读取 bundle 层的部分，省略平台及版本兼容性检查：

const manifest = dropRetiredBundles(dir, readProfileManifest(binName, dir))
const bundles = manifest.dsh?.profile?.bundles ?? []
const layers: ProfileLayer[] = []
const skippedBundles: SkippedBundle[] = []

for (const packageName of bundles) {
  try {
    const packageDir = resolveBundleDir(binName, packageName, installAnchor, dir)
    const bundleManifest = readProfileManifest(binName, packageDir)
    const bundle = bundleManifest.dsh?.bundle
    if (bundle === undefined) {
      throw new Error(`${binName}: profile bundle ${JSON.stringify(packageName)} declares no dsh.bundle in its package.json`)
    }
    // 省略平台及版本兼容性检查。
    const patchPaths = bundlePatchPaths(packageDir, bundle)
    const patches = patchPaths.flatMap(patchPath => loadOverlayPatches(binName, patchPath))
    layers.push({ packageName, packageDir, patchPaths, patches })
  } catch (error) {
    skippedBundles.push({ packageName, reason: String(error) })
  }
}

内置 headless 走的是同一条路径。它的初始模板选择 dsh-base 和 dsh-headless 两个 bundle，后者加入一次性任务的启动参数解析和运行器。首次使用时模板初始化 profile，以后启动器读取该 profile 实际保存的组合。

同一条配置最后听谁的​

问候语由提供方的 config.message 决定。要为当前 profile 换一句话，需要编辑该 profile 目录下的 cordis.patch.yml。同目录的 cordis.yml 是启动器每次重新生成的入口，手动修改会在下次启动时被覆盖。

在覆盖文件中，用同一个 id 定位提供方并修改问候语：

cat > "$DSH_HOME/profiles/assembly-demo/cordis.patch.yml" <<'YAML'
- id: study-provider
  config:
    message: Hello from profile
YAML

pnpm dsh --profile assembly-demo

这次消费方输出：

[consumer] Hello from profile

包里的默认配置仍然是 Hello from bundle。配置合成时，先应用 bundle 层，再应用 profile 自己的层。后续 patch 以同一个 id 定位条目，替换其中的 config。

想比较两者，可以查看配置合成结果：

pnpm dsh --profile assembly-demo --dump-default-config
pnpm dsh --profile assembly-demo --dump-config
  • --dump-default-config 展示当前所选 bundle 合成的默认配置，问候语仍为 Hello from bundle。
  • --dump-config 加入用户覆盖层，问候语变为 Hello from profile。

这两个命令展示配置合成结果，插件入口在实际启动应用时才执行。

还可以通过 --patch 为一次启动追加覆盖：

cat > "$DEMO_DIR/overlay.yml" <<'YAML'
- id: study-provider
  config:
    message: Hello from overlay
YAML

pnpm dsh --profile assembly-demo --patch "$DEMO_DIR/overlay.yml"

消费方会输出 [consumer] Hello from overlay。去掉 --patch 再启动，就回到 profile 保存的问候语。

这些文件的覆盖次序，在 readProfilePatches() 中按顺序收集：

  1. profile 选中的各个 bundle 层，顺序来自 dsh.profile.bundles。
  2. 当前 profile 的 cordis.patch.yml。
  3. $DSH_HOME/cordis.patch.yml，保存跨 profile 使用的本机覆盖。（我个人觉得，让公共配置覆盖具体 profile 的配置有些反直觉，优先级反过来会更符合预期。）
  4. 命令行 --patch 指定的文件，按参数出现顺序应用。
查看源码：收集 bundle 与用户覆盖层

以下节选保留了上述四类配置的收集顺序：

const patches = structuredClone([
  ...readBundlePatches(binName, context, initialProfile),
  ...(initialProfile?.patches ?? loadOptionalPatches(binName, context.patchPath) ?? []),
  ...(loadOptionalPatches(binName, join(context.home, PROFILE_PATCH_FILENAME)) ?? []),
  ...context.overlays,
])

命中条目后，新的 config 会整对象替换原来的 config，不会逐字段合并。本例只有一个字段，直接替换即可。覆盖复杂配置时，必须在新的 config 中重新写全仍需使用的字段。

继续使用带有 --patch "$DEMO_DIR/overlay.yml" 的启动命令。按上述覆盖顺序合成后，提供方条目如下，只摘出本例的一项：

id: study-provider
name: dsh-study-greeting/provider
config:
  message: Hello from overlay

id 和模块入口保持原值，问候语从 bundle 默认值，经过 profile 覆盖，最后变成命令行覆盖值。后面的加载过程处理的就是这个最终条目。

配置合成由 Include 插件负责。它在应用 insert 时，立即把新增条目的 id 加入索引。遇到后续 patch，再用 id 查同一个条目，逐个替换 patch 中指定的属性。

查看源码：新增条目怎样被后续配置层继续修改

节选自 applyEntryPatches()，保留本例经过的路径，省略分组插入、缺失目标与名字不符的诊断：

for (const patch of patches) {
  const { id, insert, name, ...overrides } = patch
  if (insert) {
    // 本例没有 id，向根条目列表插入。
    data.push(...insert)
    buildMap(insert)
    continue
  }
  const target = entryMap.get(id)
  // ...目标与名称检查...
  for (const [key, value] of Object.entries(overrides)) {
    if (key === 'id') continue
    target[key] = value
  }
}

这里的 target[key] = value 解释了整对象替换：当 key 是 config，替换的是整个配置对象。源码中的错误检查会对未找到的目标给出警告，并跳过该 patch。

配置怎样变成可调用的服务​

启动器已经读出了各层 patch，接下来要把它们变成运行中的插件。runProfile() 把配置入口路径和已解析的 patch 列表交给 boot()。

boot() 先创建根上下文 ctx，再挂载 Loader。此时准备好的是加载器，应用条目还没有开始加载。启动器随后通过 prepare 回调，向上下文提供应用命令行参数和退出等宿主服务。需要参数的应用插件激活后，可以从 ctx.cmdlineArgs 读取并解析它们。

宿主准备完成后，Loader 挂载前面负责合成配置的 Include 插件。它读取空的 cordis.yml，应用启动器传入的 patch，得到最终插件条目，再交给 Loader。前面那些 patch 文件的读取与解析，已经由启动器完成。

现在把最终条目中的两个输入拆开：Loader 用 name 找代码，用 config 给代码传参数。本地包的 exports 把 dsh-study-greeting/provider 指向 provider.mjs。导入后，Loader 取得带有 apply() 的插件对象，再把它与 { message: 'Hello from overlay' } 交给 Cordis 注册表。

查看源码：从配置条目导入并注册插件

节选自 Loader 的条目初始化，省略错误捕获：

moduleNamespace = await this.parent.tree.import(this.options.name, this.getOuterStack)
const plugin = this.loader.unwrapExports(moduleNamespace)
await this._patchContext([])
this.loader.showLog(this, 'apply')
this.fiber = this.ctx.registry.plugin(plugin, this.options.config, this.getOuterStack)

这时发生了一次数据到代码的转换：

配置条目
  name   → provider.mjs 导出的插件对象
  config → { message: 'Hello from overlay' }
                  ↓
注册表建立 Fiber，持有插件、配置与依赖
                  ↓ 依赖允许执行
apply(ctx, config)
  → greet() 闭包取得 config.message
  → ctx.provide('studyGreeting', { greet })

一次插件加载会建立一个运行单元，源码称为 Fiber。它记录插件的状态、依赖和需要释放的资源。注册表的 plugin() 把模块对象的 inject、条目的 config 和插件实现交给 Fiber。模块已经导入，并不等于 apply() 已经执行。Cordis 还要检查声明的服务依赖。

提供方没有声明 inject，因而无需等待外部服务就能执行入口。消费方则必须等待它要调用的服务。

回到消费方，它声明：

export const inject = ['studyGreeting', 'appReady', 'appExit']

提供方和消费方各有自己的 Fiber，通过 studyGreeting 这个服务名关联。消费方只等待 inject 中声明的服务。假设消费方先完成模块导入，而提供方尚未激活，接下来会发生：

  1. 消费方 Fiber 检查三个依赖。appReady 和 appExit 已由启动器提供，但 studyGreeting 不可用，因此保持 PENDING（等待依赖），入口尚未执行。
  2. 提供方执行 apply()，调用 ctx.provide('studyGreeting', ...) 登记服务。等入口成功完成、提供方 Fiber 进入 ACTIVE（已激活），这个服务才算可用。
  3. 提供方的状态变化触发服务通知。Cordis 找出 inject 包含 studyGreeting 的 Fiber，更新它们看到的服务，再检查各自的全部依赖。
  4. 消费方依赖齐全后进入 LOADING（执行入口），调用 apply()，取得服务并打印问候语。入口成功完成后，它也进入 ACTIVE。

依赖检查由 _checkImpl() 和 _refresh() 完成。提供方进入 ACTIVE 时会通知服务变化，reflect.notify() 随即触发相关 Fiber 的重新检查。如果提供方已经激活，消费方在第一次检查时就能取得服务。

服务和配置也有各自的归属。以 studyGreeting 为例：

数据保存在哪里在本例中的作用
最终插件配置提供方 Fiber传给 apply()，决定问候语
服务实现记录Cordis 的服务管理器 ctx.reflect保存 studyGreeting 的值、实现编号 uid 和提供方上下文
检查得到的依赖实现消费方 Fiber 的 _store判断所需服务是否可用
本次运行绑定的依赖消费方 Fiber 的 committed入口执行和清理时，使用这一组服务实现

provide() 登记的是带有 greet() 的实际对象。消费方开始运行前，Fiber 把检查通过的实现保存为本次绑定。读取 ctx.studyGreeting 时，上下文从绑定中取得服务值。随后执行的 greet()，就是提供方注册的那个函数，所以拿到的是 Hello from overlay。

_refresh() 把插件修订编号和各依赖实现的 uid 连成一个运行标记，源码称为 epoch。它回答的是“这次插件运行绑定了哪一组服务实现”。只要缺少一个必需服务，标记就变为不可运行。等全部服务就绪，标记才允许 Fiber 执行入口。

查看源码：服务实现怎样决定 Fiber 是否运行

节选自 _refresh() 与 _setEpoch()，省略注释：

_refresh() {
  let epoch = `${this._revision}`
  for (const name of Object.keys(this.inject)) {
    const impl = this._store[name]
    if (!impl) {
      epoch = INACTIVE
      break
    }
    epoch += ':' + impl.uid
  }
  this._setEpoch(epoch)
}

private _setEpoch(epoch: string) {
  const oldEpoch = this._runner.epoch
  if (epoch === oldEpoch) return
  if (this._error) return
  this._runner.epoch = epoch
  if (this.inertia) return
  this._updateState(() => {
    if (epoch !== INACTIVE && oldEpoch === INACTIVE) {
      this.inertia = this._reload()
      return FiberState.LOADING
    } else {
      this.inertia = this._unload()
      return FiberState.UNLOADING
    }
  })
}

把这次先等后启动的过程画出来：

如果服务始终没有出现，消费方入口就不会执行。启动检查会报告缺少的服务。被列为必需的插件仍未激活时，应用会拒绝启动。

这项依赖约束还持续作用于运行中的插件。在长期运行的应用中，沿同一机制推演：若停用提供方，让 studyGreeting 变为不可用，消费方的 epoch 就会变为不可运行，Fiber 随之进入 UNLOADING（清理当前运行）。清理完成后，它回到 PENDING，等待服务再次就绪。消费方自己的配置条目仍然存在，因此服务恢复后可以重新执行入口。

为什么 epoch 还包含实现编号？因为同名服务也可能换成新的实现。编号变化会使原有运行失效，消费方清理后重新加载，绑定新的实现。单纯确认“studyGreeting 这个名字存在”，无法识别这次更换。

清理顺序同样由依赖关系约束。_reload()会在提供方记录哪些 Fiber 正依赖它。_unload()先等待这些消费方清理，再释放自己登记到 Cordis 的资源。消费方的清理代码由此仍能使用旧服务完成收尾，然后解除绑定。

因此，把消费方排在提供方前面，不会让它提前调用尚不可用的服务。配置层的顺序决定提供方收到哪句问候语，Fiber 的依赖状态决定消费方何时开始、何时清理，以及何时重新运行。

服务齐全之后，谁创建 Agent​

问候服务展示了装配机制。在默认 headless 应用中，同样的机制要先让 Agent 所需的服务就位。

dsh-base 的配置中有一条 agent-loop。它加载的 AgentLoop 是一个服务插件，声明了模型、工具、会话等依赖：

export class AgentLoop extends Service implements AgentFactory {
  static inject = ['agents', 'sessions', 'llm', 'tools', 'systemPrompt', 'sessionProjections']
  // 其余类成员省略。
}

AgentLoop 在构造函数中调用 super(ctx, 'agentLoop')，通过 Service 基类把实例登记为 ctx.agentLoop。Cordis 随后执行并等待它的 [Service.init]() 初始化方法。初始化成功、运行单元进入 ACTIVE 后，依赖方才能使用这个服务。

AgentLoop 的初始化逻辑会向 Agent 注册表登记工厂：

ctx.effect(() => ctx.agents.setFactory(this), 'agentLoop.setFactory()')

工厂负责创建具体 Agent。agent-loop 条目的 config.agents 默认为空数组，没有要求启动时预建实例。此时，应用已经具备创建 Agent 的能力。

dsh-headless 增加的运行器会先等待 Loader 中的插件完成当前装配。对于没有指定已有会话（Session）的新任务，它随后调用 agents.create(...)。注册表将创建请求转交给已经登记的工厂，最终创建 ReactLoopAgent。

至此，headless 取得了一个能够接收任务的 Agent 实例。profile 决定应用装了哪些能力，Cordis 负责让这些能力按依赖就位。接收输入后怎样交替请求模型与执行工具，由实例内部的循环推进。
