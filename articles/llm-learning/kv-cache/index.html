KV Cache 与自回归：为什么首字慢、后面快

用过流式输出的聊天界面都见过这个节奏：发出问题后要等一小会儿，第一个字才蹦出来；可一旦开始，后面的字就哗哗地流。为什么"启动"和"续写"速度差这么多？

答案分两层：生成本来就是一个字一个字循环出来的（自回归），而这个循环里有一块巨大的重复计算被缓存掉了（KV Cache）。这篇把两层都说清，不需要任何环境，纯讲解。

自回归：生成就是不断地"接龙"​

第三篇讲过，模型单次只做一件事：给一段序列，算出下一个 token 的概率表。那一整段回答怎么来的？把这个动作循环起来：

每生成一个 token，就把它接到序列末尾，整个序列重新作为输入再算一轮，直到模型选出一个特殊的"结束" token。这种"自己的输出喂给自己当输入"的方式叫自回归（autoregressive）。

流式输出（打字机效果）不是什么动画技巧——服务端本来就是一轮循环产出一个 token，只是把每轮结果立刻推给你而已。

问题：每一轮都在重算同样的东西​

按上面的流程，一个明显的浪费浮出水面。第四篇说过，每个 token 要算出自己的 Q、K、V 向量。看看相邻两轮的输入：

第 1 轮输入：今天 天气           → 算 2 个 token 的 K、V
第 2 轮输入：今天 天气 真        → "今天""天气"的 K、V 和上轮一模一样
第 3 轮输入：今天 天气 真 好     → 前 3 个 token 的 K、V 又是重算

前文 token 的 Key 和 Value 每一轮都相同（内容没变、位置没变），却在被反复计算。回答越长，浪费越大：生成第 1000 个 token 时，前 999 个的 K、V 全是重复劳动。

KV Cache：算过的就存下来​

解法直白：第一次算出的 K、V 存进显存，后续轮次直接取用。这块缓存就叫 KV Cache。

于是生成过程天然分成两个阶段，速度特性完全不同：

  • 预填充（prefill）：处理你的提示词。所有输入 token 的 K、V 都要从零算一遍，提示词越长这一步越慢——这就是首字等待的主要来源。好在这批计算可以并行做，算力打满。
  • 解码（decode）：逐字生成。每轮只算最新一个 token 的量，其余全部查缓存——所以后面的字来得快，且每个字的耗时大致恒定。

两个阶段有专门的量化指标：首字延迟叫 TTFT（Time To First Token），后续出字速度叫 TPOT（Time Per Output Token）。看到模型服务的性能宣传时，可以问一句：说的是哪一个？

缓存不是免费的：显存换时间​

KV Cache 是典型的空间换时间，而这个"空间"很贵——它吃显存，且大小和上下文长度成正比：每多一个 token，每一层都要多存一份 K、V。粗略感受量级：一个 70 亿参数的模型，几万 token 的上下文攒下的缓存能到 GB 级（具体取决于模型结构和精度）。

这解释了几个日常现象：

  • 长上下文的定价更贵：不只是计算多，缓存占着显存，同一张卡能同时服务的用户就少了。
  • 各家都在改注意力结构：让多组注意力头共享同一份 K、V（术语叫 GQA/MQA，链接见文末），缓存直接砍到几分之一，换来的是长上下文服务成本大降。
  • "提示词缓存"（prompt caching）折扣：不少服务对重复的提示词前缀收更低费用——因为这段前缀的 KV Cache 可以跨请求复用，预填充直接跳过。把系统提示等固定内容放在提示词开头，命中率更高。

一个容易醒悟的误解​

"多轮对话时，模型是不是记住了我们前面聊的？"——第一篇实测隐藏系统提示时提过，服务端每次都要收到完整的对话历史。KV Cache 可能让服务端少算一点（前缀没变的部分直接复用），但那是性能优化，不是记忆：缓存里存的是算过的中间结果，请求结束随时可能被丢弃。对话的"记忆"始终靠调用方把历史原样重发，模型本身一轮结束就什么都不留。
