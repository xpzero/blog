做了一个本地部署的AI 简历工作台

最初我只想做一个能编辑、预览并打印 A4 简历的页面。做完基础版后，还想让AI帮我优化简历，再让它帮我看看有什么可以优化和扩展的地方，就成现在的效果。

项目代码：xpzero/resume-pdf-editor

项目做了什么​

编辑器以一份结构化简历数据为中心，当前支持：

  • 多份简历的新建、切换、重命名和删除，数据保存在浏览器本地存储中；AI 应用和导入前会自动创建历史快照，也可手动恢复。
  • 基本信息、教育经历、技能、工作经历、项目经历、个人评价和自定义模块编辑。
  • 教育经历的增删；工作经历和项目经历的顺序调整；技能和项目职责的拖拽排序。
  • 经典蓝、简约灰、编辑暖调、技术深色四套简历模板。
  • Markdown 导入导出、可复制文本 PDF 导入、浏览器打印 PDF。
  • 导出前的缺失字段和内容完整性检查。
  • 基于 LLM 的整份简历、技能、个人评价和项目描述优化。

PDF 导出没有使用截图或 Canvas，而是直接调用浏览器打印。这样导出的文字可以复制和搜索，版式也更接近网页预览。

目录结构​

项目后来拆成了 pnpm workspace：

信息

为什么这么拆呢？因为基本一直在做前端，而且这是一个小项目，把前后端的代码都放在同一个仓库里，后面也好找代码。而且后端用nodejs做，后面如果有重新部署到本地的情况，安装pnpm、nodejs之后，一个命令，环境就部署好了，很方便。如果是专门用后端语言，比如Java，新电脑的话，就还需要安装JDK之类的东西，相对来讲复杂一点，不太好部署。

front/     # Vite + React：编辑器、预览、模板和本地数据
backend/   # Fastify：LLM 请求、结果校验和字段级合并

本地启动：

pnpm install
pnpm dev

pnpm dev 会同时启动前端和后端。前端的 /api 请求由 Vite 转发到 Fastify 服务，浏览器不直接请求模型服务。

为什么先统一简历数据结构​

页面不是直接拼 HTML，而是维护一份简历对象。抽象后的结构大致如下：

{
  name: '陈默',
  skills: ['熟练使用 Figma 和 Sketch'],
  jobs: [['2022.04-至今', '云栖数字科技', '高级产品设计师']],
  projects: [{
    title: '智能运营工作台',
    intro: '面向运营团队的数据分析与任务协同平台。',
    points: ['负责流程梳理和核心页面设计。']
  }]
}

这让同一份内容可以被模板渲染为不同版式，也可以导出为 Markdown、传给后端校验或作为 LLM 的输入。后续新增“竞赛经历”这类内容时，只需要增加自定义模块，而不用修改每一个模板。

AI 优化怎么工作​

用户先在“更多 - LLM 配置”中填写兼容 OpenAI Chat Completions 格式的接口地址、API Key 和模型名称；配置只保存在当前浏览器会话。

随后用户可以填写目标岗位、JD 和补充描述。补充描述既可以写希望强调的方向，也可以写尚未出现在简历里、但确认真实的背景。

请求链路如下：

当前简历 + 目标岗位 + JD + 补充描述
  -> Fastify 校验请求
  -> 调用 LLM
  -> 校验模型返回的 JSON
  -> 返回优化草稿
  -> 前端显示“优化前 / 优化后”
  -> 用户确认后应用

AI 不会直接覆盖当前简历。模型没有产生实际变化时，应用按钮会被禁用；有变化时，用户先看到按技能、项目描述或个人评价拆分的对比，再决定是否应用。

做到一半踩到的坑​

API Key 不写进源码，不等于没有安全边界​

浏览器直接调用模型服务会暴露 Key，所以调用放在后端完成。当前本地开发模式仍会把 Key 保存在浏览器 sessionStorage 中，并在请求时发送给本地后端；这适合个人本地使用，不适合直接作为生产方案。

如果要部署给多人使用，应该改成服务端环境变量、用户账户或专门的密钥托管方案，并增加鉴权和限流。

Markdown 和 PDF 导入都有格式边界​

Markdown 导入最初只按 \n 分段，Windows 文件常见的 \r\n 会导致章节识别失败，所以导入前先统一换行符。

PDF 导入更复杂。能复制文字的 PDF 可以提取文本，但“提取到文本”不等于“知道哪一段是项目经历”。当前做法是保守地生成待整理草稿，而不是假装已经准确还原了所有字段。

curl 能通，Node 请求不一定能通​

这次排查中观察到：

  • curl 返回 401，说明地址可达、TLS 握手完成，且请求已经进入服务端认证逻辑。
  • Node 内置 fetch 返回 ECONNRESET，错误信息是 Client network socket disconnected before secure TLS connection was established。
  • Node 的 https.request 同样返回 401。

因此可以确认：Node 内置 fetch 在 TLS 安全连接建立前收到了连接重置。但不能断言一定是服务端主动断开，也可能来自 CDN、代理、防火墙或其他中间网络设备。

因为同一地址通过 curl 和 https.request 都能完成认证请求，问题更可能集中在 Undici（Node fetch 使用的 HTTP 客户端）或它经过的网络路径兼容性。后端最终改用 Node 的 http/https 请求通道，并把 DNS 解析失败、拒绝连接、超时和 HTTP 认证失败分别提示。

排查第三方 API 时，至少要区分三段链路：浏览器到本地后端、后端到服务商、服务商对 API Key 的认证。

TLS 是什么

TLS 是 HTTPS 在发送 HTTP 请求前建立加密连接的安全协议。客户端与服务端会先完成一次“握手”，协商加密方式并验证证书；握手失败时，请求甚至还没有进入 API 的认证逻辑。

当前限制​

  • 没有账号和云端同步；版本历史只保存在当前浏览器。
  • AI 可以改写表达，但不能补出不存在的公司、项目、技术或量化成果。
  • PDF 导入只适用于可复制文本，复杂版式仍需要人工整理。
  • LLM 配置主要面向本地开发，尚未提供生产环境的密钥和调用额度管理。

这些限制会继续保留在界面和文档中。对简历这种事实性内容，先让用户看见变化、确认变化，再应用变化，比追求完全自动化更重要。
