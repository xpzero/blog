Day 8：RAG

大模型知识有截止日期，不知道我公司的内部信息，也不能读我的私人文档。

怎么办？

RAG（检索增强生成）解决这个问题。

RAG 是什么？​

Retrieval Augmented Generation。

翻译过来就是：检索增强生成。

流程：

用户提问 → 检索相关文档 → 把文档给模型 → 模型生成回答

模型不是自己凭空编，而是先去查资料，再根据查到的内容回答。

什么时候用 RAG？​

  • 需要最新信息（新闻、股价）
  • 需要私有知识（公司文档、个人笔记）
  • 需要专业领域知识（医学、法律、客服）

大模型本身不知道这些，或者知道的不准确。

RAG 流程​

准备阶段：

文档 → 切块 → Embedding → 存向量数据库

查询阶段：

用户提问 → Embedding → 向量检索 → 获取相关片段 → 给模型 → 回答

关键步骤​

1. 文档切块​

文档太长，要切成小块。

太大：超过窗口，放不进去。 太小：丢失上下文。

常用大小：500-1000 Token。

2. Embedding​

每个块变成向量，存到向量数据库。

3. 检索​

用户提问转成向量，在数据库里找最相似的块。

关键参数：

  • Top K：取前几个相关块（通常 3-10）
  • 相似度阈值：低于多少不算相关

4. 生成​

把相关块 + 用户问题一起给模型，让模型基于这些内容回答。

向量数据库​

存向量数据的地方：

数据库特点
Pinecone全托管，收费
Milvus开源，可私有部署
Chroma轻量，开发测试用
Weaviate开源，功能全

本地跑可以用 Chroma，生产环境用 Milvus 或 Pinecone。

RAG 的局限性​

RAG 不是万能的：

  • 检索质量依赖 Embedding：如果 Embedding 不准，检索就差
  • 上下文窗口限制：检索的块再多，也放不进窗口
  • 不是实时更新：新文档要重新处理

进阶优化​

  • 混合检索：向量检索 + 关键词检索，一起用
  • 重排序：初步检索后，再排序精选
  • Query 改写：把用户问题改写得更适合检索

踩坑记录​

坑1：chunk_size 不是越大越好 太大放不进窗口，太小丢失上下文。要试。

坑2：只看相似度不够 有时候最相似的块不一定是最有用的。

坑3：Embedding 模型要匹配 中文内容要用中文 Embedding 模型，别用英文的。

总结​

  • RAG = 检索 + 生成
  • 文档切块 → Embedding → 存向量库
  • 查询时检索相关块 → 给模型 → 生成回答
  • 用于给模型加外部知识

明天聊 Agent，大模型怎么帮我干活。
