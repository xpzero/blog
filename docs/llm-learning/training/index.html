训练与微调：模型的"性格"从哪来

前面八篇拆完了推理——一句话进去、一段话出来的全过程。但有个问题一直悬着：那几百亿个参数里的"知识"和"分寸"是哪来的？为什么它会礼貌地拒绝出格请求，为什么它"记得"的资料会过时，又为什么它会自信地记错？

这些都是训练阶段刻进去的。先声明：本篇是文档和公开资料的转述整理，不含实测——训练一次大模型的成本决定了没法像前几篇那样跑个实验验证。资料来源列在文末。

两个阶段，两种性格来源​

主流聊天模型的训练大致分两步，各自塑造模型的一半"性格"：

预训练：读遍语料，学会接话​

拿海量文本（网页、书籍、代码等）做一件极其单调的事：遮住下一个词，让模型猜，猜错就调参数——就是第三篇那个"预测下一个 token"，重复几万亿次。

这个阶段产出的叫基座模型（base model）。它已经把语言规律、事实知识、推理模式压进了参数，但它只会"接话"不会"对话"：你问"北京是哪国首都？"，它可能接"上海是哪国首都？天津是哪国首都？"——因为训练语料里，试卷上一道题后面往往跟着下一道题。

两个重要推论从这里来：

  • 知识有截止日期。 参数里的"知识"就是训练语料的统计压缩，语料收集截止之后的事，模型参数里没有。
  • 记忆是有损的。 压缩几万亿 token 到几百亿参数，细节必然丢失。高频事实（巴黎是法国首都）记得牢，低频细节（某个小库的冷门函数签名）容易记串——第六篇说过模型没有"不知道"的出口，记串了也会流畅地说出来。幻觉的另一半成因在这里。

对齐：学会"好好说话"​

把只会接话的基座模型调教成助手，通常再过两道工序（统称对齐，alignment）：

  • SFT（Supervised Fine-Tuning，监督微调）：用人写的高质量问答对继续训练，教会它"这是对话，你是助手"的格式和口吻。
  • RLHF（Reinforcement Learning from Human Feedback，人类反馈强化学习）：对同一问题的多个回答让人排序打分，训练模型偏向人类喜欢的那种。近年也有 DPO 等更简化的替代方案（链接见文末）。

你感受到的"性格"——礼貌、拒绝越界话题、遇事先道歉、爱用列表——多数是这一步的产物，不是预训练语料的自然结果。副作用也在这一步产生：对齐过度会让模型变得过分谨慎或討好（研究里叫 sycophancy，谄媚），这是各家持续调整的平衡。

微调：什么条件下才值得做​

微调（fine-tuning）是在现成模型上用自己的数据继续训练。听起来是"让模型懂我的业务"的直觉方案，但它有明确的适用区间——判断框架比结论重要：

信号对了才上微调（同时满足越多越合适）：

  • 要改的是"行为"而不是"知识"。 微调擅长固化格式、语气、领域术语用法、特定输出结构；不擅长灌新知识——想让模型知道最新资料，检索（把资料放进上下文）比微调更直接可靠。
  • 提示词已到天花板。 写了详尽的提示词、给了充分示例，效果仍不达标——而不是还没认真调过提示词就想训模型。
  • 有足够多的高质量样本。 通常几百到几千条起步，且质量比数量重要：模型会连数据里的错误一起学走。
  • 调用量大到摊得平成本。 微调的收益之一是把长提示词"压进"参数，省掉每次请求的 token；低频调用摊不平训练和维护成本。

信号不对就先别动它：

  • 需求还在频繁变（提示词改一行就能上线，微调要重训重部署）；
  • 数据里有隐私或权属问题（训进参数的东西很难"删除"）；
  • 期望它"从此不再幻觉"（微调改变倾向，不提供保证）。

拿一个具体场景把框架走一遍——"客服机器人，要求回复统一用公司话术，且能回答产品细节"：

需求拆开看对信号结论
统一话术、固定格式改"行为"✓，样本好攒（历史客服记录）✓适合微调
回答产品细节这是"知识"，且产品每月更新 ✗用检索，别训
上线前还在改需求需求未稳 ✗先用提示词顶着

同一个项目里，一半需求适合微调、一半不适合——微调不是"上"或"不上"的整体决定，而是按需求逐条判断。

实操上，行业主流路径是循序渐进：先提示词，再检索（RAG），最后才考虑微调——三者也常组合使用。前两步的实践属于应用层，展开在 Agent 系列。
