上下文窗口：长了为什么崩，中间为什么被漏掉

把一份长文档丢给模型让它回答问题，常见两种翻车：要么直接报错"超出长度限制"，要么答是答了，但引用的全是文档开头和结尾的内容，中间部分像没读过一样。

这两种现象对应上下文窗口的两个层面：硬上限（超过直接拒绝）和软失效（没超限但用不好）。前面几篇的知识刚好够把两者都解释清。

窗口里装的比你以为的多​

上下文窗口（context window）是模型单次能处理的 token 总量上限——注意是总量，不是"你能发多少"。一个标称 128k 的窗口，实际是几方分的：

  • 系统提示：第一篇实测过，只发 1 个字符，服务端算了 4387 个 token——隐藏提示先占掉一块。
  • 历史对话：模型无状态，多轮对话靠每次重发全部历史，聊得越久这块越大。
  • 模型输出：生成的内容也在窗口里。输入塞得太满，留给回答的空间就不够，可能话说一半被截断。

硬上限的报错好处理（收到错误码就截断或分段）；麻烦的是下面这种。

窗口没满，能力先掉了​

实验研究发现一个稳定现象。测法很直白：把一条关键信息（比如"某人的账号是 XXX"）埋进一堆无关文档里，位置从头到尾挪动，每个位置都问模型同一个问题，看它答不答得出。结果按位置画出来是一条 U 形曲线：

回答准确率
  高 ┤ ●                                       ●
     │   ●                                   ●
     │     ●                               ●
  低 ┤        ● ● ● ● ● ● ● ● ● ● ● ● ●
     └─────────────────────────────────────────
       开头        ← 关键信息的位置 →        结尾

放在开头或结尾，模型找得到；放在中间，准确率明显下滑。这个结果以论文标题出名：Lost in the Middle（迷失在中间，链接见文末）。更扎心的是论文的另一个发现：最差的位置上，部分模型的表现甚至不如不给文档、闭卷回答——塞了一堆材料，反而帮了倒忙。

为什么会这样？前几篇的机制能给出几条线索（注意：这是研究给出的部分解释，不是定论）：

  • 注意力是稀释的。 第四篇说过，每个位置对前文所有 token 分配权重、总和为 1。前文 500 个 token 时每个平均能分到不少；50000 个 token 时，同样的注意力要摊得极薄，中间部分的信号容易被淹没。
  • 训练数据的偏置。 训练语料里，关键信息天然多出现在开头（标题、摘要）和结尾（结论）；训练时见得少的模式，用的时候就弱。
  • 位置编码的外推。 第五篇提过，不少模型的长窗口是靠 RoPE 外推技巧撑出来的，训练时没真见过那么长的距离，远距离的注意力质量本身就打折。

所以"支持 128k"和"128k 里每个位置都同样好用"是两回事。宣传页写前者，你的使用体验取决于后者。

长对话为什么会"失忆"​

现在可以把常见的"聊久了忘事"拆成三种不同的病因：

  1. 真被截断了。 历史超过窗口，应用只能丢弃最早的消息（或做摘要压缩），被丢掉的内容模型是真的看不到了。 典型场景：聊了一下午的会话里问"我们最开始定的方案是什么"，它给出一个从没出现过的答案——开头的消息早就不在发送的历史里了。
  2. 迷失在中间。 历史都在窗口内，但你几十轮前说的那句关键设定，正好落在 U 形曲线的谷底。 典型场景：第 3 轮说过"回答都用英文"，第 40 轮它突然改回中文；把设定重新说一遍立刻恢复——信息在，只是没被"看"到。
  3. 注意力被带偏。 上下文里塞了大量无关内容（比如粘贴的长日志），相关信息的权重被稀释。 典型场景：贴了 500 行日志让它找报错原因，它揪着日志里无关紧要的一行大做文章，反而没注意你在开头写的复现步骤。

三种病因对策不同：第 1 种要控制历史长度、重要设定重复申明；第 2、3 种的通用解法是别把窗口当垃圾桶——上下文越干净、关键信息越靠前或靠后，效果越稳。分不清是哪种时有个简易鉴别法：新开一个对话，只带上关键信息重问一遍——恢复正常就是 2 或 3（信息被淹没），依旧答错才可能是模型本身不会。

为什么窗口不能无限大​

窗口大小不是厂商抠门，是三条成本曲线压着：

  • 计算量随长度平方涨。 第四篇提过 n 个 token 有 n×n 对注意力打分：窗口从 4k 到 128k，长 32 倍，这部分计算涨约 1000 倍。
  • KV Cache 随长度线性涨。 第七篇算过量级，长上下文直接吃显存。
  • 数据难。 几十万 token 且前后真有依赖关系的训练样本本来就稀少。

理解了成本，也就理解了另一件事：把窗口用满不等于用好。费用按 token 计，长输入的预填充又慢（首字延迟涨），效果还可能掉——三头亏。先做减法（删无关内容），再考虑检索（只把相关段落塞进上下文，这就是 RAG 的动机，属于应用层话题，见 Agent 系列）。

用的时候真正要注意的​

  • 给长文档任务做位置设计：指令和关键约束放开头或结尾，别埋在材料中间；材料很长时，问题重复一遍放在末尾是常见有效的土办法。
  • 窗口预算要留出口：预估输出长度，别让输入把窗口顶满。
  • 截断策略自己定：靠服务端报错兜底不如自己数着 token 截（第一篇讲过怎么数），至少能决定丢哪段，而不是被动丢最早的。
  • 长上下文能力要实测：不同模型在同样长度下的表现差异很大，拿自己的真实文档做几次"把关键句藏在不同位置"的测试，比看宣传数字可靠。
