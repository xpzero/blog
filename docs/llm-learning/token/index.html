Token 与分词：模型不按"字"读你的文本

"你好"是几个字？人会说 2 个字，电脑存储它要占 6 个字节，而在大模型的世界里还有第三种量法：Token 数。模型能处理多长的输入按它算、接口用量按它算，但它既不是字数也不是字节数。

这篇做两件事：先在本地把一段文本的 Token 切分看个明白，再发真实请求验证——本地数出来的数，和服务端实际算的数，到底一不一致。

Token 是什么​

模型不能直接处理字符串，它处理的是数字序列。所以文本进模型前要过一道分词器（tokenizer）：

"Hello, how are you?"
  ↓ 分词器查表切分
["Hello", ",", " how", " are", " you", "?"]
  ↓ 每段换成词表里的编号
[13225, 11, 1495, 553, 481, 30]
  ↓
模型拿到的就是这串数字

每一段叫一个 Token，可能是完整单词、半个单词、一个汉字、一个词组，也可能是标点或空格。切分规则来自一张预先统计好的词表（vocabulary），逻辑很像查词典：常用说法（"你好""怎么样"）被收录成独立词条，一次切出来；生僻组合词典里没有，只能拆成更小的碎片逐个对付。

要注意切分靠的是统计频率而不是语法——什么算"一个词"由训练数据里的出现频次决定，和语文课上的分词没有必然关系。

本地切一次看看​

OpenAI 开源了它的分词器 tiktoken，可以直接观察切分结果：

import tiktoken

enc = tiktoken.get_encoding("o200k_base")

for s in [
    "Hello, how are you?",
    "你好，最近怎么样？",
    "const items = list.filter(x => x.active);",
]:
    tokens = enc.encode(s)
    print(f"{s!r}")
    print(f"  字符数={len(s)}  token数={len(tokens)}")
    print(f"  切分: {[enc.decode([t]) for t in tokens]}")

我机器上的输出（uv run --with tiktoken python demo.py）：

'Hello, how are you?'
  字符数=19  token数=6
  切分: ['Hello', ',', ' how', ' are', ' you', '?']
'你好，最近怎么样？'
  字符数=9  token数=5
  切分: ['你好', '，', '最近', '怎么样', '？']
'const items = list.filter(x => x.active);'
  字符数=41  token数=10
  切分: ['const', ' items', ' =', ' list', '.filter', '(x', ' =>', ' x', '.active', ');']

三个值得停下来看的点：

  • 空格属于后一个 Token（' how'、' items'），不是独立的。
  • 中文不是一字一个 Token：你好、怎么样 各是一个整体。9 个字符只有 5 个 Token，比英文"划算"。
  • 代码切得很碎：.filter、(x、); 这种符号组合各占一个，41 个字符 10 个 Token。

词表不同，结果完全不同​

上面用的 o200k_base 是 OpenAI 较新的词表。换成老一代 cl100k_base，同一句中文：

文本cl100k_baseo200k_base
Hello, how are you?66
你好，最近怎么样？105
const items = list.filter(x => x.active);1010

英文和代码没变，中文差了一倍——因为新词表收录了更多中文词组。所以"这段话多少 Token"永远要问"用哪个分词器数的"，把 A 模型的计数套到 B 模型上没有意义。

按 tiktoken 0.13.0 的注册表：GPT-4o 及之后的对话模型（GPT-4.1、GPT-5、o 系列）都用 o200k_base；GPT-4 和 text-embedding-3-* 系列还停在 cl100k_base；开源的 gpt-oss 用 o200k_harmony（o200k_base 加一批对话格式特殊 Token 的超集）。

发真实请求：本地数的和服务端数的一致吗​

本地估算只是估算，计费和长度限制以服务端为准。接口每次响应都带 usage.prompt_tokens（服务端实际统计的输入 Token 数），可以拿它对账。

直接对账有个障碍：服务端算的是发给模型的全部内容，不只是你写的那句话（下一节细说）。所以用差值法：先发一个字符 "A" 做基线，再发 "A" + 待测文本，两次 prompt_tokens 相减，得到的就是服务端对这段文本的计数：

from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()
client = OpenAI()  # BASE_URL 和 KEY 从 .env 读取

def ptokens(content):
    r = client.chat.completions.create(
        model="gpt-5.6-luna",
        messages=[{"role": "user", "content": content}],
        max_tokens=1,
    )
    return r.usage.prompt_tokens

base = ptokens("A")
for s in ["Hello, how are you?", "你好，最近怎么样？",
          "const items = list.filter(x => x.active);"]:
    print(f"{s!r}: delta={ptokens('A' + s) - base}")

我这边的实测输出（2026-08，代理服务，模型 gpt-5.6-luna；换服务商数字可能不同）：

文本本地 o200k_base服务端差值
Hello, how are you?66
你好，最近怎么样？55
const items = list.filter(x => x.active);1010

三段全部一致——说明这个服务用的分词器和 o200k_base 兼容，本地估算可信。但这个结论只对我测的这个服务成立，接入别家时值得用同样的方法再对一次账。

意外发现：你发 1 个字符，服务端算了 4387 个 Token​

上面差值法的基线本身才是这次实测最大的收获：

baseline (content='A'): prompt_tokens=4387

我只发了一个字母，服务端却统计了 4387 个输入 Token。多出来的约 4380 个，是这个服务在我的消息之前注入的系统提示（system prompt）——角色设定、回答规则、工具说明等，对调用方完全不可见，但每次请求都随行。

直觉上，发多少内容就该算多少账；实际上你看到的输入和模型实际收到的输入，可能差两个数量级。两个直接推论：

  • 剩给你的窗口比标称的小。模型上限若是 128k，隐藏提示先占掉一块。
  • 直连官方 API 时这个开销很小（消息结构本身只占十几个 Token）；走代理、网关或套壳服务时，它们注入了什么、占多少，用基线法一测便知。

开发时真正要注意的​

  • 别用字符数截断长文本。 中文、英文、代码的"字符/Token 汇率"完全不同，按字符截可能在 Token 层面仍然超限。要截就用分词器数着截。
  • 预算是三方分的：隐藏系统提示 + 你的输入 + 模型输出，共享同一个上下文窗口。只算自己写了多少字会误判。
  • 重复内容最贵。 多轮对话每次都要把历史全量重发（模型无状态，详见 Agent 系列第三篇），历史越长每轮的输入 Token 越多。
  • 本地估算用对词表。 接 OpenAI 系模型用 tiktoken；其他家找官方分词器或用上面的差值法实测。
