上下文窗口

模型按 Token 一步步生成回答，但一次请求能带入的上下文有限。把一份很长的需求文档粘进聊天框后，为什么模型可能拒绝请求，或者回答漏掉前面的条件？先检查上下文窗口。

它限制的是什么​

上下文窗口是一次请求中模型可处理的 Token 容量。通常需要同时容纳系统指令、用户输入、工具调用记录、检索到的资料和模型输出。不同模型和接口对输入、输出以及保留 Token 的限制不同，应查对应文档。

系统指令 + 历史消息 + 当前问题 + 附加资料 + 输出预算 <= 可用窗口

这只是预算关系，不是数学推导。请求前若没有为输出预留空间，即使输入刚好可接受，生成也可能受限或失败。

一个可操作的处理方式​

处理长文档时，先按标题或段落切成有语义边界的小块。对每块提取标题、来源和摘要；用户提问时只选择相关块放入上下文。

长文档 -> 按章节切块 -> 为块保存来源 -> 按问题选择少量块 -> 提问

这比把全部文档反复发送更容易控制长度，也让回答可以标出引用来源。若任务需要跨章节结论，还应明确保留相关章节，而不能只依赖单块摘要。

长窗口不是无限记忆​

模型只能使用当前请求实际传入的内容。对话界面是否自动保留历史、何时压缩历史、工具结果如何裁剪，都是产品实现细节，不能从"窗口很大"推断出来。

长上下文也不保证每个位置都被同等利用。把最关键的约束写得清楚、靠近任务说明，并通过有代表性的长输入测试，是比堆叠资料更可靠的做法。

常见问题​

  • 只按字符切分，忽略 Token 和输出预算。
  • 摘要覆盖原文后，丢掉数字、否定条件和引用位置。
  • 把私有资料放入第三方服务前，未确认数据处理和保留规则。
  • 以为模型知道未提供的最新或内部信息。
