概率与采样：temperature 到底改了什么

同一个问题问两遍，答案经常不一样。这有点反常识：计算器按一万遍 1+1 都是 2，为什么大模型不是？

第三篇埋了答案的一半：模型的输出不是一句话，而是一张概率表——词表里约 20 万个候选 token，各自带一个概率。从表里挑一个的过程叫采样（sampling），随机性全部来自这一步。temperature、top_p 这些常见参数，改的都是"怎么挑"，不碰模型本身。

从概率表到一个词​

拿到概率表后，最直接的两种挑法：

  • 贪心（greedy）：永远选概率最高的。输出稳定，但容易机械、重复——概率第二高的候选永远没机会，哪怕它只差 0.1%。
  • 按概率抽签：像一个转盘，好 占 21% 的扇区、热 占 13%……转到哪个选哪个。文本更自然多样，代价是偶尔转到低概率的怪词。

实际系统都在这两个极端之间调节，调节旋钮就是采样参数。

temperature：给概率表变形​

temperature 在 softmax 换算概率之前介入：把所有 logits 除以 T 再换算。效果一句话：T 越小，分布越尖；T 越大，分布越平。

logits 不变，换 T 后的概率表：

T = 0.5          T = 1.0          T = 1.5
好 → 35%         好 → 21%         好 → 16%
热 → 12%         热 → 13%         热 → 11%
冷 →  5%         冷 →  9%         冷 →  9%
（高分更突出）    （原始分布）      （差距被抹平）
  • T → 0：分布尖到只剩第一名，等价于贪心。适合抽取字段、分类这类要稳定的任务。
  • T = 1：按模型原始分布抽。
  • T > 1：低概率候选被抬高，更"放飞"，也更容易出错。

top_p（又叫 nucleus sampling）是另一个旋钮：按概率从高到低累加，只保留累计达到 p 的头部候选（比如 top_p: 0.9 表示只在覆盖 90% 概率质量的那几个词里抽），尾部长长的怪词直接出局。它和 temperature 可以同时用：一个变形，一个截断。

实测：把 temperature 拧到两端​

道理讲完验证一下。同一个提示各请求 6 次，对比 temperature: 0 和 1.5（2026-08，代理服务，模型 gpt-5.6-luna）：

提示：写一句 5 个字左右的开场问候，风格随意，只输出这句话。

temperature=0.0:
  嗨，最近好吗？ / 大家好呀！ / 嗨，最近好吗？ /
  嗨，最近好吗？ / 嗨，最近咋样？ / 嗨，最近怎么样？

temperature=1.5:
  嗨，最近好吗？ / 嗨，最近好吗？ / 嗨，最近好吗？ /
  嗨，最近好吗？ / 嗨，最近还好吗？ / 嗨，最近好吗

两个和教科书对不上的观察，各有一课：

第一，temperature: 0 没有给出完全一致的输出（6 次里 4 个变体）。就算贪心，工程上也不保证每次一字不差：服务端的浮点运算顺序、多台机器分担请求等细节都会引入微小扰动。官方文档也只说"更确定"（more deterministic），从不承诺"相同"。不要假设 T=0 就能拿到完全一样的输出；确实需要结果稳定，就在自己的程序里处理（比如缓存住第一次的结果）。

第二，1.5 没有比 0 更发散——参数可能根本没到模型。 这次实测走的是代理服务，而这个代理已被证实会吞参数：max_tokens: 3 时照样返回了完整长句，请求 logprobs 也不返回。temperature 是否被转发，从外部无法确认。这是所有套壳/网关服务的通病：你设置的参数和上游模型实际收到的参数，中间隔着一层黑盒。直连官方 API 时参数行为以官方文档为准；走代理时，先用小实验验证参数是否生效，再依赖它。

logprobs：官方的"看牌"接口​

想直接看那张概率表，官方 chat 接口有 logprobs: true + top_logprobs: n 参数，会随每个生成 token 返回它的对数概率和前 n 名候选——是观察"模型在两个词之间摇摆"的第一手窗口。可惜我这个代理不返回该字段，没法贴实测输出；参数格式和返回结构见 OpenAI 文档，直连时可用。

这解释了"一本正经的胡说"的一半​

概率表还藏着幻觉（hallucination）的一个结构性成因：模型没有"不知道"这个出口。 无论问题多冷门，softmax 出来的表里总有一个 token 排第一，采样总能挑出一个词，一个接一个，句子永远能续下去——哪怕每一步都只是"矮子里拔将军"。生成的流畅度和内容的正确性是两回事，前者是采样机制保证的，后者没有任何机制保证。

另一半成因在训练侧（模型为什么"记错"），第 9 篇讲。

开发时真正要注意的​

  • 按任务定 T：抽取、改写、函数调用用低 T；头脑风暴、文案生成用高 T。没把握就从默认值（通常 1）开始。
  • 别指望 T=0 输出完全一致：上面实测过了。
  • 走代理先验参数：花 6 次请求跑个对照实验，比事后排查"为什么调了没反应"便宜。
  • temperature 和 top_p 一般别同时调：两个都动，效果互相纠缠，难以归因。官方文档也建议二选一。
