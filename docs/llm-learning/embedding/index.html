Embedding：把"意思相近"变成一个能算的数

博客搜索有个经典问题：文章里写的是"垂直水平居中"，用户搜"元素居中对齐"，关键词匹配一条都命中不了。字符串层面它们确实不相等——但人一眼能看出是一个意思。

"意思相近"能不能变成一个程序可以计算的量？这就是 Embedding 干的事。它也是上一篇 Token 之后的下一站：token ID 只是编号，编号本身没有含义（13225 和 13226 毫无关系），模型真正处理的是编号换出来的向量。

从地图坐标说起​

"两家店离得近不近"从来不是难题：查经纬度，两组数字一减就知道。位置这种抽象概念，一旦被表示成数字坐标，"近"和"远"就变成了可以计算的东西。

Embedding 把同样的思路用在"意思"上：把一段文字映射成一组固定长度的数字（常见几百到几千维），使得意思相近的文本，坐标也相近。区别在于地图只有经度、纬度 2 个维度且各有含义，而文字的这几百个维度是模型自己学出来的，每一维具体代表什么人类说不清——但整体距离是有效的。

"怎么把按钮居中"      → [0.0101, 0.0714, 0.0609, -0.0146, -0.0300, …]   (共 512 维)
"按钮如何水平垂直居中" → [另一组 512 个数，方向和上面很接近]
"今天晚饭吃什么"      → [方向差得远的一组数]

衡量"方向相近"最常用的是余弦相似度（cosine similarity）：两个向量夹角的余弦值，1 表示方向完全一致，0 表示无关（垂直）。计算就是点积除以模长，细节见文末链接，不影响往下读。

实测：五句话谁和谁近​

Embedding 由专门的模型生成（和聊天模型是两类东西）。我的代理服务没开放 embedding 接口，所以这次在本地跑：fastembed 加载开源中文模型 BAAI/bge-small-zh-v1.5（约 100MB，ONNX 推理，不需要 GPU 和 torch）：

from fastembed import TextEmbedding
import math

model = TextEmbedding("BAAI/bge-small-zh-v1.5")

query = "怎么把按钮居中"
cands = [
    "按钮如何水平垂直居中",                  # 同义改写
    "flex 布局里子元素垂直水平居中",          # 相关但说法不同
    "怎么把按钮删除",                        # 字面很像、意思不同
    "How do I center a button with CSS?",   # 同义英文
    "今天晚饭吃什么",                        # 无关
]
vecs = list(model.embed([query] + cands))

def cos(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    na = math.sqrt(sum(x * x for x in a))
    nb = math.sqrt(sum(x * x for x in b))
    return dot / (na * nb)

for i, c in enumerate(cands, start=1):
    print(f"{cos(vecs[0], vecs[i]):.4f}  {c}")

我机器上的输出（模型下载走了镜像：HF_ENDPOINT=https://hf-mirror.com HF_HUB_DISABLE_XET=1）：

和"怎么把按钮居中"比余弦相似度
按钮如何水平垂直居中0.7987
怎么把按钮删除0.7232
flex 布局里子元素垂直水平居中0.4060
How do I center a button with CSS?0.2869
今天晚饭吃什么0.2148

读这组数：成功的和露馅的​

成功的一半： 同义改写拿了最高分，无关句子垫底。开头那个搜索问题在这里确实解决了——"居中"和"水平垂直居中"没有一个字的连续重合，向量却认出了它们。

露馅的一半更值得看：

  • "怎么把按钮删除"拿了 0.72，只比正确答案低 0.08。它和查询六个字里重了五个，意思却相反。至少对这个小模型来说，字面重合会明显抬分——embedding 不是"理解了意思"，是"在训练数据里，长这样的句子通常出现在相近的语境"。
  • 同义英文只有 0.29，比字面无关的"删除"低得多。bge-small-zh 是中文模型，跨语言对齐很弱。换多语言模型（如 text-embedding-3-large、multilingual-e5）这项会显著提高——分数是模型的属性，不是文本的属性。

两个实用推论：

  • 相似度数值只有相对意义。 0.7 算高还是低完全取决于模型和文本分布，不存在通用阈值。工程里用它排序（谁更相关），排完序再截断，别硬编码"大于 0.8 才算相似"。
  • 换模型必须全量重算。 不同模型的向量空间互不兼容，维度都未必一样（这个 512 维，OpenAI text-embedding-3-small 是 1536 维），混在一个库里比较是无意义的。

Embedding 模型和聊天模型是两条线​

容易混淆的点：聊天模型内部也有 embedding 层（token ID 进模型的第一站就是查表换向量），但对外提供的 embedding 服务是独立的模型，专门为"句子级相似度"训练过。上一篇查过 tiktoken 注册表：text-embedding-3-* 至今用的还是老词表 cl100k_base，和 GPT-4o 系不同步——两条产品线，各自演化。

用途也不同：聊天模型输出文字；embedding 模型输出向量，向量存进数据库供检索。最典型的组合是 RAG——用户提问转成向量，从文档库里捞最近的几段，塞给聊天模型当参考资料。这属于应用层话题，展开在 Agent 系列。

开发时真正要注意的​

  • 选模型先看语言。 中文场景用中文或多语言模型；上面实测已经演示了拿中文模型算英文会发生什么。
  • 短文本效果好于长文本。 一整篇文章压成一个向量会丢很多信息，检索场景通常先切块（chunk）再各自向量化。
  • 向量有存储成本。 512 维 float32 每条 2KB，百万条就是 2GB，还没算索引。维度和精度都是可以谈的（不少服务支持降维输出）。
  • 本地跑通再上服务。 fastembed 这条路线零 API 依赖，适合先验证方案；生产再评估托管服务的延迟、成本和模型质量。
