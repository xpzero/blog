Day 4：上下文窗口与长文本处理

上下文窗口是模型的"记忆容量"——超过上限，早期的内容就会被"遗忘"。

什么是上下文窗口？​

定义： 模型能够同时处理的 Token 数量上限。

类比理解：

  • 就像人的短期记忆
  • 能同时记住的事情有限
  • 超过容量，最早的事情会被遗忘

包含内容：

上下文窗口 = 系统提示 + 历史对话 + 当前输入

常见模型的上下文窗口​

模型上下文窗口约等于适用场景
GPT-3.54K-16K3-12 页文档简单对话
GPT-48K-128K6-96 页文档长文档分析
Claude 3200K约 150 页超长文档
Kimi200K约 150 页中文长文本

注意： 窗口越大，费用通常越高！

为什么会"遗忘"？​

现象： 对话进行很久后，模型"不记得"之前说过的话。

原因：

对话轮次增加 → Token 累积 → 超过窗口 → 早期内容被挤出

示例：

第 1 轮：用户设定"请用表格回答"
...
第 50 轮：模型不再用表格回答（设定被挤出窗口）

技术原因：

  1. 计算复杂度： 注意力机制的计算量随 Token 数平方增长
  2. 内存限制： 存储大量 Token 需要巨大内存
  3. 成本考虑： 长上下文 = 高费用

长文本处理策略​

策略 1：分块（Chunking）​

原理： 将长文本切成小块，分批处理

适用场景： 长文档分析、批量数据处理

示例：

100 页报告 → 分成 10 章 → 每章分别总结 → 综合所有总结

优点：

  • 不受窗口限制
  • 可以并行处理
  • 每块处理更精细

缺点：

  • 可能丢失跨章节联系
  • 需要额外的综合步骤

实现代码思路：

# 伪代码
def process_long_document(doc, chunk_size=4000):
    chunks = split_into_chunks(doc, chunk_size)
    summaries = [summarize(chunk) for chunk in chunks]
    final_summary = combine_summaries(summaries)
    return final_summary

策略 2：滑动窗口​

原理： 每次保留部分上文，引入新内容

适用场景： 连续分析、流式处理

示例：

第 1 轮：处理第 1-10 页
第 2 轮：处理第 5-15 页（保留 5-10 页作为上下文）
第 3 轮：处理第 10-20 页
...

优点：

  • 保持一定连续性
  • 适合渐进式分析
  • 不会完全丢失上下文

缺点：

  • 仍然有信息损失
  • 早期内容逐渐淡出
  • 处理速度较慢

策略 3：摘要压缩​

原理： 定期将长对话压缩成摘要

适用场景： 长时间对话、多轮交互

示例：

20 轮对话后：
"让我们总结一下前面的讨论：[摘要]

现在继续讨论..."

优点：

  • 保留关键信息
  • 节省 Token
  • 可以回顾历史

缺点：

  • 摘要可能丢失细节
  • 需要额外的摘要步骤
  • 摘要质量影响后续对话

自动摘要触发条件：

  • 每 N 轮对话后
  • Token 数达到阈值时
  • 话题转换时

策略 4：RAG（检索增强生成）​

原理： 只把相关的片段放入上下文，而不是全文

工作流程：

用户提问 → 检索相关文档片段 → 将片段+问题给模型 → 生成回答

类比：

  • 就像开卷考试
  • 不需要背诵全书
  • 只需要找到相关章节

详细说明：

Step 1：准备阶段（一次性）

  1. 将知识库文档切成小片段（通常 500-1000 Token）
  2. 每个片段转为向量（Embedding）
  3. 存入向量数据库

Step 2：查询阶段（每次提问）

  1. 用户提问 → 转为向量
  2. 在数据库中找最相似的片段（通常取 Top 5）
  3. 只把相关片段 + 问题一起给模型

优点：

  • 几乎无限的知识容量
  • 只使用相关信息，效率高
  • 成本低（不需要处理全文）
  • 可以实时更新知识库

缺点：

  • 需要额外的检索系统
  • 检索质量影响结果
  • 需要维护向量数据库
  • 初始设置较复杂

RAG 架构图：

用户提问
    ↓
Embedding 模型 → 向量
    ↓
向量数据库检索 → Top K 相关片段
    ↓
片段 + 问题 → LLM
    ↓
生成回答

实际应用场景​

场景 1：分析长文档​

问题： 要分析一本 300 页的书，但模型只能处理 50 页

解决方案：

方法：分块 + 综合

步骤：
1. 将书分成 6 个部分（每部分 50 页）
2. 让模型分别总结每个部分
3. 将 6 个总结合并
4. 让模型基于总结给出全书概述

进阶： 可以针对特定章节深入提问

场景 2：长时间对话​

问题： 聊了很久后，模型"忘记"了初始设定

解决方案：

方法：定期重申 + 摘要

技巧：
1. 每 10 轮重申一次关键设定
2. 定期总结对话要点
3. 重要信息在后续对话中重复提及

示例：

用户：记住，所有回答都要用表格
...
（10 轮后）
用户：重申一下，回答格式要求是什么？
助手：所有回答都要用表格形式

场景 3：知识库问答​

问题： 公司有 10 万份文档，如何让 AI 回答相关问题？

解决方案：

方法：RAG 检索增强

架构：
用户提问 → 检索系统 → 相关文档片段 → 模型 → 回答

示例：
用户问："退货政策是什么？"
系统检索 → 找到《退货政策》文档的第 3 段
模型基于这段内容回答

实际部署：

  • 使用 Pinecone、Weaviate 等向量数据库
  • 使用 LangChain、LlamaIndex 等框架
  • 定期更新知识库

动手实践​

任务 1：体验上下文限制​

实验：

  1. 复制一段 3000 字的长文本
  2. 让模型总结开头、中间、结尾的内容
  3. 观察是否能准确回忆全文

记录：

文本长度：____ Token
开头总结准确率：____%
中间总结准确率：____%
结尾总结准确率：____%

任务 2：模拟"遗忘"现象​

步骤：

  1. 开始新对话，设定规则："请用表格回答所有问题"
  2. 持续对话 20+ 轮，每轮内容较长
  3. 观察第几轮模型开始"忘记"规则

记录：

设定轮次：第 1 轮
遗忘轮次：第 ____ 轮
可能原因：上下文窗口被挤出

任务 3：尝试分块处理​

材料： 找一篇 5000 字的文章

步骤：

  1. 将文章分成 3 段
  2. 让模型分别总结每段
  3. 让模型基于三个摘要给出整体总结
  4. 对比：分块总结的完整性 vs 直接全文总结

任务 4：理解 RAG​

思考题：

  1. RAG 和直接放全文进上下文，各有什么优缺点？
方式优点缺点
直接放全文信息完整，理解全局受窗口限制，成本高
RAG几乎无限容量，成本低依赖检索质量，可能遗漏
  1. Embedding 在 RAG 中起什么作用？

将文本转为向量，实现语义相似度匹配，找到相关内容。

今日总结​

核心概念：

  • 上下文窗口 = 模型的"记忆容量"
  • 超过窗口 = "遗忘"早期内容
  • RAG = "按需查阅"而不是"背诵全文"

处理策略：

  • 分块：将长文本切成小块
  • 滑动窗口：保留部分上文
  • 摘要压缩：定期总结关键信息
  • RAG：只检索相关片段

选择策略：

  • 文档分析 → 分块
  • 连续对话 → 滑动窗口或摘要
  • 知识库问答 → RAG
