Day 4：上下文窗口与长文本处理

上下文窗口是模型的"记忆容量"——超过上限，早期的内容就会被"遗忘"。

什么是上下文窗口​

定义：模型能够同时处理的 Token 数量上限。

类比：就像人的短期记忆，能同时记住的事情有限，超过容量，最早的事情会被遗忘。

包含内容：

上下文窗口 = 系统提示 + 历史对话 + 当前输入

常见模型的上下文窗口​

模型上下文窗口约等于
GPT-3.54K-16K3-12 页文档
GPT-48K-128K6-96 页文档
Claude 3200K约 150 页
Kimi200K约 150 页

注意：窗口越大，费用通常越高！

为什么会"遗忘"​

现象：对话进行很久后，模型"不记得"之前说过的话。

原因：

对话轮次增加 → Token 累积 → 超过窗口 → 早期内容被挤出

示例：

第 1 轮：用户设定"请用表格回答"
...
第 50 轮：模型不再用表格回答（设定被挤出窗口）

长文本处理策略​

策略 1：分块（Chunking）​

将长文本切成小块，分批处理。

100 页报告 → 分成 10 章 → 每章分别总结 → 综合所有总结

优点：

  • 不受窗口限制
  • 可以并行处理
  • 每块处理更精细

缺点：

  • 可能丢失跨章节联系
  • 需要额外的综合步骤

策略 2：滑动窗口​

每次保留部分上文，引入新内容。

第 1 轮：处理第 1-10 页
第 2 轮：处理第 5-15 页（保留 5-10 页作为上下文）
第 3 轮：处理第 10-20 页
...

策略 3：摘要压缩​

定期将长对话压缩成摘要。

20 轮对话后：
"让我们总结一下前面的讨论：[摘要]

现在继续讨论..."

策略 4：RAG（检索增强生成）​

只把相关的片段放入上下文，而不是全文。

工作流程：

用户提问 → 检索相关文档片段 → 将片段+问题给模型 → 生成回答

类比：开卷考试——不需要背诵全书，只需要找到相关章节。

RAG 架构：

用户提问
    ↓
Embedding 模型 → 向量
    ↓
向量数据库检索 → Top K 相关片段
    ↓
片段 + 问题 → LLM
    ↓
生成回答

实际应用场景​

场景 1：分析长文档​

问题：要分析一本 300 页的书，但模型只能处理 50 页。

解决方案：

方法：分块 + 综合

步骤：
1. 将书分成 6 个部分（每部分 50 页）
2. 让模型分别总结每个部分
3. 将 6 个总结合并
4. 让模型基于总结给出全书概述

场景 2：长时间对话​

问题：聊了很久后，模型"忘记"了初始设定。

解决方案：

方法：定期重申 + 摘要

技巧：
1. 每 10 轮重申一次关键设定
2. 定期总结对话要点
3. 重要信息在后续对话中重复提及

场景 3：知识库问答​

问题：公司有 10 万份文档，如何让 AI 回答相关问题？

解决方案：

方法：RAG 检索增强

架构：
用户提问 → 检索系统 → 相关文档片段 → 模型 → 回答

核心要点​

  • 上下文窗口 = 模型的"记忆容量"
  • 超过窗口 = "遗忘"早期内容
  • RAG = "按需查阅"而不是"背诵全文"
场景推荐策略
文档分析分块
连续对话滑动窗口或摘要
知识库问答RAG
