模型微调：让模型学会固定做法

通用模型会写代码、会聊天，但未必知道团队的回复格式或产品名词。提示词能解决一次性要求；当同一种要求反复出现，且可以准备高质量示例时，微调才值得尝试。

微调到底改了什么​

微调是在已有模型基础上继续训练，不是从零造一个模型。训练样本告诉它：“看到这种输入时，应该按这种方式回答”。它更像在练习表达习惯，不是一个可靠的资料库；需要引用最新文档时，RAG 往往更合适。

例如，希望模型把 bug 报告整理成固定模板：

{"messages":[{"role":"user","content":"登录后白屏，Safari 17 可复现"},{"role":"assistant","content":"现象：登录后白屏\n环境：Safari 17\n建议：检查控制台错误和登录回调"}]}

先写 20 条这样的样本，再让基础模型用同样提示词回答。若基础模型已经稳定做到，就不必训练。

常见选择​

全量微调会更新全部参数，成本高，也要保存完整模型副本。个人实验通常从 LoRA 开始：冻结原模型，只训练附加的小参数；QLoRA 再把基础模型以低精度存放，以换取更低显存占用。

选择顺序可以很简单：先提示词，再 LoRA；显存不够再考虑 QLoRA；只有数据、预算和评估都充分时才考虑全量微调。所谓“低显存可训练”仍取决于模型大小、上下文长度、批量和软件版本，不能只看显卡容量。

最小实验的检查表​

  1. 明确一个可判断的目标，例如“输出必须有现象、环境、建议三行”。
  2. 准备少量干净、无敏感信息的输入输出对，并留出从不训练的测试样本。
  3. 训练一个小型 LoRA 适配器，保存训练配置和基础模型版本。
  4. 用同一组测试问题对比训练前后，再人工检查错误和编造内容。

下面的小脚本可先检查每条对话是否有用户和助手消息：

import json

for line_no, line in enumerate(open("train.jsonl", encoding="utf-8"), 1):
    roles = [message["role"] for message in json.loads(line)["messages"]]
    if "user" not in roles or "assistant" not in roles:
        print(f"第 {line_no} 行缺少 user 或 assistant")

没有输出表示这个最基本的格式检查通过，不代表答案质量通过。

容易踩的坑​

  • 样本答案互相矛盾时，模型不会替你选出正确版本。
  • 训练太久会记住样本措辞，遇到新问题反而变差，要看验证集并及时停止。
  • 微调后仍会幻觉，也可能损失原有的通用能力，因此始终与基础模型对比。
  • 业务数据可能含个人信息、密钥或版权内容，提交到第三方训练服务前必须确认合规。
