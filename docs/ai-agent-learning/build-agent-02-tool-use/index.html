从零手写 Agent（二）：让模型用上它接触不到的数据

上一篇跑通了调用，但模型能回答的只有它训练时见过的公开知识。真实需求往往不是这样：

  • 「我们内部系统里这个订单是什么状态？」——数据在你的数据库里，模型看不到
  • 「北京今天多少度？」——实时信息，训练数据里不可能有

这两类需求指向同一个缺口：模型需要一个途径去接触它接触不到的东西。一边是私有数据（内部系统、本地文件、数据库），一边是公共实时服务（天气、搜索、汇率）。

解决办法叫 function calling（函数调用），也叫 tool use。这篇把它跑通。

先说清一个关键事实​

模型不会执行你的代码。

这是最容易误解的地方。整个流程是这样的：

模型只输出一个意图：「我想调用 get_weather，参数是 {"city": "北京"}」。真正去查天气的是你的代码。查完把结果交回给模型，它再决定下一步——继续调别的工具，还是直接回答。

注意图里那个圈：用户只参与入口和出口，中间转几圈用户是不知道的。这个自循环就是 Agent 的核心。

第一步：告诉模型有哪些工具​

模型不会自己知道你写了什么函数，你得用 JSON Schema 描述给它听：

TOOLS = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "查询指定城市今天的天气",
            "parameters": {
                "type": "object",
                "properties": {
                    "city": {
                        "type": "string",
                        "description": "城市名，例如 北京",
                    },
                },
                "required": ["city"],
            },
        },
    },
]

这段结构分两层：外层的 {"type": "function", "function": {...}} 是 OpenAI 协议规定的固定包装；内层的 parameters 是标准 JSON Schema，描述这个函数收什么参数。

description 不是注释，它是提示词。 模型完全靠这两个 description 判断「该不该调这个工具」和「参数该传什么」。写得含糊，模型就会该调不调，或者传错参数。这是整套机制里最需要花心思的地方。

后面的例子还会用到第二个工具 calculate，声明结构和上面完全一样，只是参数换成 expression：

{
    "type": "function",
    "function": {
        "name": "calculate",
        "description": "计算一个数学表达式的结果",
        "parameters": {
            "type": "object",
            "properties": {
                "expression": {
                    "type": "string",
                    "description": "待计算的表达式，例如 (38 - 12) * 3",
                },
            },
            "required": ["expression"],
        },
    },
}

两个都放进 TOOLS 列表，请求时整个列表一起传给模型——它自己判断该用哪个、或者两个都用。

第二步：写工具的实现​

def execute_tool(name: str, args: dict) -> str:
    if name == "calculate":
        return str(eval(args["expression"]))
    elif name == "get_weather":
        return f"{args['city']}今天晴，最高气温38℃"
    return f"未知工具：{name}"

这里的 get_weather 返回的是写死的假数据，calculate 也只是个最容易验证的小例子——真实项目里它们该换成查数据库、调内部接口、请求第三方 API。用假数据是为了先把流程跑通，看清数据怎么流转。

注意返回值是字符串。工具结果最终要作为一条消息回传给模型，模型只能读文本。

（eval 会执行任意代码，只适合本地学习，正式项目里绝对不能这么写。）

第三步：循环​

def run_agent(user_input: str, max_turns: int = 10):
    messages = [
        {"role": "system", "content": "你是一个有用的助手，可以调用工具来帮助用户。"},
        {"role": "user", "content": user_input},
    ]

    for _ in range(max_turns):
        response = client.chat.completions.create(
            model=MODEL, messages=messages, tools=TOOLS
        )
        message = response.choices[0].message
        messages.append(message)          # 模型的回复要留在上下文里

        if not message.tool_calls:        # 没有工具调用，说明它想好了
            print(f"Agent: {message.content}")
            return

        for tool_call in message.tool_calls:
            name = tool_call.function.name
            args = json.loads(tool_call.function.arguments)   # 参数是 JSON 字符串
            result = execute_tool(name, args)

            messages.append({
                "role": "tool",
                "tool_call_id": tool_call.id,   # 必须对应上是哪次调用的结果
                "content": result,
            })

    print("[达到最大轮次，停止]")

四个要点：

一轮工具调用往 messages 里塞两类消息：带 tool_calls 的 assistant 消息（模型的意图），以及每个调用对应的 role="tool" 消息（执行结果）。两者靠 tool_call_id 配对。

必须循环，不能只处理一次。 模型可能拿到天气结果后，接着要调计算工具。

本 demo 的出圈条件是 not message.tool_calls——模型不再要求调工具就算讲完了。 这是最简单可行的判断，但要知道它只是这个 demo 的选择，不是通用规则。

协议层面更规范的信号其实是 finish_reason：按 OpenAI 文档，模型要调工具时该返回 finish_reason="tool_calls"，讲完了才是 "stop"。但这个字段是否如实返回取决于具体服务端的实现，不一定可靠，所以这里选择看 tool_calls 这个更直接的依据。

真实的 Agent 停止条件远不止这一条，通常还要考虑：

  • finish_reason == "length"——回复被 token 上限截断了，此时 tool_calls 是空的，但答案并不完整，当成「讲完了」就错了
  • 预算耗尽——token 花超、耗时超时
  • 用户中断——按下 Ctrl-C 或点了停止
  • 专门的「完成」工具——让模型显式调用 done() 来声明任务结束，比推断更可控
  • 对产物做校验——它说文件写好了，就读回来确认内容对不对，不对就继续

max_turns 是我们自己加的保护，不属于协议。 模型感知不到它的存在，它只是个 for 循环的上限——万一工具一直报错、模型一直用同样的参数重试，循环就永远不结束，而每转一圈上下文都在变长，持续消耗 token。这里用「转满 10 圈就停」是 demo 里最简单的兜底方式；真实项目可能换成按 token 预算、按耗时、或者检测到重复调用就打断。

触发上限后不抛异常，只打印一句提示，本轮任务算没做完。

tool_call_id 是怎么配对的​

完整链路：

我们把 TOOLS（工具声明）传给模型
  → 模型说「我要调 get_weather」，并为这次调用发一个 id
  → 我们执行工具，把结果连同同一个 id 回传
  → 两端靠这个 id 配对

对应到字段就是 assistant.tool_calls[i].id 对上 tool 消息的 tool_call_id。

一个容易搞错的精度：id 是发给「这一次调用」的，不是发给「工具」的。 同一个工具连调两次会拿到两个不同的 id，因此是两条独立记录、两条独立结果。

为什么回传时必须靠 id？ 因为来回两个方向的数据结构不对称：

# 模型 → 我们：tool_calls 是数组，谁的参数是谁的，结构上已经分好了
tool_calls[0]  → name='get_weather',  arguments='{"city":"北京"}'
tool_calls[1]  → name='calculate',    arguments='{"expression":"(38-12)*3"}'
# 我们 → 模型：多条扁平的并列消息，彼此平级，没有任何结构表明归属
tool:  tool_call_id=call_A  content="晴 38℃"
tool:  tool_call_id=call_B  content="78"

模型发来时有数组结构兜底，我们回传时什么结构都没有，只能靠 id。

配对起作用的地方有两处：

一是让模型正确归属结果。 并行调用时上下文里有多条结果，模型靠 id 才知道「晴 38℃」来自天气工具、「78」来自计算器。若错配，它会说出「北京今天 78℃」这种话。

二是模型服务端的校验带来「早失败」。 假如不校验，模型会看到「我发起了 2 个调用但只有 1 个结果」的残缺上下文——它可能重复调用，也可能直接编一个缺失的结果，那就变成难以发现的幻觉。校验把这个错误挡在请求阶段，变成一个明确的报错。

顺带说明：现在这份代码是顺序执行、顺序回填的，所以即使没有 id 也不会错配。id 的价值要等工具改成并发执行（真实项目常这么做，工具多是 IO 密集的）才真正显现——那时回填顺序不再等于声明顺序。

配对失败会怎样​

校验方是模型服务端，不是模型、也不是我们的代码——execute_tool_calls 只是把 tool_call.id 原样填回去，从不检查。而且校验发生在下一次请求时，所以错误延迟一轮才暴露：工具执行那一刻一切正常，下一轮 create() 才炸：

id 写错:       BadRequestError 400 - No tool output found for function call call_b1ih5s...
缺 tool 消息:  BadRequestError 400 - No tool output found for function call call_b1ih5s...

注意这两种情况报的是同一个错。说明模型服务端检查的是「assistant 声明的每个 tool_call 是否都有对应输出」，而不是「这条 tool 消息的 id 是否存在」。所以报错里给出的是那个没被响应的 call id，排查时别顺着它去找拼写错误。

效果​

问一句同时需要两个工具的话：

$ uv run main.py
  [工具调用] get_weather({'city': '北京'})
  [返回结果] 北京今天晴，最高气温38℃
  [工具调用] calculate({'expression': '(38 - 12) * 3'})
  [返回结果] 78
Agent: 北京今天晴，最高气温 38℃。(38 - 12) × 3 = 78。

模型自己判断出要调两个工具、自己组织了参数、拿到结果后自己汇总成一段回答。我们没写任何「如果用户问天气就调 get_weather」这样的判断逻辑。

值得注意的是它一次响应里就返回了两个 tool_calls（并行调用），所以上面代码里那层 for tool_call in message.tool_calls 是必要的。

为什么一次会返回两个​

因为模型判断这两件事互不依赖：查天气和算 (38-12)*3 谁先谁后都行，后者也不需要前者的结果当输入。既然如此，一次性都提出来可以省一轮往返。

把问题换成有依赖关系的，行为立刻不同：

问「北京天气怎么样？顺便算一下 (38 - 12) * 3」
  本轮返回 2 个调用 -> get_weather{"city":"北京"}, calculate{"expression":"(38 - 12) * 3"}

问「查一下北京今天的最高气温，然后把这个气温乘以 3」
  本轮返回 1 个调用 -> get_weather{"city":"北京"}

第二种情况它只调了天气——因为 expression 里填不了一个还不知道的数值。等拿到 38 之后，下一轮才会调 calculate。这正是「必须循环，不能只处理一次」的实际体现。

顺带一句：Chat Completions 接口有 parallel_tool_calls=False 参数可以禁用并行调用，但它是否生效取决于服务端实现。别指望用这个开关来简化代码，老老实实遍历 tool_calls 才稳。
