从零手写 Agent（四）：流式输出，以及被切碎的工具调用

上一篇的 Agent 能连续对话了，但用起来有个明显的难受之处：问一个需要长篇回答的问题，屏幕上什么都没有，几秒后突然「啪」地出现一整段。

ChatGPT 那种一个字一个字往外冒的效果，是怎么做的？

答案是给请求加一个参数 stream=True。但真正麻烦的不是文本——是工具调用在流式下可能被切成碎片，处理不好会直接报错。

流式的本质​

非流式返回一个完整对象；流式返回一串 chunk，每个 chunk 只带「这一小步新增了什么」，这个增量叫 delta。

所以取值从 .message 变成了 .delta：

stream = client.chat.completions.create(
    model=MODEL, messages=messages, tools=TOOLS, stream=True
)

for chunk in stream:
    delta = chunk.choices[0].delta   # 注意不是 message

delta 有三种形态：只有文本、只有工具调用片段、什么都没有（最后那个表示结束的 chunk）。所以两个分支都得写成「有才处理」。

文本：边打印边留副本​

content = ""

for chunk in stream:
    delta = chunk.choices[0].delta

    if delta.content:
        print(delta.content, end="", flush=True)   # 实时输出
        content += delta.content                    # 同时攒完整文本

两个参数容易漏：

  • end="" 去掉 print 默认的换行，否则每个字都换行
  • flush=True 强制立刻输出。不加的话内容会被输出缓冲区攒着，攒够一批才显示——流式效果就没了

为什么还要 content += ... 攒一份？因为打印是给人看的，而这段文本还要回填进 messages 给模型看。两份都得要。

工具调用：碎片要自己拼​

这是流式最麻烦的地方。一个工具调用可能被拆到多个 chunk 里送来，你可能会看到这样的形态：

chunk0  index=0  id='call_A'  name='get_weather'  args=''
chunk1  index=0  id=None      name=None           args='{"ci'
chunk2  index=0  id=None      name=None           args='ty":"北'
chunk3  index=0  id=None      name=None           args='京"}'
chunk4  index=1  id='call_B'  name='calculate'    args=''      ← 换调用了

看出规律了：同一个调用的所有分片 index 相同，且只有首个片段带 id 和 name，后续片段只有 arguments 的一小截。

这个形态不是我凭空编的：官方 SDK 内部对 arguments 做的是字符串累加（acc_value += delta_value），社区里贴出的真实转储也长这样（arguments='{"ra'、后续片段 id=None）。但这些是观察，不是保证。

这里要说清楚一件事：协议并没有规定「必须切碎」。 它保证的是 arguments 属于增量语义、需要你拼接；至于切成几片，是模型逐 token 生成时的实现产物。一个提供方把参数一次性发完，同样是合规的——那只是「只有一个增量」的退化情况。

中转网关就常常这样。我实测过某个网关：让模型写一个 1865 字符的长参数，arguments 依然只有一个分片，id、name、完整参数一次给全；而同一次请求里的文本回复却是正常逐字流式的，说明网关单独缓冲了 tool_calls。

所以下面的累加逻辑在那种网关上一次都不会被触发。但代码仍然要写——你无法预设对面怎么切，换个提供方、换个网关，甚至同一家改一版实现，碎片都可能出现。

所以要维护一批「进行中的调用」，按 index 归位、逐段累加：

calls: dict[int, dict] = {}

for chunk in stream:
    delta = chunk.choices[0].delta

    # delta.tool_calls 在纯文本 chunk 里是 None，直接迭代会 TypeError
    for tc in delta.tool_calls or []:
        # index 是 tool_calls 数组的下标：同一个调用的分片 index 相同，换调用才会变
        slot = calls.setdefault(tc.index, {"id": "", "name": "", "arguments": ""})

        if tc.id:
            slot["id"] = tc.id                           # id 只在首片出现
        if tc.function and tc.function.name:
            slot["name"] = tc.function.name              # 覆盖：name 不会被切碎
        if tc.function and tc.function.arguments:
            slot["arguments"] += tc.function.arguments   # 累加：参数是碎片

# dict 的遍历顺序是插入顺序，未必等于 index 大小，排一下还原调用顺序
ordered = [calls[i] for i in sorted(calls)]

按上面的形态推演一遍：

chunkindex动作calls 状态
00新建槽位 0，取到 id 与 name{0: {A, get_weather, ""}}
10落回槽位 0，累加{0: {A, get_weather, '{"ci'}}
20同上{0: {A, ..., '{"city":"北'}}
30同上{0: {A, ..., '{"city":"北京"}'}} ← 完整了
41index 变了，新建槽位 1{0: {A...}, 1: {B, calculate, ""}}

arguments 必须用 += 而不是 =。 覆盖之后只剩最后一截，json.loads 必然失败。而 name 相反，首片段一次给全，直接赋值就行。

另外我们不需要「这个调用结束了」的信号——slot 拿到的是字典的引用，写 slot 就是直接写进 calls，属于原地增量更新，循环退出时每条自然都完整了。

（补一句避免误解：原始 chunk 流里确实没有结束信号。官方那套高层 client.chat.completions.stream() API 会发 tool_calls.function.arguments.done 事件，但那是它在客户端靠 index 变化反推出来的——发现 index 变了，就认为上一个调用收完了。用 create(stream=True) 拿原始 chunk 的话，这个事件不存在。）

顺带说清一个容易混淆的点：id 是「每次调用」唯一，不是「每个工具」唯一。同一个工具连续调两次会得到两个不同的 id，因此会是两条独立记录，都会被执行，不会误合并。

为什么用 index 而不是 id？​

用 id 归拢看起来更直观——它才是「这次调用」的身份。但官方 SDK 用的是 index，而且缺失就直接报错（openai/lib/streaming/_deltas.py）：

try:
    index = delta_entry["index"]
except KeyError as exc:
    raise RuntimeError(f"Expected list delta entry to have an `index` key; {delta_entry}")

两种键的取舍：

  • index（官方）：index 是数组下标，每个分片都带，天然支持多个调用的分片交错到达。缺点是遇到「把所有调用都标成 index=0」的异常网关，会把它们合并成一条，参数拼出 {...}{...} 直接 json.loads 失败。
  • id：不受 index 标错影响。但后续分片本来就不带 id，只能落到「最近一个调用」——这隐含假设一个调用发完才发下一个。真遇到交错下发，call_A 的碎片会全被塞进 call_B，两条都拼坏。

OpenAI 原生是顺序下发的，两种写法都能跑通；但既然规范以 index 为准，就跟着规范走。

收尾：必须自己拼一条 assistant 消息​

非流式时可以直接 messages.append(message)，流式没有这个现成对象，得自己按同样的结构拼出来：

messages.append({
    "role": "assistant",
    "content": content or None,
    "tool_calls": [
        {
            "id": slot["id"],
            "type": "function",
            "function": {"name": slot["name"], "arguments": slot["arguments"]},
        }
        for slot in ordered
    ],
})

这一步不能省。 下一轮请求时，模型靠上下文里这条消息才知道自己发起过哪些调用；紧随其后的 role="tool" 消息也靠 tool_call_id 与它对应。

缺了它会在哪报错？不是在拼装的时候，而是下一次调用 client.chat.completions.create() 时——模型服务端在校验 messages 阶段就拒了请求，SDK 抛出 BadRequestError：

BadRequestError: Error code: 400 - No tool output found for function call call_xxx.

也就是说错误延迟一轮才暴露：拼装那一刻代码跑得好好的，下一轮请求才炸。第二篇有更详细的说明。

其实官方有现成的​

前面手写的两件事——累积分片、拼 assistant 消息——官方 SDK 都替你做好了，用另一套高层 API：

with client.chat.completions.stream(model=MODEL, messages=messages, tools=TOOLS) as stream:
    for event in stream:
        if event.type == "content.delta":
            print(event.delta, end="", flush=True)

    message = stream.get_final_completion().choices[0].message
    messages.append(message)      # 已经拼好了，直接塞

实测输出（工具调用部分）：

tool_calls.function.arguments.delta    index=0 '{"city":"北京"}'
tool_calls.function.arguments.done     index=0 '{"city":"北京"}'

get_final_completion() 返回的 message 里 id / name / arguments 全部拼装完毕，可以直接 append 进上下文。生产代码建议直接用这套，少写几十行容易出错的拼装逻辑。

那本文为什么还手写？两个原因：

  • 这个系列叫「从零手写」，把 stream() 当黑盒用，就看不到流式到底发生了什么；
  • 它并没有消除对 index 的依赖，只是把这份依赖从你的代码挪进了 SDK。前面说的「网关把所有调用标成 index=0」那种情况，用它照样会出问题，而且更难排查——毕竟报错发生在别人的库里。

知道有这条捷径，再决定要不要走，比不知道好。

效果​

逐字出现是时间维度上的效果，静态代码块表达不了，所以录了一段：

工具调用的部分依然是整块出现的（因为要等参数拼完整才能执行），最后那段文本回复则是逐字冒出来的。

$ uv run main.py
你: 北京天气怎么样？再算下 (38-12)*3
  [工具调用] get_weather({'city': '北京'})
  [返回结果] 北京今天晴，最高气温38℃
  [工具调用] calculate({'expression': '(38-12)*3'})
  [返回结果] 78
Agent: 北京今天晴，最高气温 38℃。(38-12)×3 = 78。
如果你觉得「看起来没在流式」

大概率不是代码问题，而是两个容易混淆的现象。

模型可能先做内部推理。 推理期间它一个 content chunk 都不吐（响应的 usage 里能看到 reasoning_tokens），所以观感是「先卡住几秒，然后才开始出字」，很容易误判成没在流式。

短回答看起来就是一次性出现。 像上面那句「38℃，结果 78」只有十几个字，几个 chunk 在极短时间内就出完了，肉眼无法分辨。要看效果得问需要长回答的问题。
