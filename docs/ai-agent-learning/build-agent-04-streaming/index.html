从零手写 Agent（四）：流式输出，以及被切碎的工具调用

上一篇的 Agent 能连续对话了，但用起来有个明显的难受之处：问一个需要长篇回答的问题，屏幕上什么都没有，几秒后突然「啪」地出现一整段。

ChatGPT 那种一个字一个字往外冒的效果，是怎么做的？

答案是给请求加一个参数 stream=True。但真正麻烦的不是文本——是工具调用在流式下会被切成碎片，处理不好会直接报错。

流式的本质​

非流式返回一个完整对象；流式返回一串 chunk，每个 chunk 只带「这一小步新增了什么」，这个增量叫 delta。

所以取值从 .message 变成了 .delta：

stream = client.chat.completions.create(
    model=MODEL, messages=messages, tools=TOOLS, stream=True
)

for chunk in stream:
    delta = chunk.choices[0].delta   # 注意不是 message

delta 有三种形态：只有文本、只有工具调用片段、什么都没有（最后那个表示结束的 chunk）。所以两个分支都得写成「有才处理」。

文本：边打印边留副本​

content = ""

for chunk in stream:
    delta = chunk.choices[0].delta

    if delta.content:
        print(delta.content, end="", flush=True)   # 实时输出
        content += delta.content                    # 同时攒完整文本

两个参数容易漏：

  • end="" 去掉 print 默认的换行，否则每个字都换行
  • flush=True 强制立刻输出。不加的话内容会被输出缓冲区攒着，攒够一批才显示——流式效果就没了

为什么还要 content += ... 攒一份？因为打印是给人看的，而这段文本还要回填进 messages 给模型看。两份都得要。

工具调用：碎片要自己拼​

这是流式最麻烦的地方。一个工具调用会被拆到多个 chunk 里送来，标准形态长这样：

chunk0  id='call_A'  name='get_weather'  args=''
chunk1  id=None      name=None           args='{"ci'
chunk2  id=None      name=None           args='ty":"北'
chunk3  id=None      name=None           args='京"}'
chunk4  id='call_B'  name='calculate'    args=''      ← 换调用了

看出规律了：只有首个片段带 id 和 name，后续片段只有 arguments 的一小截。

所以要维护一个「进行中的调用」列表，逐段累加：

calls: list[dict] = []

for chunk in stream:
    delta = chunk.choices[0].delta

    # delta.tool_calls 在纯文本 chunk 里是 None，直接迭代会 TypeError
    for tc in delta.tool_calls or []:
        # 出现没见过的 id，说明是一个新调用
        if not calls or (tc.id and all(c["id"] != tc.id for c in calls)):
            calls.append({"id": tc.id or "", "name": "", "arguments": ""})

        # 带 id 的片段归回它自己的调用，不带 id 的归到最近一个
        slot = next((c for c in calls if tc.id and c["id"] == tc.id), calls[-1])

        if tc.function and tc.function.name:
            slot["name"] = tc.function.name              # 覆盖：name 不会被切碎
        if tc.function and tc.function.arguments:
            slot["arguments"] += tc.function.arguments   # 累加：参数是碎片

按上面的形态推演一遍：

chunk动作calls 状态
0call_A 没见过，新建[{A, get_weather, ""}]
1无 id，落到最近一个[{A, get_weather, '{"ci'}]
2同上[{A, ..., '{"city":"北'}]
3同上[{A, ..., '{"city":"北京"}'}] ← 完整了
4call_B 没见过，新建[{A...}, {B, calculate, ""}]

arguments 必须用 += 而不是 =。 覆盖之后只剩最后一截，json.loads 必然失败。而 name 相反，首片段一次给全，直接赋值就行。

另外不存在「这个调用结束了」的信号，也不需要——slot 拿到的是字典的引用，写 slot 就是直接写进 calls，属于原地增量更新，循环退出时每条自然都完整了。

一个真实踩到的坑：index 不可靠​

很多教程会教你用 tc.index 来区分是第几个调用，因为标准实现里每个调用有递增的 index。

我在自己用的服务上实测发现，两个不同的工具调用返回的 index 都是 0：

chunk[0]  tool_call(index=0, id='call_CxY3...', name='get_weather', args='{"city":"北京"}')
chunk[1]  tool_call(index=0, id='call_ahWJ...', name='calculate',   args='{"expression":"(38-12)*3"}')
chunk[2]  finish='stop'  (空)

按 index 归拢的后果是两串 JSON 被拼在一起，变成 {"city":"北京"}{"expression":"..."}，报错：

json.decoder.JSONDecodeError: Extra data: line 1 column 14 (char 13)

改成按 id 归拢就绕过了这个问题——id 是每次调用唯一的，比 index 可靠。

顺带说清一个容易混淆的点：id 是**「每次调用」唯一，不是「每个工具」唯一**。同一个工具连续调两次会得到两个不同的 id，因此会是两条独立记录，都会被执行，不会误合并。

收尾：必须自己拼一条 assistant 消息​

非流式时可以直接 messages.append(message)，流式没有这个现成对象，得自己按同样的结构拼出来：

messages.append({
    "role": "assistant",
    "content": content or None,
    "tool_calls": [
        {
            "id": slot["id"],
            "type": "function",
            "function": {"name": slot["name"], "arguments": slot["arguments"]},
        }
        for slot in calls
    ],
})

这一步不能省。 下一轮请求时，模型靠上下文里这条消息才知道自己发起过哪些调用；紧随其后的 role="tool" 消息也靠 tool_call_id 与它对应。缺了它，接口会因为 tool 消息找不到归属而报错。

效果​

逐字出现是时间维度上的效果，静态代码块表达不了，所以录了一段：

工具调用的部分依然是整块出现的（因为要等参数拼完整才能执行），最后那段文本回复则是逐字冒出来的。

$ uv run main.py
你: 北京天气怎么样？再算下 (38-12)*3
  [工具调用] get_weather({'city': '北京'})
  [返回结果] 北京今天晴，最高气温38℃
  [工具调用] calculate({'expression': '(38-12)*3'})
  [返回结果] 78
Agent: 北京今天晴，最高气温 38℃。(38-12)×3 = 78。

如果你觉得「看起来没在流式」​

大概率不是代码问题，而是两个容易混淆的现象。我对一个 200 字左右的回答做了时间统计：

内容 chunk 数: 167
首个 chunk 到达: 2.88s
最后 chunk 到达: 5.94s
前 5 个: 2.88 / 2.89 / 2.90 / 2.92 / 2.94
后 5 个: 5.89 / 5.89 / 5.90 / 5.92 / 5.94

首字延迟了 2.88 秒。 这段时间模型在做内部推理（响应的 usage 里能看到 reasoning_tokens），推理期间一个 content chunk 都不吐。所以观感是「先卡住几秒，然后才开始出字」，很容易误判成没在流式。

短回答看起来就是一次性出现。 像上面那句「38℃，结果 78」只有十几个字，几个 chunk 在 100 毫秒内出完，肉眼无法分辨。要看效果得问需要长回答的问题。

还有一种情况确实和代码无关：有的模型服务端会先收完整个响应再一次性把 SSE 推给你。我在同一个网关上就抓到过所有 chunk 时间戳完全相同的情况。判断方法就是上面这样给每个 chunk 打时间戳——如果时间戳全都一样，那就是模型服务端在缓冲。
