Claude Code 工作原理：从语言模型到可执行 Agent

Claude 模型本身不能直接读取本地文件、运行命令或修改代码，但 Claude Code 却可以围绕一个目标连续搜索、编辑、验证并根据错误继续调整。它是怎样把一次模型调用变成一个能够持续行动的 Agent 的？

要回答这个问题，需要把 Claude Code、Claude 模型、上下文、工具、权限和外部环境之间的关系拆开，再观察它们如何组成“观察、决策、行动、反馈”的循环。

本文以 Claude Code 2.1.88 源码快照为依据，关注这些机制及其边界。具体实现可能随版本变化，但模型与宿主程序的职责划分、工具反馈循环和上下文限制仍然是理解这类 Agent 的基础。

1. 最核心的结论​

Claude Code 不是一个语言模型直接控制电脑，也不是一个模型在后台连续思考。

它本质上是下面几个部分组成的闭环系统：

语言模型
  + 上下文组装器
  + 结构化工具协议
  + 工具执行环境
  + 权限与安全边界
  + 会话状态和错误恢复
  = 一个可持续行动的编程 Agent

如果只保留一句话，可以这样理解：

宿主程序把当前问题和环境信息交给模型，模型提出下一步动作，宿主程序检查并执行动作，再把结果交回模型；这个过程不断重复，直到模型不再要求执行动作，或者系统决定必须停止。

整个系统的核心不是某一个函数，而是一个反复运行的“观察、决策、行动、再观察”循环：

用户目标
   │
   ▼
整理当前上下文
   │
   ▼
模型判断下一步
   │
   ├── 直接回答 ────────────────┐
   │                            │
   └── 请求使用工具             │
            │                   │
            ▼                   │
       校验与权限判断            │
            │                   │
            ▼                   │
         执行工具                │
            │                   │
            ▼                   │
       把结果放回上下文           │
            │                   │
            └── 再次请求模型 ────┘
                                 │
                                 ▼
                              最终回答

模型负责“提出什么动作”，宿主程序负责“这个动作能不能做、怎样做、做完发生了什么”。这条边界是理解整个系统的关键。

下面的架构图展示了各部分的边界。只有 Claude Code 能直接连接模型、调度工具并控制真实环境；模型本身不直接连接文件系统或 MCP Server。

2. 系统中的四个角色​

2.1 语言模型：决策者，不是执行者​

模型可以：

  • 理解用户目标；
  • 阅读已经提供给它的代码和工具结果；
  • 推测下一步最有价值的动作；
  • 生成文本回答；
  • 生成结构化的工具调用请求；
  • 根据工具错误调整后续方案。

模型不能直接：

  • 读取本地文件；
  • 执行 Shell 命令；
  • 修改磁盘；
  • 访问一个没有通过工具提供给它的网站；
  • 让操作绕过宿主程序的权限判断；
  • 在两次 API 请求之间自行保存运行状态。

模型说“我要读取这个文件”和文件真的被读取，是两件完全不同的事情。前者只是模型输出的一段结构化请求，后者是宿主程序执行工具产生的真实副作用。

2.2 宿主程序：Agent 的控制器​

Claude Code 本身是运行在用户机器上的宿主程序。它负责：

  • 接收用户输入；
  • 选择模型和模型参数；
  • 组装本次模型能看到的上下文；
  • 告诉模型当前有哪些工具；
  • 解析模型的流式输出；
  • 判断模型是否请求了工具；
  • 校验工具参数；
  • 执行权限规则和安全检查；
  • 调用本地工具或远程 MCP 工具；
  • 把执行结果重新加入会话；
  • 决定继续、重试、压缩上下文还是停止；
  • 记录会话，以便恢复。

所以 Claude Code 的“Agent 性”主要来自宿主程序实现的循环，而不是模型拥有了一个长期运行的心智进程。

2.3 工具：模型与真实世界之间的动作接口​

工具是受宿主程序控制的能力，例如：

  • 读取文件；
  • 搜索代码；
  • 修改文件；
  • 运行命令；
  • 查询网页；
  • 启动子 Agent；
  • 调用 MCP 服务。

每个工具都同时包含两层含义：

给模型看的能力描述
  = 工具叫什么、能做什么、参数长什么样

给宿主程序运行的实现
  = 如何校验、如何授权、如何执行、如何返回结果

模型看到的是能力契约，不是工具的实现代码。

2.4 用户和策略：最终信任边界​

模型可以建议动作，但不能成为自己行为的最终授权者。

真正的边界来自：

  • 用户的明确许可；
  • 项目和个人权限规则；
  • 企业策略；
  • 工具自己的安全判断；
  • 沙箱；
  • Hook 或外部审批系统；
  • 无人值守环境中的默认拒绝策略。

这使系统形成一个基本原则：

决策能力与授权能力必须分离。

3. 一次用户请求为什么会触发多次模型调用​

用户看到的是“一次提问”，但 Agent 内部通常会进行多轮模型请求。

例如用户说：

把配置字段 oldName 改成 newName，并运行测试。

一个可能的真实过程是：

第 1 次模型请求
  模型：先搜索 oldName 出现在哪里
  输出：搜索工具调用

宿主程序
  执行搜索，把结果放回会话

第 2 次模型请求
  模型：需要读取其中几个文件
  输出：多个读取工具调用

宿主程序
  并发读取安全的文件，把内容放回会话

第 3 次模型请求
  模型：知道如何修改了
  输出：编辑工具调用

宿主程序
  检查权限，修改文件，把编辑结果放回会话

第 4 次模型请求
  模型：需要验证
  输出：测试命令工具调用

宿主程序
  检查命令权限，运行测试，把输出放回会话

第 5 次模型请求
  模型：测试通过，不再请求工具
  输出：最终总结

因此要区分两个概念：

用户的一轮对话
  ≠ 一次模型推理

用户的一轮对话
  = 若干次模型推理 + 若干次工具执行 + 一个最终结果

模型每次只需要决定“在当前已知信息下，下一步最合理的动作是什么”。它不必在第一轮就准确规划完整过程。这种逐步反馈降低了复杂任务一次性规划失败的风险。

4. 工具调用为什么能够工作​

4.1 工具先被描述成一种结构化语言​

宿主程序向模型发请求时，不只发送对话文本，还会发送本轮可用工具的结构描述。

抽象来看，一个工具描述类似：

{
  "name": "Read",
  "description": "读取指定文件",
  "input_schema": {
    "path": "string",
    "offset": "number",
    "limit": "number"
  }
}

这相当于给模型增加了一套动作语言。模型不必用自然语言说“请帮我读取文件”，而是可以输出机器可解析的内容：

{
  "type": "tool_use",
  "id": "tool-123",
  "name": "Read",
  "input": {
    "path": "src/app.ts"
  }
}

这里仍然没有发生文件读取。它只是一个动作提案。

4.2 宿主程序把动作提案变成真实操作​

收到工具请求后，宿主程序通常要经过下面这些门：

工具是否真实存在
  → 参数结构是否合法
  → 参数在当前环境中是否合理
  → Hook 是否允许或修改它
  → 权限规则是否允许
  → 是否需要用户确认
  → 是否应在沙箱中执行
  → 才调用真实工具

任何一层失败，都可以阻止工具执行。

4.3 工具结果为什么还要交回模型​

模型无法自动看到操作系统中刚刚发生的事情。工具执行完成后，宿主程序必须显式构造一个与工具调用 ID 配对的结果：

{
  "type": "tool_result",
  "tool_use_id": "tool-123",
  "content": "文件内容……"
}

下一次请求模型时，这个结果会成为上下文的一部分。模型因此获得新的观察，再决定下一步。

这就是 Agent 的反馈闭环：

模型提出动作
  → 环境执行动作
  → 环境返回观察
  → 模型根据观察继续决策

4.4 工具失败也具有信息价值​

如果参数错误、权限被拒绝、命令失败或文件不存在，宿主程序通常不会直接让整个 Agent 崩溃，而是把错误包装成工具结果交回模型。

于是模型可能进行自我修正：

第一次：读取错误路径
  → 工具返回文件不存在

第二次：模型根据错误搜索正确路径
  → 找到文件

第三次：重新读取

所谓“Agent 会纠错”，通常不是模型撤销了内部思考，而是外部环境把失败作为新的观察反馈给它。

4.5 为什么工具调用和结果必须配对​

每个工具请求都有唯一 ID，结果必须引用同一个 ID。这个配对有三个目的：

  • 让模型知道结果属于哪个动作；
  • 支持一轮中存在多个工具调用；
  • 在中断和错误情况下保持消息协议合法。

即使一个工具没有真正执行，例如被用户中断，宿主程序也往往需要生成一个“已中断”的结果。否则下一次模型请求会看到一个永远没有结果的动作，协议状态就不完整了。

5. Agent 循环是一台状态机​

Claude Code 的核心可以抽象成一台状态机：

这台状态机保存的不是模型内部思想，而是宿主程序能够观察和管理的状态，例如：

  • 当前消息历史；
  • 本轮已经产生的工具请求；
  • 工具执行结果；
  • 当前权限模式；
  • 是否被中断；
  • 已经使用了多少轮；
  • 是否已经尝试过上下文压缩；
  • 是否正在进行错误恢复；
  • 还有多少预算。

这也解释了为什么 Agent 可以在模型请求之间保持连续性：连续性由宿主程序保存并在下一次请求时重新提供，而不是模型进程一直保持激活。

6. 上下文才是模型的“当前世界”​

6.1 模型没有直接访问整个会话和项目​

每次调用模型时，模型只能看到本次请求中实际发送的内容。它不会天然看到：

  • 完整项目；
  • 终端当前屏幕；
  • 磁盘最新状态；
  • 所有历史对话；
  • 上一次调用后宿主程序内部发生的一切。

Claude Code 必须把它认为有用的信息编译成一次请求。这些信息可能包括：

  • 系统行为说明；
  • 用户当前目标；
  • 选定的历史消息；
  • 已执行工具的结果；
  • IDE 选区；
  • 文件变化；
  • 工作目录和环境信息；
  • 可用工具的结构；
  • 项目说明文件；
  • Skill 展开的指令；
  • 恢复或压缩产生的摘要。

所以模型所处的“世界”不是现实环境，而是宿主程序构造出的上下文投影。

6.2 四种状态不要混为一谈​

Claude Code 同时存在四类状态：

状态含义
界面状态用户在终端中看到的流式文字、Spinner、确认框
会话记录为恢复和审计保存的消息与工具事件
模型上下文当前这一次 API 请求真正发送给模型的内容
外部环境磁盘、Git、进程、网络服务的真实状态

它们通常相关，但并不相等。

例如：

  • 一条流式文字可能正在界面显示，但还没有成为完整消息；
  • 一段旧工具输出可能存在会话记录中，但因上下文太长而不再发送给模型；
  • 文件已经被用户在外部编辑，但模型要等宿主程序提供文件变化后才能知道；
  • 某些系统进度消息只用于 UI，不会进入模型上下文。

6.3 每次请求都要重新组装上下文​

在一次工具续轮之后，宿主程序通常构造这样的新上下文：

此前仍然有效的历史
  + 模型刚刚输出的文字、思考块和工具请求
  + 对应的工具结果
  + 工具执行期间出现的新环境信息
  = 下一次模型请求

在发送之前，还要进行协议规范化，例如：

  • 合并可以合并的连续消息；
  • 去掉只服务于 UI 的内容；
  • 修复不完整的工具调用和结果；
  • 删除不符合 API 约束的空消息；
  • 确保思考块和普通内容的排列合法；
  • 只发送本轮真正可用的工具描述。

可以把这一步理解为“上下文编译”：内部状态很丰富，但必须被编译成模型 API 能理解、长度允许、语义完整的请求。

这张图中的多个输入并不是简单拼接。Claude Code 会根据当前状态选择内容，并且可能用摘要或文件引用替代原始大段信息。

7. Claude Code 所谓的“记忆”是什么​

7.1 模型本身不保存跨请求记忆​

模型 API 基本上是无状态的。每次请求都像重新唤醒一个模型实例，并把当前需要它知道的信息重新告诉它。

它表现得记得前文，是因为历史被再次发送了。

它表现得记得工具操作，是因为工具结果被发送了。

它表现得能恢复会话，是因为本地保存的记录被重新读取并重建成上下文。

7.2 会话记录不等于模型记忆​

完整会话可以被持久化，但上下文窗口有限，不可能永远把所有记录原样发送给模型。

因此系统会进行多层处理：

完整会话记录
  → 选择当前有效边界之后的消息
  → 缩减过大的旧工具结果
  → 清理低价值内容
  → 必要时生成摘要
  → 得到本轮模型上下文

这意味着：

“系统存过这条信息”不等于“模型当前还看得到这条信息”。

7.3 压缩不是无损存储​

上下文接近上限时，Claude Code 会把较早的对话和工具结果压缩成摘要，再保留近期、关键或尚未完成的内容。

压缩解决的是容量问题，但会引入信息损失：

  • 具体命令参数可能被概括；
  • 某个失败尝试的细节可能丢失；
  • 文件内容可能只剩结论；
  • 原始措辞和细粒度因果关系可能不再存在。

因此长会话中的 Agent 并不是拥有无限记忆，而是在不断维护一个有损的工作记忆。

这也是为什么重要约束最好写入项目说明、测试或代码，而不是只在很早的一轮对话中提过一次。

8. Thinking 是什么，不是什么​

8.1 Thinking 是模型响应的一种内容块​

支持扩展思考的模型可以在最终文本或工具请求之前产生 thinking 内容。宿主程序可以选择：

  • 开启或关闭；
  • 使用固定思考预算；
  • 让模型自适应决定思考量；
  • 在 UI 中显示、折叠或隐藏；
  • 接收被服务端隐藏的 redacted thinking。

从系统角度看，thinking 仍然只是模型响应协议中的一种内容块。

8.2 Thinking 不直接控制工具​

宿主程序不会因为 thinking 中写了“我要删除文件”就真的删除文件。可执行动作必须以正式的结构化工具请求出现，并经过完整的校验与权限流程。

因此有一条重要边界：

thinking
  = 模型生成决策的中间内容

tool_use
  = 宿主程序可以解析和审查的动作提案

真实副作用
  = 动作提案通过权限后，由工具实现产生

8.3 Thinking 不等于长期记忆​

原始 thinking、会话摘要和最终回答是三类不同内容：

  • thinking 是某次推理输出的一部分；
  • 摘要是为节省上下文而生成的历史压缩；
  • 最终回答是面向用户的结果。

旧 thinking 还可能因为签名、模型或 API 合法性要求而被清理。不能把它当成一个稳定、永久、可恢复的内部思维档案。

8.4 Thinking 也不是可信的安全依据​

无论模型在 thinking 中怎样解释自己的意图，安全系统都不应只相信它的自述。权限判断应基于可观察的工具名称、结构化参数、路径、命令和策略，而不是“模型说它没有恶意”。

9. 流式输出为什么不仅是逐字打印​

9.1 流里有两类信息​

模型流式响应不只有文本字符，还包含结构事件，例如：

消息开始
内容块开始
文本增量
思考增量
工具参数 JSON 增量
内容块结束
使用量和停止原因
消息结束

因此 Claude Code 的流处理同时服务两个目标：

  • 让用户尽快看到文字和状态变化；
  • 把不完整的增量最终组装成语义完整的消息或工具请求。

9.2 临时显示与正式消息分离​

用户在屏幕上看到的逐字输出属于临时 UI 状态。只有当一个内容块完整结束后，它才适合作为正式语义单元进入消息历史。

这种分离非常重要：

  • 半截 JSON 不能执行；
  • 半截 thinking 不能视为完整消息；
  • 网络中断时，临时显示不一定适合进入下一次模型上下文；
  • 完整块才能稳定地持久化和恢复。

9.3 为什么工具可以在整条回复结束前开始执行​

如果一个工具调用块已经完整结束，即使模型还在输出后续内容，宿主程序也可以提前开始执行该工具。

这样可以降低延迟：

模型继续生成后面的内容
          与
工具开始读取文件或查询服务
          同时进行

但它也增加了复杂度。宿主程序必须处理：

  • 后续流突然失败；
  • 流式请求改为非流式重试；
  • 同一个工具请求不能被重复执行；
  • 中断后必须补齐协议结果；
  • 并行完成顺序不能破坏逻辑顺序。

所以“流式工具执行”本质上是一种降低延迟的投机执行机制，需要额外的一致性保护。

10. 工具为什么有时并发、有时串行​

模型可以在一轮输出多个工具请求。宿主程序不会简单地把所有工具同时运行。

判断重点不是“这个工具看起来快不快”，而是它们是否可以安全地并发。

适合并发的例子：

  • 读取互不相关的多个文件；
  • 执行多个只读搜索；
  • 查询多个互不依赖的资源。

通常需要串行的例子：

  • 连续修改同一个文件；
  • 前一个命令会改变后一个命令的输入；
  • 会改变工作目录、权限或 Agent 上下文的操作；
  • 具有不可逆副作用的动作。

即使多个工具并发完成，宿主程序也可能按照模型原始请求顺序应用它们产生的上下文变化。这样能避免“谁先跑完”随机改变下一轮语义。

因此并发策略遵循的是：

执行可以并行
  但语义提交必须确定

这和数据库中“并发工作、按规则提交”的思想相似。

11. 权限、安全和沙箱是三件不同的事​

11.1 能力、授权、隔离​

安全系统中最容易混淆的是下面三个概念：

概念回答的问题
能力暴露模型本轮是否知道这个工具存在
权限授权这个具体动作是否允许执行
沙箱隔离即使执行，它能影响多大的环境范围

例如模型可以看到 Bash 工具，不代表任何命令都会执行；命令得到授权，也不代表它一定在完全不受限制的系统环境中运行。

11.2 权限是分层决策，不是一个布尔开关​

一个动作是否允许，通常需要综合：

企业和管理员策略
  → 用户、项目和会话规则
  → 工具级规则
  → 针对具体参数的安全检查
  → 当前权限模式
  → Hook 或外部审批
  → 必要时询问用户

结果通常不只有允许和拒绝，而是三态：

allow：可以执行
ask：需要进一步决定或询问
deny：不能执行

ask 很重要，因为系统需要表达“这件事不是明确禁止，但也不能自动决定”。

下面的图只描述通用决策原则。实际工具还可能加入更具体的文件路径、Shell 命令、企业策略和沙箱检查。

权限流程决定“能不能做”，沙箱决定“允许执行后最多能影响哪里”。

11.3 为什么 deny 必须比普通 allow 更强​

安全规则不能简单采用“最后一条配置覆盖前面配置”。否则一个低信任来源的 allow 就可能覆盖企业策略中的 deny。

更合理的原则是：

  • 明确 deny 优先；
  • 针对具体危险参数的安全检查优先；
  • 普通 allow 只能在没有更强限制时生效；
  • 权限模式不能随意绕过不可绕过的策略；
  • 没有交互能力时，对 unresolved ask 默认保守处理。

这解释了为什么某些所谓的“自动接受”或“绕过提示”模式仍然不能突破所有安全边界。它们改变的是常规确认流程，不应取消企业 deny、敏感路径检查或工具自身的安全约束。

11.4 权限模式不是沙箱模式​

几个常见误解：

  • 自动接受编辑，不等于允许修改任何敏感路径；
  • 不弹确认框，可能意味着 ask 被拒绝，而不是自动允许；
  • 计划模式约束 Agent 的工作方式，但不等于操作系统级隔离；
  • 绕过常规权限提示，也不应绕过硬性 deny 和安全检查；
  • 沙箱降低命令影响范围，但不能代替权限规则。

权限决定“能否做”，沙箱决定“做了以后最多影响哪里”。两者是互补关系。

11.5 为什么无人值守模式通常更保守​

交互终端可以弹出确认框，但 SDK、后台任务或无头模式可能没有人可以回答。

此时安全的默认方式是：

如果外部审批 Hook 能决定
  → 使用 Hook 的决定

如果没有任何机制能解决 ask
  → 拒绝，而不是假设允许

这是一种 fail closed 原则：失去审批能力时收紧权限，而不是扩大权限。

12. 文件和 Shell 为什么需要特殊权限逻辑​

12.1 文件路径不是普通字符串​

如果只检查用户输入的路径字符串，很容易被符号链接或路径变形绕过。

可靠的文件权限判断需要考虑：

  • 原始路径；
  • 相对路径解析后的绝对位置；
  • 中间目录中的符号链接；
  • 最终真实路径；
  • 目标不存在时最近的真实父目录；
  • 悬空符号链接的目标；
  • .git、编辑器配置、Shell 配置等敏感位置。

因此“允许编辑项目目录”不是简单判断字符串是否以项目路径开头，而是要判断动作最终会作用到哪里。

12.2 Shell 命令也不是普通字符串​

命令中可能包含：

  • 管道；
  • && 和 ||；
  • 重定向；
  • 子命令；
  • 环境变量前缀；
  • 命令替换；
  • 多条复合语句。

如果权限系统只检查开头的命令名，就可能允许：

一个看似安全的命令 && 一个危险命令

因此 Shell 权限需要尽量理解命令结构，对复合命令中的各部分、涉及路径以及是否脱离沙箱进行判断。

这仍然不能让任意 Shell 分析变得绝对完美，所以显式用户确认、沙箱和最小权限仍然必要。

13. Hook 的原理：给 Agent 循环插入外部治理逻辑​

Hook 可以理解为宿主程序在关键事件上开放的中间件接口。

常见插入点包括：

用户输入模型之前
工具执行之前
需要权限决定时
工具成功之后
工具失败之后
模型准备结束时
子 Agent 准备结束时

Hook 可以做的事情包括：

  • 阻止一次输入或工具调用；
  • 修改工具参数；
  • 提供额外上下文；
  • 代表外部系统批准或拒绝；
  • 记录审计信息；
  • 要求模型根据检查结果继续修正；
  • 在 CI、企业审批或自定义策略中接管部分决策。

13.1 Hook allow 不是绝对授权​

如果一个前置 Hook 表示允许，宿主程序仍可能继续检查：

  • 企业 deny；
  • 明确 ask 规则；
  • 敏感路径；
  • 工具自己的安全限制；
  • 必须由用户参与的操作。

合理的语义是：

Hook allow
  = Hook 这一层没有反对

最终 allow
  = 所有不能被绕过的层都没有反对

13.2 Stop Hook 为什么可以让模型继续​

模型输出最终文本后，宿主程序可以运行结束检查。如果检查发现任务没有达到要求，例如测试未通过或输出缺少必要内容，它可以把错误作为新上下文，再调用一次模型。

所以“模型已经停止生成”不一定等于“Agent 生命周期已经结束”。最终停止权属于外层状态机。

14. MCP 的本质：把远程能力接入同一种工具协议​

MCP 并没有改变 Agent 的基本原理。它做的是让外部服务以统一方式提供：

  • 工具描述；
  • 输入 schema；
  • 结构化结果；
  • 资源或提示信息。

Tools、Resources 和 Prompts 是 Server 提供给 Client 的能力或内容；Roots 的方向相反，是 Client 告诉 Server 可以在哪些范围内工作。

模型看到 MCP 工具后，仍然只是产生结构化工具请求；宿主程序仍然负责权限和调用；结果仍然要回到下一轮上下文。

但 MCP 增加了新的信任边界：

是否允许连接这个服务
  → 是否允许向模型暴露这个服务的工具
  → 是否允许调用某个具体工具
  → 是否信任返回内容只作为数据而不是指令

远程服务自称“只读”只能作为调度提示，不能自动成为安全证明。服务配置、企业策略、具体工具权限和用户授权仍然需要独立存在。

从安全角度看，MCP 返回的数据还可能包含提示注入内容。模型可以阅读这些数据，但宿主程序不应因此取消本地权限边界。

15. Skill 的本质：改变上下文，不直接获得权限​

Skill 通常用于向模型注入某一类任务的专门说明、流程、模板或资源。

它主要改变的是：

模型知道什么
模型应该按什么步骤思考
模型应该优先使用哪些工具
模型应该怎样组织结果

Skill 本身不应等价于获得额外系统权限。加载了一个部署 Skill，不代表模型就自动有权执行生产部署；实际动作仍然需要经过对应工具和权限链。

因此 Skill 属于“认知和流程扩展”，工具属于“行动能力扩展”，权限属于“行动边界”。

16. 错误恢复为什么分很多层​

系统中的“重试”并不是一种统一行为。不同错误发生在不同层，如果混在一起处理，很容易重复执行有副作用的工具。

图中的回路语义不同：HTTP 重试是在尝试完成同一个请求，而 Agent 续轮、压缩和错误反馈都会改变下一次模型看到的输入。

16.1 网络或 API 重试​

这一层的目标是完成同一次模型请求，例如处理：

  • 临时网络失败；
  • 限流；
  • 服务过载；
  • 身份认证刷新；
  • 流连接失败。

原则上它不应该被视为一个新的 Agent 决策轮。

16.2 流式请求降级​

如果流式响应失败，系统可能改用非流式请求。危险之处在于：流失败前可能已经产生并启动了工具调用。

因此降级时必须知道：

  • 哪些工具只是部分生成；
  • 哪些工具已经完整生成；
  • 哪些已经执行；
  • 新请求是否可能再次生成同一个工具调用。

防止重复副作用，是这一层最重要的一致性问题。

16.3 Agent 续轮​

工具执行完成后再次调用模型，不是失败重试，而是正常的反馈循环。此时新请求包含了新的工具结果，语义已经发生变化。

16.4 上下文恢复​

当输入过长时，系统可以：

  • 删除低价值的旧结果；
  • 把大型工具输出改成摘要或文件引用；
  • 压缩旧历史；
  • 在压缩后重新调用模型。

这是“改变输入后再试”，不是原请求的简单重放。

16.5 输出截断恢复​

模型达到最大输出 token 时，系统可以增大输出额度，或者把已截断内容放回历史并要求继续。

这要求宿主程序判断已有输出能否作为合法上下文，尤其要处理未完整的 thinking 或工具块。

16.6 权限和工具错误恢复​

权限拒绝或工具失败通常会作为观察交给模型。模型可以换一种安全方案，也可能重复提出同样动作。

系统需要限制无限重复，例如：

  • 最大 Agent 轮数；
  • token 或费用预算；
  • 连续拒绝计数；
  • Hook 阻止继续；
  • 用户中断。

17. 中断为什么要贯穿整个系统​

用户按下中断后，不能只停止终端显示。中断信号需要传播到：

  • 当前模型请求；
  • 网络流；
  • 正在运行的工具；
  • Hook；
  • 自动权限分类器；
  • MCP 请求；
  • 后续 Agent 循环。

与此同时，系统还要修复消息一致性：

  • 已产生的工具请求需要对应“已中断”结果；
  • 半截流式内容要决定是否保留；
  • 不应在中断后意外启动下一轮模型请求；
  • 新用户输入可能要作为新的方向加入会话。

所以中断不是一个 UI 功能，而是一种跨模型、工具和状态机传播的协作式取消协议。

18. Agent 到底在什么时候停止​

最常见的正常终止条件是：模型产生了最终回答，并且没有再请求任何工具。

但外层系统还可能因为以下原因结束：

  • 用户中断；
  • 达到最大轮数；
  • 达到 token、费用或任务预算；
  • 上下文无法继续压缩；
  • 模型或网络错误无法恢复；
  • Hook 明确阻止；
  • 工具阶段无法继续；
  • 权限系统要求停止；
  • 无头环境无法解决必须人工确认的动作。

反过来，下面这些情况可能让模型“已经回答”后仍继续：

  • Stop Hook 发现结果不合格；
  • 客户端预算机制要求模型继续补全；
  • 输出达到上限但仍可恢复；
  • 外层工作流要求额外验证。

因此最终完成是宿主状态机的判断，而不是只读取模型的停止原因。

还要注意：程序层面的 completed 只说明循环正常收尾，不必然证明用户目标在现实世界中真的成功。真正的成功最好由测试、文件状态或外部系统结果来验证。

19. 会话恢复为什么不是“唤醒同一个模型”​

恢复会话时，系统做的是重建状态，而不是连接到上一次仍在运行的模型实例。

大致过程是：

读取持久化会话
  → 找到有效历史边界
  → 修复不完整工具调用
  → 清理空消息和不合法内容块
  → 恢复必要的会话元数据
  → 重新组装模型上下文
  → 发起新的模型请求

恢复后的模型之所以表现得像“接着之前工作”，是因为它重新看到了足够的历史和摘要。

这会带来三个限制：

  • 没有持久化的临时状态无法恢复；
  • 已经被压缩掉的细节只能依赖摘要；
  • 外部环境可能已经变化，历史中的假设不一定仍然成立。

因此可靠恢复不仅要重放聊天记录，还需要重新观察当前文件、Git 状态和外部服务。

20. 交互模式、无头模式和 SDK 的区别​

它们可以共享同一个 Agent 循环，但外围能力不同。

方面交互终端无头模式或 SDK
输入人在终端提交参数、stdin 或结构化消息
输出实时 UI文本、JSON 或事件流
权限询问可以弹确认框需要外部控制协议或 Hook
中断键盘操作信号或 API 控制消息
流式状态Spinner、逐字文本、工具 UI结构化事件
默认安全策略可以等待用户决定无法询问时通常拒绝

所以差异主要不在“模型更聪明”，而在宿主如何提供输入、显示输出和解决权限询问。

21. 一个完整例子：修复测试失败​

假设用户要求：

修复当前失败的单元测试，不要改变对外 API。

第一步：构造初始世界​

宿主程序把以下内容提供给模型：

  • 用户目标；
  • 项目说明；
  • 当前工作目录；
  • 可用工具；
  • 权限规则允许模型感知到的能力；
  • 可能存在的 Git 状态或 IDE 上下文。

模型此时仍然不知道哪个测试失败，因为测试还没有运行。

第二步：模型提出观察动作​

模型输出一个运行测试的工具请求。宿主程序解析命令，检查：

  • 命令结构是否安全；
  • 是否匹配 deny 或 ask 规则；
  • 是否应进入沙箱；
  • 是否需要用户确认。

通过后才真正运行测试。

第三步：环境反馈​

测试输出作为工具结果返回。模型下一轮看到堆栈和失败断言，但它并没有直接“看见终端”，只是看见宿主程序提供的结构化结果。

第四步：模型请求更多信息​

模型可能并发读取失败测试和实现文件。读取是只读且互不依赖时，可以并发执行。

如果文件过大，工具可能只返回一部分内容或把完整结果保存到临时位置，避免一次塞满上下文。

第五步：模型提出修改​

模型输出编辑请求。宿主程序检查真实路径、符号链接、敏感目录和编辑权限。通过后才写入文件。

编辑成功结果回到上下文。模型不能只凭“我刚才打算修改”来假设磁盘已经修改成功。

第六步：验证​

模型再次请求运行测试。测试可能：

  • 通过，于是模型总结结果；
  • 失败，于是失败成为新观察，循环继续；
  • 被拒绝，于是模型尝试更安全的验证方式；
  • 超时或中断，于是系统返回相应错误结果。

第七步：完成判断​

当模型不再请求工具并给出最终文本，外层还可以执行结束 Hook。若 Hook 要求检查 Git diff 或测试状态，Agent 仍可能继续。

这个例子中没有任何一步需要模型直接拥有文件系统。它只需要反复：

根据当前证据提出下一步

真正的环境操作全部由宿主控制。

22. 为什么这种架构会表现出“自主性”​

Claude Code 看起来能够自主完成任务，主要来自五种机制叠加：

22.1 目标保持​

用户目标和关键约束会持续存在于上下文或摘要中，使模型每轮都能围绕同一任务决策。

22.2 环境反馈​

模型每次行动后都会获得文件、命令、测试或网络结果，不必只凭最初信息猜测。

22.3 小步决策​

模型只需选择下一步，而不是一次生成完整且不可修改的计划。

22.4 错误可观察​

失败被转换成新证据，模型可以调整路径。

22.5 外层持续调度​

宿主程序自动重复请求模型，直到满足停止条件。

这种“自主性”更接近一个受控反馈系统，而不是一个独立意识：

自主表现
  = 目标 + 反馈 + 迭代 + 工具 + 状态管理

23. 这套机制的根本限制​

23.1 模型判断具有概率性​

同样的上下文可能产生不同的下一步。工具和权限可以约束动作，但不能保证模型总能选择最佳方案。

23.2 上下文是有限且有损的​

长任务中，早期细节可能被压缩。模型不是基于完整历史做决定，而是基于当前上下文投影。

23.3 工具结果不一定可信​

网页、MCP 服务、仓库文件甚至命令输出都可能包含误导或提示注入。它们应被视为外部数据，而不是自动升级为系统指令。

23.4 权限只能控制已建模的边界​

权限规则越理解工具参数和真实路径，保护越精细；对于任意 Shell、第三方工具或复杂远程副作用，静态判断不可能完美。

23.5 工具副作用未必可撤销​

读取失败可以重试，但发送请求、删除远程资源、发布版本等动作可能无法安全重放。宿主程序必须避免把模型/API retry 和工具 retry 混为一谈。

23.6 最终文本不等于真实成功​

模型说“已修复”只是一个语言输出。可靠性来自测试、类型检查、Git diff 和外部状态验证，而不是来自回答语气有多确定。

24. 用几个问题检验是否真正理解​

模型能直接运行命令吗？​

不能。模型只能生成命令工具请求，宿主程序授权并执行。

模型能看到完整仓库吗？​

不能。它只能看到被放进当前上下文的文件内容、搜索结果和环境信息。

为什么工具结果在下一轮很重要？​

因为模型 API 没有环境感知，必须通过结果获得行动后的新观察。

一次用户提问是不是只调用一次模型？​

通常不是。每次工具反馈、恢复或结束检查都可能触发新的模型请求。

Thinking 中写的动作会自动执行吗？​

不会。只有正式工具请求通过权限后才会产生副作用。

恢复会话是不是恢复同一个模型进程？​

不是。它是读取记录、修复状态、重新组装上下文，再调用模型。

权限允许是不是代表绝对安全？​

不是。权限、沙箱、工具实现和外部服务信任是不同层次。

MCP 工具和内置工具的 Agent 原理相同吗？​

基本相同，都是“描述能力、生成请求、宿主执行、返回结果”；MCP 额外引入远程服务信任边界。

Skill 是不是一种超级权限？​

不是。Skill 主要扩展模型的说明和流程，实际动作仍受工具权限控制。

Agent 为什么能连续做很多步？​

因为外层状态机不断把上一步结果加入下一次模型请求，而不是因为模型在后台一直思考。

25. 补充答疑：信息流、MCP 与工具选择​

这一节集中回答阅读本文时容易混淆的几个问题。它们实际上围绕三条边界：

Claude Code 与模型的边界
工具暴露与工具调用的边界
会话存储与模型上下文的边界

25.1 Prompt 到 Agent 再到模型，信息怎样流转​

首先需要修正“Prompt → Agent → 模型”这个说法。

Agent 不是夹在用户和模型之间的另一个智能实体。这里所说的 Agent，是由 Claude Code 宿主程序、Claude 模型、工具和反馈循环共同组成的系统。

更准确的关系是：

用户
  → Claude Code 接收和整理信息
  → Claude 模型作出决策
  → Claude Code 执行决策中的工具请求
  → 执行结果再次交给模型

完整时序如下：

一次模型 API 请求中通常包含：

系统行为说明
+ 项目专用指令
+ 当前用户 Prompt
+ 经过选择或压缩的历史消息
+ 工具调用和工具结果
+ IDE、文件变化等附加信息
+ 本轮工具的名称、描述和参数 Schema
+ 模型、Thinking 和输出配置

工具 Schema 通常位于 API 请求专门的工具字段中，而不是伪装成普通用户聊天消息，但它同样会消耗模型上下文。

某些本地命令和 Slash Command 可以由 Claude Code 直接处理，因此并非每次用户输入都会到达模型。

25.2 MCP 调用是否属于工具调用​

如果调用的是 MCP Server 提供的 Tool，那么它属于工具调用。

从模型角度看，内置工具和 MCP 工具遵循同一种协议：

内置工具
  模型生成 tool_use
  → Claude Code 在本地执行
  → 返回 tool_result

MCP 工具
  模型生成 tool_use
  → Claude Code 向 MCP Server 发送 tools/call
  → 返回 tool_result

主要区别是执行实现所在的位置：

类型工具实现在哪里
内置工具Claude Code 本地程序中
MCP 工具外部 MCP Server 中

无论实现在哪里，模型都不能直接执行它。模型只能生成结构化调用请求，Claude Code 仍然负责权限检查、调用和结果回灌。

25.3 MCP Resource 是什么​

MCP Resource 可以理解为 MCP Server 提供的“可读取资料”。它偏向数据，而 Tool 偏向动作。

一个 Resource 通常包含：

URI
+ 名称
+ 描述
+ MIME 类型
+ 可以读取的文本或二进制内容

例如：

docs://api/authentication
database://schema/users
logs://payment-service/latest
config://production/features

MCP Client 一般先列出资源，再根据 URI 读取：

resources/list
  → 查看 MCP Server 提供哪些资源

resources/read
  → 读取指定 URI 的内容

Resource、Tool、Prompt 和 Root 的区别如下：

MCP 概念主要含义示例
ResourceServer 提供的可读取数据文档、数据库结构、日志
ToolServer 提供的可执行动作查询订单、创建 Issue、发送消息
Prompt可复用的提示模板代码审查模板、故障分析模板
RootClient 告诉 Server 可以在哪些范围工作一个允许访问的项目目录

Resource 通常不会因为 MCP Server 已连接就自动把全部内容塞进模型上下文。更常见的过程是：

Claude Code 获得 Resource 列表
  → 用户或模型决定读取某个 Resource
  → Claude Code 请求 MCP Server
  → Resource 内容成为工具结果
  → 内容进入下一次模型请求

在 Claude Code 中，列出和读取 MCP Resource 本身可以被包装成内置工具，因此模型最终仍能通过工具协议访问 Resource。

25.4 谁从许多工具中选出特定工具​

“Agent 选择工具”实际上包含两次性质完全不同的选择。

第一次：Claude Code 做资格筛选​

Claude Code 判断哪些工具有资格成为候选工具，例如：

MCP Server 是否已经连接
工具功能是否启用
当前平台和模型是否支持
当前运行模式是否允许
当前 Agent 或子 Agent 是否有权使用
工具是否被明确的 deny 规则整体禁止
MCP Server 是否已经获得配置和连接许可

这一步回答的是：

哪些工具可以进入本轮候选集合？

它通常不回答：

当前用户的问题最适合哪一个工具？

例如一百个已安装工具，经过连接状态、运行模式和策略筛选后，可能剩下五十个候选工具。

第二次：模型做语义选择​

模型根据以下信息决定当前是否需要某个工具：

用户目标
+ 当前会话上下文
+ 工具名称
+ 工具描述
+ 工具参数 Schema

模型负责生成：

工具名称
+ 工具调用 ID
+ 具体参数

Claude Code 随后再次进行权限检查，因此“模型选择了工具”不等于“工具一定会执行”。

可以把职责概括为：

Claude Code 决定哪些工具有资格被考虑
模型决定当前任务想使用哪个工具
Claude Code 决定这次具体调用能否执行
工具实现或 MCP Server 负责真正执行

25.5 候选工具会不会被一股脑提供给模型​

需要区分标准加载和延迟加载两种模式。

标准加载​

当候选工具不多、当前模型或 API Provider 不支持延迟工具协议，或者 Tool Search 没有启用时，Claude Code 可以把筛选后工具的完整 Schema 一起提供给模型。

Read 完整 Schema
Edit 完整 Schema
Bash 完整 Schema
GitHub 查询工具完整 Schema
Slack 发送工具完整 Schema

所以准确地说：

在标准加载模式下，经过资格筛选的工具确实可能被一次性全部发送给模型。

这不等于模型会调用全部工具。模型仍会根据任务选择零个、一个或多个工具。

Tool Search 延迟加载​

当 MCP 工具很多时，发送全部完整 Schema 会占用大量 token，也会增加模型选错工具的概率。

这里必须先明确 Tool Search 的归属：

ToolSearch 是 Claude Code 实现并注册的内置工具，不是 Claude 模型内部自带的搜索功能，也不是 MCP Server 提供的工具。

模型会收到 ToolSearch 的工具 Schema，因此能够像调用 Read 一样输出对它的 tool_use。真正维护候选工具池、执行关键词匹配并返回工具引用的是 Claude Code。

延迟加载还要求当前模型和 API Provider 支持 defer_loading、tool_reference 等协议能力。协议支持使模型能够使用搜索结果，但不代表搜索算法运行在模型内部。

部分负责者
ToolSearch 的实现Claude Code
候选工具池和搜索索引Claude Code
决定何时搜索并生成搜索词Claude 模型
延迟工具和工具引用协议模型 API 与 Provider 必须支持
MCP 工具的原始定义MCP Server

此时 Claude Code 可以只提供：

核心工具的完整 Schema
+ ToolSearch 的完整 Schema
+ 延迟工具的名称列表

延迟工具在完整 Schema 被加载前不能正式调用。

假设用户说：

把测试结果发送到 Slack。

过程可能是：

1. 模型看到用户目标和延迟工具名称

2. 模型判断需要 Slack 发送能力

3. 模型输出对 Claude Code 内置 ToolSearch 的调用
   query = "slack send message"

4. Claude Code 执行 ToolSearch，在候选工具池中搜索

5. Claude Code 返回 mcp__slack__send_message 的工具引用

6. 下一次模型请求加入该工具的完整 Schema

7. 模型生成正式的 mcp__slack__send_message 调用

8. Claude Code 检查权限并请求 MCP Server 执行

流程可以概括为：

因此，Tool Search 搜索的是 Claude Code 已经掌握的候选工具池，不是互联网。模型负责请求搜索，Claude Code 负责真正搜索。

Tool Search 中的职责仍然是分开的：

模型根据任务生成搜索词
Claude Code 根据名称、描述和搜索提示匹配工具
模型看到完整 Schema 后决定是否正式调用

当前实现的搜索主要是工具名称、描述和提示词匹配，不是另一个隐藏模型先完整理解用户任务再替主模型选择工具。

25.6 MCP 工具 Schema 在整个过程中做什么​

一个 MCP 工具定义通常类似：

{
  "name": "get_order",
  "description": "根据订单编号查询订单",
  "inputSchema": {
    "type": "object",
    "properties": {
      "order_id": {
        "type": "string"
      }
    },
    "required": ["order_id"]
  }
}

三个部分分别回答：

name
  → 调用哪个工具

description
  → 这个工具适合解决什么问题

inputSchema
  → 调用这个工具需要哪些参数

模型看到这个定义后，可能生成：

{
  "type": "tool_use",
  "name": "mcp__orders__get_order",
  "input": {
    "order_id": "A100"
  }
}

Schema 是模型与工具之间的调用契约，不是工具实现本身。

“Schema 不符合”可能表示三种不同情况。

Schema 不符合 MCP 协议格式​

MCP 要求工具输入 Schema 的根类型是对象。如果 MCP Server 返回的工具列表不能通过 MCP 协议校验，Claude Code 就无法正常加载这批工具。

在当前源码快照中，工具列表作为一个整体接受协议校验。校验失败后，这次获取会被视为失败并返回空工具列表。因此结果未必是只忽略一个错误工具，也可能是该 MCP Server 的整批工具都没有进入候选工具池。

Schema 合法，但与当前任务无关​

这不是 Schema 错误。

例如用户要求修改 CSS，而候选工具中存在订单查询工具。在标准加载模式中，它仍可能被提供给模型，只是模型通常不会调用它。在延迟加载模式中，模型通常不会搜索或加载它的完整 Schema。

模型生成的参数不符合 Schema​

Schema 会指导模型生成参数，但不能假设模型永远不会出错。

对于 MCP 工具，MCP Server 仍然应该校验实际收到的参数。如果参数不合法，Server 应返回错误：

模型生成错误参数
  → MCP Server 拒绝调用
  → 错误作为 tool_result 返回
  → 模型在下一轮修正参数

不能因为前面已经存在模型和 Claude Code，就省略 MCP Server 自己的输入校验。

25.7 上下文窗口限制的是 API 还是模型​

这两个说法是同一限制的两个角度：

模型能力角度
  → 模型一次只能处理有限数量的 token

API 接口角度
  → API 对单次请求实施这个模型限制

上下文窗口可能包含：

系统指令
+ 项目说明
+ 对话历史
+ 工具 Schema
+ 工具调用和工具结果
+ 文件内容
+ 图片等附件
+ 为模型输出预留的空间

因此，限制的不是用户 Prompt 一个字段，而是模型这一次推理需要处理的整体信息。

还要区分：

Claude Code 可以在磁盘上保存很多会话记录
  ≠ 模型一次可以看到全部记录

会话过长时，Claude Code 必须选择、删除、缩减或压缩历史，再构造下一次 API 请求。

25.8 为什么把重要约束写进项目说明、测试或代码​

主要目的不只是方便人查看，而是把容易从对话中丢失的约束，变成持久且可以重新发现或自动验证的项目事实。

不同载体的作用不同：

载体主要作用
专用项目指令在之后的任务中重新告诉模型规则
普通文档帮助人和 Agent 理解背景，但不一定自动加载
测试自动证明实现是否违反约束
类型、Schema 和代码检查从实现层面限制非法状态

例如：

约束只在早期聊天中出现
  → 可能在上下文压缩时丢失

约束写进项目指令
  → 后续会话可以重新加载

约束写成测试
  → 即使模型忘记，测试失败也会重新暴露问题

约束写进类型或 Schema
  → 某些错误实现直接无法通过检查

因此大致可以理解为：

聊天中的约束是临时工作记忆
项目说明是持久提醒
测试和代码约束是可执行规则

25.9 Thinking 内容块的作用​

Thinking 的首要作用不是在界面上制造参与感，而是让支持扩展思考的模型在生成最终回答或工具调用之前，使用额外推理预算处理复杂问题。

它可以帮助模型：

分析复杂代码关系
比较多个解决方案
规划工具使用顺序
根据工具错误重新判断
在输出前检查一致性

从 API 协议角度，不同内容块的责任是：

thinking
  → 模型推理过程中的内容

text
  → 面向用户的回答

tool_use
  → 可以被宿主程序解析和审查的动作提案

界面可以显示、折叠、概括或隐藏 Thinking，但这只是展示层功能。用户看到的内容也未必是完整原始推理，可能是摘要、过滤内容或 redacted thinking。

Thinking 本身不能触发真实操作。即使 Thinking 中出现“读取文件”或“删除文件”，只有正式的 tool_use 通过权限检查后才会执行。

25.10 流式响应中何时开始执行工具​

在流式工具执行开启时，Claude Code 不必等待整条模型回复结束，但也不能刚看到工具名称就执行。

工具参数可能分成多个片段到达：

tool_use 内容块开始
  → 工具名：Read
  → 参数片段：{"pa
  → 参数片段：th":"src/
  → 参数片段：app.ts"}
  → tool_use 内容块结束

前面的半截 JSON 不能解析，也不能安全执行。

只有工具调用块完整后，Claude Code 才能确定：

工具名称
工具调用 ID
完整参数 JSON
内容块已经结束

之后才进入：

参数解析
  → Hook
  → 权限检查
  → 并发安全调度
  → 真正执行工具

此时模型可能仍在生成后面的内容：

模型继续流式输出
          与
已完成的工具调用块开始执行
          同时发生

因此最准确的表述是：

当流式工具执行开启，并且某个 tool_use 内容块已经完整接收后，Claude Code 可以在整条模型响应结束前启动该工具，但仍然必须先通过参数、Hook、权限和调度检查。

如果工具参数仍不完整、需要等待用户授权、工具之间不能安全并发，或者流式工具执行没有开启，就不会立即执行。

25.11 这一组问题的统一结论​

可以用下面这张职责表结束这组问题：

问题主要负责者
保存完整候选工具池Claude Code
连接和获取 MCP 工具Claude Code 与 MCP Server
判断工具是否有资格成为候选Claude Code 的配置、模式和策略系统
判断任务语义上可能需要什么工具Claude 模型
搜索延迟工具模型生成查询，Claude Code 执行 Tool Search
定义工具需要什么参数工具 Schema
生成本次工具参数Claude 模型
判断具体调用是否允许Claude Code 权限系统
验证 MCP 参数和执行逻辑MCP Server
把执行结果交回模型Claude Code
决定继续调用工具还是最终回答Claude 模型与外层 Agent 状态机

最简化的总流程是：

Claude Code 先筛选候选资格
  → 模型根据任务选择能力
  → 必要时使用 Tool Search 加载完整 Schema
  → 模型提出正式工具调用
  → Claude Code 校验和授权
  → 本地工具或 MCP Server 执行
  → Claude Code 把结果放回下一轮上下文

26. 最终心智模型​

理解 Claude Code 时，可以始终把它拆成下面六个问题：

1. 模型这次实际看到了什么？
2. 模型提出了什么结构化动作？
3. 谁校验并授权了这个动作？
4. 动作在哪个环境中真正执行？
5. 执行结果怎样进入下一轮上下文？
6. 外层状态机为什么选择继续或停止？

只要这六个问题能够回答，大部分看似复杂的行为都能解释清楚。

Claude Code 的本质不是“给语言模型加一个终端”，而是建立一套完整的控制系统：

模型负责提出可能的下一步
上下文系统负责提供有限的当前世界
工具协议负责表达可执行动作
权限系统负责划定信任边界
执行器负责改变真实环境
反馈循环负责让模型根据结果继续修正
持久化和恢复负责跨时间维持任务连续性

真正让它成为 Agent 的，不是其中任何一个部件，而是这些部件形成了一个受控、可观察、可中断、可恢复的闭环。
