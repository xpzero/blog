从零手写 Agent（七）：让多个话题互不干扰

现在这个 Agent 一个进程只有一段对话，退出就没了。想同时开几条不同话题的线、各自记着自己的上下文——该怎么做？

这一篇做多会话，顺便把持久化一起做掉。会用到的东西前面都出现过，不需要新的 API 知识，难点全在状态怎么组织。

先看清问题：上下文是共享状态​

第三篇为了让模型有记忆，把 messages 从「每次新建」改成「整个会话复用同一份」。这带来了记忆，同时也带来了副作用。

messages 是共享状态，所有话题都往同一个列表里堆：

def chat(stream: bool = False) -> None:
    messages = [{"role": "system", "content": SYSTEM_PROMPT}]   # 只有一份
    while True:
        ...

后果有三个：

串味。 你先讨论「重构 tools 目录」，再问「帮我写个匹配邮箱的正则」，模型会把前面的项目背景带进后面的回答。更麻烦的是它可能把之前的工具调用结果当成当前任务的依据。

越聊越贵。 每次请求都要重发整个 messages。一条杂糅了五个话题、聊了 50 轮的对话，每次请求都在为无关历史付 token。

迟早超限。 单条线单向增长，最终撞上上下文长度上限。

原理：一份变多份，加一个指针​

多会话听起来像个功能，实现上就是一次数据结构的替换：

改造前                          改造后
                                sessions = {
messages = [...]                  1: [system, user, assistant, ...],
                                  2: [system, user, ...],
                                  3: [system],
                                }
                                current_id = 2      ← 指针

当前会话 = sessions[current_id]。 就这么简单。三个关键推论：

① 切换只是改一个整数。 /switch 1 不读磁盘、不调模型、不做任何 IO，只把 current_id 从 2 改成 1。所以切换的代价接近零，历史内容一直在内存里，从来没被"卸载"过。

② 每次请求只发当前会话的 messages。 隔离就是这么实现的——模型压根看不到其他会话的内容，因为我们没发给它。

③ 「会话」是 Chat Completions 下的纯客户端概念。

这一点最值得说清。Chat Completions 的请求体里能放的字段是这些：

model、messages、tools、tool_choice、stream、temperature、max_tokens …

没有任何一个字段能表达「这是第 3 号会话的第 5 轮」。 因为这个接口是无状态的（第一篇就讲过），它每次收到的就是一个孤立的 messages 数组，无从知道这数组是你从哪条线上取出来的。

所以「会话」完全是我们自己造出来的抽象：把消息按话题分组、维护一个当前指针、请求时只发其中一组。模型服务端对此毫无感知。

不过这不是 LLM 的固有属性，而是接口选择的结果。换成 OpenAI 的 Responses API 就不一样了——它支持 store: true 把对话存在服务端，下次用 previous_response_id 接续，current_id 这套东西可以交给服务端维护，这一篇的大半工作会变成调用参数。选 Chat Completions 就得自己管，好处是所有状态都在你手上，看得见也改得动。

数据结构与命令​

会话对象只需要两个字段：

@dataclass
class Session:
    id: int
    messages: list

    @property
    def summary(self) -> str:
        """取首句用户输入作为摘要，/list 时用来辨认是哪条线"""
        for message in self.messages:
            if _field(message, "role") == "user":
                return _clip(_field(message, "content") or "", SUMMARY_MAX_CHARS)
        return "(空会话)"

摘要不存，每次从 messages 现算——这是「能计算的不要存储」。

为什么不存下来（点开看推理）

摘要属于派生数据，就是首句 user 消息的前若干字。一旦把它作为字段存下来，就有了「两份真相」：messages 变了，summary 不会自动跟着变，于是每个修改 messages 的地方都得记着同步它。

现在这样的地方就有三处：追加 user 消息、工具循环里追加 assistant 与 tool 消息、从文件加载时构造会话。而且随着功能增加只会更多。

漏掉任何一处，/list 就显示过时的摘要。而这种 bug 特别阴：列表看起来完全正常，只是内容和实际对不上，不专门核对根本发现不了。

而现算的成本几乎为零，一个循环找第一条 user 消息而已。

不过这条有边界：如果会话攒到上千条，/list 为了算摘要得把每个文件的全部 messages 都读进来，那时候存摘要就划算了——用一点同步负担换列表的响应速度。规则是「规模小的时候现算」。

命令是一个前置拦截：以 / 开头的输入不进上下文，交给会话管理消费。

while True:
    user_input = input(f"[{manager.current.id}] 你: ").strip()
    if user_input.lower() in ("quit", "exit", "q"):
        break

    # 斜杠命令由 sessions 包消费，不发给模型
    if handle_command(user_input, manager):
        continue

    messages = manager.current.messages
    messages.append({"role": "user", "content": user_input})
    loop(messages)
    manager.save_current()

提示符里带上会话号（[2] 你:），这样任何时候看一眼就知道自己在哪条线上——不加这个，切换提示滚上去之后就只能靠记忆。

几条边界规则，都是不定清楚就会卡住或崩掉的地方：

情况行为
/new新建并立即切换过去
新会话 id已有最大 id + 1，不复用
/del 当前会话拒绝，提示先切换
/switch 到不存在的号提示无效，留在原会话
「不许删当前会话」这条限制为什么划算

它顺带保证了「至少有一条会话存在」——唯一的那条必然就是当前会话，自然删不掉。

于是删除逻辑里既不需要「删完自动切换到剩下的最后一条」的分支，也不需要单独判断「只剩一条时拒绝」。一条限制换掉两个分支。

持久化：不落盘的多会话价值有限​

多会话和持久化是两件独立的事——多会话可以纯内存（只在本次运行内切换），持久化也不需要多会话（单条对话同样能存盘）。但只做前者，重启全丢，开了几条线的意义就没了。所以它们常被当成一件事做。

什么时候写​

每轮对话结束后写当前会话。 「一轮结束」指内层工具循环跑完、模型给出文本回复之后。

为什么偏偏是这个时机

因为此刻 messages 里的 tool_calls 与 role="tool" 结果一定是配对完整的，落盘的文件因此永远合法。

如果改成「每追加一条消息就写」，就会把「模型已声明工具调用、工具还没执行完」的残缺状态存下来。下次加载后第一次请求直接 400——就是第二篇那个 No tool output found for function call。

与其事后修补残缺文件，不如只在状态一定完整的时刻写。

不要在退出时写

程序崩了、Ctrl-C、直接关终端，这三种情况都不会走到退出逻辑。每轮写一次的代价是几十 KB 的 IO，换来的是任何时候挂掉最多丢最后一轮。

写什么​

这里有个必踩的坑。messages 里混着两种类型：

messages 里的类型: ['dict', 'ChatCompletionMessage']
直接 json.dumps 失败: Object of type ChatCompletionMessage is not JSON serializable

因为非流式路径是 messages.append(message)——直接把 SDK 返回的 pydantic 对象塞进了列表。发请求时 SDK 认得它，存盘就不行了。所以要统一转换：

def _to_plain(message) -> dict:
    if isinstance(message, dict):
        return message
    return message.model_dump(exclude_none=True)

exclude_none=True 会去掉一堆值为 None 的字段（refusal、audio、annotations），文件干净很多。

数据放在 .sessions/<id>.json，一个会话一个文件：只写改动的那条、文件小、手工能看能删、/del 就是删文件。

.sessions/ 务必加进 .gitignore

里面是你和模型的全部对话内容，和 .env 一样属于不该进仓库的东西。

空会话不写盘，所以启动时新建的那条、或者 /new 出来还没聊的那条，都不会产生垃圾文件。

磁盘只在启动时读一次​

def __init__(self, system_prompt: str):
    self._load_all()            # 一次性读入 .sessions/ 下全部会话
    self._next_id = max(self._sessions, default=0) + 1
    self.new()                  # 启动时总是新建一条并进入

之后 /switch 都是纯内存操作。单个文件读坏了就跳过并打印一行提示，不该因为一条会话损坏而起不来。

插曲：新功能暴露了一个旧 bug​

实现完之后我跑了一轮验证，/list 显示：

  1  算一下 1+1  (2 条消息)

不对。聊完一轮应该是 3 条（system + user + assistant），怎么只有 2 条？落盘文件确认了——assistant 那条根本没存进去。

顺着查下去，问题在流式路径：

# 没有工具调用 → 任务完成
if not calls:
    return          # ← 直接返回，没把模型的文本回复写进 messages

流式循环里，只有带工具调用的那种情况才会拼一条 assistant 消息追加进去；模型给出纯文本回复时，直接就 return 了。

也就是说：流式模式下的多轮对话，一直在丢失模型自己的回复。 模型看不到自己上一轮说过什么。非流式路径没这问题（messages.append(message) 是无条件执行的）。

修复只有两行：

# 没有工具调用 → 模型给出了最终回复，与非流式一样要写回上下文
if not calls:
    messages.append({"role": "assistant", "content": content})
    return

修完再问它「我刚问你什么了？」，回答变成「你刚才问我'算一下 2+3'」——上下文里终于有它自己的话了。

这个 bug 存在了整整一篇文章的时间，之前没暴露，是因为既没有持久化、也没有人数过消息条数。像持久化、日志、计数这类把内部状态外显出来的功能，往往会顺带抓出隐藏很久的问题。这也是"可观测性"值得早做的理由之一。

效果​

从图里能看到几件事：

  • 提示符前面的 [3] / [1] / [2] 随切换变化，随时知道自己在哪条线
  • /switch 不带参数会提示用法，而不是报错
  • 切换后会回显该会话的上一轮问答，接得上此前的对话
  • 3 号是本次启动新建的空会话，显示「还没聊过」

隔离是否真的生效，可以这样验：在 2 号会话让它「记住一个词：西瓜」，切回 1 号问「我刚让你记的词是什么」——它会回答「你没有让我记过任何词」，同时又能准确说出 1 号里问过的第一个问题。

已知边界​

  • 假设只有一个进程。同时开两个终端各跑一份，两边都在启动时读了同一份快照，之后各写各的，后写的覆盖先写的
  • 空会话会留在 /list 里。它们不落盘，重启就消失，属于可以接受的噪音
  • id 跨重启可能复用。未落盘的空会话号会被下次启动重新用掉
  • 没有上下文裁剪。单条线聊得足够久，照样会超限——多会话只是让你更容易「换条线」，不是解决方案
