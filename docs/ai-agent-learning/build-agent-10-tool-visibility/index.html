从零手写 Agent（十）：工具明明执行了，为什么页面上看不见？

前面把 Agent 接上网页时，我留下了一个很明显的缺口：后端已经把工具调用过程变成 SSE 事件，前端也收到了它们，但页面真正显示出来的仍然只有消息气泡和最终文本。

前面迁移到 Responses API 后，这个缺口没有消失。比如向页面发送：

北京今天天气怎么样？再算一下 (38-12)*3。

Agent 可以调用天气和计算工具，再给出最终回答。但如果页面只显示：

北京今天晴，最高气温38℃。

(38-12)*3 的计算结果是 78。

我看不到它调用了什么工具，也不知道每个工具拿到了什么参数、返回了什么结果。

这次不增加新工具，也不修改 Agent 如何决定调用工具，只解决一个问题：把已经到达浏览器的工具执行过程显示出来。

工具事件在哪一层消失了​

先检查浏览器收到的 SSE，可以看到工具名称、参数和结果都已经到达。继续检查 adapter，也能找到对应的 tool-call part。问题出在最后一步：Assistant 消息没有给工具 part 配置可见组件，数据已经进入前端状态，却没有对应的界面。

这篇的重点是补上页面渲染，事件协议不是主线。完整的数据流和代码位置收在下面的折叠内容中。

工具调用怎样从模型请求变成页面上的执行状态？

这条链路涉及五个位置：

代码位置职责
server/agent/loop.py 的 stream_events()读取 Responses API 输出、执行本地工具并产生项目事件
server/api.py 的 chat()把项目事件序列化成 SSE
web/src/adapter.ts 的 chatAdapter.run()把 SSE 事件整理成前端消息 part
web/src/App.tsx 的 AssistantMessage对连续工具 part 分组和计数
web/src/ToolCallPart.tsx选择工具名称、状态、参数和结果的渲染组件

tool_call 是项目事件，不是 Responses API 原始名称​

模型通过 Responses API 返回的是 function_call。Agent loop 读取它、执行本地 Python 工具，再把结果作为 function_call_output 交回模型。

与此同时，Agent loop 还会产生 tool_call 和 tool_result。这是 demo-agent 自己定义的项目事件，用来把同一次执行过程交给 CLI、HTTP 和网页，不是 OpenAI 的原始事件名称。

这层项目事件协议把“发生了什么”和“怎么展示”分开。同一个 tool_call，CLI 可以打印成一行文字，网页则可以显示成带状态的折叠项。前端也不需要直接理解 Responses API 的完整 Item 结构。

后端按执行顺序发送两类事件​

模型请求调用天气工具时，浏览器先收到：

{
  "type": "tool_call",
  "id": "call_123",
  "name": "get_weather",
  "args": {
    "city": "北京"
  }
}

工具执行结束后，再收到：

{
  "type": "tool_result",
  "id": "call_123",
  "content": "北京今天晴，最高气温38℃"
}

FastAPI 不改变这些字段，只负责转成 data: <json>\n\n 格式的 SSE 帧。

adapter 把两个事件整理成同一个 part​

收到 tool_call 时，adapter 先创建一个还没有结果的 tool-call part：

parts.push({
  type: "tool-call",
  toolCallId: event.id,
  toolName: event.name,
  args: event.args,
  argsText: JSON.stringify(event.args, null, 2),
});

页面此时已经知道工具名称和参数，但 result 还不存在，因此显示为执行中。

收到 tool_result 后，adapter 根据相同的 id 找回原来的 part：

const index = parts.findIndex(
  part =>
    part.type === "tool-call" &&
    part.toolCallId === event.id,
);
const toolPart = parts[index];

if (toolPart?.type === "tool-call") {
  parts[index] = {
    ...toolPart,
    result: event.content,
  };
}

同一个 part 因此经历了下面的变化：

只有 toolName、args，没有 result
                ↓
页面显示“执行中”
                ↓
写入 tool_result.content
                ↓
页面显示“已完成”，并能展开结果

这里的 argsText 不是后端额外返回的字段，而是前端把 args 格式化成字符串，方便通用组件直接展示。

数量和详情分别从哪里来​

前端不会分析最终回答，也不会从文字中猜测工具数量。App.tsx 把连续的 tool-call parts 归入同一个组，part.indices.length 就是页面显示的工具调用数量。

页面内容数据来源
“2 个工具调用”前端统计分组内的 tool-call parts
工具名称tool_call.name
调用参数tool_call.args
执行结果tool_result.content
执行中或已完成assistant-ui 根据 part 是否已有结果及消息状态计算
图标、折叠和动画前端 ToolFallback、ToolGroup 组件

原来只接了 Runtime，没有接现成页面组件​

项目已经安装了 @assistant-ui/react，也在使用 useLocalRuntime、ThreadPrimitive 和 MessagePrimitive。我原本以为工具展示需要全部自己写，继续查看 assistant-ui 的文档和源码后才发现，它还有一层可安装的 Elements：

@assistant-ui/react
    Runtime、消息状态和无样式 Primitives

assistant-ui Elements
    Thread、ToolFallback、ToolGroup 等带样式的 React 源码组件

官网示例里的完整聊天页面不是 @assistant-ui/react 自动生成的，其中使用的 Elements 组件源码会安装进项目：

src/components/assistant-ui/elements/
├── tool-fallback.aui.tsx
└── tool-group.aui.tsx

安装后源码属于当前项目，可以翻译文案、调整样式，也可以只使用其中两个组件。

给 Vite 项目补上 Elements 的样式基础​

当前前端只有普通 CSS，而官方 Elements 使用 Tailwind CSS、shadcn/ui 和 Lucide 图标。先给 Vite 增加 Tailwind 插件和 @ 路径别名：

vite.config.ts
import react from "@vitejs/plugin-react";
import tailwindcss from "@tailwindcss/vite";
import { fileURLToPath } from "node:url";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [react(), tailwindcss()],
  resolve: {
    alias: {
      "@": fileURLToPath(new URL("./src", import.meta.url)),
    },
  },
});

tsconfig.app.json 使用相同映射：

{
  "compilerOptions": {
    "paths": {
      "@/*": ["./src/*"]
    }
  }
}

然后初始化 shadcn，并从 assistant-ui registry 安装两个组件：

pnpm add -D tailwindcss @tailwindcss/vite
pnpm dlx shadcn@latest init -t vite -b radix -p nova -y
pnpm dlx shadcn@latest add \
  https://r.assistant-ui.com/tool-fallback.json \
  https://r.assistant-ui.com/tool-group.json \
  -y

registry 同时加入这两个组件需要的 Collapsible、Lucide 图标和动画样式。初始化器还会把 shadcn CLI 包和 @import "shadcn/tailwind.css" 写入项目；当前页面不依赖那份通用样式，所以我删除这条 import，并运行 pnpm remove shadcn，只保留已经生成到 src/ 的组件源码。这里也没有安装 @assistant-ui/ai-sdk，因为数据仍然来自项目自己的 adapter。

用 ToolFallback 展示单次调用​

ToolFallback 是没有专属 UI 时的通用工具渲染器。它已经处理了几件容易写得不一致的细节：

  • 执行中、完成、中断和等待操作使用同一套 SVG 图标；
  • 图标、文字和折叠箭头具有固定尺寸与对齐方式；
  • 参数、结果和错误可以展开查看；
  • 有计时数据时显示工具耗时；
  • 后续加入人工审批时可以显示操作按钮。

项目保留一层很薄的 ToolCallPart，只组合官方导出的部件，并把固定文案改成中文：

export function ToolCallPart(props: ToolCallMessagePartProps) {
  const {
    toolName,
    argsText,
    result,
    status,
  } = props;

  return (
    <ToolFallbackRoot>
      <ToolFallbackTrigger
        toolName={toolName}
        status={status}
      />
      <ToolFallbackContent>
        <ToolFallbackError status={status} />
        <ToolFallbackArgs argsText={argsText} />
        <ToolFallbackResult result={result} />
      </ToolFallbackContent>
    </ToolFallbackRoot>
  );
}

实际组件还保留了 requires-action 和取消状态的分支，为后续工具审批留下接口；当前文章暂时不会触发它们。

工具状态不再由页面根据文字猜测。assistant-ui Runtime 会根据工具 part 和 Assistant 消息的运行状态，向渲染组件提供 status：

工具尚无 result，消息仍在生成 → running
工具已经有 result             → complete
请求被取消或消息失败           → incomplete
运行时要求用户操作             → requires-action

当前项目还不能可靠显示“本地工具执行失败”。execute_tool() 会把异常转换成普通文本结果，项目事件里没有独立的失败标记，因此前端只能确认结果已经返回，不能仅根据一段文字把它标成失败。这个边界没有因为换用现成组件而消失。

用 ToolGroup 收起连续调用​

只渲染单个工具还不够。一次任务可能连续调用多个工具，如果每个调用都占据一张大卡片，聊天内容很快会被执行细节淹没。

assistant-ui 提供了 MessagePrimitive.GroupedParts。这里把相邻的 tool-call part 归为 group-tool，再交给官方 ToolGroup：

<MessagePrimitive.GroupedParts
  groupBy={groupPartByType({
    "tool-call": ["group-tool"],
  })}
>
  {({ part, children }) => {
    switch (part.type) {
      case "group-tool":
        return (
          <ToolGroupRoot
            variant="ghost"
            defaultOpen={part.status.type === "running"}
          >
            <ToolGroupTrigger
              count={part.indices.length}
              active={part.status.type === "running"}
            />
            <ToolGroupContent>
              {children}
            </ToolGroupContent>
          </ToolGroupRoot>
        );

      case "tool-call":
        return part.toolUI ?? <ToolCallPart {...part} />;

      case "text":
        return <TextPart {...part} />;

      default:
        return null;
    }
  }}
</MessagePrimitive.GroupedParts>

执行中默认展开，可以立即看到哪个工具已经返回、哪个仍在运行；加载已有的完成消息时默认收起，只留下一行“2 个工具调用”。用户需要时再逐层展开参数和结果。

variant="ghost" 也去掉了多余的外框。Assistant 最终文本与工具组处于同一内容区域，不再出现气泡里再套多张厚重卡片的效果。

这次改动没有碰后端​

这一篇的功能代码仍然都在前端。后端已经提供了展示所需的名称、参数、调用标识和结果，缺少的是把现有消息 part 渲染出来。

前端验证执行了：

cd web
pnpm lint
pnpm build

lint、TypeScript 检查和 Vite 生产构建均通过。

引入 Elements 也不是零成本：项目增加了 Tailwind、Radix、Lucide、相关动画依赖和 shadcn 生成的组件源码。换来的不是新的 Agent 能力，而是一套经过组合的工具状态、折叠交互和可访问性基础。对于只需要一个静态聊天框的页面，这组依赖未必值得；这个项目后面还要继续做工具审批，因此选择复用它。

仍然存在的边界​

工具过程出现以后，页面不再只是一个最终答案窗口，但它距离完整的 Agent 运行界面还有几步：

  • 工具异常没有结构化失败状态；
  • 后端事件还没有记录每一步耗时；
  • 页面刷新后不能恢复正在执行的任务；
  • 用户只能看，不能取消或重试具体工具；
  • 高风险工具仍然会直接执行；
  • 通用组件会把完整参数和结果放进页面，没有脱敏与长度限制。

最后一点意味着 write_file 的待写内容、read_file 的文件内容或很长的联网结果都可能进入 DOM。视觉上的折叠不等于数据没有传到浏览器，也不等于解决了大结果的性能问题。后续需要按工具决定展示字段、截断策略和敏感信息处理方式。

高风险工具的问题更直接：现在用户可以看见 write_file 写了什么，但等卡片出现时，工具可能已经执行完了。看得见不等于管得住。

下一篇继续处理这个问题：让高风险工具在执行前暂停，等待用户批准或拒绝。
