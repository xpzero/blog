从零手写 Agent（八）：把它接上网页

命令行里的 Agent 已经能用了，但它只属于一个终端窗口。想要 ChatGPT 那样的网页界面——消息气泡、逐字上屏、会话列表——该怎么把现有的代码接上去？

这一篇做最基础的前后端联通：后端把 agent loop 包成 HTTP 服务，前端用现成的组件库渲染对话。做完会发现，真正的工作量不在「加接口」，而在一次思路上的改造：让 loop 不再直接打印，而是产出事件。

仓库先分成两半​

前后端是两个技术栈（uv 管 Python、pnpm 管前端），先把目录分开：

demo-agent/
├── server/    # 后端：agent/ sessions/ tools/ + CLI 入口（原有代码整体平移）
└── web/       # 前端：Vite + React + assistant-ui

两边依赖各自独立管理，互不感知。

平移有个附带效果：文件工具的根目录（第五篇那个 ROOT）随着 tools/ 的位置自动收缩到了 server/ 内——Agent 读写不到前端代码和仓库根。边界宁小勿大，真需要时改一行就扩。

核心改造：print 变事件​

现有的 run_tool_loop_stream 是为终端写的，所有输出都靠 print。HTTP 服务没有终端，这条路走不通。

问题的本质是：loop 把「发生了什么」和「怎么展示」焊死在一起了。拆开——loop 只负责产出结构化事件，怎么呈现由消费方决定：

def stream_events(messages: list, max_turns: int = 10) -> Iterator[dict]:
    """agent loop 的核心：不做任何打印，把过程产出为事件"""
    ...
    yield {"type": "text_delta", "text": delta.content}
    ...
    yield {"type": "tool_call", "id": ..., "name": ..., "args": ...}
    yield {"type": "tool_result", "id": ..., "content": result}
    ...
    yield {"type": "done", "content": content}

五种事件：text_delta（文本增量）、tool_call（模型发起调用）、tool_result（执行结果）、done（最终回复）、max_turns（触发上限）。

原来的 CLI 函数变成了事件流的一个消费者，行为一字不差：

def run_tool_loop_stream(messages: list, max_turns: int = 10) -> None:
    """CLI 消费事件流：文本逐字打印，工具调用与结果按行展示"""
    for event in stream_events(messages, max_turns):
        if event["type"] == "text_delta":
            print(event["text"], end="", flush=True)
        elif event["type"] == "tool_call":
            print(f"  [工具调用] {event['name']}({event['args']})")
        ...

这个模式值得记住：同一个循环，两种消费方式。CLI 打印它，HTTP 把它序列化成 SSE。以后加第三种消费者（比如日志、评测）也不用再动 loop。

后端：三个接口就够​

FastAPI 一共三个端点：

GET  /api/sessions           会话列表（复用 SessionManager）
POST /api/sessions           新建会话
POST /api/sessions/{id}/chat 发消息，返回 SSE 事件流

SSE 端点就是把事件逐条写成 data: {json} 的格式：

@app.post("/api/sessions/{session_id}/chat")
def chat(session_id: int, body: ChatRequest):
    if not manager.switch(session_id):
        raise HTTPException(status_code=404, detail=f"没有 {session_id} 号会话")

    messages = manager.current.messages
    messages.append({"role": "user", "content": body.message})

    def sse():
        for event in stream_events(messages):
            yield f"data: {json.dumps(event, ensure_ascii=False)}\n\n"
        # 流走完时配对一定完整，此刻落盘（与 CLI 的时机一致）
        manager.save_current()

    return StreamingResponse(sse(), media_type="text/event-stream")

两个细节：

  • 落盘时机原样复用第七篇的结论——流走完时 tool_calls 与结果配对完整，文件永远合法
  • CORS 必须放行前端的源。vite dev server 跑在 5173、后端在 8000，跨端口即跨源，不加 CORSMiddleware 浏览器会直接拦掉请求

用 curl 先验一遍，事件按序流出：

$ curl -sN -X POST localhost:8000/api/sessions/1/chat -d '{"message":"北京天气？再算 5*8"}' ...
data: {"type": "tool_call", "id": "call_hxT5...", "name": "get_weather", "args": {"city": "北京"}}
data: {"type": "tool_result", "id": "call_hxT5...", "content": "北京今天晴，最高气温38℃"}
data: {"type": "tool_call", "id": "call_Yx53...", "name": "calculate", "args": {"expression": "5*8"}}
data: {"type": "tool_result", "id": "call_Yx53...", "content": "40"}
data: {"type": "text_delta", "text": "北京"}
data: {"type": "text_delta", "text": "今天"}

前端：assistant-ui + 一个 adapter​

UI 组件库选了 assistant-ui。选型时对比过一圈：open-webui（148k★）、NextChat（88k★）那些高星项目是完整产品，接自定义后端只能把自己伪装成 OpenAI 兼容端点，工具调用过程和后续的确认交互都塞不进去；assistant-ui 是纯 React 组件库，后端无关、协议自己定，正适合这里。

接入靠一个 ChatModelAdapter——它是 assistant-ui 和我们后端之间的翻译层：

export const chatAdapter: ChatModelAdapter = {
  async *run({ messages, abortSignal }) {
    // 取最后一条用户消息，POST 给后端，逐条解析 SSE
    ...
    for await (const event of readSse(response.body)) {
      if (event.type === "text_delta") {
        currentText += event.text;
        ...
      } else if (event.type === "tool_call") {
        parts.push({ type: "tool-call", toolCallId: event.id, ... });
      }
      yield { content: [...parts] };
    }
  },
};
前端怎样发起 SSE 请求，为什么没有使用 EventSource？

这里直接使用 fetch 发起 POST 请求：

const response = await fetch(
  `${API_BASE}/api/sessions/${sessionId}/chat`,
  {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ message: text }),
    signal: abortSignal,
  },
);

后端返回的媒体类型仍然是 text/event-stream。前端从 response.body 获取 ReadableStream，再逐块读取：

const reader = response.body.getReader();
const decoder = new TextDecoder();

while (true) {
  const { done, value } = await reader.read();
  if (done) break;

  buffer += decoder.decode(value, { stream: true });
  // 按空行拆分 SSE 帧，再解析 data: 后面的 JSON
}

text/event-stream 是后端响应格式，EventSource 则是浏览器提供的一种 SSE 客户端 API，两者不是并列的两种协议。这个接口需要通过 POST 发送 JSON，而原生 EventSource 主要用于 GET 请求，不能直接携带请求体，所以这里选择 fetch + ReadableStream 消费同样的 text/event-stream 响应。

fetch 还可以接收 abortSignal，让运行时中止仍在读取的请求。相应地，SSE 帧解析和断线重连需要由项目自己处理；原生 EventSource 的自动重连能力不会自动获得。

两个容易踩的点：

  • 每次 yield 的是当前累积的完整 content，不是增量——这是 assistant-ui 的约定，和后端 SSE 的增量语义正好相反，adapter 要自己攒
  • SSE 解析要按帧切。fetch 读到的 chunk 可能含多条消息、也可能只有半条，得用 buffer 按空行（\n\n）分帧，不能假设一个 chunk 恰好是一条

UI 部分用 ThreadPrimitive / MessagePrimitive / ComposerPrimitive 这些无样式原语拼起来，配几十行 CSS。

一次真实的「没有反应」​

联通后第一次真机测试，问了句「杭州天气如何」——页面毫无反应。

排查过程值得记录。先确认两个服务都活着：会话列表接口秒回，说明后端没挂。再用 curl 原样复现浏览器的请求——25 秒后答案正常流出。最后绕过我们的服务直连模型网关，一句「回复OK」花了 29 秒。

结论：链路没有任何问题，是网关那一刻极慢。但用户（我自己）的体感是「挂了」。

这暴露了第一个真实的 UI 缺口，而且它不在我事先预测的任何清单里：没有等待指示。CLI 卡住时你会等，网页空白时你只会认为它坏了。修复很小：

<ThreadPrimitive.If running>
  <p className="thinking">思考中…</p>
</ThreadPrimitive.If>

效果​

要诚实地说：目前页面上真正能看到的，只有消息气泡和模型的文本回复。这一篇完成的是「联通」，不是「功能」：

  • 工具调用事件已经流到了前端（adapter 里也攒进了 parts），但没有给它配渲染组件，页面上不可见
  • 会话持久化只发生在后端（与 CLI 共用 .sessions/），页面刷新就是一条新会话，UI 上无任何体现
  • 流式链路是通的（curl 可见逐条事件），但页面上还没验证到肉眼可见的逐字效果——那次实测赶上网关极慢，回复又短

这些不是遗漏，是刻意的止损点：先让数据流端到端跑通，呈现层的每一块都留给后面单独做。
