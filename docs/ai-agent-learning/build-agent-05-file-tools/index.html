从零手写 Agent（五）：让 Agent 读写本地文件

前四篇的工具都是玩具：写死的假天气、一个小计算器。真正有用的 Agent 得能碰到真实的东西——比如「帮我看看这个文件里写了什么」、「把整理好的内容存成 markdown」。

这一篇加两个工具：read_file 和 write_file。代码本身很短，麻烦的是路径安全。

先解决一个工程问题：工具怎么组织​

第二篇那个 if/elif 分发，在工具变多之后就不合适了：

def execute_tool(name: str, args: dict) -> str:
    if name == "calculate":
        ...
    elif name == "get_weather":
        ...
    # 每加一个工具就多一个分支

改成字典分发，execute_tool 只负责查表、调用、兜异常：

TOOL_HANDLERS = {
    "calculate": calculate,
    "get_weather": get_weather,
    "read_file": read_file,
    "write_file": write_file,
}


def execute_tool(name: str, args: dict) -> str:
    handler = TOOL_HANDLERS.get(name)
    if handler is None:
        return f"未知工具：{name}"

    try:
        return handler(args)
    except Exception as e:
        return f"{name} 执行出错：{e}"

这里捕获所有异常是刻意的，不是偷懒。

原因是 args 由模型生成，属于不可信输入：字段可能缺失、路径可能不存在、表达式可能写错。把错误转成文本回传给模型，它下一轮就能看到原因并自行纠正：

缺字段:      calculate 执行出错：'expression'
非法表达式:  calculate 执行出错：invalid syntax (<string>, line 1)
未知工具:    未知工具：foo

如果直接抛出异常，整个 agent 循环会当场崩掉——用户输了一句话，程序直接退出。

路径安全：这一步不能省​

工具的实现只有几行：

def read_file(args: dict) -> str:
    return resolve(args["path"]).read_text(encoding="utf-8")


def write_file(args: dict) -> str:
    target = resolve(args["path"])
    target.parent.mkdir(parents=True, exist_ok=True)   # 自动建父目录

    content = args["content"]
    target.write_text(content, encoding="utf-8")

    # 回一条明确的结果，模型才知道写成功了、落在了哪
    return f"已写入 {target.relative_to(ROOT)}（{len(content)} 字符）"

关键全在 resolve 里。想清楚一件事：path 是模型生成的，不加限制它就能读 ~/.ssh/id_rsa，或者覆盖任意文件。

from pathlib import Path

# 根目录固定为项目目录，模型只能在这个范围内读写
ROOT = Path(__file__).resolve().parent

BLOCKED = {".env", ".git"}


def resolve(path: str) -> Path:
    target = (ROOT / path).resolve()      # resolve 会展开 .. 与符号链接

    if not target.is_relative_to(ROOT):
        raise ValueError(f"路径越界，只能访问项目目录内的文件：{path}")

    relative = target.relative_to(ROOT)
    if relative.parts and relative.parts[0] in BLOCKED:
        raise ValueError(f"该路径禁止访问：{path}")

    return target

三个设计点：

先 resolve() 再判断。 Path.resolve() 会把 .. 和符号链接都展开成真实路径，所以 ../../etc/hosts 这种绕不过去。如果先判断字符串再拼路径，就会被各种变形绕开。

屏蔽 .env

里面是 API key。一旦被 read_file 读出来，它就会作为工具结果进入 messages，然后随下一次请求发给模型服务端。这不是理论风险，是必然发生的数据流。

屏蔽 .git。 避免仓库元数据被改写。

实测效果：

读取:      3.12
越界:      read_file 执行出错：路径越界，只能访问项目目录内的文件：../../etc/hosts
绝对路径:  read_file 执行出错：路径越界，只能访问项目目录内的文件：/etc/hosts
黑名单:    read_file 执行出错：该路径禁止访问：.env
写入:      已写入 notes/demo.md（5 字符）

顺手把工具拆成一个文件一个​

工具挤在一个文件里迟早失控，拆成包：

tools/
├── __init__.py      # 登记模块，汇总 TOOLS / TOOL_HANDLERS
├── paths.py         # 路径校验
├── calculate.py
├── get_weather.py
├── read_file.py
└── write_file.py

每个工具文件导出两样东西：SCHEMA（给模型的声明）和 run(args)（实现）。声明和实现放在同一个文件，就不会出现「加了实现忘了加声明」这种低级问题。

__init__.py 里工具名直接从 SCHEMA 里取，不手写第二遍：

MODULES = (calculate, get_weather, read_file, write_file)

TOOLS = [module.SCHEMA for module in MODULES]
TOOL_HANDLERS = {module.SCHEMA["function"]["name"]: module.run for module in MODULES}

这样新增一个工具只有两步：建文件、在 MODULES 里登记。没有第三步。

效果​

不需要写任何调用代码，直接说人话：

$ uv run main.py
你: 在 notes 目录下建一个 hello.md，内容写一句项目介绍
  [工具调用] write_file({'content': '这是一个用于演示和实践的项目……', 'path': 'notes/hello.md'})
  [返回结果] 已写入 notes/hello.md（37 字符）
Agent: 已在 notes/hello.md 中写入项目介绍。

你: 读一下 tools/calculate.py，告诉我它导出了什么
  [工具调用] read_file({'path': 'tools/calculate.py'})
Agent: 导出了 SCHEMA（描述 calculate 工具及其 expression 参数）和 run(args)……

遗留的风险，说清楚​

write_file 会直接覆盖已有文件，没有确认、没有备份。改坏了只能靠 git 找回。

真实的编码 Agent 在这里都会加人工确认环节，而且它不是可选项——一旦 Agent 同时具备「读外部内容」和「写本地文件」两种能力，风险会突然放大。
