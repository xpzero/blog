从零手写 Agent（一）：第一次用代码调用大模型

大模型只能在网页上聊天吗？我想让它成为程序的一部分——比如自动整理我的笔记、自动查数据——该从哪里开始？

答案是：调用它的 HTTP 接口。网页版聊天框本身也只是这个接口的一层界面。这篇就把最小的一次调用跑通，并看清返回的数据长什么样。

这是一个系列的第一篇，最终会做出一个能调用工具、能多轮对话、能读写文件和联网搜索的命令行 Agent。全部代码在 xpzero/demo-agent。

准备环境​

用 uv 管理依赖（pip 也可以，命令换一下即可）：

uv init demo-agent
cd demo-agent
uv add openai python-dotenv

两个依赖的作用：

  • openai：官方 SDK。注意它不只能连 OpenAI——大多数模型服务商都提供「OpenAI 兼容」接口，换个地址就能用同一套代码
  • python-dotenv：把密钥从代码里挪到 .env 文件，避免误提交到仓库

在项目根目录建 .env：

OPENAI_API_KEY=你的密钥
OPENAI_BASE_URL=你的服务地址
务必确认 .env 已被 .gitignore 忽略

密钥一旦提交到公开仓库，就算之后删掉，历史记录里依然能翻出来。

最小的一次调用​

from dotenv import load_dotenv
from openai import OpenAI

# 读取 .env，把里面的键值对放进环境变量
load_dotenv()

# 不传参数时，SDK 自动从环境变量读 OPENAI_API_KEY 和 OPENAI_BASE_URL
client = OpenAI()

response = client.chat.completions.create(
    model="gpt-5.6-luna",  # 换成你的服务提供的模型名
    messages=[{"role": "user", "content": "Say Hi!"}],
)

print(f"{response.choices[0].message.role} reply: {response.choices[0].message.content}")

uv run main.py 就能看到模型的回复。这段代码只有三步：读配置、建客户端、发请求。

看懂 messages 和响应结构​

这两个结构后面每一篇都会用到，第一次就得看清。

请求侧的 messages 是一个列表，每个元素代表对话里的一条消息：

messages=[{"role": "user", "content": "Say Hi!"}]

role 表示这条消息是谁说的，常见三种：

role含义
system给模型的全局指示，比如「你是一个简洁的助手」
user用户说的话
assistant模型说的话

响应侧光看文档不如直接逐层打印出来：

print(response)
print(response.model_dump_json())
print(response.choices[0])
print(response.choices[0].message)
print(f"{response.choices[0].message.role} reply: {response.choices[0].message.content}")

最外层是一个 ChatCompletion 对象（为便于阅读，下面省略了部分为 None 的字段）：

ChatCompletion(
    id='resp_8cb23a2d3293faa5016a714dbb53988195bbdd7839ec33e1c4',
    choices=[Choice(finish_reason='stop', index=0, message=ChatCompletionMessage(
        content='Hi!', role='assistant', tool_calls=None))],
    created=1785810363,
    model='gpt-5.6-luna',
    object='chat.completion',
    usage=CompletionUsage(completion_tokens=6, prompt_tokens=14, total_tokens=20, ...)
)

response.model_dump_json() 是同一份数据的 JSON 形式，接口原始返回长的就是这样：

{"id":"resp_8cb23a2d...","choices":[{"finish_reason":"stop","index":0,"message":{"content":"Hi!","role":"assistant","tool_calls":null}}],"created":1785810363,"model":"gpt-5.6-luna","object":"chat.completion","usage":{"completion_tokens":6,"prompt_tokens":14,"total_tokens":20}}

再往里剥两层：

Choice(finish_reason='stop', index=0, message=ChatCompletionMessage(content='Hi!', role='assistant', tool_calls=None))

ChatCompletionMessage(content='Hi!', role='assistant', tool_calls=None)

assistant reply: Hi!

四个值得注意的字段：

choices 是列表，所以取值要写 choices[0]。接口设计上允许一次返回多个候选回复，默认只返回一个。

usage 是计费依据。 这次请求 prompt_tokens=14（我们发出去的）、completion_tokens=6（模型生成的）、total_tokens=20。注意我们只写了 Say Hi! 三个词却花了 14 个 token——因为角色标记等结构本身也要占。后面几篇上下文越堆越长，这个数字会涨得很快。

finish_reason='stop' 表示模型自己讲完了。如果是 length 就说明被 token 上限截断了，回复不完整。

tool_calls=None 这个字段现在是空的，但它是下一篇的主角。模型想调用工具时，内容就出现在这里。

关键认知：这次调用是无状态的​

这一点新手最容易误会。上面这段代码跑两次，模型完全不记得第一次说过什么。

它不是「忘了」，而是这个接口本身没有记忆——每次请求都是独立的一次函数调用，模型能看到的全部信息就是你传进去的 messages。网页版聊天框之所以能连续对话，是因为前端把历史消息全都重新发了一遍。

所以「多轮对话」不是模型的能力，是你的代码要做的事。

两个容易踩的坑​

模型名不能乱写。 model 参数的取值取决于你用的服务，填错会直接报错。如果你用的是第三方兼容网关，模型名往往和 OpenAI 官方的不一样。

OPENAI_BASE_URL 决定请求发到哪。 不设置就是发给 OpenAI 官方。用第三方服务时必须设置，否则密钥和地址不匹配，会得到 401 之类的认证错误。

这里要交代一个后面几篇会反复出现的词：网关。它指的就是 OPENAI_BASE_URL 指向的第三方中转服务——请求路径变成「你的代码 → 网关 → 真正的模型提供方 → 网关 → 你的代码」。它实现了「OpenAI 兼容接口」，所以同一套 SDK 代码换个地址就能用。

但兼容不等于等价：转发过程中可能丢字段或改行为。凡是标注「实测这个网关如何」的结论，都是在特定服务上观察到的结果，换成 OpenAI 官方或别家可能不一样。

顺手厘清：为什么说我们的 Python 程序是「客户端」
我们的 Python 程序  ──HTTP 请求──▶  网关  ──▶  模型提供方
    （客户端）                     （模型服务端这一侧）

它虽然是后端语言写的，但相对 LLM 接口而言是发请求的那一方，所以是客户端。后面几篇提到「模型服务端校验了什么」，指的都是 OPENAI_BASE_URL 那一侧，不是我们的程序。

客户端和服务端是相对角色，不是按语言划分的。假如把这个 Agent 包成 HTTP 服务给网页调用，它就同时是「网页的服务端」和「LLM 接口的客户端」。

效果​

$ uv run main.py
assistant reply: Hi!

一句 Say Hi! 发出去，拿到了模型的回复。这就是所有 LLM 应用的起点——网页版聊天框、编程助手、乃至后面几篇要做的 Agent，底层都是在重复这一次调用。

下一步​

现在这个程序有三个限制：

  1. 无记忆——每次运行都是全新开始
  2. 无法访问任何外部信息——只知道训练时见过的公开知识
  3. 只能说话，不能做事——没法查数据、没法改文件

下一篇解决第三个，顺便打开前两个的口子：让模型用上它本来接触不到的数据，比如内部系统的数据、或者实时天气。用到的正是上面那个空着的 tool_calls 字段。
