从零手写 Agent（十一）：给工具调用加上权限判断和用户审批

之前已经在前文：工具明明执行了，为什么页面上看不见？中把工具名称、参数和结果放到了网页上。现在我能看到 write_file 准备写什么，但工具卡片出现时，文件可能已经被覆盖了。

图中已经出现目标路径、逐行 Diff 和批准、拒绝按钮，页面也明确提示“文件尚未修改”。这不是单纯增加两个按钮：模型提出一次工具调用后，后端需要在真正执行前回答两个连续问题：

  1. 这次具体操作应该直接执行、询问用户，还是拒绝？
  2. 如果需要询问，怎样暂停当前任务，等用户决定后再安全恢复？

我把完整流程改成：

模型选择工具并生成参数
        ↓
工具描述这次具体操作
        ↓
PermissionService 根据规则裁决
        ├── allow → 直接执行
        ├── ask   → 保存现场，等待用户审批
        └── deny  → 不执行，返回拒绝结果
        ↓
每个 function_call 都得到对应的 function_call_output

这套权限规则参考并改写自 OpenCode 的权限机制：沿用 allow、ask、deny 三种 action、按操作对象细分规则，以及“最后一个匹配规则优先”的设计。本文核对的是 OpenCode 1ead9e3 提交；下面的 Python 接口、工具适配、Session 持久化和 /resume 流程则是针对当前项目重新实现的，并不等同于 OpenCode 的完整审批流程。

本文对应的 demo-agent 实现固定在 e651fbf 提交，正文中的接口、事件和测试数量均以这个版本为准。

先明确要验证什么​

这次操作的是后端机器上的文件系统，不是浏览器上传的文件。文件工具把 server/ 作为根目录，可以先准备不会误伤项目的演示文件：

mkdir -p server/notes
printf '这是允许自动读取的演示内容。\n' > server/notes/permission-read-demo.txt
printf '原始内容：请不要自动覆盖\n' > server/notes/approval-demo.txt
printf '原始内容：权限规则应阻止覆盖\n' > server/notes/permission-deny-demo.txt

对应的验收条件是：

场景是否出现审批文件或工具应该发生什么
read + notes/permission-read-demo.txt → allow否直接读取并返回内容
write + notes/approval-demo.txt → ask是审批卡出现时文件仍是原内容
用户批准已完成审批只写入一次，并返回真实工具结果
用户拒绝已完成审批文件不变，并返回拒绝结果
write + notes/permission-deny-demo.txt → deny否不执行，也不能通过按钮绕过
审批时刷新页面恢复审批卡后端保存的参数和 Diff 仍可继续处理

验证结束后，这三个文件可以删除；它们不是应用运行所需的数据。

后端怎样判断一次工具调用​

后端的权限判断分成三步：先明确模型在工具调用中的职责，再把不同工具的参数转换成统一的权限请求，最后用规则得到执行结果。

模型只提出工具调用​

发送给 Responses API 的工具 Schema 告诉模型有哪些工具以及参数形状。模型可以返回：

{
  "name": "write_file",
  "arguments": "{\"path\":\"notes/approval-demo.txt\",\"content\":\"这是经过用户批准后写入的内容。\"}"
}

Responses 的 function_call.arguments 是 JSON 字符串。Agent loop 先用 json.loads() 解码，并确认结果是对象，之后才把解析后的 path 和 content 交给工具与权限层。

但这只能表示模型提出了一个调用。模型生成的路径和内容仍是不可信输入，它不负责判断：

  • 路径是否越出允许访问的目录；
  • 当前规则是否允许写入这个文件；
  • 是否需要用户批准；
  • 用户批准前文件是否已经变化。

权限配置也不放进工具 Schema。它属于后端执行规则，不需要发给模型，更不能由模型在参数中选择 allow 或 deny。

工具怎样生成权限请求​

模型返回 function_call 后，Agent loop 可以拿到工具名和解析后的参数。接下来首先要确定：应该把什么数据交给 PermissionService？

如果直接传入每个工具的原始参数，权限服务就必须分别理解 write_file.path、get_weather.city、web_search.query 和 fetch_url.url，并跟着所有工具 Schema 一起变化。只传工具名又会丢失具体操作对象。例如，下面两个调用使用的都是 write_file：

write_file + notes/approval-demo.txt
write_file + notes/permission-deny-demo.txt

前者需要用户确认，后者应当直接禁止，仅凭 write_file 无法区分。因此，每个工具先把自己的参数转换成统一的数据结构。这里沿用 OpenCode 源码中的 PermissionRequest 概念，把它简化成一个 permission 对应一个 target。它不是向用户发起审批，而是工具提交给权限服务的一条待裁决操作描述：

server/services/permission/service.py
@dataclass(frozen=True)
class PermissionRequest:
    permission: str
    target: str = "*"

两个字段分别表示：

PermissionRequest
├── permission：操作类别，例如 read、write
└── target：本次操作的具体对象，例如 notes/a.txt

write_file 先复用文件工具原有的路径解析，再生成请求：

server/tools/files/write.py
def permission_requests(args: dict) -> tuple[PermissionRequest, ...]:
    target = resolve(args["path"])
    return (PermissionRequest("write", target.relative_to(ROOT).as_posix()),)

对于本次示例，它描述的是：

permission = write
target     = notes/approval-demo.txt

read_file 使用 read + 规范化路径。天气、计算、搜索和网页抓取分别使用自己的权限名，并把城市、表达式、查询词或 URL 作为 target。工具只描述准备做什么，不能自行返回 allow、ask 或 deny。

Agent loop 通过 describe_tool_permissions(call.name, args) 调用对应工具的 permission_requests()。如果工具不存在，或者没有生成合法的权限请求，这一步就会失败，工具不会执行。

权限请求怎样匹配规则​

到这里，PermissionRequest 只说明“准备做什么”，还没有说明“能不能做”。PermissionService 需要继续把它与一组“匹配条件与处理结果”的对应关系进行匹配：

permission 模式 + target 模式 → action

项目把一条这样的对应关系表示为 PermissionRule：

server/services/permission/rules.py
@dataclass(frozen=True)
class PermissionRule:
    permission: str
    target: str
    action: PermissionAction
    source: str = "builtin"

例如：

read  + *                                  → allow
write + *                                  → ask
write + notes/permission-deny-demo.txt     → deny

为了不用每次修改 Python 代码来调整这些对应关系，当前应用启动时从 server/permission.json 读取权限配置。它的“权限名既可以直接映射 action，也可以继续按 target 细分”的写法，来自 OpenCode 的权限配置对象语法：

server/permission.json
{
  "*": "ask",
  "read": {
    "*": "allow"
  },
  "write": {
    "*": "ask",
    "notes/permission-deny-demo.txt": "deny"
  },
  "calculate": "ask",
  "get_weather": "allow",
  "web_search": "allow",
  "fetch_url": "allow"
}

JSON 使用嵌套结构方便人直接编辑，规则引擎使用统一的 PermissionRule 对象进行匹配。字符串值表示这个权限对所有 target 使用同一动作，对象值可以按 target 继续细分。load_permission_rules() 读取并验证配置，再按照 JSON 中的顺序展开：

*           + *                                  → ask
read        + *                                  → allow
write       + *                                  → ask
write       + notes/permission-deny-demo.txt     → deny
calculate   + *                                  → ask
get_weather + *                                  → allow
web_search  + *                                  → allow
fetch_url   + *                                  → allow

配置读取遵循 fail closed：文件不存在、JSON 损坏、顶层不是对象、target 对象为空，或者 action 不是 allow、ask、deny，都会让服务创建失败。代码不会在配置错误时静默放宽成 allow。

加载链是：

server/permission.json
        ↓
load_permission_rules() 读取并验证
        ↓
PermissionRule[]
        ↓
RulePermissionService
        ↓
ServiceContainer.permission
        ↓
Agent loop 与审批恢复流程

ServiceContainer 让 Agent loop 依赖 PermissionService 接口，而不是依赖这一个 JSON 规则实现。测试可以注入固定结果的服务，以后也可以换成数据库或远端鉴权实现。

RulePermissionService 收到请求后，要求一条规则同时匹配 request 的 permission 和 target。当前通配符支持 * 和 ?，匹配区分大小写，并把反斜杠规范成 /。

同一个请求可能匹配多条规则，因此采用“最后一个匹配规则优先”。OpenCode 的 evaluate() 实现 同样在同时匹配 permission 和 pattern 后取 findLast()；上面的拒绝路径既匹配 write + *，也匹配后面的精确路径规则，最终得到 deny。

server/services/permission/rules.py
def _evaluate(self, request: PermissionRequest) -> tuple[PermissionAction, str]:
    for rule in reversed(self._rules):
        if _matches(request.permission, rule.permission) and _matches(
            request.target, rule.target
        ):
            return (
                rule.action,
                f"匹配 {rule.source} 规则：{rule.permission} {rule.target}",
            )
    return self._default_action, "没有匹配规则，使用默认权限"

配置开头的 * + * → ask 是一条能够匹配所有请求的全局兜底规则。除此之外，RulePermissionService 在完全没有规则匹配时还有一个代码级兜底结果 ask。两者当前结果相同，但前者来自项目配置，后者用于防止遗漏配置时自动放行。

一个工具如果描述了多个权限请求，最终结果按 deny > ask > allow 聚合；任何一项被禁止，整次调用就不能执行。

三个结果的含义不能混淆：

结果是否立即执行是否进入用户审批
allow是否
ask否是
deny否否

deny 是后端规则直接禁止，不会显示“批准”按钮；用户无权用一次审批绕过它。reject 则是权限结果为 ask 后，用户拒绝当前调用。

三种权限结果怎样进入 Agent loop​

allow：直接执行​

read_file 按当前配置匹配 read + * → allow，所以读取演示文件时直接得到工具结果，不会出现审批按钮：

Agent loop 在真正分发工具前统一裁决：

server/agent/approval.py
requests, authorization = _check_call(
    call.call_id, call.name, args, permission_service, session_id
)

if authorization.action == "allow":
    pending["output"] = execute_tool(call.name, args)
elif authorization.action == "ask":
    preview = preview_tool(call.name, args)
else:
    pending["outcome"] = "denied"

权限服务本身出现异常也不会回退成自动执行。审批批次会记录一次 deny 和错误输出，让模型仍能收到与原 call_id 对应的结果。

deny：直接返回拒绝结果​

写入专用拒绝路径时，后面的精确规则覆盖 write + * → ask，结果变成 deny：

这个分支不会生成 Diff、不会创建待审批请求，也不会调用 write_file。后端仍返回合法工具结果：

权限规则拒绝执行工具 write_file：
匹配 permission.json 规则：write notes/permission-deny-demo.txt；工具未执行。

保留工具结果很重要。Responses 上下文已经有一个 function_call，下一次请求前必须补上使用同一 call_id 的 function_call_output，不能因为拒绝执行就把原调用删掉。

ask：生成 Diff，但不写文件​

普通写入匹配 write + * → ask。这个阶段允许解析路径、读取旧内容和生成预览，但不能产生拟议的写入副作用：

server/tools/files/write.py
def preview(args: dict) -> dict:
    target = resolve(args["path"])
    content = args["content"]
    existed = target.exists()
    old_content = target.read_text(encoding="utf-8") if existed else ""

    # 使用 difflib.ndiff 生成 context、added、removed 行
    # ...

    return {
        "type": "code_diff",
        "path": str(target.relative_to(ROOT)),
        "additions": additions,
        "deletions": deletions,
        "lines": lines,
        "_guard": {
            "canonical_path": str(target),
            "existed": existed,
            "content_hash": sha256(old_content.encode("utf-8")).hexdigest(),
        },
    }

生成 Diff 时，后端还会保存一份名为 _guard 的校验信息。浏览器只能看到 Diff，不会收到 _guard。

_guard 记录生成 Diff 时的文件状态：

  • 解析后的真实文件路径；
  • 文件当时是否存在；
  • 根据当时文件内容计算出的 SHA-256 摘要。

SHA-256 摘要可以理解为文件内容的指纹。用户批准后，后端会重新读取文件并计算指纹，用它判断文件内容是否在等待期间发生了变化。

用户点击批准后，后端不会立即覆盖文件。它先取得目标路径对应的进程内锁，避免同一服务进程中的其他请求同时检查和修改这个文件。取得锁后，再依次完成三项操作：

  1. 重新把工具参数中的路径解析成真实路径，确认它仍然指向生成 Diff 时的文件；
  2. 重新读取文件，确认文件是否存在以及内容摘要都没有变化；
  3. 所有检查通过后，才写入用户批准的新内容。

如果路径、文件状态或内容发生变化，这次审批会失效，后端不会覆盖一份用户没有看过的内容。这把锁只能协调当前服务进程中的请求，不能阻止其他进程或外部程序修改文件。

权限规则不能代替这些工具硬限制。文件工具仍先负责：

  • 把真实路径限制在 server/ 内，阻止 .. 和符号链接逃逸；
  • 禁止访问首层 .env、.git 和 .sessions；
  • 校验参数类型；
  • 在获批写入前复核路径和内容摘要。

即使以后配置一条 write → allow，路径越界和敏感目录限制也不能被绕过。需要注意的是，Diff 和摘要 guard 只属于 ask 审批路径；自动允许的写入会直接执行，所以扩大 write 的 allow 范围前必须单独评估风险。

ask 怎样跨请求等待用户​

为什么审批不能继续占用原来的 SSE​

在加入审批之前，一次 /chat 请求对应一次连续运行的 Agent loop。浏览器建立 SSE 连接后，后端在同一条连接中接收模型输出、执行工具、发送工具结果，必要时再次请求模型，直到得到最终回答才关闭连接：

POST /chat
    │
    └── SSE 保持连接
          │
          ├── 模型返回 function_call
          ├── 后端执行工具
          ├── 返回 tool_result
          ├── 再次请求模型
          └── 返回 done，关闭 SSE

虽然这条 SSE 在 Agent loop 结束前一直保持连接，但后端始终在继续工作，不需要等待用户作出决定。

加入 ask 后，流程中第一次出现了时间不确定的人工等待。最直接的想法是让 stream_events() 停在审批位置，同时保持原来的 SSE 请求：

POST /chat
    │
    └── SSE 保持连接
          │
          ├── PermissionService 返回 ask
          ├── 页面显示审批卡
          ├── 等待用户……
          ├── 用户批准或拒绝
          └── 从原位置继续执行

但 stream_events() 是同步 generator。它暂停时保存的调用栈和局部变量只存在于当前 Python 进程与当前 HTTP 请求中：

  • 用户可能几秒、几分钟甚至更久以后才作出决定；
  • 页面刷新或网络中断会关闭原来的 SSE；
  • 服务重启后无法恢复 generator 的局部状态；
  • 长时间占用连接仍然不能提供可靠的恢复能力。

因此，ask 不能继续依赖原来的 SSE。后端需要先把恢复执行所需的数据保存到 pending_approval，发送 approval_required 后结束当前连接：

第一次 SSE
PermissionService 返回 ask
        ↓
保存 pending_approval
        ↓
发送 approval_required
        ↓
关闭 SSE

用户批准或拒绝
        ↓
保存决定和工具结果
        ↓
POST /resume 建立新的 SSE
        ↓
继续 Agent loop

对应到本次实现的交互顺序是：

项目仍使用 store=False，也不依赖 previous_response_id。恢复时把工具结果追加到本地保存的完整 Items，再发起新的 Responses 请求。

待审批状态需要保存什么​

内部 pending_approval 保存同一次模型响应中的整批调用，而不是只保存当前这一个 write_file：

{
  "schema_version": 2,
  "remaining_turns": 9,
  "outputs_committed": false,
  "calls": [
    {
      "id": "call_write",
      "name": "write_file",
      "args": {
        "path": "notes/approval-demo.txt",
        "content": "这是经过用户批准后写入的内容。"
      },
      "permission": {
        "action": "ask",
        "requests": [
          {
            "permission": "write",
            "target": "notes/approval-demo.txt"
          }
        ],
        "reason": "匹配 permission.json 规则：write *"
      },
      "decision": null,
      "outcome": null,
      "output": null,
      "guard": {
        "canonical_path": "/absolute/path/to/server/notes/approval-demo.txt",
        "existed": true,
        "content_hash": "根据预览时旧文件内容计算出的 SHA-256 摘要"
      },
      "preview": {
        "type": "code_diff",
        "path": "notes/approval-demo.txt",
        "additions": 1,
        "deletions": 1,
        "lines": [
          {"kind": "removed", "text": "原始内容：请不要自动覆盖"},
          {"kind": "added", "text": "这是经过用户批准后写入的内容。"}
        ]
      }
    }
  ]
}

这些字段分别解决不同问题：

  • 后端保存的 args 是执行事实来源，批准接口不接受浏览器重传的路径和内容；
  • permission.requests 把用户看到的调用与获批对象绑定；
  • decision 只记录用户的 approved/rejected，outcome 记录最终的 completed/rejected/denied/failed，避免“用户批准但重新检查失败”被显示成执行成功；
  • guard 防止文件变化后继续使用旧 Diff；
  • remaining_turns 防止审批后重新获得完整的 10 次模型请求预算；
  • outputs_committed 防止重复追加同一批 function_call_output；
  • 整批 calls 让同一次模型响应中并列返回的工具调用最终仍按原顺序提交输出。
pending_approval 就是保存在 Session 里吗？

是的。pending_approval 是 Session 的一个字段，并会随会话保存到 .sessions/<session_id>.json。

展开查看 pending_approval 如何保存与恢复

Session 的数据结构是：

@dataclass
class Session:
    id: int
    items: list
    pending_approval: dict | None = None

权限结果为 ask 时，后端先把审批批次赋给当前 Session，再通过 SessionManager.save() 将它和会话一起写入 .sessions/<session_id>.json：

构造审批批次
        ↓
session.pending_approval = batch
        ↓
SessionManager.save(session)
        ↓
写入 .sessions/<session_id>.json

Session 中的两个数据区域用途不同：

Session
├── items
│     └── 模型协议历史，包括原始 function_call
│
└── pending_approval
      └── 后端恢复审批所需的参数、权限、Diff、guard、决定和结果

工具参数在两处都会出现：items 保存模型返回的原始 function_call，pending_approval 保存后端已经解析并检查过的调用状态。用户批准或拒绝后，审批接口直接更新 pending_approval 中对应的 call，并再次保存 Session。

整批调用都有结果后，/resume 才把 function_call_output 追加到 items，然后继续 Agent loop。任务完成后，后端把 session.pending_approval 清空。

读取 pending_approval
        ↓
commit_outputs() 追加到 items
        ↓
继续 Agent loop
        ↓
任务完成
        ↓
session.pending_approval = None

这里保存的不是原来的 generator，也不是完整页面状态，只是重建审批卡并继续执行所需的数据。浏览器请求 Session 快照时，后端会返回公开版 pending_approval，其中不包含文件 guard。

加载 Session 时还会校验 schema_version: 2、运行字段、调用基本字段和权限请求；无法识别的旧版本不会假装成可恢复状态。

为什么先持久化再显示审批卡​

Agent loop 找到等待审批的调用后，必须先执行 checkpoint：

server/agent/loop.py
batch = prepare_batch(
    parsed_calls,
    max_turns - turn - 1,
    services.permission,
    session_id,
)
awaiting = pending_call_ids(batch)

if awaiting:
    if on_approval is None:
        raise RuntimeError("当前调用方没有提供工具审批处理器")
    on_approval(batch)

FastAPI 回调把 batch 放进当前 Session 并写入磁盘。保存成功后，页面才会依次收到带 approval_required: true 和 preview 的 tool_call，以及终止本次 SSE 的：

{
  "type": "approval_required",
  "call_ids": ["call_write"]
}

如果顺序反过来，页面可能已经显示批准按钮，后端却还没有能处理这个按钮的状态；用户刷新后只会得到一张无法恢复的卡片。

用户决定后怎样继续 Agent loop​

审批卡出现后，用户可以批准或拒绝一个工具调用。批准和拒绝接口负责处理单个调用；只有整批调用都有结果后，/resume 才会继续 Agent loop。

approve、reject 和 resume 分别负责什么​

后端提供三个接口：

POST /api/sessions/{session_id}/approvals/{call_id}/approve
POST /api/sessions/{session_id}/approvals/{call_id}/reject
POST /api/sessions/{session_id}/resume

它们分别负责：

接口职责本次 write_file 示例
approve保存批准决定，重新检查后执行这个工具调用批准 call_write，复核权限和文件状态后写入 notes/approval-demo.txt
reject保存拒绝决定，生成“工具未执行”的结果拒绝 call_write，不修改文件，并保存“用户拒绝执行工具”的结果
resume整批调用都有结果后，提交工具输出并继续 Agent loop把 call_write 对应的 function_call_output 追加到 items，再请求模型继续回答
展开查看 approve、reject 和 resume 的关系
                处理一个待审批调用
                         |
           +-------------+-------------+
           |                           |
+----------+----------+     +----------+----------+
| approve             |     | reject              |
| 重新检查并执行      |     | 不执行工具          |
| 保存最终执行结果    |     | 保存拒绝结果        |
+----------+----------+     +----------+----------+
           |                           |
           +-------------+-------------+
                         |
              整批 ask 是否都有结果？
                         |
           +-------------+-------------+
           |                           |
+----------+----------+     +----------+----------+
| 否：等待其他调用    |     | 是：POST /resume    |
+---------------------+     +----------+----------+
                                       |
                              追加 function_call_output
                                       |
                                继续 Agent loop

approve 和 reject 都只处理单个调用，不会直接继续 Agent loop。只有整批 ask 都有结果后，前端才请求 /resume。

如果当前只有一个待审批调用，批准和拒绝都会使这批调用立即就绪：

approve → /resume
reject  → /resume

权限规则直接返回的 deny 不同：如果这一批没有任何 ask，后端会在原来的 SSE 中提交拒绝结果并继续 Agent loop，不需要 /resume。

批准和拒绝接口只使用 URL 中的 session_id 和 call_id，不接受浏览器重新提交的工具参数。实际执行始终使用 pending_approval 中已经保存的 args。

用户批准后为什么还要重新检查​

用户点击批准，并不表示后端可以立即执行。执行前，后端会：

读取后端保存的 args
        ↓
重新生成 PermissionRequest[]
        ↓
与审批时保存的 requests 精确比较
        ↓
使用当前 PermissionService 再检查一次
        ├── deny → 不执行
        └── allow / ask → 当前批准作为这一次调用的允许
        ↓
复核 write_file guard
        ↓
真正执行

重新检查很重要：用户等待期间服务可能重新部署或重启，并加载新的权限配置或工具代码。新规则变成 deny 时，即使用户之前已经点了批准，工具仍不能执行；只编辑 permission.json 而不重启当前服务，则不会改变已经加载的规则。

批准接口会保存真实工具输出；相同批准请求可以安全重试，不会再次执行工具。

用户拒绝后怎样形成工具结果​

拒绝不会执行工具。审批接口先把拒绝原因保存到 pending_approval 中对应调用的 output；随后 /resume 会用这段文本生成与原调用配对的 function_call_output：

{
    "type": "function_call_output",
    "call_id": call_id,
    "output": "用户拒绝执行工具 write_file；工具未执行。",
}

原来的 function_call 不能删除，否则模型上下文会留下一个无法配对的调用。deny 与用户 reject 最终都会产生与原 call_id 对应的结果，区别只在原因：前者由规则禁止，后者由用户拒绝一次已经允许询问的调用。

resume 怎样把整批结果交还给模型​

批准和拒绝最终都会在 pending_approval 中留下一个工具结果。等所有 ask 都处理完成后，前端请求 /resume；后端调用 commit_outputs()，按模型原始调用顺序把每个结果追加到 items，然后重新进入 stream_events()。

所有 ask 都有结果
        ↓
POST /resume
        ↓
commit_outputs()
        ↓
function_call_output 追加到 items
        ↓
stream_events() 继续请求模型
模型最终会收到什么

用户批准或拒绝不会变成一条新的用户消息。所有权限分支最终都会生成与原 function_call 使用相同 call_id 的 function_call_output，区别只在 output 内容。

展开查看完整的 Items 拼接过程

项目维护的是 Responses API 的 Items 列表。第一次请求模型前，items 大致是：

Session.items
├── system
└── user

Agent loop 直接把它作为 input：

client.responses.create(
    input=items,
    tools=TOOLS,
    store=False,
)

模型返回工具调用后，后端先保存完整的 response.output：

items.extend(response.output)

此时列表变成：

Session.items
├── system
├── user
├── reasoning（可能存在）
└── function_call
      call_id = call_write
      name    = write_file

接下来，权限和审批决定 function_call_output.output 的内容：

PermissionService.check()
│
├── allow
│     └── 直接执行工具
│           └── output = 真实工具结果
│
├── ask
│     ├── 用户批准
│     │     └── 重新检查权限和文件 guard
│     │           ├── 仍可执行
│     │           │     └── output = 真实工具结果
│     │           └── deny / 检查失败
│     │                 └── output = 未执行的原因
│     │
│     └── 用户拒绝
│           └── output = 用户拒绝执行工具
│
└── deny
      └── output = 权限规则拒绝执行工具

无论进入哪个分支，最后都通过 commit_outputs() 追加相同结构的 Item：

{
    "type": "function_call_output",
    "call_id": "call_write",
    "output": "当前分支产生的结果文本",
}

四种典型结果只有 output 不同：

情况发送给模型的 output
权限直接 allow已写入 notes/a.txt（15 字符）
ask 后用户批准已写入 notes/a.txt（15 字符）
ask 后用户拒绝用户拒绝执行工具 write_file；工具未执行。
权限直接 deny权限规则拒绝执行工具 write_file：……；工具未执行。

因此，下一次请求模型时，items 是：

Session.items
├── system
├── user
├── reasoning（可能存在）
├── function_call
│     call_id = call_write
└── function_call_output
      call_id = call_write
      output  = 真实结果或未执行原因

Agent loop 再次调用：

client.responses.create(
    input=items,
    tools=TOOLS,
    store=False,
)

对模型来说，权限直接允许和用户批准的数据结构完全相同；用户拒绝和规则禁止也仍然是合法的工具结果。模型通过 output 文本判断工具最终是否执行。

permission、decision、outcome、Diff、文件 guard 和 approval_required 只供后端或页面使用，不会加入模型的 input。

同批多个调用怎样确定执行和提交顺序​

同一次模型响应可能并列返回多个工具调用。后端先保存所有 function_call，等整批 ask 都处理完后，再按照模型原始调用顺序追加对应的 function_call_output：

function_call A
function_call B
function_call_output A
function_call_output B

这里需要区分两种顺序：

  • commit_outputs() 保证回灌模型的结果顺序与原始调用顺序一致；
  • 每个批准接口会立即执行对应工具，因此有副作用工具的实际执行顺序取决于用户点击批准的顺序。

如果还要保证副作用严格按照模型调用顺序发生，就需要把实际执行推迟到整批调用都有决定之后。

页面刷新后怎样恢复审批​

页面刷新可能发生在两个不同时间点，前端需要分别处理：

页面刷新
    │
    ├── 还有 ask 没有决定
    │     └── 重建审批卡，继续等待用户
    │
    └── 所有决定已经保存
          └── 自动请求 /resume，继续 Agent loop

仍待决定：从 Session 快照重建审批卡​

session ID 保存在 localStorage。页面刷新后，前端先用它请求当前 Session：

GET /api/sessions/{session_id}

如果 pending_approval.calls 中仍有未决定的 ask，loadPendingMessages() 会把后端保存的调用重新转换成 assistant-ui 的 tool-call part：

web/src/adapter.ts
function restoredToolPart(call: PendingCall): ThreadAssistantMessagePart {
  return {
    type: "tool-call",
    toolCallId: call.id,
    toolName: call.name,
    args: call.args,
    argsText: JSON.stringify(call.args, null, 2),
    ...(call.output !== null && { result: call.output }),
    ...(call.preview !== null && { artifact: call.preview }),
    ...(call.permission.action === "ask" && call.outcome === null && {
      approval: { id: call.id },
    }),
  };
}

ToolCallPart 识别 code_diff artifact 后重新展示 Diff。前端把这条 Assistant 消息标记为 requires-action，告诉 assistant-ui 当前消息仍在等待工具决定。

用户点击按钮时，前端先请求后端保存决定和对应结果，成功后才调用 respondToApproval() 更新 assistant-ui 的页面运行状态（Local Runtime）。网络请求失败时，卡片仍保持待审批，用户可以重试。

决定已保存：自动调用 resume​

还有一种情况：用户的最后一个决定已经保存到后端，但页面在请求 /resume 之前刷新了。此时 loadPendingMessages() 找不到未决定的 ask，会设置 resumeOnLoad = true：

所有决定已经保存在 pending_approval
        ↓
页面在请求 /resume 前刷新
        ↓
loadPendingMessages() 发现没有未决定调用
        ↓
resumeOnLoad = true
        ↓
Runtime 启动一次 run
        ↓
adapter 请求 POST /resume

/resume 会先返回这一批调用的 tool_result。adapter 恢复执行时必须保留之前重建的 tool-call parts，才能根据相同的 call_id 把结果更新到正确的审批卡上。

审批恢复能恢复到什么程度​

这只是审批恢复，不是完整聊天历史恢复。Session API 不返回完整 Items，其中可能包含的 encrypted reasoning 也不会发送给页面；前端只重建当前审批所需的临时 Assistant 消息，不会恢复此前所有文本和工具时间线。

验证能证明什么​

自动化测试覆盖什么​

截图只能证明页面能呈现某种状态，不能单独证明文件在审批前未修改、deny 没有调用工具或重复批准只执行一次。因此后端测试使用模拟的 Responses 流事件和临时目录，分别检查：

  • allow 直接执行且不创建待审批调用；
  • ask 在 checkpoint 前没有执行工具；
  • preview() 生成 Diff 后目标文件不变；
  • deny 不执行工具、不进入审批，但生成匹配原 call_id 的输出；
  • 配置按 JSON 顺序展开，最后匹配规则优先；
  • 配置损坏和非法 action 会加载失败；
  • 拒绝不执行工具，批准和输出提交可幂等重试；
  • 批准前权限变成 deny 时阻止执行；
  • 文件在预览后变化时，旧审批失效；
  • 待审批状态可以 JSON 往返；
  • API 快照公开三态权限但不公开 guard；
  • 同轮多个调用的输出按模型调用顺序提交。

cd server

cd ../web
pnpm lint

哪些行为仍需手动验证​

真实 OpenAI 或兼容网关上的完整页面流程还需要在发布前手动验证。这里的后端测试证明项目收到相应 function call 后的编排行为；四张界面图证明实际 React 组件能够呈现对应状态，但它们都不能保证任意模型一定会按提示选择指定工具。

结论与实现边界​

这次建立了什么​

改造后的核心不是“危险工具弹窗”，而是把提议和执行之间增加一个后端控制点：

模型负责提出工具调用
工具负责描述本次具体操作
PermissionService 负责裁决 allow / ask / deny
审批工作流负责 ask 的暂停、决定与恢复
执行器只运行通过当前检查的后端参数

还没有解决的问题​

当前实现仍有明确限制。

工具与数据安全​

  • calculate 仍直接对模型表达式使用 eval()，ask 只是默认执行屏障，不是沙箱；即使 target 保存了具体表达式，也没有把表达式限制为安全数学语法；
  • 当前配置中的 read + * → allow 仍是较宽的读取规则，敏感边界主要依赖文件工具的根目录和首层黑名单；
  • Diff 只处理 UTF-8 文本和逐行变化，不显示文件末尾换行差异，也没有大文件折叠、大小限制或脱敏；
  • write_file 获批后直接覆盖，没有备份或跨进程事务；

状态一致性与恢复​

  • 工具完成副作用后、Session 保存输出前仍存在崩溃窗口；
  • 文件锁和会话运行锁都只在当前进程有效，不能协调多个 worker、CLI 或外部程序；
  • /resume 中断时仍保留旧批次的 remaining_turns；重试可能重新获得这段预算，严格的跨请求轮次核算需要独立 Run 状态；
  • 模型流中断后的通用恢复仍没有独立 Run 记录支持。

配置、部署与客户端能力​

  • 权限配置只在应用启动时加载，没有热更新；
  • API 没有身份认证，session_id 也是递增整数；当前默认开发命令只绑定本机回环地址，这套“用户审批”不能直接当成多用户部署的授权系统；
  • CLI 在终端同步询问，尚未像 HTTP 流程一样持久化等待中的审批。
