从零手写 Agent（十二）：用 Session Service 把会话存进 PostgreSQL

在前文：给工具调用加上权限判断和用户审批中，pending_approval 和会话一起保存到 JSON 文件。页面刷新后，后端可以重新读取工具参数、Diff 和用户决定，继续处理审批。

这次希望把这些状态统一存进 PostgreSQL，并像权限服务一样，为会话提供一个明确的 Python 接口。

检查原来的代码时，有两个问题需要一起回答：Session 应该由谁负责保存？网页已经显示出文字或工具结果时，数据库里保存到哪一步了？

例如，Agent 完成一次自动工具调用后，还会再次请求模型。如果只在最终回答结束时保存，中间已经得到的工具结果就仍然只在内存里。页面刷新、进程退出，都可能发生在这个间隙。

本文对应实现是 3d3eaf4。验证使用 PostgreSQL 16.2，查询到的事务隔离级别为 Read Committed。页面验证使用可控的 Responses 流驱动现有 Agent loop，HTTP、PostgreSQL 和 React 页面均使用实际实现；它验证的是编排与存储行为，真实模型的工具选择需要另外观察。

先明确 Session 保存了什么​

Session 就是一条会话。它保存的 items 是下一次请求 Responses API 时使用的上下文：用户消息、完整模型输出、工具调用和工具结果都在里面。

Session
├── id                 会话编号
├── items              模型上下文
├── pending_approval   等待或恢复审批所需的后端状态
└── revision           这份会话内容的版本号

其中 revision 是本次增加的字段。每次成功保存会话，版本号加一，用来识别基于旧内容发起的写入。

持久化表示程序退出以后数据仍然存在。前面的 JSON 文件已经实现了持久化；这次选择 PostgreSQL，是为了让 Session 有统一的查询入口、事务和版本检查。

当前仍按一个 FastAPI 实例运行。同一实例可以处理多条 Session，每条 Session 的运行过程由进程内锁和运行标记保护。

用 SessionService 统一存取​

SessionService 是后端中的 Python 接口。API 和 CLI 通过它创建、读取、保存会话，具体数据库操作交给 PostgresSessionService。

接口沿用权限服务使用的 Protocol。可以把它理解为一份约定：符合约定的实现，都提供下面这些方法。

server/sessions/service.py
class SessionService(Protocol):
    """会话存取接口；每次读取返回独立的 Session 快照。"""

    def create(self, system_prompt: str) -> Session: ...

    def get(self, session_id: int) -> Session | None: ...

    def list_sessions(self) -> list[SessionSummary]: ...

    def save(self, session: Session) -> None: ...

    def delete(self, session_id: int, expected_revision: int) -> bool: ...

    def close(self) -> None: ...

这里有三个实际约定：

  • create() 立即插入数据库，返回的空会话 ID 在重启后继续有效；
  • get() 返回一份独立快照，也就是本次读取获得的 Session 副本；
  • 当前版本的 save() 返回 None，成功后会原地更新传入对象的 revision。

最后一项也是替换存储实现时需要遵守的契约。只实现同名方法还不够，调用方下一次保存依赖更新后的版本号。

API 始终从 URL 取得明确的 Session ID，例如 /api/sessions/42/chat。CLI 则自己保存当前选中的会话，/switch 改变的是这个终端的选择。这样“当前会话”就属于使用者，数据库负责保存全部会话。

在一行里保存完整上下文​

PostgreSQL 的 sessions 表保存一整份 Session 快照。下面摘录主要列，完整 CHECK 约束见建表脚本。

CREATE TABLE public.sessions (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    items JSONB NOT NULL,
    pending_approval JSONB,
    revision BIGINT NOT NULL DEFAULT 0,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
列含义
id数据库生成的会话编号；导入旧数据时可以保留原 ID
items用 JSONB 保存有顺序的 Items 数组
pending_approval审批批次；空值表示当前没有该批次
revision内容版本，创建时为 0
created_at、updated_at创建时间和最近一次保存时间

JSONB 是 PostgreSQL 保存 JSON 结构的一种类型。它保留数组元素的顺序，因此工具 call 和 output 的顺序仍由应用控制；JSON 文本中的缩进和对象键顺序则不属于保存契约。

SDK 返回的 Item 是 Pydantic 对象。写入前继续调用 model_dump(exclude_none=True) 转成普通数据，再交给 Psycopg 的 Jsonb 适配器。读取后得到 Python 字典和列表，继续作为模型 input 使用。

revision、时间戳和审批预览属于应用状态。发送给模型的仍然是完整 items，其中的 encrypted reasoning 也原样保留。

数据库事务什么时候结束​

事务是一组数据库操作共同成功或失败的边界。保存时发生异常，数据库回滚；提交成功，新的状态才正式生效。

项目用连接池管理 PostgreSQL 连接。连接池可以理解为一组反复借用和归还的连接：

FastAPI 启动 → 创建连接池
一次 Session 操作 → 借用连接 → SQL → 提交 → 归还连接
FastAPI 关闭 → 关闭连接池

连接池的创建和关闭发生在 FastAPI 的 lifespan 中，也就是应用启动和关闭时执行的逻辑。每次借用连接、执行 SQL 和提交事务，则发生在具体的 Session Service 方法里。CLI 在入口处创建服务，退出时关闭连接池。

模型调用和 SSE 传输都发生在短事务之外。Agent 等待模型输出期间，数据库连接已经归还到池中。

Revision 怎样发现旧快照​

假设两个调用都读到 Session 的第 0 版。第一个保存后，数据库变成第 1 版；第二个仍拿着第 0 版，就应该收到冲突。

A 读取 revision=0
B 读取 revision=0
        ↓
A 保存成功，数据库变成 revision=1
        ↓
B 按 revision=0 保存
        ↓
数据库拒绝这次旧版本写入

版本判断和修改放在同一条 SQL 中，由数据库作为一次操作处理，这就是这里所说的原子条件更新。下面是 save() 的核心，省略了异常包装：

with self._pool.connection() as connection:
    row = connection.execute(
        """
        UPDATE public.sessions
        SET items = %s,
            pending_approval = %s,
            revision = revision + 1,
            updated_at = clock_timestamp()
        WHERE id = %s AND revision = %s
        RETURNING revision
        """,
        (
            Jsonb(items),
            None if pending is None else Jsonb(pending),
            session.id,
            session.revision,
        ),
    ).fetchone()
    # 完整实现会在 row 为空时区分会话不存在和版本冲突。

session.revision = row[0]

%s 是由 Psycopg 绑定的参数位置。WHERE id = %s AND revision = %s 表示：找到这条 Session，并确认内容仍是本次读取的版本，才执行更新。

这里的顺序很重要。RETURNING 取得新版本号时，事务还在进行；正常退出连接池上下文后，Psycopg 完成提交，然后代码才更新内存中的 session.revision。

本次在真实 PostgreSQL 上读取了两份 Session 2 快照。A 保存成功后变为 revision 1；B 使用 revision 0 保存，得到 SessionRevisionConflict。再次查询数据库，内容仍为 A 写入的 snapshot A。

session_id      = 2
A revision      = 1
B revision      = 0
B save          = SessionRevisionConflict
stored revision = 1
stored content  = snapshot A

数据库保存的是当前快照。revision 标记这个快照的版本，本次实现每次更新都会替换 items 和 pending_approval。

Checkpoint：选择完整状态保存​

checkpoint 可以理解为应用选定的检查点：当前内存中的状态已经完整，现在调用 Session Service 保存。

这里说的是应用回调，与 PostgreSQL 自身的 CHECKPOINT 管理命令含义不同。前者决定保存哪份会话，后者属于数据库内部的磁盘写入管理。

最容易混淆的是普通文本回答。

文本先流式显示，完整回答随后保存​

文本 delta 到达时，Agent loop 立即产生 text_delta，后端通过 SSE 发给浏览器。前端此时就可以显示文字。

页面中的文本还在增长时，已经能看到部分回答：

验证时同时查询数据库：Session 1 的 revision 为 1，Items 数量为 2，分别是 system 和已经保存的 user。完整回答结束后，revision 变成 2，Items 数量变成 3，新增完整 assistant output。

因此，这里的“保存后再完成”是指保存成功后发送 done。文本增量仍然实时发送。

自动工具结果配对后保存​

模型通过 function_call 提出工具调用。后端执行或拒绝工具后，通过相同的 call_id 生成 function_call_output。

自动工具分支增加了一个很小的回调：

server/agent/loop.py，摘录
if not awaiting:
    commit_outputs(items, batch, services.permission, session_id)
    if on_checkpoint is not None:
        on_checkpoint()

# 随后才逐个 yield tool_call 和 tool_result。

这里的 commit_outputs() 指把工具结果追加到内存 Items。真正提交 PostgreSQL 的是 on_checkpoint() 调用的 SessionService.save()。

工具执行或拒绝
    ↓
call 与 output 配对完整
    ↓
checkpoint 保存 Session
    ↓
发送工具事件
    ↓
继续请求模型

验证天气工具时，最终回答还在生成，Session 1 已经是 revision 11、12 个 Items。完整最终回答保存后，再变成 revision 12、13 个 Items。这证明自动工具轮次已经先于最终回答落库。

审批批次一起保存​

等待用户决定时，保存的是完整 function_call 和同轮 pending_approval。批次中记录已经解析的参数、权限结果、Diff、guard、决定和执行结果，供后续请求读取。

保存 Items + pending_approval
    ↓
发送工具卡与 approval_required
    ↓
结束本次 SSE
    ↓
用户批准或拒绝
    ↓
保存决定与结果
    ↓
resume 提交工具 output 后保存
    ↓
继续模型循环

模型返回同一批多个工具时，pending_approval 保存整批调用；commit_outputs() 按模型原始调用顺序追加结果。结果的排列顺序与工具实际执行时间是两个不同概念，批准接口仍会执行用户刚批准的工具。

进程锁与 revision 各自负责什么​

当前保留 SessionRuntime：每条会话对应一个短锁，开始 Agent 任务时还会登记运行 token。

机制本次职责
会话锁 RLock在当前进程内串行处理读取、修改、保存等短操作
运行 token标记同一 Session 正在处理任务，重叠请求得到 409
revision保存时确认 Session 内容仍是读取时的版本
checkpoint选择完整状态，并安排保存与事件发送顺序

稳定终止事件发出前释放运行 token，响应关闭时再做兜底清理。释放时核对 token 身份，避免旧响应的清理逻辑影响后来的任务。

对于本次单实例部署，运行 token 控制执行过程，revision 保护数据库写入。将来部署多个实例时，再通过数据库中的运行权协调它们。

建表和导入旧 JSON 是两步​

schema migration 是数据库结构迁移。例如本次的 0001_create_sessions.sql 创建 Session 表，schema_migrations 记录文件版本和 checksum（文件内容摘要）。

在 server/.env 中准备数据库连接，测试库使用独立地址：

DATABASE_URL=postgresql://user:password@localhost:5432/demo_agent
TEST_DATABASE_URL=postgresql://user:password@localhost:5432/demo_agent_test

在仓库根目录执行：

make db-migrate

本次在临时 PostgreSQL 实例上实际执行了两次 uv run python migrate.py。首次返回：

[已执行 migration] 0001_create_sessions.sql

第二次返回：

[数据库 schema 已是最新版本]

随后使用独立的 JSON 示例验证数据导入。在 server/ 执行：

uv run python -m sessions.migrate_json --source /path/to/session-fixtures --dry-run
uv run python -m sessions.migrate_json --source /path/to/session-fixtures --apply

--dry-run 校验文件，--apply 写入已经建表的数据库。目标表需要为空；导入过程中取得表锁，保留原 ID，并把 ID 序列推进到足够高的位置。

本次导入示例 Session 42 后，revision 为 0；随后新建 Session 得到 ID 43。测试还覆盖了 identity 已经使用到 100 的情况，导入旧 ID 后仍从 101 继续分配。

正式迁移时，先停止旧入口写入，备份 JSON，再执行预检和导入。旧文件保留的是切换时刻的备份，新版本继续把后续变化写到 PostgreSQL。

仍有不足，后续完善​

这次先建立了 Session Service、PostgreSQL 持久化、revision 检查和稳定保存点。还有几项需要继续完善：

  • 本次恢复审批后点击批准，后端已保存工具输出和最终回答，Session 1 到达 revision 7，但页面报告 Duplicate key toolCallId-call_2 in useResources，最终回答未能显示。刷新后可以继续对话，数据库推进到 revision 9；这条完整页面流程仍需修复并补测试；
  • save() 原地更新 revision 的接口契约、数据校验与迁移健壮性还可以继续收紧；
  • 工具副作用与 Session 保存之间仍有窗口，结果保存异常时应先核对实际操作，再决定重试；
  • 多实例运行权、独立 Run 记录和中断恢复将在后续补齐。

目前最清楚的分工是：Session Service 负责怎样存，revision 负责识别旧版本，checkpoint 负责选择保存时机，页面通过项目事件展示进度。
