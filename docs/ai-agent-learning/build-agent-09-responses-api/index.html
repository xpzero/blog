从零手写 Agent（九）：从 Chat Completions 切到 Responses API

为什么切换 API​

最近看一些新模型的介绍时，我注意到它们支持 Responses API。有些资料还说，它比之前的 Chat Completions API 更适合构建 Agent。

我并不知道 Responses API 是什么，也不知道“更适合”具体体现在哪里，因此把 demo-agent 从 Chat Completions API 切换到了 Responses API。

这次迁移不只是把 client.chat.completions.create() 换成 client.responses.create()。Chat Completions 中的 choices[0].delta 变成了带有明确类型的流事件，原来需要手动拼接的流式工具参数，也可以在这个项目中直接读取完整的 function_call Item。

本文对比的是同一个项目的两个固定版本：

  • 迁移前：commit 852f225
  • 迁移后：commit 5c85226

Responses API 的主体改动形成于 commit 42db7df，最终版本继续把会话存储按破坏性迁移处理，删除旧 messages 会话文件的读取器，只保留 Items 格式。

OpenAI 的迁移指南将 Responses API 描述为 Chat Completions 的演进版本，并推荐新项目使用它。不过，“演进”并不能直接说明我的代码会发生什么变化，还是要从迁移前的 Agent loop 看起。

迁移前：Chat Completions API​

从 choices 数组读取结果​

Chat Completions 的响应围绕 choices 数组组织。非流式请求通常从第一个候选结果中读取消息：

completion = client.chat.completions.create(
    model=MODEL,
    messages=messages,
)

message = completion.choices[0].message
text = message.content
tool_calls = message.tool_calls

choices 是候选结果数组。这个项目只需要一个结果，因此一直固定读取 choices[0]。

开启流式输出后，每次收到的不再是完整 message，而是一个 chunk。项目继续从第一个 choice 中读取 delta：

for chunk in stream:
    delta = chunk.choices[0].delta

    if delta.content:
        content += delta.content
        yield {
            "type": "text_delta",
            "text": delta.content,
        }

    for tool_call in delta.tool_calls or []:
        ...

它的结构可以简化成：

chunk
└── choices[0]
    └── delta
        ├── content
        └── tool_calls

每个 chunk 的形状大致相同，代码要继续检查 delta.content、delta.tool_calls 等字段，才能知道这次收到的是文本还是工具调用。

手动拼接流式工具参数​

第四篇处理流式输出时已经遇到过这个问题：工具调用不是一次完整返回，id、工具名和 JSON 参数可能分散在多个 chunk 中。多个工具并行调用时，这些碎片还可能交错出现。

迁移前的代码用 index 区分每个工具调用，并为它们分别保存状态：

calls: dict[int, dict] = {}

for chunk in stream:
    delta = chunk.choices[0].delta

    for tool_call in delta.tool_calls or []:
        slot = calls.setdefault(
            tool_call.index,
            {
                "id": "",
                "name": "",
                "arguments": "",
            },
        )

        if tool_call.id:
            slot["id"] = tool_call.id

        if tool_call.function and tool_call.function.name:
            slot["name"] = tool_call.function.name

        if tool_call.function and tool_call.function.arguments:
            slot["arguments"] += tool_call.function.arguments

这段代码做了四件事：

  1. 根据 index 判断碎片属于哪个工具调用；
  2. 保存只在部分 chunk 中出现的 id；
  3. 保存工具名；
  4. 用 arguments += ... 拼出完整的 JSON 字符串。

手动重建 assistant 工具消息​

等流结束后，还要按 index 排序，再把这些状态重新组装成一条 assistant 消息：

ordered = [calls[index] for index in sorted(calls)]

messages.append(
    {
        "role": "assistant",
        "content": content or None,
        "tool_calls": [
            {
                "id": slot["id"],
                "type": "function",
                "function": {
                    "name": slot["name"],
                    "arguments": slot["arguments"],
                },
            }
            for slot in ordered
        ],
    }
)

模型已经发起过工具调用，下一轮请求必须把这件事放回上下文。因为流里没有一条可以直接保存的完整 assistant 消息，这部分也要由项目自己构造。

工具执行完成后，再追加一条 role="tool" 的消息：

messages.append(
    {
        "role": "tool",
        "tool_call_id": slot["id"],
        "content": result,
    }
)

Chat Completions 版本的问题​

因此，Chat Completions 版本的 Agent loop 不只是在“读取流”，还维护了一套工具调用的临时状态。多个工具调用交错出现时，项目既要识别每个碎片的归属，又要确保拼出的参数和下一轮上下文保持完整。这些代码依赖 choices[0].delta 的具体结构，也是这次迁移希望简化的部分。

迁移后：Responses API​

切换 API 调用入口​

迁移前的请求是：

stream = client.chat.completions.create(
    model=MODEL,
    messages=messages,
    tools=TOOLS,
    stream=True,
)

迁移后改为：

stream = client.responses.create(
    model=MODEL,
    input=items,
    tools=TOOLS,
    stream=True,
    store=False,
    include=["reasoning.encrypted_content"],
)

这里只能看出一些参数变化：

  • chat.completions.create() 变成 responses.create()；
  • messages 变成 input；
  • 本地上下文变量从 messages 改名为 items；
  • 项目使用 store=False，继续在本地管理会话，而不是依赖服务端保存 Response。

真正改变 Agent loop 的，是响应结构。

choices[0].delta 变成有类型的事件​

Responses 的流不再从 choices[0].delta 读取。每个事件都有一个 type，直接说明它代表什么：

response = None

for event in stream:
    if event.type == "response.output_text.delta":
        yield {
            "type": "text_delta",
            "text": event.delta,
        }

    elif event.type == "response.completed":
        response = event.response

    elif event.type == "response.failed":
        ...

    elif event.type == "response.incomplete":
        ...

    elif event.type == "error":
        ...

这里的“有类型”不是指 Python 的类型注解，而是事件本身带有 type 字段。例如：

response.output_text.delta  新增了一段文本
response.completed          响应已经完整结束
response.failed             请求失败
response.incomplete         响应没有完整生成
error                       流处理发生错误

处理方式从“进入 choices[0].delta 后检查里面装了什么”，变成了“先看事件类型，再读取对应字段”。OpenAI 的流式迁移说明也采用了这种按事件类型消费 Responses Stream 的方式。

从 choices 到 output Items​

choices 不只从 Stream 中消失了。完整响应也不再通过 choices[0].message 表达，而是提供一个 output 数组：

calls = [
    item
    for item in response.output
    if item.type == "function_call"
]

Responses 把一次执行过程中的不同内容表示成不同 Item，例如：

response.output
├── message
├── reasoning
└── function_call

最终文本还可以直接从辅助属性读取：

response.output_text

两种响应结构可以简化为：

Chat Completions

response
└── choices[]
    └── message
        ├── content
        └── tool_calls[]
Responses

response
├── output[]
│   ├── message
│   ├── reasoning
│   └── function_call
└── output_text

对于这个只需要一个模型结果、但需要保存文本、推理信息和工具调用过程的 Agent，output Items 比固定读取 choices[0] 更贴近现有执行过程。

删除工具参数拼接​

迁移后的项目仍会实时转发文本，但不再实时展示生成中的工具参数。因此可以等到 response.completed，再读取完整的 function_call Item：

calls = [
    item
    for item in response.output
    if item.type == "function_call"
]

parsed_calls = [
    (call, json.loads(call.arguments))
    for call in calls
]

原来的这些代码都被删除了：

calls[index] 临时状态
保存 id 和 name
arguments += 参数碎片
按 index 排序
手动重建 assistant.tool_calls

执行工具时，可以直接使用完整 Item 上的字段：

for call, args in parsed_calls:
    yield {
        "type": "tool_call",
        "id": call.call_id,
        "name": call.name,
        "args": args,
    }

    result = execute_tool(call.name, args)
这不是说 Responses 没有工具参数增量

Responses 仍然可以产生 response.function_call_arguments.delta 等事件。这个项目不需要把生成中的工具参数展示给用户，所以选择忽略参数增量，在 response.completed 后读取完整结果。

因此准确的结论是：这个项目可以删除工具参数拼接，不是所有使用 Responses API 的程序都不再需要处理参数增量。

不再手动重建工具调用消息​

Responses 版本把完整的 response.output 加入本地上下文：

items.extend(response.output)

工具执行完成后，再追加一个 function_call_output Item：

items.append(
    {
        "type": "function_call_output",
        "call_id": call.call_id,
        "output": result,
    }
)

这里的 call_id 必须与原 function_call 对应。完整流程仍然是：

模型返回 function_call
        ↓
项目执行本地 Python 函数
        ↓
项目追加 function_call_output
        ↓
再次请求模型生成最终回答

这与 OpenAI 的函数调用流程一致。Responses API 没有替项目执行 get_weather、calculate、文件读写或 Tavily 搜索；它改变的是这些步骤在请求和响应中如何表达。

直接保存 response.output 还有一个好处：不需要从流式碎片中手动重建上下文，也不容易只保存文本而漏掉 reasoning 或并行工具调用。

工具 schema 也变平了​

Chat Completions 版本把函数声明放在 function 内：

SCHEMA = {
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "查询指定城市今天的天气",
        "parameters": {
            ...
        },
    },
}

Responses 版本使用扁平结构：

SCHEMA = {
    "type": "function",
    "name": "get_weather",
    "description": "查询指定城市今天的天气",
    "parameters": {
        ...
    },
    "strict": False,
}

这主要是协议格式变化，没有工具参数拼接那么明显，但六个自定义工具都要同步调整。

会话直接改用 Items​

迁移后的 items 不只包含普通对话消息，还可能包含 reasoning、function_call 和 function_call_output。这次把会话存储格式也作为协议迁移的一部分，Session 不再保留旧 messages 格式的读取分支：

@classmethod
def from_dict(cls, data: dict) -> "Session":
    return cls(id=int(data["id"]), items=list(data["items"]))

新会话和重新保存的会话也统一使用 items 键。迁移前由 Chat Completions 版本写入的 .sessions/*.json 不能直接继续使用；升级前如需保留历史，需要单独备份或转换。这是一次有意的破坏性数据格式变更，换来的是生产代码从加载、运行到落盘都只处理 Items，不长期保留两套协议。

迁移前后对比​

哪些循环没有消失​

看到工具参数拼接被删除后，很容易进一步猜测：Responses API 是不是已经内置了 Agent loop，项目自己的循环也可以删掉？

这个项目仍然保留三层不同的循环：

循环是否保留作用
会话输入循环保留接收用户的下一条消息
Agent 工具循环保留在模型、本地工具和下一次模型请求之间往返
单次请求的 Stream 读取循环保留实时消费文本、完成和错误事件
工具参数分片归并删除不再手动维护 index 和 arguments 碎片

前端同样没有停止拼接文本。当前链路是：

OpenAI Responses Stream
        ↓ 后端读取并转换事件
FastAPI SSE
        ↓ 前端 fetch + ReadableStream
assistant-ui 累积文本并显示

后端不再为了获得最终答案而拼接文本，因为 response.output_text 已经提供完整结果；前端为了逐步显示，仍然要把收到的 text_delta 累加成当前完整文本。

这次没有使用的 Responses 能力​

Responses API 提供内置 Web Search 等工具，但这次迁移没有启用它们。项目里的 web_search 仍然是原有的 Tavily 自定义函数，也仍然由本地 Agent loop 执行。

服务端会话状态和多模态输入也不在这次迁移的验证范围内。项目选择 store=False 并在本地保存完整 Items，因此不能根据这次代码切换评价这些尚未使用的能力。

迁移结果​

这次迁移的主体形成了 commit 42db7df，涉及 Agent loop、六个工具 schema、会话存储、CLI、FastAPI、前端错误事件、README 和测试。最终的 commit 5c85226 又删除了旧 messages 会话读取器，把存储格式收敛为 Items。

迁移完成时的验证记录包括：

  • 13 个后端测试通过；
  • 前端 lint 通过；
  • TypeScript 和 Vite 生产构建通过。

测试覆盖的不只是文本回复，还包括并行工具调用、最大轮次、流结束但没有 response.completed、无效 JSON 参数和 Items 的 JSON 往返。

从代码量看，这不是一次只修改 endpoint 的迁移；Items 会话序列化和测试也增加了代码。但 Agent loop 中最容易出错的协议拼装状态确实减少了：不再按 index 归拢工具调用，不再手动拼接参数，也不再重建 assistant 工具消息。

Responses API 具体解决了什么​

Responses API 不是一个替我执行本地工具的 Agent 框架。get_weather 怎么运行、文件能写到哪里、工具失败后怎么处理，这些仍然由项目负责。

它更像是一个适合表达 Agent 执行过程的统一接口：文本、推理信息、工具调用和工具结果不必全部塞进一条 chat message，而是可以作为不同的 Item 保存和继续传递；流中的不同阶段也用明确的事件类型表达。

对 demo-agent 来说，“比 Chat Completions 更方便”最终落在几个可以从代码中确认的变化上：

  1. 不再固定进入 choices[0].delta 后检查可选字段；
  2. 可以按明确的事件类型消费 Stream；
  3. 可以从完整 function_call Item 读取工具名、call_id 和参数；
  4. 可以直接保存完整的 response.output，不再重建 assistant 工具消息；
  5. 原有 Agent loop 继续保留，但其中用于拼装 Chat Completions 协议碎片的代码可以删除。

这次迁移能支持的结论只到这里。Responses API 还提供服务端会话状态、内置工具和多模态输入，但这个 demo 没有使用它们，不能仅凭这次代码切换评价这些能力。
