FastAPI 到底替你做了什么

断断续续学过一些 Python，但一直没用它写过 Web 服务。最近想试试，一搜，教程和新项目几乎都在用 FastAPI。

那就直接从它开始。这篇不比较框架优劣，只回答两个问题：一个 HTTP 请求进来，FastAPI 中间替你做了哪些事；以及它不管哪些事。

前提：本文代码在 Python 3.11 / FastAPI 0.115 / Pydantic 2.x 下写成。Pydantic 是 FastAPI 依赖的校验库，它 1.x 和 2.x 的写法差别很大，抄旧代码容易报错，后面会单独说。

先让它跑起来​

Python 和 Node 有个区别：依赖默认装到全局，多个项目会互相冲突，所以要先建一个项目专属的隔离环境（virtual environment，虚拟环境）。Python 没有 node_modules 那样的目录级隔离，这一步不能省。

mkdir fastapi-demo && cd fastapi-demo

python3 -m venv .venv           # 建虚拟环境，产生一个 .venv 目录
source .venv/bin/activate       # 激活；Windows 是 .venv\Scripts\activate

pip install "fastapi[standard]"  # pip 相当于 npm，standard 表示装上常用配套

激活后命令行提示符前会多一个 (.venv)，表示后续 pip install 都只装进这个目录。

新建 main.py：

from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class ChatRequest(BaseModel):
    message: str
    max_turns: int = 10

@app.post("/sessions/{session_id}/chat")
def chat(session_id: int, body: ChatRequest):
    return {"session": session_id, "echo": body.message, "turns": body.max_turns}

启动：

fastapi dev main.py

这几行里 FastAPI 各自做了什么：

  • @app.post(...) 把下面的函数注册成这个路径的处理器，和 Express 的 app.post('/path', handler) 是一回事。
  • 继承 BaseModel 让 ChatRequest 获得校验能力，这是 Pydantic 提供的，max_turns: int = 10 的默认值也由它处理。
  • 函数返回一个 dict，FastAPI 自动序列化成 JSON，不需要手动调用类似 res.json() 的东西。
  • session_id 和 body 从哪里取值、要不要校验，完全由那几个类型注解决定——这是下一节的重点。

现在打开 http://localhost:8000/docs，你会看到一个接口文档页面，能直接填参数点「Execute」发请求。这个页面你一行都没写。

关键前提：Python 的类型注解本来是不管事的​

这一节是理解 FastAPI 全部价值的前提。

学 Python 的时候大概见过类型注解，但有件事容易忽略：解释器完全不检查它们。它们只是给人和编辑器看的备注：

def add(a: int, b: int) -> int:
    return a + b

print(add("1", "2"))    # 输出 12 —— 字符串拼接，没有任何报错

a: int 写在那里，传字符串照样跑，结果还是错的。这和 TypeScript 完全不同：TS 至少编译期会拦你，Python 连这一步都没有。所以在普通 Python 代码里，类型注解基本是文档性质的。

FastAPI 做的事就是：把这些原本不管事的注解，变成运行时真的生效的规则。

同一句 session_id: int，在普通函数里是备注，在 FastAPI 的路由函数里，它同时意味着「从 URL 路径取这个值」「转成整数」「转不动就拒绝请求」「在文档里标记为整型」。

一句声明，四件事。下面拆开看。

一处声明，四件事​

一、参数从哪来，不用自己判断​

Express 里你得自己分清 req.params.id、req.query.page、req.body.message。FastAPI 里你只声明参数，它按三条规则自己判断来源：

情况从哪取
参数名出现在路径模板里（{session_id}）URL 路径
类型是 BaseModel 的子类请求体（body）的 JSON
其他普通类型（int/str/bool 等）查询字符串（?page=2）

所以上面例子里，session_id 来自路径，body 来自 JSON body，你一个字都没多写。想显式指定就用 Path() / Query() / Body() 标注，但多数时候不需要。

二、校验和类型转换，不用自己写​

URL 里的东西全是字符串，/sessions/42/chat 里的 42 也是。但因为声明了 session_id: int，进函数时它已经是整数了。

传个不是数字的进去：

curl -s localhost:8000/sessions/abc/chat \
  -H 'Content-Type: application/json' \
  -d '{"message":"hi"}'

请求根本进不了函数，直接返回 422，body 里说明哪个字段错了、错在哪（Pydantic v2 的结构大致如下，细节可能随版本微调）：

{
  "detail": [
    {
      "type": "int_parsing",
      "loc": ["path", "session_id"],
      "msg": "Input should be a valid integer, unable to parse string as an integer",
      "input": "abc"
    }
  ]
}

loc 是出错位置。少传 message 的话它会变成 ["body", "message"]。

这条的真正价值是：函数体里的参数一定是合法的。不用再写一堆 if not message: return 400，业务代码里没有校验噪音。

三、接口文档免费送​

三个地址自动存在：

  • /docs —— Swagger UI，能点着发请求的交互式文档
  • /redoc —— 另一套排版风格
  • /openapi.json —— 机器可读的接口描述（OpenAPI 是接口描述的通用规范）

全部由上面的类型注解推导出来，不用额外写注释或 yaml 配置。

前后端协作时这条可能比校验更实用：前端不用等你写文档、不用来问参数叫什么，/openapi.json 还能直接生成 TypeScript 类型。

四、编辑器能补全​

因为参数有真实类型，敲 body. 时编辑器知道有 message 和 max_turns。这不算框架特性，是类型注解的副产品——但只有当框架真的以类型为中心时，你才有动力把注解写全。

这四件事有个共同点：它们都是推导出来的，不是另外写的。你只声明了业务需要的那部分信息（参数叫什么、是什么类型、必填还是有默认值），参数解析、校验、错误响应、接口文档全部由这份声明派生。声明和实现之间不会失同步，因为它们是同一份东西。

异步不是可选项​

上面那些是「省事」。接下来这个是「能不能做」，也是我觉得最值得理解的部分。

同步和异步是两套并行的世界​

JS 里有个默认前提：I/O 天生是异步的。fetch 一定返回 Promise，没有「同步版 fetch」可选，整个生态只有一套异步模型。

Python 不是。Python 里同步和异步是两个并行的世界，各有一整套库：

用途同步库异步库
HTTP 请求requestshttpx.AsyncClient、aiohttp
等待time.sleep()await asyncio.sleep()

def 定义的是普通函数，async def 定义的是协程函数（对应 JS 的 async function），只能用 await 调用。选错一边会出问题，这是后面那个坑的根源。

WSGI 和 ASGI：两种并发模型​

Python 的 Web 框架和服务器之间有一个约定接口。老的那套叫 WSGI，接口是同步的；新的叫 ASGI，接口是异步的。差别落在并发模型上：

  • WSGI：一个请求占住一个 worker（工作进程或线程）直到返回。有 4 个 worker，同时就只能处理 4 个请求，第 5 个用户排队。
  • ASGI：等待中的请求是挂起的协程，占的是内存不是 worker。单个进程能同时挂着大量等待中的连接。

FastAPI 只跑在 ASGI 上，配套的服务器是 uvicorn（前面 fastapi dev 启动的就是它）。所以异步在这里不是可选项，而是默认模型。

什么场景下这个差别变成硬需求​

普通 CRUD 接口几十毫秒就返回了，worker 占用时间很短，WSGI 完全够用。

但调大模型的接口时间构成是这样的：解析请求 1ms、等模型返回 3 到 30 秒、拼装响应 1ms。如果再做流式输出（逐字上屏），一个连接要挂几十秒才断开。

这时候 WSGI 那 4 个 worker 会被 4 个用户占死。这不是性能优化问题，是同时能服务几个人的问题。

流式输出在 FastAPI 里可以直接写。下面是可运行的 SSE 端点（SSE 即 Server-Sent Events，服务端持续往一个 HTTP 连接里推数据的标准做法）：

import asyncio
from fastapi import FastAPI
from fastapi.responses import StreamingResponse

app = FastAPI()

@app.get("/stream")
async def stream():
    async def gen():
        for i in range(5):
            yield f"data: {i}\n\n"       # yield：产出一个值，然后交出控制权
            await asyncio.sleep(1)
    return StreamingResponse(gen(), media_type="text/event-stream")

yield 是 Python 的生成器语法，和 JS 的 yield 作用一致：产出一个值就暂停，下次再要时继续。data: xxx\n\n 是 SSE 规定的帧格式，两个换行表示一帧结束。

验证（-N 关掉 curl 的缓冲，否则看不出效果）：

curl -N localhost:8000/stream

数字会每秒出现一个，而不是 5 秒后一起出来。把循环换成模型返回的 token 流，这就是一个逐字上屏的对话接口。

Depends：把「每个接口都要但不属于业务」的东西挪走​

数据库连接、当前登录用户、配置对象——这类东西每个接口都要，但写在业务函数里很脏。FastAPI 的做法叫依赖注入：

from fastapi import Depends, FastAPI, Header, HTTPException

app = FastAPI()

def get_current_user(x_token: str = Header()):
    """从请求头取 token 并换成用户信息，失败直接中断请求"""
    if x_token != "secret":
        raise HTTPException(status_code=401, detail="token 无效")
    return {"name": "alice"}

@app.get("/me")
def me(user: dict = Depends(get_current_user)):
    return user

Depends(get_current_user) 的意思是「这个参数的值，交给那个函数去算」。它类似 Express 的中间件，但更好的地方是：结果直接作为有类型的参数送进来，而不是塞在 req.user 上靠约定传递。

依赖函数自己也能声明参数（这里是请求头 Header()），也能再依赖别的函数。收益有三个：鉴权逻辑不用复制到每个接口、测试时可以整体替换掉（app.dependency_overrides）、依赖项的参数同样会进 /docs。

它其实不是一个新框架​

用了一段时间后再回头看，有个认知对查文档很有用：FastAPI 是两个库的粘合层，不是从零造的框架。

层由谁负责做什么
WebStarlette路由、请求/响应对象、中间件、WebSocket、测试客户端
数据Pydantic类型校验、类型转换、JSON 序列化、生成 JSON Schema
粘合FastAPI 自己读函数签名的注解，决定参数来源、校验、生成 OpenAPI

你写 @app.post(...) 用的是 Starlette，写 message: str 用的是 Pydantic。FastAPI 真正原创的只有一件事：把函数签名当成接口契约。

实际好处：遇到中间件、后台任务、WebSocket 的问题查 Starlette 文档；遇到校验规则、自定义类型、序列化的问题查 Pydantic 文档。搜 FastAPI 反而绕远。

坑与局限​

按踩到的概率排序。

在 async def 里写同步阻塞调用​

这是最容易犯、后果最重的错误，也是前面「两个并行世界」那节的现实后果。可以直接观察：

import time

@app.get("/bad")
async def bad():
    time.sleep(5)          # 同步阻塞塞进了协程 —— 事件循环被卡死
    return {"ok": True}

@app.get("/good")
def good():
    time.sleep(5)          # 普通函数，FastAPI 会丢到线程池执行
    return {"ok": True}

同时发两个 /bad，第二个要等约 10 秒；同时发两个 /good，两个都在 5 秒左右返回。

原因：def 路由 FastAPI 会放进线程池，互不影响；async def 路由直接跑在事件循环上，你在里面同步阻塞，整个进程所有连接一起卡住——相当于在浏览器主线程里跑死循环。

判断标准很简单：

用的库是异步的（httpx.AsyncClient、await client.chat.completions.create）就写 async def；是同步的（requests、多数同步数据库库）就写 def。不确定时写 def，性能差一点但不会卡死。

官方在这篇讲得更细。

它只管 HTTP 这一层​

没有数据库映射层（ORM）、没有后台管理页、没有内置用户模型、没有数据库迁移工具。

它的职责边界很清楚：把 HTTP 请求变成一次带类型的 Python 函数调用，到此为止。数据库用什么、表结构怎么迁移、后台页面从哪来，全部要自己选库拼起来。做纯接口服务时这是优点——没有你不需要的东西；做一个完整业务后台时，这些活加起来不少。

别把跑分当选型理由​

官方文档提到的高性能来自 TechEmpower 基准测试。但调模型的服务里，瓶颈几乎总是模型本身的响应时间——框架层省下的毫秒对总耗时没有意义。

真正有意义的是前面说的连接模型：能不能同时撑住大量长连接。选它是为这个，不是为跑分。

Pydantic 1.x 到 2.x 是破坏性变更​

抄网上旧代码经常在这里报错。看到这些就是 v1 的写法：

v1v2
@validator@field_validator
.dict().model_dump()
class Config:model_config = ...

什么时候适合用它​

这一节是个人判断，不是文档结论。

适合的场景：

  • 给前端或客户端提供 JSON 接口，尤其是接口契约需要清晰的
  • 调大模型、做流式输出，需要同时挂住大量长连接的
  • 已有的 Python 代码（脚本、算法、数据处理）想包一层 HTTP 暴露出去

需要权衡的场景：

  • 要成套的后台管理页、用户系统、数据库迁移——这些它都不提供，得自己拼
  • 团队不写类型注解——它一半的价值来自注解，不写等于放弃
